## THE CAVEAT THAT TRAVELS WITH EVERY USE OF THESE

**These are an approximate oracle, never an exact one.** Nothing ties them to commit
`dd2b86efef9e77168f304a86e8a8411877578bbe`. They are published marketing assets, regenerated by
hand at unknown times, and the path segment `v5` indicates at least five prior revisions. The
owner has no macOS access (OD-0001), so they cannot be re-shot against the pinned commit.

Therefore, per contract sections 4, 6 and 10:

- They MAY be used to check proportion, ordering, iconography, theme color, material character,
  control grouping, and the presence and rough placement of every element.
- They MAY NOT be used to claim pixel parity, and no measurement taken from them is a SOURCE FACT.
- Any number derived from them is recorded as APPROXIMATE with this caveat attached.
- Where a capture and the pinned source disagree, **the source wins** and the disagreement is
  recorded (contract section 6: README, comments, changelogs and screenshots help discovery but
  can be stale).
- No Windows capture will be presented as a parity match against these.

## Capture geometry from source (SOURCE FACT)

`App/Captures/WebsiteCaptures.swift:658-659` defines the two canonical window sizes:

- `wide = NSSize(width: 1320, height: 860)` - identical to the main window default in
  `App/Window/WindowManager.swift:19`
- `narrow = NSSize(width: 860, height: 560)` - identical to the main window `contentMinSize`

`:1049-1055` takes the pixel scale from `NSScreen.main?.backingScaleFactor ?? 2`, sets
`sourceRect` from a rect in display coordinates, computes width and height as
`Int(rect.width * scale) & ~1` (forced even), and sets `scalesToFit = false`. So the published
2080x1300 files are a cropped region captured at 2x, not the whole 1320x860 window. The crop rect
per capture is to be read out of the harness and mirrored exactly on Windows, so that Windows
captures are produced in the same states, at the same logical sizes, from the same fixtures.
