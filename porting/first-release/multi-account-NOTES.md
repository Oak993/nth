# Multiple accounts per provider (owner idea, 2026-10-05, not yet scheduled)

Status: IDEA being refined with the owner. Nothing is built. Not part of OD-0103 unless the owner says so.

## Agreed so far (owner, 2026-10-05)
- Connect several accounts per provider once: e.g. 3x Claude Code (Pro $20, Max 20x, Max 20x), 2x Codex (two ChatGPT accounts), several OpenRouter keys.
- CLIs: one install, one private folder per account (CLAUDE_CONFIG_DIR, CODEX_HOME; other CLIs via a per-account HOME/USERPROFILE/APPDATA/LOCALAPPDATA, tested per CLI; Credential-Manager-backed CLIs stay single-account).
- API providers (OpenRouter, DeepSeek, Z.ai, OpenAI-compatible): several keys, nickname, credits left, Allowed switch, order (in order / most credits first / spread evenly), optional cap per key, silent fallback on 402/429 within the same turn, per-thread pin.
- Settings stay uncluttered: inside the Models page; one account looks exactly like today; 2+ opens a small glass list.
- Limit setting: "When an account reaches its limit: Ask me / Switch automatically / Wait for reset".
- Owner rule: the setting starts unset. The first time a limit is hit and the user has not chosen, Marrow asks in the chat (switch or wait). If the user already chose in Settings, never ask. A safety so no user misses it.

- Names (owner, 2026-10-05): with one account no name shows anywhere. Adding a second gives both a short default name from the plan, numbered when equal (Claude Max 1 / Claude Max 2, Claude Pro + Claude Max, Codex 1 / Codex 2); the user can set a custom name (Rename in the row menu or tap the name, about 24 characters). Going back to one account hides names again but keeps custom names.
- Remember scope (owner, 2026-10-05): the in-chat limit card remembers at one of three scopes, chosen with one mutually exclusive control "Remember: Just this time / This thread / All threads" (default Just this time). All threads writes the Settings value. This thread is stored on the thread and shown and cleared from the composer model menu ("This thread: Switch automatically · Use Settings"). Settings holds only the all-threads value (Ask me / Switch automatically / Wait for reset), with a caption that threads can keep their own choice. Precedence: thread choice, then Settings, then ask.
- Account popover and priority (owner, 2026-10-05): a new small control next to the composer's model chip, only when a provider has 2+ accounts (proposal: a glass monogram capsule with the active account's short name and a hairline usage arc). It opens a premium glass popover listing that provider's accounts in priority order (custom or default names), each with usage bars and reset time. The user reorders by dragging (or moving a row up); row 1 is the default: new threads start on it, and when it runs out Marrow goes to row 2, then row 3. The order is global and the same list appears in Settings > Models. Tapping a row instead pins this thread to that account ("Back to order" undoes). Exhausted rows stay in place, dimmed with their reset time, and are skipped. API keys use the same popover with credits instead of bars.
- Limit card APPROVED (owner, 2026-10-05, verbatim "Agreed with this idea"), on this text:
  Claude Max 1 reached its 5-hour limit · resets 3:40 PM
  [ Switch to Claude Max 2 ] [ Wait ]
  Remember: ( Just this time ) ( This thread ) ( All threads )

Same remember scopes (Just this time / This thread / All threads).
- Handoff context (owner, 2026-10-05): when moving to another account, the user can choose Full conversation (uses more of the new account's limit) or Compact summary (like Claude's compact: keeps all key details, uses less). A Settings row "When moving to another account, bring: Full conversation / Compact summary", starts unset; if unset, the first switch card offers it. Lead's technical note: the summary must be written by an account that still has usage, so Marrow prepares it ahead of time on the running account when it nears its limit (about 90%), and falls back to the new account's light model only if there was no chance; if the chat was already compacted it is already small.
- Rule for every choice (owner, 2026-10-05): every one of these choices (limit: switch/wait; other provider; mid-reply: finish/stop; bring: full/compact) works the same way: a Settings row that starts unset; if unset, the first in-chat card asks; every card carries one Remember line (Just this time / This thread / All threads) that applies to all choices made on that card. Settings holds the all-threads values; thread choices live on the thread (composer menu, Use Settings to clear).
- Marrow's own digest (owner asked 2026-10-05 why an AI must write the summary): Compact summary is built by Marrow itself, no AI, free and instant: every user message verbatim; the task and plan/todo state; files changed and the current diff; commands run with pass/fail and the last error; the last few turns in full; and the bulky parts (file dumps, long logs, search output) dropped, since the new account can re-read the files. Limits: code cannot judge meaning ("why we chose X") the way a model can, so an AI-polished summary stays an optional extra (prepared at about 90% if wanted). A local on-device model is possible later but not proposed for the first release.
- Nothing missed (owner, 2026-10-05: Marrow writing it is better; the next model must get all information without missing any key detail). Safeguards: (1) kept word for word: every user message and every assistant reply text; (2) only re-readable tool output is shortened (file reads, searches), while non-reproducible output (command results, errors, web pages, approvals) is kept, long ones as head and tail; (3) nothing is deleted: the full conversation is saved as a handoff file and the summary tells the new model where it is, so it can look up any detail; (4) a "What was handed over" view for the user; (5) fidelity tests: recorded chats are handed over and the new side must answer detail questions (files, decisions, numbers, instructions) correctly.
- Handshake (owner idea 2026-10-05, after Pacific Rim's neural handshake): as an account nears its limit (about 90%, while it still has usage), a Handshake starts. (1) Marrow builds its lossless digest; (2) the outgoing account writes a short briefing for its successor (the meaning: goal, why decisions were made, what is next, pitfalls); (3) the incoming account reads digest and briefing and reads back in a few lines what it understood; (4) Marrow checks the read-back against the digest (files, open tasks, the user's latest instructions) and fills any gap before the switch. Status "Handshake complete · Claude Max 2 is in sync". Visual: the two account marks link with a thread of light in the composer capsule (about 1.2 s; crossfade under Reduce Motion). Lead proposal: on by default (it spends a sliver of the outgoing account's last usage), Settings toggle; owner to confirm.
- Handshake timing (owner, 2026-10-05): Marrow, not the AI, tracks usage (PlanLimits already reads each plan's windows), polling more often near the end. The start point depends on the plan (owner: Pro about 90%; 5x/20x about 98-99%), and the user can choose it in Settings. Lead design: "Start the Handshake: Smart (recommended) / At [slider 80-99%]". Smart = Marrow measures how fast this thread spends usage and the handshake's own cost, and starts when what is left is just enough for the handshake plus one step plus a margin (plan-aware defaults if no data, owner-set 2026-10-05: $20 plans 95%, 5x/10x/20x plans 98%). Safe pause: the switch happens only between steps (after a tool finishes, never mid-edit). Hot standby: the incoming account is started and briefed in the background while the outgoing one is still working, so the switch itself is instant. Seamless: the reply continues in the same bubble; only the capsule mark changes with a tiny in-sync tick; the CLI's own limit message stays the hard-stop fallback.
- Handshake animation (owner, 2026-10-05): must be the most premium moment, a level above the rest of the app, an experience found nowhere else, with the link visibly established between the two accounts beside the composer. Page shows three concepts: A neural filaments, B phase lock, C liquid glass; four phases Standby, Linking, In sync, Switch; never blocks streaming or typing; Reduce Motion crossfade; optional soft sound off by default; its GPU programs join the OD-0108 warm-up so it never stutters.
- Handshake defaults (owner, 2026-10-05): $20 plan starts at 95%; 5x, 10x or 20x plans at 98%. By default Marrow watches smartly and decides itself (Smart); the user can set their own point in Settings.

- Link up (owner, 2026-10-05): the "Also check with" checkbox is rejected. Getting work checked by another account is a premium, intuitive link-up mode: linked marks join the composer capsule (e.g. [ M1 <-> P ]). Page shows A tap to link, B drag to link, C link mode; no checkboxes.
- Local LLM (owner idea, 2026-10-05): a local model can be set up and used everywhere accounts are (popover, pills, Handshake). Lead design: a new port-only provider "Local" that talks to OpenAI-compatible servers on this PC (Ollama :11434, LM Studio :1234, llama.cpp/vLLM, or an address the user types), found automatically on loopback; models listed from the server; no key, no limits ("No limit", "Stays on this PC" in place of usage bars); it reuses the API-provider path with Marrow's native tools. In pills it is the natural last step that never runs out. Caveats to show plainly: local models are weaker at long tool-using work and have smaller context windows (the Handshake digest suits them); speed depends on the PC's GPU. Marrow does not download models itself in the first version; it points to the server's own app.
