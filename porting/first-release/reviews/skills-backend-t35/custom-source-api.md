# RR-18 custom-source API (Round 2)

Public namespace: `Marrow.Services.Port.Skills.Custom`. The open root's `SkillsHost.CustomSources` implements `ICustomAddBackend`:

```csharp
Task<IReadOnlyList<CustomAddCandidate>> Check(CustomAddRequest request, CancellationToken cancel);
Task<OwnItem> Add(CustomAddCandidate candidate, IProgress<double> progress, CancellationToken cancel);
```

`CustomAddKind`: Plugins / Skills / Tools. `CustomAddSource`: Folder / Zip / GitHub. Request fields: Kind, Source, Location, Name, Command. Candidate fields: Key, Name, Description, Problem. This mirrors T36's internal UI request/candidate records; its adapter can convert enums/records and await Add, ignoring the returned OwnItem. Retain the exact candidate from Check. Keys belong to that host and validated frozen snapshot; forged, consumed and stale keys fail. `Discard` releases unselected snapshots. A candidate with Problem is listed but cannot be added. An empty list means no matching manifests were found. Validation/read errors throw and are suitable for the sheet's error presentation.

A skill needs SKILL.md with a valid name and description. A plugin needs `.claude-plugin/plugin.json` or `.codex-plugin/plugin.json` with a valid name. A tool source needs an MZ Windows `.exe`, a display name and a valid command; all adjacent files are retained. A single executable can be given an alias. In a bundle containing several executables, the command must uniquely match the primary executable's basename; helpers are kept. The backend copies inputs and never executes their code. ZIP roots can contain several found items. GitHub Location accepts `owner/repository`, `owner/repository/sub-folder/path`, or the same path after `https://github.com/`. No UI request/adapter signature change is needed. Sub-folder backslashes normalize to `/`; absolute paths, dot segments, empty segments, encoded paths and unsafe Windows components fail before transport work. The original URL path is validated before URI dot normalization. HEAD resolves to a full commit. Root requests retain the commit's codeload archive. Sub-folder requests use commit-pinned GitHub contents listings and raw file URLs **only inside that folder**, never a full repository archive followed by filtering. Listings reject links, submodules, outside/non-child paths, duplicate Windows paths, inconsistent lengths and the API's potentially incomplete 1000-entry listing. Branch/ref URLs and private repositories are unsupported.

`List(kind)`, `SetEnabled(id, enabled)`, `Remove(id)`, `Commands()`, `PluginDirectories()` and `Snapshot()` expose the persisted own library. The registry is `skills/own/registry.json`; payloads and command entries live under `skills/own/items/<id>`. This is separate from provider imports (`skills/imported`, OD-0118) and managed catalogue state. Reset of downloaded catalogue items leaves own copies, as it leaves imported copies; explicit Remove deletes an own copy. No original user source is written or removed. Registry records include source kind/original location, full GitHub commit, normalized `Provenance.SubPath` (empty for root sources), pinned archive or contents URL, source fingerprint, check time and exact installed file size/SHA-256 inventory. Subtree `SourceSha256` is the canonical selected tree's path/content fingerprint; root ZIP `SourceSha256` hashes the downloaded archive bytes. No licence or equivalence is invented for user content.

Publish a private item tree first, then atomically replace the registry. Independent selected items publish their trees concurrently; name/command reservations and registry commits remain serialized. Failed registry publication rolls back the tree and preserves the validation token for retry. Commands become registered only through the committed registry, survive reopening and disappear when disabled/removed. Commands are per-item `.cmd` entries beside the copied payload; command enumeration verifies all installed bytes before returning paths. Provider children receive the enabled, verified command bins through `ProviderCustomCommands.ForChild`, after existing PC tools and before WindowsApps stubs. Custom skill and plugin-skill copies join generations; Claude/Grok plugin generations retain supported Claude manifests, hooks and resources. Codex-only manifests contribute ordinary skills without a claim of Claude-compatible hooks. Owned generations keep their bytes and leases after Remove of the original own item.

All filesystem and GitHub effects have injectable ports (`ICustomSourceFiles`, `ICustomGitHubSource`; `SkillsHostOptions.CustomFiles/CustomGitHub`). New tests use in-memory files and archive bytes; no real filesystem source reads, network, downloads, installers or provider sessions. Production traversal rejects links/reparse points, unsafe Windows paths, duplicate/colliding archive paths and excessive input (4096 files / 128 MiB). These limits are engineering resource bounds, not catalogue size facts.

Explicit custom skill additions take precedence over catalogue names, reserve disclosure budget first and list first (skills-PLAN 2.7). Provider imports keep OD-0118's separate behavior. Source `disable-model-invocation` is respected; unsupported providers omit explicit-only custom skills, and native named invocation remains available.
