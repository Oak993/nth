## 2. Findings that change the plan

1. **Pi is not launched with `--no-skills` in real sessions.** The port (PiCLI.cs:93 [verified fix]; 53 is the Swift line) and the Mac source (PiCLI.swift:53) pass `--no-skills` only to the throwaway `pi --mode rpc --no-session` probe that reads the model list. Live Pi sessions already load the user's skills, and `get_commands` already lists them. So for Pi, Marrow adds `--skill`, it does not need to lift a block.
2. **Claude Code already receives Anthropic's own claude.ai skills for signed-in users.** On this machine the `initialize` response lists `docx`, `pdf`, `pptx`, `xlsx`, `skill-creator`, `docs`, `morning`, `import-memory` and `schedule` (from the claude.ai sync under `~/.claude/skills/synced` and `~/.claude/plugins/synced`), as well as bundled skills such as `code-review`, `verify`, `simplify`, `batch`, `loop` and `claude-api`. [verified fix: `schedule` appears once in the live list and is not in the docs' bundled-skills list (doctor, run, verify, run-skill-generator, debug, code-review, batch, loop, claude-api, workflow-authoring, simplify), so it is not a bundled skill here.] Docs: sync needs Claude Code v2.1.273 or later, a claude.ai sign-in (not an API key, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN` or an `apiKeyHelper`), and is off in bare mode, with `--safe-mode`, with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC`, under a managed `strictPluginOnlyCustomization` lock, or when `--setting-sources` omits `user` (the port passes `user`, so sync works). [verified fix: added] The sync runs in the background and "never delays startup"; for a non-interactive (`-p`) run the docs say to set `CLAUDE_CODE_SYNC_SKILLS=1` so the run downloads the skills and waits for the list before answering (https://code.claude.com/docs/en/skills). The port uses `-p`, so a first launch on a new machine may list synced skills late unless Marrow sets that variable. Marrow's bundle for Claude should therefore skip names that the sync already provides and mainly serve API-key users and everyone else.
3. **Codex already ships its own system skills.** Codex 0.159.3 writes `imagegen`, `openai-docs`, `review-agent`, `skill-creator` and `skill-installer` into `$CODEX_HOME/skills/.system` on first run (seen in this machine's `~/.codex/skills/.system` and again in the temporary CODEX_HOME I used). Its desktop plugin marketplaces here also enable `documents`, `pdf`, `presentations`, `spreadsheets` and `template-creator` (config.toml, `openai-primary-runtime`). A Marrow bundle for Codex should not duplicate these.
4. **Only Claude namespaces plugin skills.** Every other provider uses bare names, so a Marrow skill called `pdf` can clash with a user's `pdf`. See section 4 for the policy. [verified fix: added] Even on Claude, the bare short name is shared: the docs say a plugin skill's bare `/name` works only "unless another command already uses that name", and a synced claude.ai skill loses its short name to any other command and then runs only as `/anthropic-skills:<name>`. So a Marrow `marrow:pdf` next to a synced `pdf` is safe, but the user will see two `pdf` entries; skipping synced names (finding 2) avoids that.
5. **Token cost.** Every provider lists all skill names and descriptions in the model's context: Claude's listing budget is 1% of the context window with each description cut at 1,536 characters; Codex's skills catalog defaults to 2% of the window; the config schema says of `skills.max_context_tokens`: "Defaults to 2% of the model context window and is capped at 10,000 tokens when set" (codex-rs/core/config.schema.json at the pinned commit), so 10,000 is the ceiling for a configured value, not for the default [verified fix]. A bundle of dozens of skills is not free. Marrow should write only the enabled skills into the provider folders (a Settings toggle per skill, default on for a short curated list).

## 3. Per-provider details

### 3.1 Claude Code

How the port launches it today: ClaudeSession.cs:154-231 builds the argument list shown in the table, then `--append-system-prompt`, then `--resume` or `--session-id`. The catalog probe `Handshake` (ClaudeSession.cs:278-286) uses a shorter list with `--no-session-persistence` and the same `--setting-sources user,project,local`. Skills show up as `commands` in the `initialize` control response and become `SlashCommand` entries (Provider.cs `ClaudeCommands`). `Skill` tool calls are shown as `Skill · <name>` (ClaudeSession.cs:1028).

Discovery paths (Windows): personal `%USERPROFILE%\.claude\skills\<name>\SKILL.md`; project `.claude\skills` in the working directory and every parent up to the repository root; nested folders load on demand; `.claude\skills` inside any `--add-dir` folder; installed plugins; skills synced from claude.ai; bundled skills. Source: https://code.claude.com/docs/en/skills (read 2026-10-02).

Ways to add an extra folder, all tested LIVE on 2.1.287 with the same flags as the port, by sending the `initialize` control request and reading `commands`:

| Test | Result |
|---|---|
| `--plugin-dir <dir>` with `.claude-plugin/plugin.json` `{"name":"marrow"}` and `skills/mrw-hello/SKILL.md` | listed as `marrow:mrw-hello` |
| Same plugin, passed through env `CLAUDE_CODE_PLUGIN_DIRS` instead of the flag | listed as `marrow:mrw-hello` |
| `--plugin-dir` on a folder with no manifest | listed as `<folder name>:<skill>` (here `nomanifest:mrw-nomf`) |

Confirmed.

I could not run a real model turn to invoke the skill (the account hit its weekly limit), so slash dispatch of `/marrow:<skill>` rests on the docs and on the listing above.

Facts from the docs (https://code.claude.com/docs/en/plugins/loading, https://code.claude.com/docs/en/plugins/create, https://code.claude.com/docs/en/env-vars, read 2026-10-02):
- `--plugin-dir` loads for that session only and never copies or writes to the user's settings. The plugin id is `<name>@inline`. It replaces a same-named installed marketplace plugin. A user can turn it off with `"enabledPlugins": {"marrow@inline": false}`.
- Plugin skills are namespaced `/<plugin>:<skill>`, so they cannot collide with a personal or project skill. "The bare `/fancy` also invokes the skill unless another command already uses that name."
- Version gates: `--plugin-dir` itself is old; a folder-of-plugins needs v2.1.265; `CLAUDE_CODE_PLUGIN_DIRS` needs v2.1.280 (separator `;` on Windows; each path absolute or starting with `~`, relative paths are skipped [verified fix]; project and local settings cannot set it). Managed settings can switch session-only plugins off, and a plugin id named in managed `enabledPlugins` beats a same-named `--plugin-dir` copy.
- `--add-dir` precedence among same-named skills: Enterprise over Personal over Project; the add-dir row is listed last. The folder is also added to the tool-access roots, which helps skills that ship scripts.
- Live change detection covers `SKILL.md` text inside `~/.claude/skills`, project and add-dir skills. Plugin content needs `/reload-plugins` (the create page: "When you edit the plugin's files during the session, run `/reload-plugins`"). In a `-p` session there is no one to type that, so Marrow should regenerate its views before it starts a Claude process, not during one.
- `--add-dir` also loads that folder's `.claude/commands/` and `.claude/agents/`, and its `.claude/settings.json` can contribute `enabledPlugins` `true` values (lowest precedence); these loads depend on the `project` setting source, which the port passes [verified fix: added].
- Skills frontmatter fields Marrow can rely on: `name`, `description`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `paths`, and the `${CLAUDE_SKILL_DIR}` substitution (a variable, not a frontmatter field). The docs also list `when_to_use`, `argument-hint`, `arguments`, `disallowed-tools`, `model`, `effort`, `context`, `agent`, `background`, `hooks`, `shell`, `metadata`, `license` and `compatibility`; `license` is accepted but not acted on [verified fix].
- SDK equivalents (for reference, the port drives the CLI directly): `plugins: [{type:"local", path}]`, `additionalDirectories`, `settingSources`, and a `skills` allow-list option. https://code.claude.com/docs/en/agent-sdk/skills

Cleanest mechanism: `--plugin-dir <Marrow data>\views\claude\marrow`. No write into `~\.claude`, no collisions, the user can disable it, and the app can tell its own skills apart by the `marrow:` prefix. Add the flag in `Start()` and in `Handshake()` so the composer's slash list is the same before and after a session starts. If bare names (`/docx`) are wanted, `--add-dir <Marrow data>\views\claude-addon` (with `.claude\skills\...` inside) works but loses to the user's own same-named skill and also drags in that folder's `commands/` and `agents/`; keep it as a second choice. The port already probes `claude --help` for optional flags (ClaudeSession.cs:137-149); add `--plugin-dir` to that probe and skip the flag if it is missing.

### 3.2 Codex

How the port launches it: one private `codex app-server` per connection (CodexSession.cs:889-894, argv `["app-server"]`), used by both real sessions and the slash-command probe `ListCommands` (CodexSession.cs:630-648: `skills/list` with `cwds` and `forceReload`). The turn input carries `{type:"skill", name, path}` when the command has a skill path (Provider.cs `CodexInput`). `thread/start` already takes a `config` overlay (CodexSession.cs:493-534; used for Hydra and `mcp_servers`).

Discovery (DOCS: https://developers.openai.com/codex/skills, which now redirects to https://learn.chatgpt.com/docs/build-skills): repo `$CWD/.agents/skills` and `$REPO_ROOT/.agents/skills`, user `$HOME/.agents/skills`, admin, and system. "If two skills share the same name, Codex doesn't merge them; both can appear in skill selectors." Disable with `[[skills.config]] path=... enabled=false`. `agents/openai.yaml` carries UI metadata and `policy.allow_implicit_invocation`.

The extra-root method (LIVE and SOURCE):
- `codex app-server generate-json-schema` on 0.159.3 lists a client request `skills/extraRoots/set` with params `{ "extraRoots": [absolute path, ...] }`, response `{}`. Other skill methods: `skills/list` (`cwds`, `forceReload`), `skills/config/write` (enable or disable by `name` or `path`, writes the user's config), notification `skills/changed`, and plugin methods `plugin/list`, `plugin/install` and others.
- Source at openai/codex commit `2739e828581c3deee59a270cd740675dc278ed14` (2026-10-02, latest release rust-v0.160.0 of 2026-10-01): `codex-rs/app-server/src/request_processors/catalog_processor.rs:595-611` registers the roots with the file watcher and calls `skills_service().set_extra_roots(...)`, then sends `skills/changed`. The test `skills_extra_roots_set_updates_process_runtime_roots` (`app-server/tests/suite/v2/skills_list.rs:1214`) shows each call replaces the whole list, a missing folder is accepted, and an empty list clears it. The state is in memory in that app-server process; nothing is written to `config.toml`.
- LIVE test (temporary `CODEX_HOME`, JSON lines on stdio, `initialize` then `initialized`): `skills/list` before showed only the five system skills. After `skills/extraRoots/set {extraRoots:["<dir>"]}`, `skills/list` (forceReload) also showed each `<dir>\<name>\SKILL.md` with scope `user`. The folder is a flat list of `<skill>\SKILL.md` folders (no extra `skills\` level).
- Collision test: with `user-skill` in `$CODEX_HOME/skills` and another `user-skill` in the extra root, `skills/list` returned both (same name, different paths). The port's `SlashCommand.Suggestions` keeps the first name only, and `CodexInput` sends the path, so the app must decide which copy it shows (see section 4).
- Not possible to confirm live: skill use in a real turn (no model call). The input format is the one the port already uses for `$skill` items.
- [verified fix: re-run and extended] Second reader, Codex 0.159.3, temporary `CODEX_HOME`: before the call `skills/list` showed `user-skill` (scope `user`, from `$CODEX_HOME\skills`) and the five `.system` skills; `skills/extraRoots/set` returned `{}`; after it, both `user-skill` copies were listed with scope `user` (two paths), plus the extra-root skills. A missing folder was accepted (`{}`). A relative path was refused with JSON-RPC error -32600 "AbsolutePathBuf deserialized without a base path", so Marrow must send absolute paths. No `config.toml` was created in the temporary home.
- [verified fix: minimum version found] The method arrived in rust-v0.136.0 (released 2026-06-01): its release notes list "#24977 Add runtime extra skill roots API", and `codex-rs/app-server-protocol/schema/json/v2/SkillsExtraRootsSetParams.json` exists at tag rust-v0.136.0 but not at rust-v0.135.0. Older Codex answers with an error, which the plan already tolerates.

Other Codex mechanisms and why not:
- `CODEX_HOME` points the whole CLI at another home: it also moves `auth.json`, sessions, config and memories, so it would log the user out and hide their skills. Not suitable.
- Writing into `$CODEX_HOME/skills` or `~/.agents/skills` mixes Marrow's files with the user's. Not suitable.
- The plugin route (`[marketplaces.*] source_type="local"` and `[plugins."x@y"] enabled=true` in `config.toml`, or `plugin/install`) writes the user's config and the plugin cache. Not needed now that `extraRoots` exists.
- `config.skills.bundled.enabled=false` (config schema at the same commit, `codex-rs/core/config.schema.json`) hides Codex's own system skills if Marrow ever wants that. Not recommended.

Cleanest mechanism: in `Connect` (shared by sessions and `ListCommands`), right after the initialize handshake, send `skills/extraRoots/set` with `<Marrow data>\views\flat`; ignore an error reply (older Codex without the method) and carry on without the bundle. Re-send on every new connection. Minimum Codex version for the method: 0.136.0 [verified fix: was "not known"].

### 3.3 GitHub Copilot CLI

Port: the app speaks the Copilot SDK JSON-RPC protocol over `copilot --headless --stdio` (CopilotSession.cs:602-615) and calls `session.create` or `session.resume` with the parameters built in `SessionParameters()` (call at CopilotSession.cs:109-112, method from line 124 [verified fix]: `clientName`, `workingDirectory`, `streaming`, `systemMessage`, optional `customAgents`...). Commands come from `session.commands.list` (CopilotSession.cs:458-478, request at 465). A `skill` tool call renders as `Skill · <name>` (CopilotSession.cs:1306 [verified fix]).

Discovery (DOCS https://docs.github.com/en/copilot/how-tos/copilot-cli/customize-copilot/add-skills): project `.github/skills`, `.claude/skills`, `.agents/skills`; personal `~/.copilot/skills` or `~/.agents/skills`. `/skills add` can register another location interactively, and the shell command `copilot skill add <FILE | URL | DIRECTORY>` (with `copilot skill list|enable|disable`) does the same from the command line [verified fix: added]; both change the user's own Copilot state, so Marrow should not use them. The CLI configuration directory is `COPILOT_HOME` (the `--config-dir` flag is deprecated), https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference. No documented flag or env var for extra skill folders on the command line.

The session-level option (SOURCE): github/copilot-sdk commit `9b28c9467ab91a641cbef3fe8e4c706122e8ed8c` (2026-10-02). `nodejs/src/client.ts` sends `skillDirectories` and `disabledSkills` in both `session.create` (line 1854-1857) and `session.resume` (line 2135-2138). The docs (`docs/features/skills.md`) say `skillDirectories` points at a parent folder and the CLI "discovers all `SKILL.md` files in immediate subdirectories"; scanning happens when skills first load, folders are not watched, and a `skills.reload` RPC refreshes the catalog; `disabledSkills` takes skill names from frontmatter. Built-in runtime skills are controlled by `includedBuiltinSkills` and are untouched by default in the CLI mode the port uses (the doc: under `mode: "copilot-cli"` "the field is omitted unless you set the option"; only `mode: "empty"` sends an empty list, client.ts:1606-1631). A same-named clash is not given a rule; the doc's advice is to use `disabledSkills` or reorganise folders.

Cleanest mechanism: add `["skillDirectories"] = [ "<Marrow data>\views\flat" ]` to the dictionary returned by `SessionParameters()` so create and resume both carry it. Per-session user toggles can use `disabledSkills` instead of rewriting folders. Not tested live (Copilot is not installed here); whether `session.commands.list` includes skills still needs a check with the real CLI.

## 4. Name collisions: one policy for all providers

| Provider | What a clash does | Marrow policy |
|---|---|---|
| Claude | no clash: `marrow:<name>` | publish all enabled skills |
| Codex | both kept, same name, two paths | drop the Marrow copy if the user's folders (`$CODEX_HOME/skills`, `~/.agents/skills`, repo `.agents/skills`) have the name; or prefix |
| Copilot | undocumented | drop on clash |
| OpenCode | later load overwrites earlier, not deterministic (files are parsed with unbounded concurrency, skill/index.ts:240-243) | drop on clash; also never ship a skill named `customize-opencode` [verified fix] |
| Pi | first found wins, warning; `--skill` folders are scanned last, so the user's copy wins [verified fix] | drop on clash (only to avoid the warning) |
| Command Code | user's defaults win | no action needed |
| Antigravity, Cursor, Grok, Devin | undocumented (no clash rule on any of the four vendors' pages) [verified fix] | drop on clash |

Rule: the user's own skill always wins. Before writing the per-provider view, Marrow scans that provider's user and project skill folders (the paths in section 1) for the names it is about to publish and leaves out any it finds. For providers that show bare names, an alternative is a fixed `marrow-` prefix on the name; this makes clashes impossible and makes Marrow's skills recognisable, at the cost of longer slash names and of deviating from upstream names (frontmatter `name` must still match the folder name for OpenCode and Pi's portable form).

## 5. Recommended layout and the fallback that works everywhere

Proposed folder (under the existing data root, `%LOCALAPPDATA%\Marrow Code`, already used by Pi's support folder, PiCLI.cs:14-18; the name contains a space, which is fine because every argument is passed as a separate argv item and I verified Claude with a spaced path; JSON values need the usual backslash escaping):

```
Marrow Code\skills\
  store\<skill>\SKILL.md (+ scripts, references, assets)     canonical copy, shipped with the app
  enabled.json                                               Settings toggles
  views\claude\marrow\.claude-plugin\plugin.json             {"name":"marrow", ...}
  views\claude\marrow\skills\<skill>\...                     Claude and Grok (--plugin-dir)
  views\flat\<skill>\...                                     Codex extraRoots, Copilot skillDirectories,
                                                             OpenCode skills.paths, Pi and Command Code --skill
```

Marrow regenerates the views from `store` and the enabled list when the app starts or when a toggle changes, by copying (no symlinks or junctions: Windows may refuse them without privileges). The folders are private to Marrow, so nothing in `~\.claude`, `~\.codex`, `~\.agents`, `~\.copilot`, `~\.config\opencode`, `~\.pi`, `~\.commandcode` or `~\.gemini` is created or edited. Uninstalling Marrow leaves no trace in a provider.

Fallback for providers without a clean overlay (Cursor, Devin, Antigravity until tested, any CLI that is too old) and the only route for the API-key providers: Marrow-side loading.
1. Put a short catalog (name, one-line description, path) into the system prompt, like `ProjectGuidance`; cap it to the same budgets the CLIs use (about 1-2% of context).
2. Expose the skills in the composer as slash commands that Marrow owns (`SlashCommand` already supports a name and a detail).
3. When the user picks one, or the model asks for it, send the `SKILL.md` body as part of the prompt together with the skill's absolute folder path; for native API sessions add a small `use_skill` tool that returns the file text and bundled references, because the file tools cannot read outside the project.
4. Scripts that need a runtime (Python, Node, Office tools) must be runnable by the provider's own shell tool, so the skill folder must be readable by the agent: on CLIs this usually needs the Marrow `views` folder in the allowed-directories list (Claude `--add-dir` does that; others need a check).
