# MA-0: multiple-account feasibility

Research date: 2026-10-05. Repository baseline: `claude/verify-terminal-20261001`, commit `889c9ebd523cbfedb39d9bf06e22ba7b9988ea46`. Deliverable branch: `codex/ma-0`. This is a feasibility study for C#/.NET 10 and Avalonia 12.1.2; it contains no production changes.

**Recommendation:** build explicit account selection and local/API endpoint support first. Separate CLI processes can generally receive separate environments today. Reliable account identity, quota isolation, transcript transfer and permission-preserving recovery require further work. Do not ship unrestricted personal-account rotation to avoid subscription limits: Command Code explicitly permits one account per person; OpenCode explicitly prohibits multiple accounts used to circumvent limits; several other providers prohibit bypassing limits or protective measures.

Evidence labels used below: **REPO** is behavior visible in the baseline C# source; **DOC** is current public primary documentation or upstream source; **DECISION** is a proposed engineering choice; **UNRESOLVED** needs a provider answer or a version-specific Windows experiment. Repository citations use `path:line` at the baseline above. Web pages are mutable and were accessed on the research date. Upstream source snapshots are identified where available. No Windows CLI login, Credential Manager mutation, transcript migration, paid inference, or account-switch experiment was performed. Documentation does not establish compatibility with the exact CLI versions installed by an owner.

## 1. CLI credentials, sessions and Windows isolation

`~` below means the CLI's resolved home, normally `%USERPROFILE%` on Windows. A documented configuration override is not automatically a credential or session override. Changing environment variables does not change the Windows user SID, Credential Manager vault, browser cookies, Windows known-folder APIs, or service-side account identity. A shared keyring can defeat folder isolation, but a keyring with a directory-derived target can preserve it.

Thus the smallest **launch-only** change is an account-aware environment builder passed through the existing configuration. It must start with the existing complete block, not just two variables.

The launch overlay alone is insufficient for product correctness. Login/status/catalog/quota/logout must all use the same account context (`:499`, `:608`). DECISION: key caches by provider + account + endpoint/auth scope; bind each turn/session/resume to AccountId and generation, while treating shared organization quotas as shared quota buckets. Never mutate the app's global environment to switch accounts.

Hydra also requires identity work: HydraPair/HeadProfiles choose provider/model/effort, not account (`src/Marrow.Core/Models/Hydra.cs:165`, `:283`). Native Claude teams share one CLI's auth; same-provider native routing is chosen without account identity (`src/Marrow.App/AppModel+Hydra.cs:91`). Different accounts require independent Marrow-managed head runtimes and an account-aware routing comparison. A sequential user-made pill is an ordered routing policy; Hydra is concurrent work. Both must retain permission mode, MCP/skills generation, worktree ownership and account attribution.

REPO polling behavior: Registry suppresses successful repeat reads for **60 seconds**, unless forced; it is an on-demand throttle, not a timer (`src/Marrow.Services/Providers/ProviderRegistry.cs:1303`). UsagePanel requests reads when attached (`src/Marrow.App/Views/Usage/UsagePanel.cs:113`). In-flight forced reads are coalesced, but a 25-second watchdog clears loading without cancelling the underlying operation; failures/null preserve old data and do not advance a successful timestamp (`ProviderRegistry.cs:1325`, `:1351`, `:1380`). Late results could be attributed to a newly selected account unless keyed and generation checked.

DECISION: initial ceiling one read per active account per 60 seconds, with jitter, bounded global concurrency, cancellation, exponential backoff/Retry-After, timestamp/freshness display and no polling of idle accounts. This is a conservative proposed budget, **not a provider guarantee**. Prefer supported live notifications. Manual refresh must respect server throttling. Never reuse a previous account's snapshot on auth failure.

`UsageLimitSignal` is substring/error-reset detection, not prediction (`src/Marrow.Services/Providers/UsageLimitSignal.cs:10`, `:33`). `AutoContinue` notes limits, waits until turn completion/reset plus a 60-second margin (five-second floor), then sends ContinueMessage to the same account (`src/Marrow.App/Runtime/AutoContinue.cs:56`, `:116`). It can directly read quota outside Registry's throttle (`:177`), and its HandOff **throws NotImplementedException / MARROW_STUB** (`:112`). It is not a proactive Handshake. A quota percentage cannot predict next-turn cost, and quota changes from other clients remain possible. Handshake can aim to stop before a configurable threshold, but cannot guarantee never hitting a limit.

| Resume failure today | ThreadRuntime warns then starts a new session without the failed ResumeID (`src/Marrow.App/Runtime/ThreadRuntime.cs:2037`, `:2049`, `:2060`). ACP can independently fall back to session/new (§2). | Current fallback does not guarantee restored CLI conversation. Handshake must not treat successful process launch as successful continuity. Require explicit import/resume verification or show an honest new-session context-transfer result. |

DECISION: persist resume bindings by `(MarrowThreadId, Provider, AccountId, nativeSessionId, transcriptRoot, version, checkpoint)`, retaining earlier bindings for rollback. A handoff transaction records source quiescence, destination auth/entitlement, context/import result, and destination acknowledgement before advancing the pill. Limit hops and retries; prevent loops and duplicate tools. Hydra heads must finish or checkpoint before the parent handoff; account switches must not lose outstanding head results or merge worktrees twice.

Required Windows experiment (per permitted provider/version): create a harmless local test conversation/tool result in A, fully close it, use documented export/path resume or carefully copy only required transcript artifacts, launch B with separate credentials, verify B's identity and several prior turns/tool references, continue, close/reopen, then return to A. Test invalid IDs, missing sidecars, compaction, large histories, Unicode/long Windows paths and refusal/rollback. Never read or publish test tokens. Until this passes, native account-transfer support remains UNVERIFIED.

## MA-0 validation and limits
