## 0. The answer in one screen

1. **What "pre-installed" really means.** Claude ships four document skills (Word, Excel, PowerPoint, PDF), the example skills in `anthropics/skills`, a set of Claude Desktop skills, and skills compiled into the Claude Code CLI. ChatGPT ships one skill (`skill-creator`). The Codex CLI ships five system skills in its binary. The Codex **desktop app** also installs a "primary runtime" with proprietary document, PDF, slide and spreadsheet plugins; the Codex CLI does not ship those.
2. **The skills people most expect cannot be shipped.** These are the document skills from both companies: Anthropic's `docx`, `xlsx`, `pptx`, `pdf` and OpenAI's `documents`, `presentations`, `spreadsheets` and `pdf` plugins. Their licences forbid copying and distribution, and OpenAI's also depend on a proprietary engine. Marrow covers most of this work with OpenAI's older Apache-2.0 `doc` and `spreadsheet` (recovered from git history at pinned commits) and OpenAI's Apache-2.0 `pdf`. The matching slide skill, `slides`, is held back until its licence question is answered (Q14). Who already has the vendors' own versions:
   - **Claude:** users signed in with `/login` to a claude.ai account on Claude Code 2.1.273 or later get Anthropic's versions through the sync. An API key is not enough.
   - **Codex:** users who also have the Codex desktop app may get OpenAI's versions. That app installs the primary runtime and enables its marketplace in the shared `~/.codex/config.toml`. Whether the Codex CLI that Marrow runs then lists them is checked live in WU-11.
   - **Everyone else:** gets only the open set.
3. **The bundle (section 1):**

   | Group | Skills | Licence |
   |---|---|---|
   | Anthropic | 13 | Apache-2.0 |
   | OpenAI and Codex (4 system skills from the Codex binary, plus `plugin-creator` from `openai/skills` `.system`, which codex main no longer ships) | 5 | Apache-2.0 |
   | Open document skills (`slides` held for Q14) | 3 | Apache-2.0 |
   | OpenAI's curated set | 29 | Apache-2.0, plus MIT from Notion and Vercel |
   | **Total** | **50 skill folders** | |

   All 50 are installed. They take about 17 MB (WU-2 measures it). 16 are switched on by default. That is fewer than before, because the catalogue the model sees is shared with the user's own skills, and Marrow's skills must never push the user's skills out of it (2.7). (r3) One of the 16, `review-agent`, is explicit-only, as upstream marks it, so 15 enter the model's catalogue.
4. **Installation (section 2):**
   - **Where it lives:** only in Marrow's own data folder (`%LOCALAPPDATA%\Marrow Code\skills\`).
   - **Integrity:** every file is a plain, read-only copy inside folders whose access list denies writing, creating, renaming and deleting (r2). The whole folder tree, extra files included, is checked against a manifest compiled into Marrow before every view build and before a generation is handed to a session.
   - **Views:** each chat gets its own generation, a view folder that never changes during a session, at one stable path per chat (`chat-<chatId>`, r3), so a resumed chat finds its skill scripts where its history says they are. Writes made in one chat cannot reach another. Spare generations are built ahead, off the chat path, and claimed by renaming them into place, so a launch or resume does not wait for the copy.
   - **Removal:** a before-uninstall hook, a "Reset skills data" action and written manual steps remove the locked folders (r3).
   - **How each provider is pointed at it:** with its own per-session mechanism. Claude and Grok use `--plugin-dir` (each with its own generation). Codex uses `skills/extraRoots/set`. Copilot uses `skillDirectories`, with a retry without it if the CLI rejects it. OpenCode uses `OPENCODE_CONFIG_CONTENT` with `skills.paths`, merged with every one of the user's config sources and copying the user's entries verbatim. Pi and Command Code use `--skill`; for Command Code only when its `--help` lists the flag.
   - **What it never touches:** nothing is written into any of the user's folders or configs. Bundled skills that would tell the agent to write into another provider's folder are patched (r2).
   - **Clashes:** when a name clashes, the user's skill (or the vendor's own) always wins.
5. **The app (section 3):** skills already appear in slash suggestions for Claude, Codex and Pi. The new parts are:
   - a Settings "Skills" page (switches, source, licence, what each skill needs or does);
   - a missing-tool state with an optional install;
   - a notices entry.

   Each goes on a canvas as variants first (OD-0070). The page uses Marrow's own glyphs and text-only attribution. It never shows vendor logos and never uses "Claude skills" or "ChatGPT skills" as labels.
6. **Work (section 4):** 21 ordered units, test-first, offline tests only.
7. **Owner questions (section 5):** 17 questions, each with a recommendation (r3 adds Q16, original equivalents of vendor-only skills, and Q17, the user's own skills under API providers).

## 2. Installation

### 2.1 Where the bundle lives, and how it is kept intact

**Locations**
- **In the package:** `<install>\current\skills\` inside the Velopack payload, replaced on every app update. It holds `bundle.json` (the manifest), `ATTRIBUTION.md`, and `store\<source>\<skill>\...` (r2: a source level, because Anthropic and OpenAI both ship a `skill-creator`; `<source>` is `anthropics-skills`, `openai-codex` or `openai-skills`).
- **Store:** on first start of each version, Marrow copies the payload into `%LOCALAPPDATA%\Marrow Code\skills\store\<bundleVersion>\<source>\<skill>\`. The data root is resolved through `DevDataRoot.LocalApplicationData()`, so Debug runs with `MARROW_DEV_DATA_ROOT` stay isolated. The copy keeps provider paths stable while Velopack swaps `current`.
- **Settings:** `%LOCALAPPDATA%\Marrow Code\skills\enabled.json` holds the per-skill switches and the bundle version they were set against.

**Integrity** (r1 replaced hard links and the "first start only" check; r2 covers added files, concurrent sessions, repair and deletion)
- **The aim:** no edit made through a skill file survives into another session or another provider. A process that rewrites Marrow's own binaries is outside what Marrow can defend.
- **The trust root:** a per-file SHA-256 manifest of the whole bundle, compiled into `Marrow.Services` as an embedded resource. The `bundle.json` files on disk are not trusted, because `%LOCALAPPDATA%` (including the Velopack install folder) is writable by any process the user runs, agents included.
- **Copies, not links:** store and view files are plain copies, never hard links, symlinks or junctions, so a write through a view cannot reach the store. Upstream already tells agents that "The installed skill path may be read-only" and to copy a skill before editing it (`skill-creator/SKILL.md:440`) [r1 checked].
- **Locked folders** (r2). After a store folder or a generation is complete, Marrow marks every file read-only **and** adds one inheritable deny entry to the folder's access list for the current user's SID: write data and add file, append data and add subfolder, write extended attributes, write attributes, delete, and delete child (`icacls` notation `(OI)(CI)(WD,AD,WEA,WA,DE,DC)`).
  - *Why the attribute alone is not enough* [r2 checked on this PC, Python 3.14.4]: the read-only attribute covers existing files only. In a folder whose files were all read-only, `py -3 -m scripts.run` wrote `scripts\__pycache__\*.pyc`, and a `json.py` placed beside the skill replaced the standard `json` module for that run, because `-m` puts the working folder first on `sys.path`. Anthropic's `skill-creator` runs `python -m scripts.run_loop`, `scripts.package_skill` and `scripts.aggregate_benchmark` from inside its own folder, and those scripts import `json`.
  - *What the deny entry does* [r2 checked on this PC]: with it, the same `py -3 -m scripts.run` exited 0 and wrote no `__pycache__` (Python skips bytecode it cannot write, without an error), and creating `json.py`, creating a subfolder, clearing the read-only attribute, appending, deleting and renaming a file were all refused.
  - *What it is not:* a security boundary. The folder's owner can still change its access list, and an agent runs as the same user. Marrow removed the deny entry itself in the GC experiment below. The lock stops incidental writes and makes accidental ones fail loudly; the whole-tree check below is what catches a deliberate one.
  - The access list is set after the build's rename into place (2.1 "Building"). (r3, corrected) [r3 checked on this PC] Revision 2 said a deny on delete would block that rename. It does not: a locked folder was renamed without error, because its parent `views\<provider>` (not locked) grants delete-child, and after the rename a write inside it was still refused. Claiming a spare (below) relies on this. The same fact means an agent can rename a generation away or put another folder at its path; whole-tree verification catches that like any other change.
  - *Removing locked folders* (r3) [r3 checked on this PC, scratch folder with the exact deny entry]: `Remove-Item -Recurse -Force` gave "Access to the path is denied." and `rd /s /q` left every file. Explorer, cleanup tools and test teardown fail the same way. `icacls <folder> /reset /T /C /Q`, then `attrib -R <folder>\* /S /D`, then `rd /s /q <folder>` removed it completely. The data root `%LOCALAPPDATA%\Marrow Code` is not inside the Velopack install folder `%LOCALAPPDATA%\MarrowCode` (scripts/package-windows.ps1:41 `PackId`, StoragePaths.cs:70), so Velopack's uninstaller never touches it, and Program.cs today only calls `VelopackApp.Build().Run()`. Four routes remove the lock:
    1. **Before-uninstall hook.** Program.cs registers `OnBeforeUninstallFastCallback` (present in Velopack 1.2.161, the port's version; Velopack runs it when the user uninstalls, then exits the process, and stops it after 30 seconds) [r3 checked, `Velopack.xml`]. The hook first unlocks every store folder and generation under `skills\` (removes the deny entry, clears the read-only attributes), then deletes `store\` and `views\` and `condemned.json`. Unlocking comes first and covers everything before any delete starts, so that if time runs out or a file is held, whatever is left is an ordinary folder the user can delete. `enabled.json` stays, like the rest of Marrow's data, which uninstall leaves as today.
    2. **"Reset skills data"** on the Skills page (C1): ends nothing that is running; it unlocks and deletes every unleased store folder and generation, then rebuilds the store and spares. Leased ones are unlocked and deleted when their sessions end.
    3. **Manual steps** on the skill detail (C2) and in the notices, for a PC where Marrow is gone or broken: the three commands above, with the folder `%LOCALAPPDATA%\Marrow Code\skills`.
    4. **Next start after a crash:** GC already runs the unlock order at app start (below).
  - *Tests* (r3): every test that creates a locked folder does so through one fixture whose teardown runs the unlock order, and the test run fails if any folder with Marrow's deny entry remains under the test root or under a `MARROW_DEV_DATA_ROOT` the run created.
- **Whole-tree verification** (r2). "Verify" means: enumerate every entry under the folder, hidden and system entries included, and compare the result with the manifest as a set. A mismatch is any of: a file whose size or SHA-256 differs; a missing file; **any extra file or folder** (a planted `json.py`, a `.pyc`, a `__pycache__` or a `-workspace` folder alike); any reparse point (symlink or junction); any named data stream other than the file's main stream (Marrow writes files by content, so a correct file has none); a missing deny entry. Extra files are not ignored, because ignoring them is exactly what lets a planted module through. Normal use no longer produces extra files: bytecode is stopped by the lock, and the two `skill-creator` instructions that wrote beside or inside the skill folder are patched (1.2 A).
- **When Marrow verifies:**
  1. Before every view build, Marrow verifies the store against the embedded manifest. A store skill that does not match is deleted (see GC) and restored from the package payload, which is itself verified. If the payload does not match either, the skill is left out and the Skills page says so.
  2. Before a generation is handed to a session (see "Spare generations"), Marrow verifies it whole. On any mismatch the generation is condemned, a fresh one takes its place (r3: at the chat's path, see "Per-chat views"), and the repair is logged.
  3. Before each turn (r2), Marrow re-verifies the session's generation off the UI thread. A second read of files Windows has already scanned costs about 30 ms for the default set [r2 checked, below]. For Command Code, which starts one process per turn, a mismatch means the next turn gets a fresh generation (r3: at the same chat path when the old one can be deleted, see "Per-chat views"). For providers with a long-running process, which cannot be given a new folder mid-session, the session shows a notice ("A Marrow skill file changed during this chat; new chats are not affected"), and the generation is condemned when the session ends.
- **Editing a Marrow skill:** the user is told that Marrow's skills are read-only, and that to change one they copy it into their own skills folder, where their copy then wins (2.4). The text sits on the skill detail (C2) and in the "Copy to my skills" action's help. That action only shows the folder path and copy instructions; Marrow does not write into the user's folder.

**Per-chat views: one generation per chat, at one stable path** (r1 introduced immutable generations; r2 made them per session and nonce-named; r3 gives each chat one stable path)
- **Why the path must be stable** (r3) [r3 checked]. A chat's own history holds absolute paths into its generation, and a resumed chat is sent that history again. Claude Code 2.1.288 puts "Base directory for this skill: <path>" into every skill it loads (string in the installed binary) and expands `${CLAUDE_SKILL_DIR}` to that path; the result is in the transcript that `--resume` replays. Codex injects each skill as `<skill><name>…</name><path>…</path>…</skill>` (`ext/skills/src/fragments.rs:90-109` @ `2739e82`), and the port's `{type:"skill", name, path}` items carry the path too; both are in the rollout that `thread/resume` replays. Revision 2 gave every session a new `<key>-<nonce>` folder and deleted the old one at lease end, so after an app restart or any resume the model would re-run `py -3 <old path>\scripts\x.py` against a folder that no longer exists and fail mid-task.
- **Layout:** `%LOCALAPPDATA%\Marrow Code\skills\views\<provider>\chat-<chatId>\`, where `<chatId>` is Marrow's own id for the chat, which survives restarts. Other folders in `views\<provider>\` are `spare-<key>-<nonce>` (spares), `list-<key>-<nonce>` (listing generations) and `tmp-<random>` (builds in progress). `<key>` is a short hash of the bundle version and **the exact list of `<source>/<skill>` entries the generation holds** (r3: the result, not the inputs; see "Spare generations"). `<nonce>` is 8 random bytes in hex. For Claude and Grok a generation is a plugin folder (`<gen>\.claude-plugin\plugin.json` plus `<gen>\skills\<skill>\`).
- **One generation per chat, never shared** (r2, kept). A chat's generation is never given to another chat, of the same provider or any other, so a write in chat A cannot reach chat B.
  - *Session* means one Marrow chat while it is live: one provider process for Claude, Codex, Copilot, OpenCode, Pi and the ACP providers, and every per-turn process of that chat for Command Code.
- **Resuming** (r3; replaces "resuming gets a new generation" and generalises the Copilot rule of revision 2). Before any launch of a chat (first start, resume after it ended, resume after an app restart, and each Command Code turn), Marrow makes sure `chat-<chatId>` holds a fresh, complete, locked, verified generation for the current switches:
  1. If `chat-<chatId>` exists, is unleased, holds the entry list the chat needs now (its recorded `<key>` is current) and verifies, it is used as it is.
  2. Otherwise whatever is there is deleted with the unlock order (GC below), and a matching spare is renamed to `chat-<chatId>`. A rename keeps the files Windows has already scanned [r3 checked: rename 1.3 to 1.7 ms; a read-and-hash pass right after it 36 to 62 ms, against 3.4 to 6.2 s for the first pass over a fresh copy; three runs, over 255 files: the 14 default-on folders that exist as plain folders in the clones, without the history-only `doc` and `spreadsheet`].
  3. Only if the old folder cannot be deleted (a handle is still open, for example a provider process that outlived a crash) does the chat get a new path, `chat-<chatId>-<nonce>`, recorded for that chat. Marrow then tells the model where its skills now are, in the launch's own instructions: Claude through the `--append-system-prompt` the port already passes; Codex through `developer_instructions` on `thread/resume` (present in `ThreadResumeParams`, `app-server-protocol/src/protocol/v2/thread.rs` @ `2739e82`) [r3 checked]; every other provider through one line ahead of the next user message. The line reads: "Marrow's skills for this chat are now in <new path>. Paths under <old path> earlier in this conversation no longer exist; use the same relative path under the new folder."
  - A skill switched off since the chat last ran is absent from the rebuilt generation, like a deleted user skill; the switch says it applies to new chats, and the C2 detail adds "and to chats you resume".
  - For Copilot, WU-11 still checks whether Copilot keeps the path in its own session state; with the rule above that no longer changes the design.
- **Spare generations** (r2; r3 changes the key and the claim). Copying is cheap, but the first read of new files is not on this PC: copying the default set (255 files, 8.5 MB) took 0.3 to 1.1 s, and the first read-and-hash pass over the fresh copy took 1.7 to 4.3 s (r3 re-run: 3.4 to 6.2 s), while a second pass, or a pass over old files, took about 30 ms [r2 checked, Python 3.14.4, three runs]. The likely cause is on-access antivirus scanning of new files; that cause is not confirmed. To keep this off the chat path, Marrow keeps spares, built, locked and verified in the background at low priority.
  - *Key by content* (r3). Revision 2 keyed spares by their inputs, including the session's model (through the 2.7 cap) and the project (through project clashes), which a spare built at app start cannot know, so most launches would have missed and waited 2 to 5 s. Now the 2.7 cap no longer depends on the session's model (2.7: it is computed for the smallest context window the provider offers), and `<key>` hashes the resulting entry list. Project clashes and the cap only ever remove entries, so for every project without a clashing skill, and whenever everything fits, the needed key is the same and one spare serves every chat of that provider.
  - *Which spares exist:* per provider, one for the global key, plus one for each distinct key that the projects of the five most recent chats of that provider need (usually none). The needed key is computed from cached scans in a few milliseconds, never from a copy.
  - *Built ahead of need:* at app start, after a switch change, right after a spare is claimed, and (r3) as soon as the user picks a provider or a project folder for a new chat, before the first message is sent, so a project with a clashing skill has its spare ready by the time the user has typed.
  - *Claim:* an in-memory claim (two launches cannot take the same spare), a rename to `chat-<chatId>` (the spare stays locked; see "Locked folders"), the cheap second-pass verify, then launch.
  - *Budget* (r3, measured in WU-4): with a ready spare, everything Marrow adds before the provider starts is at most 150 ms on this PC (measured parts: rename under 2 ms, second-pass verify 30 to 65 ms). A launch with no matching spare builds one and waits (baseline 2 to 6 s here); WU-4's scenarios (new chat after a model change, new chat in a project without a clash, resume after a restart, new chat in a project with a clash after a picker selection) must all hit a spare, and a miss is logged with its reason.
- **Listing generations.** The catalogue probes that run no model turn (Claude's `Handshake`, Codex's `ListCommands`; ClaudeSession.cs:278, CodexSession.cs:630) use one shared listing generation per provider and `<key>`, because nothing in them can write. Codex reports a filesystem `path` for each skill and the port sends it back in the `{type:"skill", name, path}` input item, so a path under the listing generation is rewritten to the same relative path under the session's own generation before it is sent (WU-7).
- **Building:** a generation is built in `views\<provider>\tmp-<random>\`, renamed to `spare-<key>-<nonce>` or `list-<key>-<nonce>` (a new name, so the rename cannot collide), then locked, then verified. Its files are never changed after that; the only later operation is the claim rename to `chat-<chatId>`.
- **Launching:** each launch passes the chat's generation path in `--plugin-dir`, `extraRoots`, `skillDirectories`, `skills.paths` or `--skill`. A running session keeps its folder, and that folder never changes under it. Switch changes reach new chats and resumed ones, never a running session, and Codex has no reason to send `skills/changed` for Marrow's roots.
- **Codex "Always allow" for skill scripts** (r3) [r3 checked, `core/src/exec_policy.rs` @ `2739e82`]. The port offers Codex's `acceptWithExecpolicyAmendment` as "Always allow" (CodexSession.cs:1591-1594). Codex then appends the amendment's command prefix as an allow rule to `$CODEX_HOME/rules/default.rules` (`append_amendment_and_update`, `default_policy_path`), the user's own file. The prefix is either the model's requested `prefix_rule` or the full parsed command that the heuristics matched. Bare interpreter prefixes (`py`, `py -3`, `python`, `python3`, `node`, `pwsh -File`, `bash` and others) are refused as suggestions (`BANNED_PREFIX_SUGGESTIONS`), so a rule that approves a bundled script must contain the script's absolute path under the generation. Such a rule matches only that chat (and nothing at all once the chat is deleted), so the user's rules file would fill with entries for paths that no longer exist. Rule: when any element of the amendment contains Marrow's `skills\views` root (compared case-insensitively, with either slash), Marrow does not offer "Always allow" for that request; "Approve" and "Approve for session" remain, and with the stable chat path "Approve for session" covers every later run in that chat. Commands outside the views root are unchanged (Mac parity). WU-7 tests it; WU-11 records a live amendment for a bundled script.
- **Leases:** Marrow keeps an in-memory lease per live session (chat id, provider process, generation path) and per running probe.
- **Garbage collection** runs at app start, when a session ends, and after a build. It deletes a generation when no lease refers to it, condemned ones included; a `chat-<chatId>` folder of an ended chat is deleted too, because a resume claims a spare into the same path (r3). **Order** (r2): remove the deny entry (the owner may always change the access list), clear the read-only attribute on every file, then delete. [r2 checked on this PC, .NET 10.0.12] `Directory.Delete(path, recursive: true)` throws `UnauthorizedAccessException` on a folder containing a read-only file, and also on a locked generation; after removing the deny entry and clearing the attributes the same call succeeded. If deleting fails because a process still holds a handle (a skill script running from the folder, a shell whose working directory is there, or a CLI watching the root; the experiment's held file gave `IOException`), the delete is skipped and retried at the next collection. Nothing waits on it.
- **Repair while leased** (r2; r3 adds the path rule): a condemned generation that is still leased or held open stays where it is, marked condemned in memory and in a small `condemned.json` beside the views (so the mark survives a restart). It is never handed to another session. The chat's next launch follows "Resuming": the condemned folder is deleted and a spare takes the same path, or, if it is still held, the chat moves to `chat-<chatId>-<nonce>` and the model is told. GC deletes the condemned one once the lease ends and the handles close.
- **Project views** (2.4): (r3) a chat whose project has a clashing skill simply needs a different entry list, so its generation is a spare with that `<key>`, claimed into `chat-<chatId>` like any other. Revision 2's separate `p-<hash>-<key>-<nonce>` folders are gone; the same rules apply.
- **Old store versions** are deleted (with the same unlock order) at app start once no generation built from them is leased.
- **The remaining risk, stated plainly** (r2): an agent that deliberately removes the deny entry, or (r3) renames another chat's generation away and puts its own folder at that path, can change what another live session reads, because generation paths can be found and every agent runs as the same user. The next per-turn check in the other session detects it and shows the notice, but the write may already have been read. An agent with that intent can equally edit the user's own skill folders and provider configs, which every session reads; Marrow cannot prevent that either. Marrow guarantees that such a write never reaches a new session, never reaches another provider, and never survives into a spare, the store or the payload.

**Never written by Marrow**
- The user's provider folders: `~\.claude`, `~\.codex` (including `skills\.system` and `config.toml`), `~\.agents`, `~\.copilot`, `~\.config\opencode`, `~\.pi`, `~\.commandcode`, `~\.gemini`, `~\.cursor`, `~\.grok`.
- Any project folder, and the Claude managed-settings folder.

Marrow only reads these folders, to find name clashes and the user's OpenCode paths. **Uninstalling** (r2, corrected; r3 adds the hook): Marrow leaves no file or setting in any provider folder, and its before-uninstall hook unlocks and deletes its own skills store and views (2.1, "Removing locked folders"). The providers' own records are not Marrow's to edit, so they keep what they logged: Claude Code transcripts (`~\.claude\projects\*.jsonl`) and Codex rollouts (`~\.codex\sessions\`) may mention `marrow:` skill names, skill text the model read, and generation paths, and those entries remain after Marrow is uninstalled, like any other conversation history.

**Folder names** (r2, narrowed): every skill folder name equals its frontmatter `name`, and no skill folder contains a dot-folder (WU-1). The rule against dot-folders applies to **Codex roots** (`views\codex\...`), because Codex skips hidden directories below a root. Claude and Grok generations need `.claude-plugin\`, and Antigravity option 1 (2.2) needs `.agents\skills\`; those are expected there.

### 2.6 Windows dependencies: detect and explain, do not bundle

Recommendation (Q5): do not bundle Python, Node, LibreOffice, Poppler, pandoc or Playwright browsers. Together they add several hundred MB (LibreOffice alone is the largest), each has its own licence to carry, and each needs its own updates. Instead:

- **Needs in the manifest.** `bundle.json` lists each skill's needs: `python>=3.9`, `node>=18`, `pnpm`, `uv`, `git`, `gh`, `soffice`, `pdftoppm`, `pandoc`, `qpdf`, `bash`, `playwright-browsers`, `internet` (r1), `env:OPENAI_API_KEY`, `mcp:notion` and so on, plus the pip and npm packages, shown as text.
- **A dependency probe** (WU-13) runs on the Skills page and when a skill is switched on, never on the chat path:

  - It finds LibreOffice through the registry or `%ProgramFiles%\LibreOffice\program\soffice.exe`, and Git Bash through Git for Windows.
  - For environment variables it checks presence only and never reads the value.
  - It checks MCP servers against Marrow's own MCP settings.

### 2.7 Catalogue budget: the user's skills come first (r1, new)

Every provider shows the model a catalogue of skill names and descriptions, under a budget:
- **Claude:** `skillListingBudgetFraction`, 1% of the context window, with each description cut at 1,536 characters.
- **Codex:** 2% of the window, or 8,000 characters when the window is unknown. It "shortens descriptions first and may omit skills with a warning".

Turning on Marrow's skills must never shorten or drop the user's own, synced or bundled skills. The rule:

1. **Measure.**
   - Before building a generation, Marrow computes the budget in characters for that provider. (r3) It uses the **smallest context window among the models that provider offers in Marrow's model picker**, not the session's model, with the provider's documented rule and the numbers recorded by the WU-11 live measurement. So a spare built before the user picks a model is still right (2.1), and a model switch in a running session can never push the user's skills out. The cost is a smaller share for Marrow under large-window models; where the smallest window leaves too little room, step 2 leaves out Marrow's lowest-priority skills, exactly as before. WU-11 measures each provider's real cut-off, and WU-21 tests the rule.
   - It also computes the size of the entries the provider already lists: the reported names from 2.4 step 2, with their descriptions where the provider reports them, or the folder-scan text otherwise.
2. **Cap.**
   - Marrow's entries may use only the room that is left after the user's entries, with a 10% margin.
   - They may never use more than half of the budget.
   - If the enabled Marrow skills do not fit, Marrow leaves out its own lowest-priority skills for that provider (manifest `priority`; the default-on set ranks first). It never shortens the user's.
3. **Tell.** The Skills page shows "Left out for Codex to keep your own skills fully listed" on each affected row.
4. **Smaller default.** The default-on set is cut to 16 (1.2), of which 15 are listed (r3: `review-agent` is explicit-only): 4,875 characters of descriptions, or 3,798 under Claude, measured at the pins.

Explicit-only skills cost nothing under Claude and Codex, because neither lists them for the model. Native providers (2.2) use the same cap on Marrow's own catalogue block.
