# Critique: settings-usage-tour-diff-terminal

**Verdict:** COHERENT - every claim I re-checked against the source held up (literals, strings, control flow, SF Symbol names, state machines), so no file needs a re-read; what is missing is a set of specific deferred constants, three unguarded destructive/re-entrant paths, and two capture-mode / cross-file call sites that the family never resolved.

## Contradictions (a report disagrees with the source) (3)

1. R027 (TourPages.swift, unresolved_questions) says "Whether anything else calls Tour.present besides the first-run check in AppDelegate.swift (for example a Help menu item that replays the tour) is not determinable from this file alone", while R023 (SettingsView.swift, ui_elements) already documents the About app card's row "Welcome tour" / "The slideshow from the first launch: Hydra, the effort slider, panels and themes." with a Button("Show") that calls Tour.present(model:) (SettingsView.swift:970), and lists Tour.present(model:) in its side_effects. The family answers its own open question in a neighbouring report, and both still miss AppCommands.swift:101-103.

2. R023 (SettingsView.swift) describes the About app card as: icon, name, version, "Welcome tour" row, body text, license line - and separately lists AboutSoftwareUpdateSection / AboutUpdateCheckRow / AboutUpdateChromeAccessory only in calls_into. The source (SettingsView.swift:927-931 and :974-975) puts AboutSoftwareUpdateSection FIRST on the page, above the app card, and AboutUpdateCheckRow INSIDE the app card between the "Welcome tour" row and the body text. R021 describes both components in full but never states where on the About page they sit. Neither report alone gives the About page's row order.

3. R028 (UsageFloatingPanel) notes the strip draws the heads icon whenever headsProvider is non-nil, "unlike UsagePanel" which additionally requires headsProvider != provider, and calls out the duplicate-icon consequence - this is correct and confirmed (UsageFloatingPanel.swift:82-84 vs UsagePanel.swift:28). But the same report's ui_elements for the title capsule describes the second icon as "an optional second ProviderIcon(provider: headsProvider, size: 12)" with no condition, so the file entry's two sections disagree about whether a condition exists. A reader porting from ui_elements alone gets it right by accident; one porting from the UsagePanel rule gets it wrong.

## Gaps (referenced but never pinned down) (14)

1. DroppyCode/App/Views/Diff/DiffInspector.swift:626-632 - R018 states the order of show() backwards. The source is `guard let runtime, let target = resolvedAnchor() else { return }` THEN `session += 1` THEN `guard !popover.isShown else { return }`. R018's feature_notes say "show() guards on a resolved anchor and on the popover not already being shown, bumps session". The order matters: every show() call while the popover is already shown still increments `session` without touching `pendingSession`, so the stale-close guard in popoverDidClose (session == pendingSession) fails and that close will NOT clear shownRuntime.isDiffVisible and will NOT set popover.contentViewController = nil. setAnchor(_:) and setFallbackAnchor(_:) both call show() unconditionally when desiredVisible, so this is reachable in normal use.

2. DroppyCode/App/Views/Settings/MCPSettingsPage.swift:563-565 - a destructive path with no guard that no report flags. The custom-server ellipsis menu's `PopoverItem("Delete", symbol: "trash", isDestructive: true)` calls `model.mcp.deleteCustom(server)` immediately. It does NOT consult `settings.confirmBeforeDeleting` and shows no popover or confirmationDialog, unlike the archive deletes in SettingsView.swift:838-870 and :903-919 which both branch on that setting. R022 lists the menu item but never says the delete is unconfirmed.

3. DroppyCode/App/Views/Settings/MCPKeyPanel.swift:15-30 vs MCPSetupPanel.swift:17-25 - MCPKeyPanel.present has NO `isPresenting(_:)` re-entry guard and close() clears no presented-entry id, whereas MCPSetupPanel has both and explicitly returns after orderFrontRegardless when the same entry is already up. So a second call to MCPKeyPanel.present re-opens entry.keysURL in the browser and rebuilds the content view, and MCPServerCard.begin() (MCPSettingsPage.swift:533-539), MCPCustomRow.begin() and MCPInfoPopover's "Change the <label>..." button (MCPSettingsPage.swift:971-976) can all reach it repeatedly. R021 says only "the panel instance is reused"; neither R021 nor R022 flags the asymmetry.

4. DroppyCode/App/Views/Tour/TourPages.swift - R027 files as unresolved "whether anything else calls Tour.present ... (for example a Help menu item that replays the tour)". It is determinable and there are three shipped call sites plus one capture-only one: DroppyCode/App/AppCommands.swift:101-103 uses `CommandGroup(replacing: .help) { Button("Welcome tour") { Tour.present(model: model) } }`, which REPLACES the entire standard Help menu with that single item (a menu item nobody in the family describes); DroppyCode/App/AppDelegate.swift:18-19 gates on !hasSeenTour and sleeps 700 ms before presenting (R027's feature note names line 18 but omits the 700 ms delay); DroppyCode/App/Views/Settings/SettingsView.swift:970 Button("Show").

5. DroppyCode/App/Captures/TourCaptures.swift:216-220 - a capture-only path nobody classified. It calls `TourWindowController.shared.present(pages: Tour.pages)` with NO onFinish and NO onClose, so in capture mode the tour never writes hasSeenTour, and the window is torn down by `TourWindowController.shared.close()` four lines later after a 1400 ms sleep. R027 documents only Tour.present's two-closure wiring and never mentions that the controller is also driven without callbacks. R018 flagged the analogous WebsiteCaptures.isEnabled gate for the diff popover, so the family is inconsistent about capture-mode coverage.

6. DroppyCode/App/Views/Usage/UsageFloatingPanel.swift:26-28 vs DroppyCode/App/Views/Usage/UsagePanel.swift:31 - the panel's `hasSomething` gate tests `usage?.fraction != nil`, but UsagePanel's `showsContext` requires `usage?.fraction != nil && usage?.windowTokens != nil` and its `if let usage, let fraction, let window` needs both. A ContextUsage carrying a fraction but no windowTokens, on a provider exposing neither plan limits nor credits, takes the non-empty branch and renders a UsagePanel that draws nothing (a 16pt-padded empty VStack) instead of the "Nothing to show for <Provider> yet." placeholder. R028 documents both predicates separately and never reconciles them.

7. DroppyCode/App/Views/Settings/ModelsSettingsPage.swift - R022 leaves AppSettings.modelListLimit unresolved. It is 15 (DroppyCode/App/AppSettings.swift:181), enforced again at AppSettings.swift:819 (`guard !modelList.contains(pin), modelList.count < Self.modelListLimit`). It is user-visible twice: the count line "<n> of 15. Click a model to set its reasoning effort and fast mode for every new chat." (line 64) and the disabled-add help "The picker holds up to 15 models" (line 362).

8. DroppyCode/App/Views/Usage/UsageFloatingPanel.swift - R028 leaves HydraPanel.cornerRadius and HydraPanel.stripHeight unresolved although they set the entire panel geometry and every content inset it reports. They are in DroppyCode/App/Views/Chat/HydraPanel.swift:33 and :37: cornerRadius = 22, stripHeight = Chrome.chromeTopPadding + Chrome.capsuleHeight + 6 = 12 + 32 + 6 = 50. So the reported content height is measured + 58, and the empty state reports 94.

9. DroppyCode/App/Views/Settings/SettingsView.swift - R023 leaves AppSettings.defaultBackdropOpacity and the ChatZoom ladder unresolved, but both drive the reset affordances it documented in detail. defaultBackdropOpacity = 0.5 (AppSettings.swift:291; read back at :713 with `defaults.object(forKey: Key.backdropOpacity) as? Double ?? Self.defaultBackdropOpacity`), and ChatZoom.defaultIndex = 3 with stepCount = percentages.count (DroppyCode/UI/Common/ChatZoom.swift:11-13). Without these the "off stock" test abs(value - 0.5) >= 0.005 and the slider range 0...stepCount-1 cannot be ported.

10. DroppyCode/App/Views/Settings/SettingsView.swift:996-1000 - R023 records the LicensesRow resources ("LICENSE" with no extension, THIRD_PARTY_NOTICES.md, TRADEMARK.md) and says "per-file title 13pt semibold", but never gives the three user-visible titles rendered in the popover: "Droppy Code", "Third-party notices", "Trademarks". It also omits that the fallback string is built per-resource as "The <resource> file is missing from this copy of the app." using the RESOURCE name (so it reads "The THIRD_PARTY_NOTICES file is missing...", not the display title).

11. DroppyCode/App/Views/Terminal/TerminalPanel.swift:78 - a persisted field whose migration/out-of-range behaviour is unstated. R026 correctly names model.settings.terminalHeight (AppSettings.swift:144 Key "terminalHeight", default 260 at :722) and the drag clamp min(760, max(140, origin + delta)), but the clamp lives ONLY in the drag handler. `.frame(height: dragHeight ?? model.settings.terminalHeight)` uses the stored value verbatim, so a persisted height outside 140...760 (from an older build or a hand-edited plist) is applied unclamped and can only be corrected by dragging. No report states this.

12. DroppyCode/App/Views/Settings/AboutUpdateViews.swift - R021's persisted_fields is empty and its unresolved_questions never mention persistence, yet the whole AboutVersionPill standing machine it documents ("Up to date" / "Check failed" / "Not checked yet", line 626) and the check-row suffix ("Checked <relative>." vs "Not checked yet.", line 845) are driven by UpdateChecker.lastCheckedAt, which is a UserDefaults Date under the key "updateChecker_lastChecked" (UpdateChecker.swift:79, read at :118, written at :184 and :238). The sibling keys "updateChecker_release" and "updateChecker_notifiedVersion" are equally unnamed by anyone in the family.

13. DroppyCode/App/Views/Settings/MCPSettingsPage.swift:559-561 - the custom-server menu's "Disconnect" item does not set showMenu = false, while "Edit" directly above it does (line 557). Whether the popover self-dismisses on a PopoverItem action is therefore load-bearing behaviour of PopoverItem, and R022 records neither the asymmetry nor PopoverItem's dismissal contract. The same asymmetry exists in MCPConnectedRow (MCPSettingsPage.swift:184-192: "Show tools" sets showMenu = false, "Refresh" and "Disconnect" do not).

14. Localized vs verbatim Text is inconsistent across the family and nobody records it, which matters because Text("...") goes through the string catalog and Text(verbatim:) does not. In an otherwise all-verbatim usage stack, UsagePanel.swift:35 uses Text("Context window"); TerminalPanel.swift:67 and :71 use Text("No shell open in this thread") and Button("New shell"); MCPSetupPanel.swift:140 uses Text("Checking") while the adjacent status lines are verbatim. A port that treats all of these the same way will diverge wherever the catalog has an entry.

## Cross-cutting findings (9)

1. Escape is detected by the raw macOS keyCode 53 in FIVE separate places in this family, each with a different swallow policy, and no report compares them: DiffInspector.swift:663-667 (DiffPopoverCoordinator.handleKeyDown closes and returns nil), TerminalPanel.swift:335-341 (TerminalHost closes the drawer and returns nil, but only when foregroundJobIsTheShell and no KeyChord.allowedModifiers are held and the terminal view is firstResponder), MCPKeyPanel.swift:65-71 and MCPSetupPanel.swift:86-92 (both close the panel and return nil while visible), ShortcutsSettingsPage.swift:601-604 (cancels the recording, and its monitor swallows EVERY keyDown/keyUp/flagsChanged while recording). All five are NSEvent.addLocalMonitorForEvents, which has no Windows equivalent; the port needs five separate decisions, not one.

2. DiffPopoverCoordinator's mouse monitor is the one place that deliberately does NOT swallow: DiffInspector.swift:657-660 closes the popover on a left/right mouseDown outside the popover's content window but still returns the event, so the same click also activates its target (another turn's Review button opens that diff in one tap). A port that consumes the dismiss click breaks that flow. R018 states it; nobody else in the family generalizes it.

3. Four distinct AppKit top-level surfaces here, all borderless/chromeless with the same recipe: TourWindowController HostWindow (styleMask [.borderless,.fullSizeContentView], canBecomeKey/canBecomeMain overridden true, isOpaque false, backgroundColor .clear, hasShadow true, level .floating, collectionBehavior [.managed,.participatesInCycle,.fullScreenAuxiliary], isMovableByWindowBackground true, isReleasedWhenClosed false), MCPKeyPanel and MCPSetupPanel NSPanels (styleMask [.nonactivatingPanel,.fullSizeContentView,.titled,.closable], titleVisibility .hidden, titlebarAppearsTransparent, level .floating, hidesOnDeactivate false, collectionBehavior [.canJoinAllSpaces,.fullScreenAuxiliary], all three standardWindowButtons hidden), and the NSPopover in DiffPopoverCoordinator (behavior .semitransient, animates true, fixed 640x540). All rely on AppKit shaping the shadow to the window's alpha so it follows the rounded card.

4. Pre-measuring SwiftUI content with a throwaway NSHostingView before the window appears is used three times and is load-bearing each time: TourWindowController.maxBottomPanelHeight (layoutSubtreeIfNeeded + fittingSize.height, max across pages, so the tour card never resizes between pages), MCPKeyPanel.present (fittingSize.height.rounded(.up), floor 100, width 380), MCPSetupPanel.present (same, width 400). MCPSetupPanel additionally re-fits at runtime through onGeometryChange -> fit(height:), which moves origin.y by (oldHeight - wanted) so the TOP edge stays fixed.

5. Chrome.* design tokens are deferred as "defined elsewhere" by R018, R021, R022, R023 and R026, but they are plain literals in DroppyCode/UI/Chrome/Chrome.swift and should be captured once for the whole port: windowCornerRadius 26, sheetInset 0 (so the Settings detail pane has ZERO inset), sheetCornerRadius 16, trafficLightDiameter 14, trafficLightSpacing 9, trafficLightLeading 18, trafficLightTop 16, trafficLightClearance 10, chromeHorizontalPadding 14, chromeTopPadding 12, capsuleContentHeight 28, capsuleVerticalPadding 2, capsuleHorizontalPadding 12, capsuleHeight = 28 + 2*2 = 32 (computed, Chrome.swift:38), symbolSize 14, listInset 10, sectionSpacing 20, sectionHeaderSpacing 10, contentHorizontalPadding 16, rowControlTrailingPadding 10, rowButtonLabelHeight 16.

6. NSHapticFeedbackManager is used in three of this family's files and the shared `enum Haptics` is DEFINED in ShortcutsSettingsPage.swift:482-486, not in a utilities file: ShortcutsSettingsPage (.alignment on a modifier added, .generic on a rejected chord and on Clear / Reset to default, .levelChange on an accepted chord), AboutUpdateViews (.alignment and .levelChange in startCelebrationSweep), ModelsSettingsPage (NSHapticFeedbackManager .alignment on every landed drag-reorder swap). Windows has no equivalent; the port must decide once where these become no-ops.

7. The Terminal subsystem's hardest macOS dependency is not SwiftTerm but TerminalStore.swift:69-77: `foregroundJobIsTheShell(_:)` reads kinfo_proc via sysctl(CTL_KERN, KERN_PROC, KERN_PROC_PID, shell) and returns `info.kp_eproc.e_tpgid == info.kp_eproc.e_pgid`, because the pty master answers no tcgetpgrp for a process it is not the controlling terminal of. This single predicate gates whether Escape closes the drawer or reaches vim/claude/less. On Windows (ConPTY) there is no process-group concept at all, so the Escape-at-prompt rule needs a different mechanism, not a translation.

8. The login-shell launch contract is exact and must be ported literally or replaced consciously (TerminalStore.swift:28-40): executable = LoginEnvironment.userShell(), execName = "-" + shell.lastPathComponent, currentDirectory = the project directory, environment = LoginEnvironment.current overridden with TERM=xterm-256color, COLORTERM=truecolor, TERM_PROGRAM=Droppy Code, DROPPY_CODE_PROJECT_ROOT=<directory>, flattened to "KEY=VALUE" strings; args are [] with no command, and exactly ["-l", "-i", "-c", "<command>; exec <shell> -l"] for a script tab.

9. Persisted state this family writes is all AppSettings/UserDefaults with literal key names, plus two non-UserDefaults stores: MCP secrets in the Keychain (locked variables, via model.mcp.saveCustomValues) and non-secret custom-server variable values in mcp.json (the lock toggle's own help string says so: "Stored in mcp.json; click to keep it in the Keychain instead"). The update checker adds three UserDefaults keys of its own that this family reads but never names: "updateChecker_release", "updateChecker_lastChecked", "updateChecker_notifiedVersion" (UpdateChecker.swift:77-81).
