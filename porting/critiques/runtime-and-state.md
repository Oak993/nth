# Critique: runtime-and-state

**Verdict:** NEEDS_REREAD - six of seven reports hold up well against the source, but R008 (ThreadRuntime.swift, 3637 lines) never describes the ProviderEvent dispatch case by case and states a session-ID rule that the API-key branch contradicts, so the protocol and session-lifecycle spec for the port is wrong as written.

## Contradictions (a report disagrees with the source) (5)

1. R008 feature note: "A session ID is held in unsentSessionID until the first message actually goes through it, so a warmed session replaced before sending never leaves an unresumable ID on the thread." Source contradicts this for API-key providers: ThreadRuntime.swift:1490 writes `app.updateThread(threadID) { $0.providerSessionID = sessionID }` directly in the DeepSeek/Meta/Z.ai branch, bypassing `recordSessionID` (1570-1577) entirely. The hold-back exists only on the CLI path (1567) and in the `.sessionReady` handler (2082).

2. R033 says Shell's `excludedKeys` has 13 entries; Shell.swift:331-335 has 15 (the report's own enumerated list also has 15). R033 says `readers` has 51 entries; Shell.swift:144-151 has 52 (the report's own list also has 52).

3. R033 says SimpleDiff's 200_000 cap is "the same cap [that] bounds command diffs in ThreadRuntime.fileEdits". They are two separate constants with different operands: Text.swift:81 `SimpleDiff.diffLimit` is compared against `old.utf8.count + new.utf8.count` (Text.swift:101), while ThreadRuntime.swift:3366 `editDiffLimit` is compared against the produced `diff.utf8.count` (3373, 3397). R008 describes editDiffLimit correctly, so the two reports disagree about whether one constant or two exist.

4. R003 (AppDelegate) states the capture-run early return happens "before showMain, openThreadOnLaunch, the tour, bootstrap, update checks and the relaunch marker" and calls it a short-circuit of "the entire normal launch". AppDelegate.swift:9-11 shows the notification-center delegate assignment and `model = windows.model` both execute first, and applicationWillTerminate is untouched by the flag.

5. R007 states that outcomes "drives the wording the notice row shows after the wait ends (.cancelled / .handedOff(newThreadID) / .resumed), per the doc comment on LimitOutcome", implying the wording is unknown. LimitResumeBadge.swift:52-60 shows `.handedOff` is matched without binding its UUID and all three produce fixed strings; the new thread's id is never used by the row, so R007's implication that the id feeds the wording is wrong.

## Gaps (referenced but never pinned down) (17)

1. ThreadRuntime.swift:2079-2195 - the ProviderEvent switch, the single most protocol-critical control flow in this family, is not described case by case anywhere in R008. Unreported handled events: `.title` (2154-2158) is accepted ONLY when `turns.count <= 1 && !thread.hasCustomTitle && app.textEngine(preferring: thread.provider) == nil`, and the accepted title is run through `TextCleanup.withoutEmDashes`; `.modeChanged` (2146-2147) writes `thread.interactionMode` from the provider; `.commands` (2150-2153) stores the command list keyed by `thread.worktreePath ?? project.path`; `.usage` (2132-2139) bumps `saveRevision` AND calls `providers.invalidateCredits(provider)` + `providers.invalidatePlanLimits(provider)`; `.models` (2148-2149) calls `updateCatalog`; `.diff` (2140-2141) and `.assistantMessageID` (2159-2160) record only while `currentTurnID != nil`; `.requestResolved` (2129-2131) clears the id from BOTH approvals and questions; `.toolStarted` (2098-2101) starts `watchCommand` only for `call.kind == .command`; `.toolUpdated` (2104-2113) both settles the command snapshot when a command tool leaves `.running` and routes a finished tool to `hydraToolFinished` via `hydraToolHeads[id]`.

2. ThreadRuntime.swift:1430-1491 vs 1497-1567 - the API-key and CLI session-start paths differ in three ways a port will get wrong, none reported. (a) `isStartingSession = true` is set only in the CLI branch (1534); an API session that exits during `start()` is therefore NOT protected by the `if isStartingSession { break }` guard in the `.exited` handler (2172). (b) The API branch writes `providerSessionID` directly (1490) instead of going through `recordSessionID` (1567, 1570-1577), so the `unsentSessionID` hold-back does not exist for DeepSeek/Meta/Z.ai. (c) The API retry predicate is inline `thread.providerSessionID != nil && thread.providerResumeAt == nil && allowNewSession && session === candidate && !Task.isCancelled` (1479), not `Self.startsOver(after:resuming:)` (1546); it emits no "no longer has this conversation" notice and never clears `providerResumeAt`, unlike the CLI branch (1546-1553).

3. ThreadRuntime.swift:1453-1458 - the API-key session factory switch has an unreachable `default: DeepSeekSession(configuration: configuration)` arm (the branch is already gated on `thread.provider.isAPIKeyBased`, which Provider.swift restricts to .deepseek/.meta/.zai). R008 classifies no code in this file as unreachable, so a port cannot tell whether this arm is meaningful.

4. ThreadRuntime.swift:1140-1153 - `handleLocalCommand` also calls `app.providers.recordCommand("plan", for:)` / `recordCommand("compact", for:)`, which feeds the `recent` recency ranking that `SlashCommand.suggestions(_:matching:recent:)` (Provider.swift) sorts by. R008 reports the two local commands but not this side effect, and R030 documents the `recent` parameter without naming who populates it.

5. ThreadRuntime.swift:1655-1669 - `interrupt()` has a distinct `.starting` fast path: it clears `currentTurnID` and finishes the turn as `.interrupted` without ever calling `session.interrupt()` and without arming the 8 second watchdog, so the message that was on its way is dropped rather than sent. R008 reports only the watchdog.

6. ThreadRuntime.swift:1685-1695 - `resolve(_:option:)` is not just a passthrough: for a `.plan` approval with a `toolItemID` it mutates the stored `ProposedPlan.state` to `.accepted` when `option.role == .approve` and `.dismissed` otherwise, bumps `saveRevision` and schedules a save, before calling `session.resolveApproval`. Unreported by R008.

7. ThreadRuntime.swift:1158-1167 - `startTurn` silently converts a send into a queued follow-up in three cases: `phase != .idle`, `isReverting`, or `thread.isArchived`. R008 reports the follow-up queue but not these three implicit enqueues.

8. ThreadRuntime.swift:1380-1392 - `warmSession()` clears `warmup` only on success or on the phase re-check; a throwing `ensureSession` leaves `warmup` non-nil forever, permanently disabling warm starts for that runtime for the rest of the process (the comment says this is deliberate: "A start that fails is not retried on every keystroke"). Unreported.

9. AppModel.swift:1070-1077 - `discardThreadState` teardown ordering is unreported by R003: cancel the idle-stop task, `cancelPersistence()` BEFORE `stopSession()`, drop the runtime, `terminals.closeAll(for:)`, then optionally `Storage.deleteDocument`. The cancelPersistence-before-stopSession order is the opposite of `releaseIdleRuntime`'s `saveNow()` then `cancelPersistence()`, so a port that picks one order loses unsaved state in one of the two paths.

10. AutoContinue's user-facing controls are named nowhere in this family. They live in DroppyCode/App/Views/Chat/LimitResumeBadge.swift:23-38: two plain buttons labelled exactly "Cancel" (help "Stop the automatic continue") and "New thread" (help "Stop the automatic continue and pick the work up in a new thread, where you can choose another model"), shown only while `model.autoContinue.resumesAt[threadID] != nil`. The post-wait wording R007 defers to the doc comment is also there, verbatim: "Usage limit reached. Auto-continue cancelled.", "Usage limit reached. Continuing in a new thread.", "Usage limit reached. Continued automatically." (lines 56-58).

11. AutoContinue waits are never cancelled or re-armed at teardown, and R007 left this as an open question. Grepping every `autoContinue.` call site (AppModel.swift:498, 1194; ThreadRuntime.swift:2145; LimitResumeBadge.swift:14, 23, 31, 54) confirms it: `resumesAt` and `outcomes` are in-memory only, so after a relaunch the persisted `.info` notice still reads "Usage limit reached. Continuing automatically at <time>." with no countdown, no buttons (waiting == false) and no resume. That stranded-state behavior is a shipped consequence the port must reproduce or deliberately change.

12. Shell.swift:331-335 - R033 says "Excluded environment keys (13)" but `excludedKeys` holds 15 entries (the list it then prints is correct). Shell.swift:144-151 - R033 says "Reader tool allowlist (51 entries)" but `readers` holds 52 (again the printed list is correct). A port sizing a table from the stated count would be wrong twice.

13. Text.swift:81 (`SimpleDiff.diffLimit = 200_000`) and ThreadRuntime.swift:3366 (`editDiffLimit = 200_000`) are two independent constants with different operands: `diffLimit` bounds `old.utf8.count + new.utf8.count` (the inputs) at Text.swift:101, while `editDiffLimit` bounds `diff.utf8.count` (the produced hunk) at ThreadRuntime.swift:3373 and 3397. R033 asserts "the same cap bounds command diffs in ThreadRuntime.fileEdits", conflating them.

14. AppSettings.swift:709 - `chatZoom` default is recorded by R003 only as "ChatZoom.defaultIndex", leaving the shipped default undocumented. It resolves to UI/Common/ChatZoom.swift:10,13: `percentages = [80, 90, 95, 100, 110, 125, 135]`, `defaultIndex = 3`, i.e. 100%, and `clamped` is `min(stepCount - 1, max(0, index))`.

15. AppUpdater.swift:351-355 - R004 paraphrases the codesign requirement but never quotes it. Verbatim it is `anchor apple generic and certificate 1[field.1.2.840.113635.100.6.2.6] and certificate leaf[field.1.2.840.113635.100.6.1.13] and certificate leaf[subject.OU] = "NARHG44L48" and identifier "<bundleID>"`; the `leaf[subject.OU]` clause is the one that actually pins the team and is absent from the report.

16. AppUpdater.swift - `Haptics.perform(.generic/.levelChange/.alignment)` is filed by R004 only under unresolved_questions, not under platform_assumptions. It is macOS `NSHapticFeedbackManager` (trackpad-only) and has no Windows equivalent, so it belongs on the macOS-dependency list beside hdiutil/ditto/spctl/SecStaticCode.

17. AppDelegate.swift:9-15 - R003 describes the `WebsiteCaptures.isEnabled` early return as short-circuiting "the entire normal launch", but the two statements before it still run in a capture run: `UNUserNotificationCenter.current().delegate = self` and `model = windows.model`. `applicationWillTerminate` (50-55) is also not short-circuited, so `saveBeforeQuit`, `flushLiveSpend` and `MCPHub.terminateAll()` still fire in a capture run.

## Thin reports (1)

1. R008 - 32 KB of findings for a single 3637-line file (ThreadRuntime.swift), roughly a third of the finding density of R030 (58 KB / 1680 lines) or R033 (52 KB / 1588 lines) for far simpler code. The thinness is concentrated exactly where a port is most exposed: the 117-line ProviderEvent switch (2079-2195) gets no per-case treatment at all, the two session-start branches (1430-1567) are summarized as one, and single-purpose methods that mutate persisted state (resolve's plan-state write at 1685-1695, handleLocalCommand's recordCommand at 1143/1147, interrupt's .starting path at 1664-1668, startTurn's three implicit enqueues at 1159-1167) are listed in key_symbols with no behavior recorded. The Hydra material is proportionally well covered, which suggests the reader ran out of budget on the non-Hydra half rather than skipping the file.

## Cross-cutting findings (10)

1. Cmd+1 through Cmd+9 are hardcoded in two places that must stay in sync: AppCommands.swift:85-88 builds nine "Thread N" buttons with `.keyboardShortcut(KeyEquivalent(Character(String(number))), modifiers: .command)` outside the ShortcutStore system, and Shortcuts.swift:255 reserves exactly those key codes (18, 19, 20, 21, 23, 22, 26, 28, 25 = digits 1-9 with .command) so no user-assignable command can take them, refused with "macOS or Droppy Code already uses this chord." R003 and R030 each describe one half; neither connects them.

2. Two different RuntimeMode defaults ship, and the difference is deliberate security behavior. A new thread starts on `AppSettings.defaultRuntimeMode`, which defaults to `.fullAccess` (AppSettings.swift:698), while a thread decoded from library.json whose `runtimeMode` key is missing OR type-mismatched falls back to `.supervised` (Library.swift ChatThread decoder, with the comment that a thread must never quietly come back from disk with full access). R003 and R030 each report one default; a port that uses one constant for both breaks the stated invariant.

3. R003's unresolved questions about ChatThread are answered inside this family by R030 and the source: `ChatThread.hydraDefaultKey = "hydraDefaultEnabled"` (Library.swift:195) - so AppSettings' `hydraDefaultEnabled` persists under that literal - and `ChatThread.untitled = "New thread"` (Library.swift:122), which is also the fallback title R008 leaves open and the string `openThreadOnLaunch` matches on.

4. R047's unresolved on-disk paths are answered by R033: `AppInfo.name` is CFBundleDisplayName with fallback "Droppy Code" and `AppInfo.stateDirectoryName` is ".droppy-code-dev" in a development build (bundle id iordv.droppycode.dev) else ".droppy-code". So the shipped layout is ~/Library/Application Support/Droppy Code/{library.json, threads/, attachments/, wallpaper/} plus <home>/.droppy-code/{worktrees, patches} (Storage.swift:17-48).

5. Three different notions of "home" and "defaults" coexist and a port that unifies them changes behavior: Storage.stateDirectory uses `LoginEnvironment.homeDirectory` (Storage.swift:43) while TokenLedger's Codex scan uses `FileManager.default.homeDirectoryForCurrentUser` (flagged by R047); AppSettings, ChatThread.hydraDefaultEnabled and TokenLedger all route defaults through `CaptureRun.defaults ?? .standard` (WebsiteCaptures.defaults at WebsiteCaptures.swift:28 is a read-through to CaptureRun.defaults, so they are the same suite), but ShortcutStore writes key "keyboardShortcuts" to `UserDefaults.standard` directly (Shortcuts.swift:249, 262, 268) and is therefore not redirected during a capture run.

6. The notification userInfo contract spans three bundles and must be ported as one unit: thread notifications carry `["threadID": uuid.uuidString]` with request identifier == the same uuidString, one pending notification per thread (AppModel.notify); update notifications carry `["update": version]` with identifier "update-<version>" and no threadID (UpdateChecker); AppDelegate branches on `userInfo["update"] != nil` for routing and on `userInfo["threadID"]` for the silent-banner suppression.

7. Notification suppression is a double gate, described once in each report but never as a pair: AutoContinue.notify suppresses on `NSApp.isActive && app.selectedThreadID == threadID` (AutoContinue.swift:152), then AppModel.notify applies a broader gate `NSApp.isActive && isOnScreen(thread)` which also counts panel helpers and inline sidebar helpers, plus a hard `WebsiteCaptures.isEnabled` bail. AppDelegate then applies a third gate in `willPresent`, returning `[]` instead of `[.banner, .sound]`. All three must ship.

8. `RecentCache` is generational, not LRU (RecentCache.swift, per R033): at `current.count >= limit` or `currentCost > costLimit - cost` the whole current map becomes `previous` and current is emptied, so effective findable capacity is up to 2x limit and a read that hits `previous` promotes and is therefore mutating. Every cache in this family is one of these - ThreadRuntime.turnDiffs(limit 64) and revisionDiffs(limit 4), DocumentPrefetch.ready(limit 12, costLimit 16 MB), ThumbnailCache.thumbnails(120, 32 MB), ThumbnailMemory.images(120, 16 MB) - and R008 and R047 both describe them by "limit" alone.

9. Em-dash flattening happens on at least three passes and a port that implements it once will double-clean or miss: Storage.readDocument maps every loaded item through `cleanedOfEmDashes` (Storage.swift:79), ThreadRuntime's `install(_:)` normalizes again at load, and ThreadRuntime flattens streamed message/reasoning/plan deltas and provider-supplied titles live. TimelineItem.cleanedOfEmDashes rewrites only assistant text, reasoning text and plan markdown (R030); tool output, user text and notices are left alone. The exact replacement set is U+2014, U+2015, U+2E3A, U+2E3B -> ASCII hyphen, with U+2013 en dash deliberately kept (Text.swift, per R033).

10. Persisted state written outside the Application Support folder that a Windows port has to relocate explicitly: UserDefaults keys "keyboardShortcuts" (raw NSEvent.ModifierFlags bit values plus macOS virtual key codes - R030 flags this as a persisted AppKit constant), "appUpdater_pendingRelaunchVersion", "updateChecker_release"/"updateChecker_lastChecked"/"updateChecker_notifiedVersion", "migratedFromEarlierName", "droppycode.tokenActivity.liveDaily", "droppycode.tokenActivity.codexFiles", plus every AppSettings key; and JSON state files beside library.json (token-activity-live-v2.json, token-activity-codex-v3.json) with v1/v2 predecessors that are deleted or migrated on load.
