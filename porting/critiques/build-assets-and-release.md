# Critique: build-assets-and-release

**Verdict:** NEEDS_REREAD — the raw facts are unusually reliable (all 239 reported sha256 digests re-verified byte-for-byte, every lines_total correct, every ranges_read covering line 1 to the last line, and the Resources tree fully covered with no file missing and none invented), but R006 never classifies the shipped/debug status of the capture subsystem it read, and a handful of cross-file reconciliations were left as open questions that the source settles outright, two of which are live defects a port would faithfully copy.

## Contradictions (a report disagrees with the source) (6)

1. Test tooling: AGENTS.md:25 states "There is no test target and no test scripts; the build is the check" (quoted approvingly by R001 as "the upstream has no unit tests for the port to mirror"). docs/performance-2026-09-15.md:5-6 states "`scripts/run_tests.sh` builds the dev app and runs all seven suites (117 tests)" and cites scripts/benchmark_performance.sh, scripts/benchmark_file_matcher.sh and Tests/RuntimePerformanceTests.swift (relayed as fact by R054). None of those paths exist at commit dd2b86e: scripts/ holds exactly 13 files and there is no Tests/ directory. Neither R001 nor R054 noticed the conflict or checked the paths. The pinned tree matches AGENTS.md.

2. Shipped version: R002 records MARKETING_VERSION "1.6.0" (project.yml and both pbxproj project configs, lines 208 and 271) and R058 records changelog.json's newest release as 1.6.0; R059 records the site's download card as "Version 1.5.3 · Signed and notarized" (index.html:543). Neither side flags the other. 1.6.0 is correct; the HTML is stale.

3. Welcome tour length: R001 relays README.md "six pages of real captures" and CHANGELOG 1.3.0 "eight pages", filing it as unresolved; R058 relays changelog.json 1.3.0 "an eight-page welcome tour"; R059 relays index.html "Eight pages of real screenshots". 4. 5. R2 tour prefix: R056 reports tour_captures.py's docstring saying the website set goes to "tour/v4" against website_captures.py's R2_TOUR_PREFIX "site-assets/droppy-code/tour/v5" (line 48), and R058 separately reports code.js's header comment saying theme stills live under "site-assets/droppy-code/themes" against its own THEME_BASE of ".../tour/v5/themes/". Both readers filed these as unresolved; index.html resolves both, referencing tour/v5 in all 24 worker URLs. The two comments are stale, the code is right.

6. og-home accent span: R056 (scripts/og-home.html) says the accent covers "coding agents" with the comma outside; R063 (the rendered og-home.png) describes "'coding agents,' in light blue", comma included. og-home.html:96 is `All your <span class="charged">coding agents</span>,<br>...` — R056 is right, R063's visual read is off by one character.

## Gaps (referenced but never pinned down) (12)

1. R006 reads all three Captures files and never classifies them. The contract asks for shipped-vs-debug with compile-condition evidence; R006's `platform_assumptions` and `feature_notes` describe the capture run as if it were tooling, and its only note on reachability is the unresolved "how --tour-captures is parsed ... is outside this bundle". The evidence is one file away: DroppyCode/Core/Support/CaptureRun.swift:8-41 has no compile condition, and docs/audit-2026-09-15.md (read by R054) records finding S3 verbatim, "WebsiteCaptures is 900 lines of ScreenCaptureKit and AVFoundation shipped in every build for a '--website-captures' flag; compile it under a build flag", with the second pass listing "S1 to S3 not done". Neither report connects the two.

2. BROKEN AT THE PINNED COMMIT, nobody says so: scripts/tour_captures.py:36 sets `APP = DERIVED / "Build/Products/Debug/Droppy Code.app"`, but tour_captures.py:101 builds `-configuration Debug`, and project.yml's Debug config overrides `PRODUCT_NAME: "Droppy Code Dev"`. The Debug product is `Droppy Code Dev.app`, so `subprocess.run(["open", "-n", str(APP), ...], check=True)` at tour_captures.py:117 raises on a clean checkout. scripts/website_captures.py:34 has the correct path. R056 noticed the divergence but filed it as an unresolved question ("the two pipelines build different bundle names from the same scheme") instead of resolving it against project.yml, which it also read.

3. CAPTURE BUDGET MISMATCH, unflagged: TourCaptures.swift's watchdog is 600 seconds (reported by R006). scripts/tour_captures.py:118 waits 630 s, correctly above it. But scripts/website_captures.py:164 calls `wait_for_run(marker, 330)` for the same `--tour-captures` run and then `pkill -9`. R056 reported the 330 and the 630 as separate literals and R006 reported the 600, and no report notices that the `--website` path kills the tour run 270 s before the app's own deadline. (The `--website-captures` pairing is fine: website_captures.py:123 waits 120 s against an in-app 110 s watchdog.)

4. website/index.html:543 hardcodes `<small>Version 1.5.3 &middot; Signed and notarized</small>` on the download card, while project.yml carries MARKETING_VERSION 1.6.0 and website/changelog.json's newest release is 1.6.0 (generated_at 2026-09-18T17:57:43.854565+00:00). `grep -rn "index.html" scripts/` returns nothing, so no release script rewrites it. R059 recorded the literal "1.5.3" as fact and R002 recorded "1.6.0"; neither flags that the site version is hand-maintained and currently one minor release stale.

5. `data-download-link` is a dead attribute. It appears 5 times (index.html:126, :551, :700, :729 and changelog.html:125) and `grep -rn "data-download-link\|downloadLink" website/` finds no reader in site.js, code.js, changelog.js or wordscroll.js. R058 (site.js) omits it from its hook list, R058 (changelog.html) and R059 both file it as "which script rewrites the download href is unknown". The answer is: none; the href is static `/download/latest` and Netlify's 302 does the work. A port that implements a rewriter is inventing behavior.

6. ORPHANED CDN ASSET: website/index.html:369 loads `https://droppy-releases.jordylegrand.workers.dev/site-assets/droppy-code/usage/v1/limits.webp` (812x1146, the plan-limits popover shot). No script produces or uploads a `usage/v1/` key: website_captures.py declares only R2_PREFIX `site-assets/droppy-code` (line 39) and R2_TOUR_PREFIX `site-assets/droppy-code/tour/v5` (line 48), and its TOUR_STILLS table has no usage entry. R059 listed the URL among the page's fetches without noting it has no generator in the repository; R056 enumerated the R2 prefixes without noticing the page asks for a third one.

7. R056 misreads the role of tour_captures.py's WINDOW_SIZES. scripts/tour_captures.py:173-181 shows it is only the FALLBACK: `interior()` reads `<name>.json` (keys rect/window/focus) when the sidecar exists and uses `scale = image.width / rect_w`; `window_box(name)` with `scale = 2` runs only when the sidecar is missing, and its own docstring says the table is "exact only for window-only stills". R056's unresolved question "web-slash, web-quote and web-notify appear in TOUR_STILLS but have no entry in WINDOW_SIZES" is moot: `encode()` (tour_captures.py:257-262) passes only the seven tour-* names through `frame()`, and every web-* still is cut by website_captures.py from its sidecar. The port needs to know the sidecar is authoritative; the report implies the table is.

8. R056 lists only 3 of package_dmg.sh's 12 error strings. Missing, verbatim with `package_dmg: ` prefix to stderr: "App bundle not found at $APP_PATH" (:37), "Missing installer background asset at $BACKGROUND_ASSET" (:43), "Missing installer .DS_Store asset at $DSSTORE_ASSET" (:44), "Missing app icon at $VOLUME_ICON_SOURCE (needed for the DMG volume icon)" (:47), "Failed to decode $DSSTORE_ASSET" (:66), "Failed to create read-write image" (:79), "Failed to mount read-write image" (:83), "Failed to write the installer .DS_Store" (:88), "Failed to set the volume custom-icon flag" (:94), "Failed to detach read-write image" (:105), "Failed to convert image to ULMO" (:114), "hdiutil convert did not produce $OUTPUT_PATH" (:115). The AppIcon.icns precondition at :46-47 is load-bearing (the volume icon is copied out of the built bundle, so the .icon compilation R034 describes must have run first) and is not in R055's or R056's account of the dependency order.

9. R056's unresolved question about sync_dev_data.sh's four mirrored accounts is answerable and the answer is a real defect: MCPKeychain.swift:7-8 stores MCP server secrets in the SAME Keychain service (`AppInfo.name`) under accounts `"MCP <server> <field>"`. sync_dev_data.sh:36 does `rsync -a --delete` of the whole Application Support library (which carries mcp.json) and :42 does `defaults delete` then import, but :49 re-adds only "DeepSeek API Key", "Meta API Key", "Z.ai API Key", "Command Code API Key". So a mirror copies the release app's MCP server configuration into Dev with none of its secrets, contradicting quick_run.sh's own header claim (lines 10-11) that MCP sign-ins are what makes a mirror destructive.

10. R059's footer inventory gives the wrong hosts. It lists "Droppy for iPhone (/ios), Droplets (/droplets.html), Blog (/blog/), Docs (/docs.html)" and "The Trench (/trench.html)" as if site-relative. index.html:755-759 and :774 (and changelog.html:151-155, :170) are absolute: https://getdroppy.app/droplets.html, /blog/, /docs.html, /privacy-policy.html, /terms-of-service.html, /trench.html. A port copying that footer as written would ship five 404s on getdroppycode.app.

11. Nobody records that scripts/build_changelog.py silently drops the `## [Unreleased]` section. RELEASE_RE at line 20 is `^## \[(\d+(?:\.\d+)*)\](?: - (\d{4}-\d{2}-\d{2}))?\s*$`, and split_releases (lines 58-70) only starts collecting after the first match, so every Unreleased bullet is discarded, never surfaced as an error. R001 asserts both publish_release.sh and build_changelog.py "skip" it without naming the mechanism, and R056 does not mention Unreleased at all. Related edge case also unrecorded: parse_notes sets `current = None` for any unrecognised `### ` heading, after which its bullets are appended verbatim (leading `- ` included) into the release `summary`.

12. R002 lists the pbxproj's build settings but never states that no .entitlements file exists in the repository and that release.sh's `codesign --sign "$IDENTITY" --timestamp "$DMG"` (line 106) and its ExportOptions.plist (lines 60-75: method/teamID/signingStyle/signingCertificate only) pass no entitlements at all. For a Windows port this is the fact that the macOS app runs fully unsandboxed with the default hardened-runtime entitlement set, which is what lets it spawn arbitrary agent CLIs and read the user's home directory; only docs/audit-2026-09-15.md mentions it, in passing, under finding P4.

## Cross-cutting findings (7)

1. SHIPPED-IN-RELEASE, unstated by anyone: DroppyCode/Core/Support/CaptureRun.swift has no `#if DEBUG` or any other compile condition, and `grep -rn '#if' DroppyCode/App/Captures` returns nothing. AppDelegate.swift:12-13 (`if WebsiteCaptures.isEnabled { Task { await WebsiteCaptures.run(model: windows.model) } }`) and DroppyCodeApp.swift:14 (`WebsiteCaptures.prepare()`) call it unconditionally. So `--website-captures <dir>` and `--tour-captures <dir>` (CaptureRun.swift:12) are live flags in the signed, notarized Release app, and the whole ScreenCaptureKit/AVFoundation stack in WebsiteCaptures.swift (1122 lines) is linked into every shipped binary.

2. Capture-run isolation contract, for the port: when either flag is present, Storage.swift:20 redirects the store to `<outdir>/storage`, TokenLedger.swift:87 and ProviderRegistry.swift:161 read `CaptureRun.defaults` (suite `iordv.droppycode.website-captures`, wiped at every run), APIKeychain.swift:14 returns `""` for every provider key and MCPKeychain.swift:12 returns nil, ProviderRegistry.swift:538/:669/:703 short-circuit, and UpdateChecker.swift:133 refuses to start background checks. Nothing in this family states that this gating exists in the shipped app.

3. R002's open question about the three bundled resources is resolvable: DroppyCode/App/Views/Settings/SettingsView.swift:997-999 declares the tuples ("Droppy Code", "LICENSE"), ("Third-party notices", "THIRD_PARTY_NOTICES"), ("Trademarks", "TRADEMARK") and line 1033 loads them with `Bundle.main.url(forResource: file.resource, withExtension: file.resource == "LICENSE" ? nil : "md")`. Those three labels, and the extension-less LICENSE special case, are the exact spec for the Windows About > Licenses page that LICENSE term 7(a) requires.

4. The whole release-artifact naming chain is one literal, reused in five places, and no report draws it end to end: project.yml `MARKETING_VERSION: "1.6.0"` -> release.sh:19-20 `Droppy-Code-$VERSION.dmg` -> publish_release.sh tag `v$VERSION` and GitLab asset `direct_asset_path=/Droppy-Code.dmg` -> netlify.toml:11-15 `/download/latest` 302 to `.../releases/permalink/latest/downloads/Droppy-Code.dmg` -> and, separately, UpdateChecker.swift:69 `https://gitlab.com/api/v4/projects/86415974/releases?per_page=20`, which picks the newest stable release that ships a disk image. Break the `/Droppy-Code.dmg` asset path and both the website button and the in-app updater break.

5. Keychain layout: APIKeychain.swift stores every native provider key under one service, `AppInfo.name` ("Droppy Code" / "Droppy Code Dev"), with `kSecAttrAccessibleWhenUnlocked`, and only four accounts exist (CommandCodeKeychain/DeepSeekKeychain/MetaKeychain/ZaiKeychain). MCPKeychain.swift:7-8 uses the SAME service with accounts formatted `"MCP " + server + " " + field`. scripts/sync_dev_data.sh:49 mirrors only the four API-key accounts.

6. Tour page count, which R001 left unresolved: DroppyCode/App/Views/Tour/TourPages.swift:4-13 declares exactly 8 TourPage entries (tour-welcome, tour-hydra, tour-pairs, tour-slider, tour-threads, tour-recipes, tour-panels, tour-themes), matching the 8 tour-* imagesets in R035 and index.html's "Eight pages of real screenshots". README.md's "six pages" is stale.

7. No entitlements file exists anywhere in the repository (`find . -name '*.entitlements'` is empty) and no checked-in Info.plist (GENERATE_INFOPLIST_FILE = YES with only three INFOPLIST_KEY_* values). release.sh signs the DMG at line 106 with `codesign --sign "$IDENTITY" --timestamp "$DMG"` and never passes `--entitlements`; the exported app is signed by xcodebuild from an ExportOptions.plist with only method/teamID/signingStyle/signingCertificate. The app therefore ships hardened-runtime with the empty default entitlement set and no App Sandbox, which docs/audit-2026-09-15.md records as deliberate ("no sandbox because the CLIs need it off").
