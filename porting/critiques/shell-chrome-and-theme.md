# Critique: shell-chrome-and-theme

**Verdict:** NEEDS_REREAD - the reports are broadly accurate and unusually detailed, but R024 states a clamp backwards, R025 gets the RowDrag API and the placement fingerprint wrong and misses a glyph difference, and R048's Chrome.swift entry omits token values the whole family depends on.

## Contradictions (a report disagrees with the source) (5)

1. R048 documents RowDrag.settle as `settle(order:heights:fallbackHeight:pastCentre:move:) -> Bool` whose `move` closure returns Bool and gates the crossing loop (E:/Droppy/reference/droppy-code/DroppyCode/UI/Chrome/RowDrag.swift:29-35, 45, 52). R025 records the same API as `settle(order:heights:fallbackHeight:swap:)` - wrong argument label, no `pastCentre`, and no mention that the closure's Bool return stops the walk. At the sidebar call site (DroppyCode/App/Views/Sidebar/SidebarView.swift:783-793) the trailing closure's value is `withAnimation(Self.slide) { model.moveThread(...) }`, and AppModel.swift:338 / :358 declare `moveThread(_:to:placeAfter:) -> Bool` and `moveInActivity(_:to:placeAfter:among:) -> Bool`. A port that makes the move closure return Void reorders forever past a refused move.

2. R024 says the FloatingSidebarPanel resize is clamped 'with the minimum size as the lower bound'. FloatingSidebarPanel.swift:75-76 applies `min(max(minSize, next), area - origin - margin)`: the outer `min` runs last, so in a chat area narrower than minSize + 2*margin the written size is BELOW minSize (240x320) and is persisted to settings.sidebarPanelSize on that same drag tick (line 77). This contradicts R024's own, correct description of the read-side clamp at lines 29-32, which does use `max(minSize, ...)` on both arms.

3. R049 names the preferences store for "sidebarWidth"/"sidebarStartsOpen" as `CaptureRun.defaults ?? .standard`; R053 names the store for "wallpaperSoftness"/"wallpaperFile" as `WebsiteCaptures.defaults ?? .standard`. Neither says they are the same store: DroppyCode/App/Captures/WebsiteCaptures.swift:28 is `nonisolated static var defaults: UserDefaults? { CaptureRun.defaults }`. Read together the two reports imply two separate suites.

4. R050 describes the running breath ring as what a Hydra head at work wears (HydraGlyph.swift:21-24, `isRunning`). R025 describes the sidebar helper row as showing 'its HydraGlyph at 14 pt before the title' with no qualification. SidebarView.swift:1358 constructs `HydraGlyph(persona:size:status:)` with no `isRunning`, while SidebarView.swift:1478 in HeadCardsRow passes `isRunning: info.status == .running`. The same running head therefore breathes on its card and does not breathe on its helper row; no report records the difference.

5. R053's purpose line calls AppTheme a '25-case theme enum' while its own key_symbols list and AppTheme.swift:15-40 both hold 26 cases (system through matrix). The palette table in the same report also lists 26 rows.

## Gaps (referenced but never pinned down) (22)

1. FloatingSidebarPanel.swift:75-77 - the resize path can write and persist a `sidebarPanelSize` smaller than `minSize` (240x320) when `area.width - origin.x - 12 < 240`; no report describes that escape, and R024 asserts the opposite. Also unstated: the resize clamp is anchored on `origin` (the live `dragOrigin ?? rest`), so resizing while the panel is mid-drag clamps against the dragged origin, not the resting one.

2. SidebarView.swift:1358 - SidebarHelperRow's head glyph omits `isRunning`, so a running Hydra head shows no breath ring in the helper row. Unrecorded by R025 and R050.

3. SidebarView.swift:1872 - every thread row carries `.accessibilityValue(Text(isSettled ? "Settled" : ""))`. R025 enumerates the accessibility labels/values for SettledHeader, ActivityViewToggle, SettleCheck, the fold button and the helper stub, but not this one.

4. SidebarView.swift:2484-2520 - R025 calls the PlacementCache fingerprint an '18-field Fingerprint'. It has 17 fields (id, projectID, parentThreadID, isArchived, isInPanel, isSettled, settledAt, isPinned, sortOrder, activityOrder, activityOrderDay, createdAt, updatedAt, foldsHelpers, isHydraHead, hydraIndex, hasUnread), identical to ThreadPlacement's. A port sizing the invalidation key off the report gets it wrong.

5. Chrome.swift:178,180 - the exact glass tint on every capsule and circle in the app, `.regular.tint(Chrome.glassTint.opacity(0.3))`, is absent from R048; the report records only '.glassEffect(.regular.tint(...).interactive(), in:)'. The 0.3 is the one number that decides how much theme colour every chrome control carries.

6. Chrome.swift:618-646 - R048 lists `SidebarSymbol` and `SidebarIconBadge` in key_symbols but records no metrics for either, though every sidebar row, project row, badge and bottom row draws through them: SidebarSymbol is `.resizable().interpolation(.high).aspectRatio(contentMode: .fit).frame(width: Chrome.symbolSize * scale, height: ...).symbolRenderingMode(.monochrome)` with symbolSize 14; SidebarIconBadge is `.foregroundStyle(Chrome.primaryText.opacity(0.85)).frame(width: 20, height: 20)`. The 0.85 is why sidebar glyphs sit below title contrast.

7. Chrome.swift:1061-1069 - WindowDragView overrides `acceptsFirstMouse(for:) -> true` and swallows mouse-up with an empty `mouseUp` override. R048's side_effects mention only `performDrag(with:)`. The empty mouseUp is what stops a drag-release from reaching SwiftUI behind the sidebar.

8. Chrome.swift:10 sets `sheetInset = 0`, which makes every branch of RootView.swift:40-42 evaluate to zero padding: `.padding(.leading, sidebar.isVisible && !onlyFloats ? 0 : Chrome.sheetInset)`, `.padding(.trailing, 0)`, `.padding(.vertical, 0)`. R020 describes this conditional as live layout behavior without classifying it as currently inert; a port would faithfully implement a branch that does nothing today.

9. R049 leaves `titlebarHeight`, `collapsedTrafficLightTop` and `trafficLightsFitWidth` symbolic because Chrome is in another bundle, and R048 leaves the trafficLight* tokens as 'consumed elsewhere'. Nobody in the family closes the loop, yet these are the exact numbers a Windows custom caption bar needs: titlebarHeight = 0 + 12 + 32 = 44, collapsedTrafficLightTop = 0 + 12 + (32-14)/2 = 21, trafficLightsFitWidth = 18 + 60 + 10 = 88, trafficLightPitch = 23.

10. DroppyCode/Core/Support/CaptureRun.swift:10-40 - R049 and R053 both leave the defaults suite unresolved. `CaptureRun.defaults` is nil on a normal launch (everything lands in UserDefaults.standard) and only becomes `UserDefaults(suiteName: "iordv.droppycode.website-captures")` when the process is launched with the exact flags `--website-captures <folder>` or `--tour-captures <folder>`. Exact command-line flags were in scope for this read and no report in the family captured them, nor the fact that a capture run also redirects storage to `<folder>/storage` and never touches the Keychain.

11. settings.settledCollapsed has an undocumented default and an undocumented key. AppSettings.swift:712 reads `defaults.object(forKey: Key.settledCollapsed) as? Bool ?? true` and AppSettings.swift:133 defines that key as the string "settledSectionCollapsed", not "settledCollapsed". R025 lists the property and says it 'survives relaunch' but gives neither. The default decides that on a fresh install the whole settled list is never built (SidebarView.swift:531 `if collapsed { break }`).

12. settings.sidebarPanelOrigin / sidebarPanelSize persist as `[Double]` arrays, not as points/sizes: AppSettings.swift:652-672 writes `[origin.x, origin.y]` and `[size.width, size.height]` and calls `removeObject` on nil; AppSettings.swift:764-772 reads them back element-wise. R024 records only 'CGPoint?/CGSize?, nil default', so the on-disk shape and what happens to a malformed or short array are unstated.

13. AppModel.swift:377-379 - `settledFirst` is `(lhs.settledAt ?? lhs.updatedAt) > (rhs.settledAt ?? rhs.updatedAt)`. R025 leaves it as 'latest settled first' in unresolved_questions and never records the updatedAt fallback, which is exactly the migration behaviour for threads settled before settledAt was persisted.

14. R019 leaves three answerable questions open that decide user-visible strings: ShortcutStore.label(for:) is optional (RootView.swift:466 uses `if let chord = ShortcutStore.label(for: .newThread)`), and AppModel.swift:846-854 gives the palette's finish row its literal title and symbol - "Reopen thread" with "arrow.uturn.backward" when the finish action is .settle and the selected thread is settled, otherwise "<Settle|Archive> thread" with "checkmark.circle" or "archivebox". Left open, the command palette's finish row has no specified label.

15. KeyChord.allowedModifiers is left unresolved by both R025 and R029, yet it gates two shipped key paths: the archive popover's local monitor (SidebarView.swift:950) and ThreadWindow's Cmd-digit monitor (ThreadWindow.swift:13) and Escape close (ThreadWindow.swift:50). DroppyCode/Core/Models/Shortcuts.swift:6 defines it as `[.control, .option, .shift, .command]` - i.e. Fn, CapsLock and the numeric-pad flag are deliberately ignored.

16. AppTheme.swift:221-226 - `ThemeManager.current`'s didSet rebuilds spec and posts `ThemeManager.didChange` unconditionally, including when the same theme value is reassigned. R053 says it posts 'on every assignment' but does not flag that a no-op write re-tints every layer-backed spinner cell (WorkingIndicators.swift) and every HydraButton observer.

17. Popovers.swift:110 - `PopoverMenu` applies `.presentedChrome()` itself, so every ellipsis menu, chrome menu and picker popover carries capsule button shape and the theme tint. R048 documents presentedChrome() as a standalone modifier and as applied by setFixedContent, but not that PopoverMenu carries it.

18. Popovers.swift:262-273 vs :369-375 - the same RowAction runs with different timing in its two presentations. PopoverItem closes the popover first and defers `action()` into a following `Task { @MainActor in ... }` (so a sheet-presenting action survives), while RowActionMenuButtons calls `item.action()` synchronously inside the menu callback. Neither R048 nor R025 records the asymmetry, although the sidebar depends on it: the context-menu Settle posts `model.finishRequest` (SidebarView.swift:2288) while the popover Settle calls the row's own `settle()` (SidebarView.swift:2225).

19. SidebarView.swift:1462 and :846-849 - HeadCardsRow computes `cardRows = rows.count + (capped ? 1 : 0)`, so a head card with more than 12 heads is one glyph row taller for the chevron. The drag slot fallback in slotHeights uses `headCardHeight(rows: (headCount + 5) / 6)` and never adds that chevron row, so before the card has reported a measured height the reorder slot under-measures a capped card. R025 records the 12 cap and the headCardHeight formula but not the extra row.

20. SidebarView.swift:2465-2467 - `RowFrames.thread(at:)` is `frames.first { $0.value.contains(point) }?.key` over a Dictionary, so when two row frames overlap (mid-animation, or during a settle handover) the grabbed row is chosen in unspecified hash order. No report notes the non-determinism; a port using an ordered list would silently behave differently.

21. WindowManager.swift:76-78 - `makeCaptureWindow` uses the default `windowClass: DCDisplayCycleGuardedWindow.self`, not ThreadWindow, so the capture window has no Cmd-1..9 digit monitor and no Tab next/previous-thread chords. R029 describes it as 'the same window, at a fixed size', which reads as identical behaviour.

22. This family contains no protocol/IPC surface, so there is no 'protocol event handled but not reported' finding to make; the reports are correct to carry none.

## Thin reports (2)

1. R048 - the Chrome.swift entry is the thinnest relative to its weight: 1107 lines and the token source for every other file in the family, yet it omits the glass tint opacity (0.3, lines 178/180), all metrics for SidebarSymbol and SidebarIconBadge (lines 618-646) even though both are in its own key_symbols list, and the WindowDragView event overrides (acceptsFirstMouse, empty mouseUp, lines 1062-1068). Its unresolved_questions also park the trafficLight*, groupGap, listInset and sheetInset values as 'consumed elsewhere' when those exact numbers are what R049's own unresolved questions needed. The other eight files in R048 are well covered.

2. R024 - the FloatingSidebarPanel entry is 127 lines of source whose entire behaviour is arithmetic on constants, and the one piece of arithmetic that differs between the read path and the write path (the resize clamp, lines 75-76) is described backwards. Every Chrome constant it depends on is parked in unresolved_questions rather than cross-checked, so the panel's default resting origin (y = Chrome.contentTopInset = 72) is never stated as a number.

## Cross-cutting findings (8)

1. The whole chrome geometry resolves to literals once R048's tokens are applied to R049 and R024: sheetInset 0, chromeTopPadding 12, capsuleContentHeight 28, capsuleVerticalPadding 2 -> capsuleHeight 32; titlebarHeight 44; collapsedTrafficLightTop 21; contentTopInset 72 (= FloatingSidebarPanel's default resting y); veilHeight 72; trafficLightPitch 23; trafficLightsWidth 60; trafficLightsFitWidth 88. The Windows port's custom caption bar and floating panel need these, and no single report carries them.

2. Every UserDefaults key in this family (sidebarWidth, sidebarStartsOpen, wallpaperSoftness, wallpaperFile, and the AppSettings keys the sidebar reads) goes through `CaptureRun.defaults ?? .standard`, which is UserDefaults.standard on a normal launch. The alternate suite "iordv.droppycode.website-captures" is only selected by the launch flags `--website-captures <folder>` / `--tour-captures <folder>` (CaptureRun.swift:10-40), which also redirect storage to `<folder>/storage`. A port needs one settings-store indirection with the same two entry points, not per-feature stores.

3. Four independent window-level overlays draw in the same named coordinate space "droppy-code-window", established once at RootView.swift:68: GenieLayer (archive flights and Hydra panel morphs), RowGlideLayer (settle/reopen ghosts), CommandPalette and FloatingSidebarPanel. RootView measures the sidebar list frame in that space (SidebarView.swift:307 `windowFrame`) and SidebarThreadRow measures its own row in it (SidebarView.swift:1901). The port needs one window-level overlay host with a single shared coordinate origin, or none of the settle, reopen or archive animations can be aimed.

4. Reduce Motion is a global kill switch across this family, not a per-animation nicety: Chrome.panelSlide and Chrome.settleFlight swap to easeOut 0.18 / 0.20 (Chrome.swift:97-112), SidebarLayout.slideRun drops 420ms -> 220ms (WindowChrome.swift:270), traffic-light placement drops 0.32 -> 0.18 (WindowChrome.swift:221), RowGlideAnimator.launch refuses to fly at all (RowGlide.swift:76), GenieAnimator.launch and morph return false so the caller shows the real thing (Genie.swift:62, 81), HydraBreathRing installs no animation, the spinners freeze at their per-cell phase, and SettleGlideModifier fades in place. On Windows this is SPI_GETCLIENTAREAANIMATION, and it must be read in all nine places or the port's motion is inconsistent.

5. Two animations depend on rasterizing a live SwiftUI tree to a bitmap: RowGlideAnimator.render (RowGlide.swift:131-137) and GenieAnimator.launch (Genie.swift:84-87), both via ImageRenderer at `NSScreen.main?.backingScaleFactor ?? 2`. The ghost faces are re-rendered from ThreadRowFace with a deliberately different trailingClearance from the live row (SidebarView.swift:1944-1946), and MiniSpinner ships a separate `isStill: true` shapes-only variant (WorkingIndicators.swift:84-88) purely because ImageRenderer cannot capture AppKit views. Any port needs a view-to-bitmap capture with the same two-face + still-spinner discipline, or the settle/reopen/archive animations cannot be reproduced.

6. DCDisplayCycleGuardedWindow and DCNotificationGuard are pure macOS 26/27 AppKit exception nets (private `_postWindowNeeds*` overrides; NSNotificationCenter post swizzling) with no Windows analogue. They are load-bearing on macOS but must not be re-implemented; the port should record that every NSWindow subclass in the app derives from the guarded base only for that reason, and that ThreadWindow/SecondaryWindow behaviour is the part worth porting.

7. No theme in AppTheme defines a text colour. Chrome.primaryText and Chrome.secondaryText are the dynamic system colours `NSColor.labelColor` / `.secondaryLabelColor` (Chrome.swift:76-77), and Chrome.overlay(_:) is primaryText at an opacity - so every row fill, card fill, divider and panel scrim in the family is derived from the system label colour, not from the theme. The .system theme's surface is itself a dynamic NSColor resolving sRGB 1E1E20 in dark and FFFFFF in light (AppTheme.swift:180-187). A Windows port must choose its own primaryText/secondaryText equivalents before any of the 26 palettes mean anything.

8. Sidebar launch state and session state are deliberately separate: `sidebarStartsOpen` ("sidebarStartsOpen", default false) is the only thing read at launch and is written only from the Settings toggle, while `toggle()` and `endDrag()` persist `sidebarWidth` (default 268, clamped 210...440) from restingWidth and never touch startsOpen (WindowChrome.swift:286-370). The sidebar therefore always starts collapsed on a fresh install regardless of how the last session ended.
