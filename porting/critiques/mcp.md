# Critique: mcp

**Verdict:** NEEDS_REREAD - the three reports are mostly accurate and unusually specific, but R037 states a provider-config rule that the source contradicts, R038 states the wrong field-value fallback chain for MCPStore, and the OAuth callback page's verbatim assets plus several protocol field names, unreachable branches and dead APIs are missing.

## Contradictions (a report disagrees with the source) (3)

1. R037 vs source, MCPProviderConfig.swift:129-133: R037's feature_notes say "Claude, Codex and Gemini omit an empty env or headers object entirely". False for Gemini remote servers - `gemini(_:)` emits `"headers": .object(server.headers.mapValues(JSONValue.string))` unconditionally, exactly like Copilot (:60). Only the Gemini LOCAL branch guards `env` with `if !server.env.isEmpty` (:139). R037 also contradicts itself: its persisted_fields line for Gemini says `remote {httpUrl, headers}` with no optionality marker while the feature note says it is omitted. A port following the feature note writes a different gemini-settings.json than Droppy does.

2. R038 vs source, MCPStore.swift:64-70: R038 describes `value(for:of:)` as "draft first, else the Keychain secret for a .secret field, else the connection's stored value, else field.defaultValue". The source is an if/else-if: a `.secret` field reads ONLY the Keychain and never falls through to `connections[id]?.values[key]`; a non-secret field never reads the Keychain. Both kinds then fall to `field.defaultValue ?? ""`. The reported chain would make a port show a stale plaintext value for a secret field whose Keychain item is missing (including every CaptureRun, where MCPKeychain.value returns nil by design, MCPKeychain.swift:12).

3. R037 internal: its MCPProbe entry leaves "whether the 240-second mcp-remote deadline is ever reached in practice" unresolved, while its own MCPProviderConfig entry records that `mcp-remote` is minted only by `acpServers(allowsHTTP: false)` (MCPProviderConfig.swift:99). Those two facts together settle it - see the unreachable-branch gap below - but the report files them as an open question instead.

## Gaps (referenced but never pinned down) (18)

1. MCPCatalog.swift - no report records each field's `kind`, which decides whether a value goes to mcp.json or the Keychain. Exactly three built-in fields are non-secret: gitlab `instance` (.text, :31), filesystem `root` (.path, :83), sqlite `path` (.path, :389). Every other declared field is `.secret`, including postgres `url` (:372) and mongodb `url` (:407) whose values are full connection strings. So those three keys are the only ones that ever appear in `MCPConnection.values` in mcp.json for a built-in server. R032's persisted_fields lumps all field keys as "mcp.json values or Keychain entries".

2. MCPOAuth.swift:903 - the callback page's inline logo is a single `<path d="...">` of roughly 1.4 KB of exact coordinates. R037 paraphrases it ("a sprout/leaf mark plus two round dots (circle near 63,43 radius 5 ...)"). A parity port cannot reconstruct the mark from that; the `d` string must be captured verbatim, along with `<!DOCTYPE html>`, `<html lang="en">`, `<meta charset="utf-8">`, `<meta name="viewport" content="width=device-width, initial-scale=1">`, `* { box-sizing: border-box; }` and `html, body { margin: 0; padding: 0; }`, none of which R037 lists.

3. MCPOAuth.swift:19-44 - the error-message composition rule is missing. R037 prints a flat list of strings, but `discoveryFailed`, `metadataFailed`, `registrationFailed` and `tokenFailed` render as `<base> <detail>` when the detail is non-empty and `<base>` alone when empty, while `callbackFailed` and `network` render the DETAIL ALONE when non-empty and their base only when empty. So the user-visible text for a 404 during metadata lookup is "The server's sign-in details didn't make sense. The server answered 404.", not either string on its own.

4. MCPOAuth.swift:209-211, 225-232 - protected-resource metadata field names are only half recorded. R037 names `authorization_servers` and `resource` but not `scopes_supported` (the array whose non-empty strings become resourceScopes, which then drive both the registration `scope` and the authorization-URL `scope`), and it does not state that only the FIRST element of `authorization_servers` is used.

5. MCPProbe.swift:196-197 and :277-278 - the probe reads the server name and version from `result.serverInfo.name` and `result.serverInfo.version`. R037 says the probe "returns the server name, version" without ever naming the `serverInfo` object, so a port has no field path for the value it persists as `MCPConnection.serverVersion`.

6. MCPHub.swift:281 and MCPProbe.swift:89 - `checkReply` falls back to the literal string "unknown error" when a JSON-RPC error object has no `message`. That string reaches the user through LocalizedError (MCPHubError.server / MCPProbeError.malformed, which renders "The server sent something unexpected: unknown error"). Neither report lists it among the UI strings.

7. MCPProbe.swift:308 - `postJSON` builds `URLRequest(url:timeoutInterval: 30)` for every remote probe request. R037's MCPProbe timeout notes cover only the 240/90 second stdio deadlines and the 5 ms poll; the 30-second per-request HTTP timeout is absent, and it differs from MCPHub, which passes the per-call timeout (60/120/30) into its URLRequest (MCPHub.swift:453).

8. MCPProxy.swift:17-24 + MCP.swift:165 - the proxy-port file is written as a side effect of the FIRST read of `MCPProxy.port`, and that first read happens inside `MCPCatalogEntry.resolve` via `MCPProxy.url(for: id)`, i.e. potentially before `start()` is ever called. R038 records the file's format but presents it as proxy-lifecycle state rather than as something a pure-looking `resolve()` triggers.

9. MCPProxy.swift:118-128 + MCPStore.swift:22-27 - the repick path leaves the provider configs stale. `MCPStore.init` calls `MCPProxy.shared.start()` and then `exportAll()`, which bakes `http://127.0.0.1:<port>/mcp/<id>` into claude.json, codex.json, copilot.json and gemini-settings.json. If the listener afterwards enters `.failed`, `repickPort()` moves the port and rewrites proxy-port, but nothing re-runs `MCPProviderConfig.writeAll`, so every config written this launch points at the dead port. Neither R038's proxy entry nor its store entry connects these.

10. MCPBridgeSource.swift:49-56, :74-151, :225-237 - the bridge never kills a spawned child. `withTimeout` rejects after CONNECT_TIMEOUT_MS = 15000 and `loadMCPTools` catches and skips the server, but there is no `child.kill()`, `unref()` or SIGTERM anywhere in the file (grep confirms zero hits), so a server that hangs during initialize or tools/list leaves a live process for the lifetime of the Pi / Command Code host. This is the opposite of MCPHub, which tracks every child in `liveProcesses` and SIGKILLs it at quit. R037 describes the timeout as a plain skip.

11. MCPBridgeSource.swift:154 - the bridge's `postMessage` sets only Content-Type and Accept (plus lowercase `mcp-session-id`). It does NOT send `MCP-Protocol-Version: 2025-06-18`, which both MCPHub (:462) and MCPProbe (:314) do send. R037 lists the bridge's headers correctly but does not flag the divergence, which a port would silently normalize away.

12. MCPProxy.swift:308 and :369-378 - the proxy forwards the client's HTTP method verbatim, so GET (the streamable-HTTP SSE channel) and DELETE (session teardown) pass through unchanged; no report states which methods are supported. It also copies back only Content-Type, Mcp-Session-Id and Cache-Control, so `WWW-Authenticate` on a 401 is dropped - any client that tried OAuth discovery through a proxy route would see a bare 401.

13. MCPProxy.swift:263-275 - `readBody` on an early EOF (`isComplete || error != nil`) forwards whatever bytes arrived, so a request truncated below its declared Content-Length is relayed upstream rather than refused. R038 documents the 413/411/400 refusals but not this silent-truncation path.

14. MCPHub.swift:59 vs :76-95 - the `failed` set is consulted only by `tools()`; `call()` never checks it, so a server whose `listTools` threw is still launched again on a direct tool call. Separately, the `didRestart`/`dead` one-restart policy lives entirely in `ensureStdio` (:307-319): the HTTP path (:419-450) has no restart or dead state at all, and `initialized` is only cleared by `stop()`. R037 presents the restart policy without scoping it to stdio.

15. MCPStore.swift:335 - on probe success, `connectedAt`, `serverVersion` and `tools` are written only `if var connection = connections[entry.id]` exists, while `states[entry.id] = .connected(toolCount:)` is set unconditionally. A probe that succeeds with no connection row therefore shows as connected but is filtered out of `enabledServers` (which requires `connectedAt != nil`, :42) and so reaches no provider config. R038 states the success path without the guard.

16. MCPKeychain.swift:37-49 - `set()` calls `SecItemUpdate` with a query that carries no `kSecAttrAccessible`; only the `SecItemAdd` fallback (:47) applies `kSecAttrAccessibleWhenUnlocked`. An item created by an earlier build keeps whatever accessibility it had forever. R037 records the add attribute but not that updates never migrate it - a persisted attribute whose migration behavior is unstated.

17. Unreachable / dead code nobody classified, which the contract explicitly asks for: (a) `MCPProxy.stop()` (MCPProxy.swift:142) has no call site anywhere in the repository - the proxy is never shut down; R038 raised it as a question rather than resolving it. (b) `MCPOAuth.refreshIfNeeded(serverID:)` (MCPOAuth.swift:193) has no call site anywhere; R037 documents it as shipped behavior. (c) `MCPProxy.Route.headers` is always `[:]` at both registration sites (MCPStore.swift:284 and :310), so route-configured headers are dead configuration. (d) MCPProbe's `isOAuth` branch - the 240-second deadline (MCPProbe.swift:115) and the stderr "Unauthorized"/"invalid_grant" -> unauthorizedOAuth mapping (:217-219) - is unreachable for every built-in server: the only producer of a `mcp-remote` argument is `MCPProviderConfig.acpServers(allowsHTTP: false)` (:99), whose output goes to ACPSession.swift:254 and never to the probe, and the probe's sole caller (MCPStore.swift:313) always passes `entry.resolve(values:)`. Only a user-authored custom stdio server whose args literally contain "mcp-remote" can reach it.

18. MCPOAuth.swift:404-406 - the sign-in callback listener sets only `requiredLocalEndpoint = .hostPort(host: "127.0.0.1", port: .any)` and, unlike MCPProxy (:97), does not set `requiredInterfaceType = .loopback`. R037 records the endpoint but not the missing interface restriction, which is the kind of detail a port's socket-binding code has to decide.

## Thin reports (1)

1. R037 - not thin overall (MCPHub, MCPProbe, MCPProviderConfig and MCPBridgeSource are dense and mostly correct), but its MCPOAuth.swift entry is thin for a 929-line file: it paraphrases the verbatim callback-page SVG instead of capturing it, omits the base+detail error-message composition rule, omits `scopes_supported`, omits that `expires_at` is optional and that a session without it never refreshes, and omits that the callback listener does not restrict its interface type. That one file deserves a re-read.

## Cross-cutting findings (8)

1. Path literals the three reports all deferred are resolvable and matter: `AppInfo.name` is `Bundle.main.object(forInfoDictionaryKey: "CFBundleDisplayName") as? String ?? "Droppy Code"` (Core/Support/Text.swift:4) and `Storage.root` is `~/Library/Application Support/<AppInfo.name>`, overridable by `CaptureRun.storageRoot` (Services/Store/Storage.swift:19-25). So mcp.json and custom-mcp.json sit directly in that folder and MCPPaths.directory is `<that>/mcp`.

2. Directory-case collision nobody flagged: `MCPBridge.installBridge()` writes to `<Application Support>/<AppInfo.name>/MCP/droppy-mcp-bridge.mjs` (MCPBridgeSource.swift:243-246, capital MCP, built from `FileManager.urls(for:.applicationSupportDirectory)` and NOT from Storage.root), while `MCPPaths.directory` is `Storage.root/mcp` (MCP.swift:231, lowercase). On a default case-insensitive macOS volume and on Windows these are the same folder, so the bridge .mjs lands beside claude.json / codex.json / copilot.json / gemini-settings.json / proxy-port / managed.json; on a case-sensitive volume they are two folders. A second consequence: under CaptureRun, MCPPaths moves with Storage.root but the bridge directory does not.

3. Complete file inventory under MCPPaths.directory, which no single report gives: claude.json, codex.json, copilot.json (MCP.swift:236-241), gemini-settings.json (MCPProviderConfig.swift:238), proxy-port (MCPProxy.swift:15), managed.json (MCPExternalSync.swift:52). `writeAll([])` deletes only the first four (MCPProviderConfig.swift:150-152); proxy-port is never deleted by anything, so a reinstall reuses the old port, and managed.json is deleted exactly once by the migration (MCPExternalSync.swift:27).

4. The consumer side of every generated artifact is unrecorded, so the port has the file formats but not the invocations: ClaudeSession.swift:96 passes `--mcp-config <path> --strict-mcp-config` (both flags, only when claudeConfigPath() is non-nil); AntigravitySession.swift:83-84 passes `--allowed-mcp-server-names` followed by connectedIDs(); ProviderRegistry.swift:274 sets `GEMINI_CLI_SYSTEM_SETTINGS_PATH` to gemini-settings.json (the Gemini file is consumed by the Antigravity provider, not a "Gemini" provider); ProviderRegistry.swift:272 merges opencodeEnvironment() for `.opencode`; CopilotSession.swift:486 appends copilotArguments(); CodexSession.swift:257-261 merges codexOverrides() into `params["config"]["mcp_servers"]`; ACPSession.swift:254 passes acpServers(allowsHTTP: supportsHTTPMCP) as the `mcpServers` field of session/new and session/load.

5. The env var that carries the bridge path is never named in any report: PiSession.swift:105-110 and CommandCodeSession.swift:174-179 set `DROPPY_CODE_MCP_BRIDGE` to the installed .mjs path, and set `DROPPY_CODE_MCP_CONFIG` to MCPPaths.claudeConfigURL.path only when that file exists. R037 names DROPPY_CODE_MCP_CONFIG but not DROPPY_CODE_MCP_BRIDGE.

6. MCPHub's only consumer is OpenAICompatibleSession.swift:510 (tools()), :898 (parse) and :904 (call) - the in-app model-API provider. R037 left that unresolved. MCPHub.terminateAll() is called from AppDelegate.swift:54.

7. Token expiry spans R037 and R038 and is mis-stated as unconditional: `storeSession` writes `expires_at` only when the token response carried `expires_in` (MCPOAuth.swift:698-700), and `accessToken` treats a missing `expires_at` as never-expiring (`guard let expiresAt = ... else { return false }`, MCPOAuth.swift:172). Combined with MCPProxy.swift:355-361, the proxy's "401 -> fetch token again and replay once" does NOT force a refresh; it calls the same `accessToken` and, absent an expiry, gets the identical cached token, so the replay is a byte-identical retry. Neither report states this.

8. Custom-server migration risk spans R032 and R038: `MCPCustomServer.Variable` uses the synthesized decoder with no default for `isSecret` (MCPCustom.swift:15-19), so a stored variable object missing that key throws; because the throw happens inside `decodeIfPresent([Variable]...)` (MCPCustom.swift:46,48) and `MCPStore.load()` decodes the whole array with `try?` (MCPStore.swift:245-248), one bad variable silently drops EVERY custom server, not one. R032 raised the decoder question; nobody carried it to the blast radius.
