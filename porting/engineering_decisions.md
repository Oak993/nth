porting/owner_decisions_pending.md.

## ED-009

[SIDEBAR] Search uses Swift lowercased() and the picker uses localizedCaseInsensitiveContains; does a Windows ordinal-ignore-case comparison agree? :: DECIDED: they are two different comparisons and must be implemented as two different comparisons; ordinal-ignore-case is wrong for both. SOURCE FACT: the sidebar search folds with `lowercased()` then `contains` - query at App/Views/Sidebar/SidebarView.swift:739, project name at :742, thread titles at :744 against the cache built at :2653. Swift's `lowercased()` is Unicode FULL, locale-INDEPENDENT default case conversion, which can change string length. The picker path uses `localizedCaseInsensitiveContains`, which is locale-SENSITIVE. DECISIONS: (1) implement `lowercased()` as Unicode Default Case Conversion with no locale tailoring - in a JS/TS stack that is exactly `String.prototype.toLowerCase()`; never ordinal case folding, never a locale-tailored ToLower, because Turkish dotless-i tailoring and simple-vs-full mapping of U+0130 both diverge from Swift; (2) implement `localizedCaseInsensitiveContains` as a locale-sensitive collator search at secondary strength in the user's current locale - in a JS/TS stack `Intl.Collator(undefined, {usage:'search', sensitivity:'accent'})`; (3) add the pinning fixture both requirements already call for, covering at minimum U+0130, U+0131, the final sigma pair, and a combining-mark case, and assert the two comparisons disagree where the source makes them disagree. Not a product choice: the user-visible contract is 'matches the same strings the source matches', and these are the implementations that satisfy it.

## ED-010

[SIDEBAR] The scroll freeze lifts immediately on an .idle scroll phase, but WM_MOUSEWHEEL has no scroll-end signal. :: DECIDED: the 150 ms debounce is the sole governor for wheel input; wire a scroll-end to the immediate lift only where the input stack actually reports one. ## ED-011

[SIDEBAR] Chrome.glideSpring's settlingDuration drives the glide's handover; will a Windows spring solver compute the same value for response 0.6 / damping 0.86? :: DECIDED: derive the handover from the solver's own settle time, never hardcode a macOS-measured constant. SOURCE FACT: UI/Chrome/Chrome.swift:106 is `Spring(response: 0.6, dampingRatio: 0.86)`; App/Views/Sidebar/RowGlide.swift:18 aliases it, :225 drives the keyframes with it, and :228-236 is the whole contract - sleep for `max(spring.settlingDuration - 0.12, 0)`, then arrive(), then sleep 0.12, then finish(). The comments at :114-115 and :229-230 state the intent plainly: the real row comes back under the ghost's last frames so the handover never shows a gap, and the ghost goes once the keyframes have run their course. DECISION: (1) implement the spring with the same parameterisation, angular frequency omega0 = 2*pi/response = 10.472 rad/s and zeta = 0.86; (2) define settlingDuration analytically as the time the envelope decays to 1/1000 of the initial displacement, ln(1000)/(zeta*omega0), approximately 0.767 s for these values, and pin that in a unit test; (3) compute the 0.12 s handover FROM that value at runtime, so if the solver's settle time is ever retuned the ghost is still removed after the animation visually ends and never before. The failure the source is guarding against is a visible gap or a ghost outliving its motion; both are avoided by the derivation, not by matching Apple's number. AttachmentFlight.swift:102 uses the same property and takes the same treatment.

## ED-088

[ALL] Scope of OD-0012 F1 ("every remaining Droppy Code / droppy-code the app shows or sends out becomes Marrow / marrow"). DECISION: it covers everything a user can see or that the app writes into places the user owns: UI text, file and folder names in the user's home or projects (the state folder ".droppy-code" becomes ".marrow", shown in Settings; the home state directory becomes %USERPROFILE%\.marrow, with %USERPROFILE%\.marrow-dev for a development build), git data written into the user's repositories (the checkpoint ref namespace refs/droppy-code/checkpoints/ becomes refs/marrow/checkpoints/, the checkpoint author and messages per F1), and identities sent over the network or to other programs. It does not cover names that live only inside the app and its own helper processes and are never shown or stored in user space: the bridge variable DROPPY_CODE_MCP_CONFIG and the login-shell marker __DROPPY_CODE_ENVIRONMENT__ keep upstream's names (parity, invisible). The two F1 exceptions stand: droppy-code.json and DROPPY_CODE_PROJECT_ROOT. The OAuth callback page's Droppy logo is replaced by the port's own icon once the owner approves it (the owner chose a new icon design, 2026-09-23).
