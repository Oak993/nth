# Release evidence and the single verifier

`node porting/tools/verify.mjs [--gate A|B|C|D|E|F] [--json] [--no-run]` is the single acceptance entrypoint. All mandatory failures exit nonzero. C..F now validate actual evidence instead of returning NOT_IMPLEMENTED. A green marker scan or unit run cannot satisfy the semantic gates. `--no-run` reads captured evidence; it never builds or runs applications. Default D runs only the four solution test projects and their dependencies, never Marrow.Setup. No verifier builds, runs, signs or publishes an installer.

T39 is **NOT READY**. The Windows reference is absent on Linux, SwiftFont's genuine TODO remains, production/visual/native/package/final independent acceptance evidence is absent. Do not remove any failure to turn this inventory green.

## Capture and binding

1. Commit the final integrated inputs. `global.json`, tool versions and every applicable lock must match. Code/policy/reference/ledger changes invalidate earlier evidence.
2. `node porting/tools/prepare-release-evidence.mjs <new-template.json>` prepares a complete NOT_RUN input inventory, without executing tests or native programs. It refuses overwrites. The release-unit inventory is reconciled mechanically to BUILD-PLAN, each multi-account checklist bullet and later rulings. It supplements all PR/UI records; it does not replace them or grant implementation credit.
3. `node porting/tools/req_verify.mjs` runs the four unfiltered solution test projects and derives `requirements.json` from unchanged Req traits and raw TRX. Raw run records/logs/TRX/discovery lists are in `porting/verification/runs/`. Use `--project <known test.csproj> [--filter <expression>]` for scoped Linux work; it is explicitly PARTIAL and cannot pass D. `--no-run` rederives the most recent captured run. Failed/skipped/not-run/unbound/PARTIAL entries never satisfy acceptance; N/A/RETIRED remain evidenced classifications, not silently excluded. All applicable ledger IDs must be present, and each project's complete discovery list must equal its result names.
4. `node porting/tools/record-release-negative-checks.mjs` runs only the isolated synthetic tooling controls, records the real TAP output and five negative-control categories, then verifies that the inputs did not change. It does not verify the product.
5. Collect real C..F receipts; assemble `porting/verification/release-evidence.json` from the template and authentic artifacts. Do not write PASS fields without the commands/results proving them. Run the full verifier. Commit/policy changes require another run. Do not commit a report and claim its own newly changed HEAD is the revision it ran on: preserve exact run receipts separately and rerun after the final input commit. An archival report with a different HEAD correctly fails current acceptance.

Binding includes B3 commit/tree, implementation HEAD, committed src/tests trees, SHA256 over **every tracked input** outside verification outputs (including policies, all existing reference fixtures, ED/PA/ADR/OD records, unknowns, legal bytes, scripts and locks), and dirty-input detection. Verification output files are excluded from the input hash so recording a run does not invalidate itself; each referenced artifact is separately hash checked. Any changed HEAD fails. Absolute/escaping/symlink-escaping artifact paths fail. Record paths relative to the repo and retain the raw files with the summary.

## Receipt format

Each `evidence` entry needs unique `id`, `kind`, status PASS, the exact `binding`, argv-array `command`, integer `exit_code` 0, ISO start/end times, `producer`, `environment` (platform, OS/version, architecture, exact tool versions), and a nonempty `artifacts` list of relative paths/SHA256s. Windows interaction, visual, restart, failure, end-to-end, build and lifecycle receipts require actual Windows 11 x64. Linux results remain useful scoped checks, not native acceptance.

C and D `coverage` must include every applicable PR/UI ID and every FR obligation exactly once, with the unchanged `verification_method`, status, semantic review, production paths and evidence IDs. Every receipt referenced by a row must carry one ID-specific `assertions` entry containing the unchanged verification method/source evidence and named expected-versus-observed checks. Production reviews additionally trace entrypoint, handler, state transition, side effects, persistence, failure/cancellation and authority, naming the real production files. Sparse wording does not erase persistence/restart or failure/cancellation obligations. D additionally requires unit, contract, interaction, visual, restart, failure and end-to-end evidence overall. An evidence file unrelated to the row cannot cover it.

Visual assertions need a `visual` object: comparison scope (source-defined or owner-approved-deviation), method, distinct PNG `reference` and `windows` artifacts, policy and measurements JSON artifacts, B3 reference provenance, logical width/height, scale percent, theme and state. Both captures must match the stated dimensions. Policy JSON identifies ID/method/authority and named metrics with **existing, predeclared** `max` limits. Measurements JSON identifies ID, status, both capture hashes, policy hash, conditions and numerical metrics; failed, missing, changed-condition or over-limit results reject. This is an adapter for existing locked comparisons; it is not authority to create/widen tolerances or regenerate references. No manufactured Mac reference is permitted (OD-0001/0004). Retain individually unverified Mac-delegated properties.

N/A/RETIRED `exemptions` require a reason and receipts carrying the same ID/classification/provenance. An unresolved/blocking status is never an exemption. No ledger requirement is removed by these tools.

E requires a Release/win-x64 package with version/runtime identity, an actual x64 PE installer hash, package-build receipt, and hash-linked inspection JSON: package SHA256, version, runtime and runtime version, configuration, Marrow product, MarrowCode app ID, Marrow Code data identity, approved vcredist143-x64 prerequisite, CPU/Vulkan/VAD/test-clip and three legal-resource hashes. Every lifecycle receipt must name the **same package hash and scenario** and contain checked outcomes. Required scenarios: clean install/prerequisite, desktop launch, CPU/Vulkan load, close/zero surviving children, second launch/data load, upgrade/data retention, same-version no payload execution, downgrade refusal/no change, uninstall/data retention/zero surviving children. These inputs are preparation only in T39: collecting E remains Windows work under separate installer authorization.

F needs a reviewer different from the implementation author, receipts from that reviewer, every ledger and release obligation explicitly reviewed, matching deviation/owner-ruling inventories, and no unresolved finding. Final F also requires actual A..E checks, including C marker/quarantine checks. Preserve missing OD-0029/0030 provenance; never invent those rulings.

The tools validate consistency, complete coverage, results and binding. They cannot prove honest artifact authorship or human comprehension while their authors can edit them. Independent source/Windows review remains mandatory. Synthetic fixtures/green tooling controls are never product evidence.
# Canonical PE release identity (RR-43)

Gate E/F additionally read the unchanged App AssemblyInfo version/build and pinned runtime toolchain. Package version/runtime must equal these inputs. The hash-linked package inspection must include `pe_metadata.app` and `pe_metadata.setup`, each with `assembly_version` (1.7.0.0), `file_version` (1.7.0.21), `product_version` (1.7.0+build.21), `product` (Marrow), `company` (Marrow Code), and `title` (Marrow or Marrow Setup respectively). Read these from the actual final PE resources on Windows. Declared consistency alone cannot satisfy identity. This is an inspection receipt requirement, not evidence that an installer was built in T39.
Both entries also require `architecture: "x64"`, `exe_sha256`, `assembly_sha256`, and hash-linked `exe_artifact`/`assembly_artifact` retained among the matching package-build receipt's artifacts. The validator reads the EXE's PE header; inspected setup must be the exact package artifact. App `legal_copyright` must equal the unchanged AssemblyCopyright source. `scripts/inspect-release-metadata.ps1` emits these fields read-only on Windows; omitting Setup yields incomplete inspection and cannot satisfy E/F.
