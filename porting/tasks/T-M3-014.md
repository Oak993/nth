### PR-GIT-071 - A working-tree watch exists only for a local volume, is shared per directory, and the registry is bounded at 32 with the oldest torn down

- **Action:** A snapshot asks for the directory's watch.
- **Expected:** An existing registered watch for that exact directory string is returned at once. ### PR-GIT-072 - The watch streams file events over the working root and, when it lies outside, the git directory too, with no coalescing

### PR-GIT-076 - Before trusting the event count the watch writes a cookie file in the git directory and waits up to one second for its own event
- **Source:** DroppyCode/Services/Git/WorkingTreeWatch.swift:246-273 settledGeneration() - nil when there is no stream; the cookie number is the incremented cookiesWritten; the file is created at the cookie prefix plus the decimal number and removed in a defer; a task sleeps one second then expires the waiter; the waiter is resumed by whichever of the event or the timeout removes it first; an arrival returns the current generation, a timeout tears the watch down and returns nil | DroppyCode/Services/Git/WorkingTreeWatch.swift:5-21 - 'events arrive in order, so everything written before it has been counted'
- **Preconditions:** A stream exists.
- **Action:** A snapshot asks whether the last capture still stands.
- **Expected:** Without a stream the answer is nil at once, so nothing is reused. Otherwise a cookie number is allocated, a zero-byte file is created at the git root plus "/droppy-code-sync-" plus that decimal number, and removed in a deferred cleanup. If the file cannot be created the answer is nil. A one second timer is armed. The caller suspends until either the cookie's own event arrives, or the timer expires the waiter; nothing polls, and whichever removes the waiter is the one that resumes it. On arrival the current generation is returned; on timeout the watch is torn down and nil is returned.
- **Side effects:** A zero-byte cookie file in the git directory, created and deleted per snapshot
- **Persistence:** None; the file is transient.
- **Failure cases:** A volume that does not report events never delivers the cookie, so the watch is torn down and every later snapshot for that directory is taken fresh
- **Cancellation:** The timer task is cancelled when the event wins.
- **Windows path:** Platform boundary: the same cookie file trick maps onto ReadDirectoryChangesW, which delivers in order within one directory handle; the cookie is only used when the git directory lies under the root, one handle (ED-113); otherwise the watch has no stream and the answer is nil at once. UNVERIFIED on Windows: whether the event of a write made through a handle still open when the cookie is created arrives before the cookie's event (ReadDirectoryChangesW may report a last write only when the cache is flushed). Windows verification item for the GIT unit: append to a tracked file without closing it, write the cookie, and check which event arrives first. Keep the one second ceiling.
- **Verify by:** interaction test with a shimmed stream that never delivers, asserting the one second timeout and the teardown

### PR-GIT-079 - currentTree on the watch resolves to one of four states: the cached tree, joining a same-generation capture, waiting out a different-generation capture, or owning a new one
- **Source:** DroppyCode/Services/Git/WorkingTreeWatch.swift:290-337 currentTree(indexPath:capture:) - the settled generation gates everything; the index stamp is taken; the loop resolves to .tree, .join, .wait or .own; the changed set is taken at the moment a capture starts and reset to empty; the owner stores the snapshot on success and drops the changed set to nil on failure | DroppyCode/Services/Git/WorkingTreeWatch.swift:25-34 IndexStamp - modification date and size of the index file
- **Preconditions:** A settled generation was obtained.
- **Action:** A snapshot is requested.
- **Expected:** The index file's modification date and size are stamped. Then, under the lock: a stored snapshot at the same generation with an equal index stamp returns its tree directly; a capture already in flight at the same generation is joined; one at a different generation is waited out and the loop retries; otherwise this caller owns a new capture. The changed paths handed to a new capture are the watch's set only when the previous snapshot's index stamp matches, otherwise nil meaning the whole tree, and the set is reset to empty at that moment so writes during the walk land in a fresh set. The owner stores a snapshot of the tree, generation and index stamp on success, or drops the changed set to nil on failure, and then either returns the tree or throws a file-read error. A joined capture that returned nil makes the caller loop and ask again, because only the owner may rebuild the scratch index.
- **Side effects:** At most one capture per generation
- **Persistence:** In-memory snapshot only.
- **Failure cases:** A failed capture returns nil and the changed set is dropped to nil, so the next capture walks everything
- **Cancellation:** The capture is detached at utility priority and is not cancelled by a caller going away.
- **Windows path:** Direct port of the four-state resolution. The index stamp is modification time and size only, with no file identifier.
- **Verify by:** unit driving two concurrent callers at the same and at different generations
