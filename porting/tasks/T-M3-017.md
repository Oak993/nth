### PR-STORE-010 - A thread document file is named <uppercase UUID with dashes>.json inside threads/
- **Source:** DroppyCode/Services/Store/Storage.swift:50-52 - static func threadURL(_ id: UUID) -> URL { threadsDirectory.appendingPathComponent("\(id.uuidString).json") }
- **Preconditions:** threads/ resolved.
- **Action:** Any thread save, prefetch, read or delete.
- **Expected:** The file name is the UUID rendered by uuidString, which is uppercase hexadecimal with four dashes, followed by ".json". There is no lowercasing here, unlike the git checkpoint namespace which lowercases deliberately.
- **Persistence:** <root>/threads/<UUID>.json
- **Cancellation:** not cancellable
- **Windows path:** Same name. Windows file names are case-insensitive but case-preserving, so a port that lowercases would still open the file yet would write a differently cased name and break byte-comparison of a migrated store; keep uuidString casing exactly.
- **Verify by:** contract fixture

### PR-STORE-013 - An undecodable library.json is surfaced to the user and never overwritten by the next save

Library() } | DroppyCode/App/AppModel.swift:126-128 - the returned library’s projects and threads become the app’s state directly | DroppyCode/App/AppModel.swift:1299-1306 - saveLibrary builds a fresh Library from the in-memory projects and threads and calls DiskWriter.shared.encodeAndWrite(library, to: Storage.libraryURL) | DroppyCode/App/AppModel.swift:1289-1297 - scheduleSave debounces that save by 400 ms after any mutation
- **Preconditions:** library.json exists but cannot be read or is not decodable as a Library (truncated write, not valid JSON, or a non-object at the top level).

- **Expected:** Deviation, OD-0008 A10 (BLK-0010 FIX): the failed load is not swallowed. It is surfaced to the user, and library.json is not overwritten after the failed load: no writer of library.json writes over it in that run. That covers the 400 ms debounced save after a mutation (AppModel.swift:1289-1297), the immediate saveLibrary() calls on settle (AppModel.swift:805-806), reopen (:825) and thread delete (:956), and the synchronous quit-time save (:1317). The thread JSON files under threads/ are not touched by the failed load. - **Persistence:** library.json is left exactly as it was found on disk. Thread files under threads/ are written as usual.
- **Failure cases:** Per-element leniency (Library.init(from:) decoding [Lenient<Project>] and [Lenient<ChatThread>]) means a single bad record is dropped without reaching this path; only a whole-file failure does.; A library.json that does not exist is not a failed load: PR-STORE-012 applies, the app starts empty and ordinary saves create the file.

- **Windows path:** Storage.LoadLibrary tells a missing file (empty library, ordinary saves, PR-STORE-012) apart from one that exists but cannot be read or decoded. Thread file saves are not affected. Named deviation. The report is shown in the main window at launch with the OD-0012 E4 text, byte for byte: "Marrow could not read library.json, so your projects and threads are hidden. The file will not be changed until it can be read."
- **Verify by:** contract fixture: launch against a deliberately corrupted library.json (truncated, not JSON, a top-level array) and assert the main window shows, at launch, exactly "Marrow could not read library.json, so your projects and threads are hidden. The file will not be changed until it can be read."; then create a thread, wait past the 400 ms debounce, settle it, reopen it, delete it, and quit, asserting after each step that library.json is byte-identical to the corrupted input, and at the end that every threads/ file present before launch is unchanged

### PR-STORE-019 - readDocument builds its own decoder rather than using the shared one
- **Source:** DroppyCode/Services/Store/Storage.swift:76-78 - let decoder = JSONDecoder(); decoder.dateDecodingStrategy = .iso8601; guard var document = try? decoder.decode(ThreadDocument.self, from: data) | DroppyCode/Core/Support/Coding.swift:28-33 - JSONDecoder.storage exists and is configured identically
- **Preconditions:** A thread file is being read, possibly on a background thread.
- **Action:** Storage.readDocument(id).
- **Expected:** A fresh JSONDecoder is created per call with dateDecodingStrategy .iso8601. The doc comment at DroppyCode/Services/Store/Storage.swift:65 explains why: "Safe from any thread: the decoder is made here." The configuration is identical to JSONDecoder.storage, so the observable result is the same; only the instance differs.
- **Side effects:** One decoder allocation per thread read
- **Cancellation:** not cancellable
- **Windows path:** A per-call deserializer instance where the shared one is not safe to use concurrently, or a shared one that is genuinely thread-safe. The observable format is identical either way; record whichever is chosen, because a shared mutable deserializer read from the prefetch worker and the main thread at once is a data race.
- **Verify by:** unit

### PR-STORE-021 - A thread read waits for every queued write before touching the file
- **Source:** DroppyCode/Services/Store/Storage.swift:73-75 - readDocument calls DiskWriter.shared.waitForQueuedWrites() before Data(contentsOf: threadURL(id)) | DroppyCode/Services/Store/Storage.swift:376-379 - waitForQueuedWrites() { queue.sync {} } | DroppyCode/App/AppModel.swift:500-503 - releaseIdleRuntime comments that the save is queued before the runtime goes and a read that follows waits for it, "so the thread can never come back older than it left"
- **Preconditions:** A save for this thread may be sitting on the writer queue.
- **Action:** Storage.readDocument or Storage.decodeDocument.
- **Expected:** The calling thread blocks on an empty synchronous block on the serial writer queue, which returns only once every write enqueued before it has finished. The file is then read, so a thread closed and immediately reopened is never read back in its older state.
- **Side effects:** Blocks the calling thread until the writer queue drains
- **Failure cases:** If the writer queue is busy with a large document the read blocks for that long. This is on a background prefetch worker or a detached history load, never on the main actor, because both call sites are detached (DroppyCode/App/Runtime/ThreadRuntime.swift:550-554 and DroppyCode/App/AppModel.swift:444).
- **Cancellation:** The barrier itself is not cancellable; a cancelled prefetch request is discarded after the load returns.
- **Windows path:** Same barrier against the single serial write queue. It must be a real drain of the whole queue, not a per-file wait, because that is what the source does.
- **Verify by:** interaction test: queue a save, read immediately, assert the new bytes come back

### PR-STORE-023 - readDocument returns nil when the thread file cannot be decoded
- **Source:** DroppyCode/Services/Store/Storage.swift:78 - guard var document = try? decoder.decode(ThreadDocument.self, from: data) else { return nil }
- **Preconditions:** threads/<uuid>.json exists but is not a decodable ThreadDocument (for example a missing "threadID").
- **Action:** Opening that thread.
- **Expected:** nil is returned and the thread opens empty. The corrupt file is not deleted, not renamed and not reported, and the first save of the now-empty thread overwrites it.
- **Side effects:** The corrupt file is overwritten at the next save of that thread
- **Failure cases:** Only a whole-document failure reaches this; ThreadDocument.init(from:) decodes items, turns, followUps and hydraMerges through Lenient, so individual bad entries are dropped instead (DroppyCode/Core/Models/Timeline.swift:356-364).
- **Cancellation:** not cancellable
- **Windows path:** Reproduce. Unlike the library case, the blast radius is one thread and the user sees it immediately as an empty chat, so this is an ordinary quirk under AM-0001, not an escalation.
- **Verify by:** unit with a corrupt fixture

### PR-STORE-026 - readDocument reports the file byte count as the prefetch cache cost
- **Source:** DroppyCode/Services/Store/Storage.swift:80 - return (document, data.count) | DroppyCode/Services/Store/Storage.swift:300 - state.ready.insert(result.document, for: request.id, cost: result.cost)
- **Preconditions:** A prefetch request is being served.
- **Action:** Storage.readDocument returns.
- **Expected:** The second tuple element is the encoded byte count of the file as read, not the in-memory size of the decoded document, and it is what the ready cache charges against its 16 MiB budget.
- **Failure cases:** A single thread file larger than the 16 MiB cost limit is rejected by the cache outright and is re-read on every open (see the RecentCache over-budget requirement).
- **Cancellation:** not cancellable
- **Windows path:** Charge the same measure: bytes read from disk.
- **Verify by:** unit
