### PR-PROVCLI-293 - Pi builds a whole-file unified diff for edits and writes, through a no-op relativization
- **Source:** DroppyCode/Services/Providers/PiSession.swift:439-466 - editDiff and unifiedDiff with the doc comment | porting/extracts/provider-argv-and-handshakes.md section 6.9
- **Preconditions:** A finished edit or write.
- **Action:** editDiff runs.
- **Expected:** For a tool named exactly "edit": a string args.path is required, and the diff is built from args.oldText and args.newText, each defaulting to the empty string. For "write": a string args.path and a string args.content are required, and the old side is the recorded snapshot, REMOVED as it is consumed, defaulting to the empty string. Any other name returns nil. The diff is a header of "--- a/<path>" and "+++ b/<path>" on two lines, then EVERY non-empty line of the old text prefixed with "-", then EVERY non-empty line of the new text prefixed with "+", all joined by single newlines - not a real unified diff with hunks. The additions and deletions come from diffStats. The path is passed through `path.hasPrefix("/") ? path : path`, whose two branches are IDENTICAL, so the ternary is a no-op and the path is NEVER made relative; the FileEdit therefore carries the absolute path.
- **Persistence:** none
- **Failure cases:** A missing path or content yields no edits.
- **Cancellation:** not cancellable
- **Windows path:** The no-op ternary means Pi's file rows show ABSOLUTE paths where the other providers show relative ones, and on Windows those will be drive-letter paths inside a diff header that looks like a POSIX one. This is an upstream defect and is reproduced, not repaired.
- **Verify by:** unit test asserting the absolute path survives into the diff header
- **Upstream defect provider-argv-and-handshakes.md section 10 item 6 (unifiedDiff's no-op ternary; paths are never relativized): reproduce it faithfully, do not fix it.**
