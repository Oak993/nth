### PR-PROVCLI-297 - Pi auto-allows a gate request whose kind already holds a session grant
- **Source:** DroppyCode/Services/Providers/PiSession.swift:602-606 - let kindString = payload["kind"]?.string ?? "tool"; if sessionGrants.contains(kindString) { send extension_ui_response with value "Allow"; return }
- **Preconditions:** A parsed gate payload.
- **Action:** handleSelect evaluates the grant.
- **Expected:** The kind string is payload.kind or the literal "tool". When the session grants already contain that EXACT string, a reply {"type":"extension_ui_response","id":<id>,"value":"Allow"} is written at once - the plain "Allow", not "Allow for session" - and no prompt is shown and no event emitted. The grant keys stored by resolveApproval are exactly "command", "fileChange" and "tool", which match the kinds the extension emits.
- **Side effects:** One stdin line
- **Persistence:** Session grants live for the life of the session object only; they are not persisted across a relaunch.
- **Failure cases:** none
- **Cancellation:** not cancellable
- **Windows path:** None.
- **Verify by:** interaction test granting a command for the session and asserting the next command is not prompted

### PR-PROVCLI-298 - Pi gate approvals map three kinds to three row shapes and always offer the same three options
- **Source:** DroppyCode/Services/Providers/PiSession.swift:607-636 - the kind mapping, the title and detail switch, the three options and the emitted approval
- **Preconditions:** A gate request with no matching session grant.
- **Action:** handleSelect builds the approval.
- **Expected:** The tool name is payload.toolName or the literal "tool". The kind is .command for the string "command", .fileChange for "fileChange" and .tool for everything else. The row: .command -> title the unwrapped input.command or the tool name, detail the RAW input.command; .fileChange -> title the relative input.path or the tool name, detail the RAW input.path; .tool and the rest -> title the tool name, detail the PRETTY-printed input unless it is null or compacts to "{}". The options are ALWAYS exactly three, in this order: "allow"/"Approve"/.approve, "always"/"Approve for session"/.approveAlways, "deny"/"Decline"/.decline. The toolItemID is payload.toolCallId. The request is stored as pending under the extension request id and emitted as .approval.
- **Side effects:** One provider event; one pending entry
- **Persistence:** none
- **Failure cases:** none
- **Cancellation:** A stop leaves the extension waiting; there is no cancellation reply path.
- **Windows path:** None.
- **Verify by:** unit test over all three kinds

### PR-PROVCLI-299 - Pi's close path ends an active turn, then reports an exit with the status and the stderr tail
- **Source:** DroppyCode/Services/Providers/PiSession.swift:638-653 - didClose(status:)
- **Preconditions:** The process's message stream ended.
- **Action:** didClose runs.
- **Expected:** The stderr tail is taken FIRST, then the process reference cleared. When a turn was active, it is cleared and .turnCompleted is emitted with .interrupted when interruptRequested, else .failed, carrying the tail as the error when it is non-empty and nil when it is empty. Then, when the session was stopped, the method returns. Otherwise started becomes false and: an exit status of exactly 0 emits .exited(error: nil); any other status emits .exited with "Pi exited with status <status>" plus, when the tail is non-empty, a newline and the tail.
- **Side effects:** Provider events
- **Persistence:** none
- **Failure cases:** A crash mid-turn reports the turn failed and then the session exited.
- **Cancellation:** A stop suppresses the exit notice but NOT the turn completion, because the turn branch runs before the stopped guard.
- **Windows path:** The exit status appears verbatim in user-visible text, so a Windows termination code will be shown; the source formats it as a signed integer. The tail comes from the bounded stderr collector (PA-0008).
- **Verify by:** interaction test over a zero exit, a non-zero exit and a stop mid-turn

### PR-PROVCLI-300 - Pi reports itself running only when started, not stopped and holding a live process
- **Source:** DroppyCode/Services/Providers/PiSession.swift:74 - var isRunning { started && !stopped && process?.isRunning == true }
- **Preconditions:** Any state.
- **Action:** The thread asks whether the session is running.
- **Expected:** All three must hold: started is true, stopped is false, and the process exists and reports itself running. This is stricter than Command Code, which asks only the two flags, and stricter than Claude, which asks only the process.
- **Persistence:** none
- **Failure cases:** none
- **Cancellation:** not cancellable
- **Windows path:** The process must report not-running promptly after it exits, or send() will attempt a write to a dead pipe.
- **Verify by:** unit test over each of the three false cases
