### PR-TERM-100 - LoginEnvironment.which resolves a path-like name directly and a bare name by scanning colon-separated PATH for an executable file
- **Source:** DroppyCode/Core/Support/Shell.swift:415-427 which(_:in:) - a name containing "/" has its tilde expanded and is returned only when it is an executable file; otherwise PATH (from the given environment, else current, else augmentedPath(nil)) is split on ":" and each directory is joined with the bare name and tested with isExecutableFile; the first match wins; nil when none matches | porting/platform_adaptations.md:217-228 PA-0010 - Windows resolves executables through PATHEXT and separates PATH entries with semicolons; npm-installed CLIs are typically .cmd shims
- **Preconditions:** A tool name is being resolved.
- **Action:** which is called.
- **Expected:** A name containing a slash is treated as a path, with a leading tilde expanded, and is accepted only if it is executable. A bare name is looked up left to right in PATH, first executable match wins, no extension is appended.
- **Side effects:** One executability test per PATH entry until a match.
- **Persistence:** None.
- **Failure cases:** Nothing found: nil, which the by-name run overload turns into the not-found error (PR-TERM-090).
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY, tracked as PA-0010 and UNK-0006. Split PATH on semicolons, resolve through PATHEXT, and treat a backslash as well as a forward slash as the path marker. Contract section 11 requires validating the actual executable identity rather than the name for the provider whose command name is cmd, because a bare cmd resolves to the Windows command interpreter long before any provider CLI. Executable identity is validated per PA-0016: PATH resolution honours PATHEXT, and a candidate whose Windows version resource identifies it as the command interpreter (CompanyName Microsoft Corporation with OriginalFilename Cmd.Exe/Cmd.Exe.MUI, or FileDescription Windows Command Processor), or which is %SystemRoot%System32cmd.exe or %SystemRoot%SysWOW64cmd.exe, is rejected and the provider reports not installed.
- **Verify by:** contract fixture over path-like names, bare names and a PATHEXT shim

### PR-TERM-101 - The login environment is captured once by running the user's shell as an interactive login shell around a marked env dump, with an 8-second budget
- **Source:** DroppyCode/Core/Support/Shell.swift:367-385 read() - marker "__DROPPY_CODE_ENVIRONMENT__"; script is printf of the marker, then /usr/bin/env -0, then printf of the marker; the shell is run with ["-l", "-i", "-c", script] with the fallback environment and timeout 8; the region strictly between the first and last marker occurrence is split on NUL; each entry is split at its first '=' | DroppyCode/Core/Support/Shell.swift:327-328 - the doc comment: apps launched from Finder inherit a minimal PATH that cannot find provider CLIs, so this is captured once at launch
- **Preconditions:** The app is starting.
- **Action:** read() runs.
- **Expected:** The user's shell runs its login and interactive profiles and prints its whole environment NUL-separated between two copies of the marker. Only the region between the first and the last marker is parsed, and only when the first ends before the last begins, so profile output before or after the dump is ignored. Entries with an empty key or a key in the excluded set are dropped. Entries with no '=' are skipped. Values may contain '=' because only the first one splits. The whole read is abandoned after 8 seconds, leaving the fallback environment.
- **Side effects:** The user's shell profile files are executed, which can have arbitrary effects.; One child process.
- **Persistence:** None on disk; the result is cached in memory for the run.
- **Failure cases:** The shell fails, times out, or prints no markers: the fallback environment is used with only the PATH augmentation applied.
- **Cancellation:** not cancellable by the user.
- **Windows path:** PLATFORM BOUNDARY, unresolved. Windows processes inherit the user environment directly, so the login-shell read has no purpose (porting/platform_adaptations.md:206-207). OD-0008 C5 resolves UNK-0005 only for the interpreter (PowerShell 7 if installed, otherwise Windows PowerShell); it does not say what replaces this read. What replaces it is the engineering decision PA-0009 calls for (porting/platform_adaptations.md:206-214), and none is recorded in porting/engineering_decisions.md. One candidate, not yet decided, is a read of the process environment plus the user and machine Environment registry keys.
- **Verify by:** contract fixture with a scripted shell emitting markers, plus the no-marker and timeout cases

### PR-TERM-104 - The environment load is single-flight: concurrent callers await the same task
- **Source:** DroppyCode/Core/Support/Shell.swift:332-334 - the comment: the one read of the login shell; launch starts it, and anything that resolves a CLI before it lands waits on the same task, so a codex under nvm is never reported missing | DroppyCode/Core/Support/Shell.swift:357-365 load() - under the loading mutex, an existing task is returned, otherwise one is started and stored; the caller awaits its value | DroppyCode/Core/Support/Shell.swift:341-349 - current returns the cached value or the fallback; isLoaded reports whether the cache is populated
- **Preconditions:** Several call sites may need the environment before the capture finishes.
- **Action:** load() is called concurrently.
- **Expected:** Exactly one capture runs. Every caller awaits the same task and returns when it completes. A reader that does not await, using `current` directly, gets the process fallback environment until the capture lands, which is why anything resolving a CLI awaits load() first.
- **Side effects:** At most one shell process per app run.
- **Persistence:** None.
- **Failure cases:** A caller that reads current without awaiting during the window sees the fallback PATH and can report a CLI as missing. The single-flight await exists precisely to avoid this.
- **Cancellation:** The task is never cancelled; it always completes or times out.
- **Windows path:** Same single-flight discipline around whatever the Windows capture becomes.
- **Verify by:** unit test with concurrent callers counting captures

### PR-TERM-106 - The git binary is resolved once, preferring the active developer directory's git over Apple's shim
- **Source:** DroppyCode/Core/Support/Shell.swift:393-397 - the doc comment: PATH usually gives /usr/bin/git, Apple's shim that looks up the active developer directory and execs the real binary on every call, measured at 11.5 ms per call against 4.5 ms for the binary itself; the shim's own target is used instead where it can be found, and without developer tools the shim stays so its install prompt still shows | DroppyCode/Core/Support/Shell.swift:398-400 - git returns the resolved value, else which("git"), else /usr/bin/git | DroppyCode/Core/Support/Shell.swift:404-413 developerGit - only when the PATH git is exactly /usr/bin/git does it run /usr/bin/xcode-select -p with an 8-second timeout and use <developer>/usr/bin/git when that path is an executable file | DroppyCode/Core/Support/Shell.swift:389-390 - the resolution runs at the end of the environment capture
- **Preconditions:** The environment capture has finished.
- **Action:** developerGit runs, and later callers read LoginEnvironment.git.
- **Expected:** If PATH resolves git to anything other than /usr/bin/git, that path is used and no probe runs. Otherwise xcode-select -p is run once; a non-empty developer directory whose usr/bin/git is executable wins; anything else leaves the shim in place. Every later read returns the resolved value without re-probing.
- **Side effects:** At most one xcode-select child process per app run.
- **Persistence:** None.
- **Failure cases:** xcode-select fails or times out: the shim stays, which is the source's deliberate choice so its install prompt still appears.
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY. The guard can never be true on Windows, so the probe is unreachable by construction and must not be transliterated. The port's resolution is which("git") with a fallback, and the fallback path itself has to be a Windows decision rather than the literal /usr/bin/git.
- **Verify by:** unit test asserting no probe runs when PATH git is elsewhere

### PR-TERM-118 - find and fd read unless an argument is one of the seven search actions; the port adds -fprintf and the other file-writing find actions
- **Source:** DroppyCode/Core/Support/Shell.swift:198-199 - case "find", "fd": return !arguments.contains { searchActions.contains($0) } | DroppyCode/Core/Support/Shell.swift:161-162 - /// Searches that run something of their own, which may well write. private static let searchActions: Set<String> = ["-delete", "-exec", "-execdir", "-ok", "-okdir", "-x", "-X"]
- **Preconditions:** A part's tool is find or fd.
- **Action:** The rule runs.
- **Expected:** Upstream: membership is tested by EXACT equality of a whole argument against the seven-element set "-delete", "-exec", "-execdir", "-ok", "-okdir", "-x", "-X", in that set and no other. Any one match makes the part a writer; otherwise it reads. Note -x and -X are both present and are fd's execute flags, and that -execdir and -okdir are separate members rather than prefixes, so a joined form such as -exec=... does not match. The test is over the argument list, not over the part's text, unlike the awk rule. DEVIATION (OD-0008 A8): in the port -fprintf and the other write actions missing from searchActions also make the part a writer, so `find . -fprintf out.txt '%p'` is classified as writing. The ruling (BLK-0008) names only -fprintf; which other find and fd arguments count as "the other write actions" is not listed by the ruling, the source or any recorded engineering decision, so that set must be recorded as an engineering decision before this requirement is SPECIFIED.
- **Persistence:** None.
- **Failure cases:** Upstream: find -fprintf writes a file and is not in the set, so it is classified as a reader (BLK-0008). Corrected in the port by OD-0008 A8.
- **Cancellation:** not cancellable
- **Windows path:** Port the seven strings verbatim, case included (-x and -X are distinct members and a case-insensitive set would collapse them), plus the OD-0008 A8 additions.
- **Verify by:** unit asserting each of the seven members and -fprintf triggers, each member of the recorded engineering-decision set triggers, plus a negative for a joined form

### PR-TERM-119 - sort reads unless an argument starts with -o; the port also treats --output= as writing

- **Failure cases:** Upstream: `sort --output=file` writes a file and is classified as a reader (BLK-0008). Corrected in the port by OD-0008 A8.
- **Cancellation:** not cancellable
- **Windows path:** Same -o prefix test plus the ruled --output= correction (OD-0008 A8).
- **Verify by:** unit over -o, -ofile, --output=x and a plain sort, asserting --output=x is a writer
