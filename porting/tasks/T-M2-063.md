### PR-MCP-233 - Stdio replies are matched to requests by exact id: an integer request is not answered by a string id, while a fractional number is truncated and matches
- **Source:** DroppyCode/Core/Support/JSONRPC.swift:3-14 RPCID - :9 case .int(let id): self = .int(id) | :10 case .double(let id): self = .int(Int(id)) | :11 case .string(let id): self = .string(id) | :12 default: return nil | DroppyCode/Services/MCP/MCPWire.swift:169 let key = RPCID.int(id) | DroppyCode/Services/MCP/MCPWire.swift:221 let rawID = object["id"], let id = RPCID(rawID) else { return } | DroppyCode/Core/Support/JSONValue.swift:26-45 init(foundation:) - a number the JSON parser reports as floating point becomes .double, any other number .int
- **Preconditions:** A stdio request with integer id N is waiting.
- **Action:** A reply arrives.
- **Expected:** Each request waits under RPCID.int(N). A reply's id is converted the same way: a JSON integer stays that integer, a number the JSON parser reads as floating point (for example 1.5) is truncated toward zero and so answers request 1, a JSON string stays a string, and any other id is ignored. A string id therefore never answers an integer request, even when it spells the same number: a reply with "id": "1" is kept under the string (PR-MCP-232) and request 1 waits until its timer ends it, giving "The server didn't answer in time." in the hub and the timeout outcome in the probe. Event-stream replies over HTTP are matched differently (PR-MCP-117).
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** a server that echoes ids as strings times out on every request
- **Cancellation:** not cancellable
- **Windows path:** Match on a tagged id (integer or string) exactly as RPCID does, including the truncation of a fractional number; do not coerce numeric strings.
- **Verify by:** unit: replies with "id": "1" and "id": 1.5 against request 1

### PR-PROVACP-142 - A cancelled request removes its pending entry and fails with a cancellation error
- **Source:** DroppyCode/Core/Support/JSONRPC.swift:76-86 - `withTaskCancellationHandler { try Task.checkCancellation(); return try await withCheckedThrowingContinuation { continuation in pending[id] = continuation; write(...) } } onCancel: { Task { @MainActor in self?.pending.removeValue(forKey: id)?.resume(throwing: CancellationError()) } }`
- **Preconditions:** A request is in flight.
- **Action:** The awaiting task is cancelled.
- **Expected:** An already-cancelled task fails before the frame is written, because checkCancellation runs first. A cancellation during flight removes the pending entry and fails the await with a cancellation error. ### PR-PROVACP-143 - A null params member is omitted from the frame entirely
- **Source:** DroppyCode/Core/Support/JSONRPC.swift:105-110 - `guard !isClosed else { return }; var message = message; if message["params"] == .null { message.removeValue(forKey: "params") }; if sendsVersion { message["jsonrpc"] = "2.0" }; process.send(.object(message))`
- **Preconditions:** A request, notification or response is being written.
- **Action:** write() runs.
- **Expected:** Writing on a closed connection is a silent no-op. A params value that is JSON null is REMOVED, so `{"jsonrpc":"2.0","id":1,"method":"x"}` is sent rather than one carrying `"params":null`. The jsonrpc member is added last and only when sendsVersion is true, which it always is for ACP. Every ACP method call in this area passes an explicit params object, so the elision is observable only for a hypothetical parameterless call.
- **Side effects:** One framed line written to stdin.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Same elision rule, per port_impacts #1.
- **Verify by:** contract fixture

### PR-PROVACP-144 - Notifications and responses have exactly the members the source writes
- **Source:** DroppyCode/Core/Support/JSONRPC.swift:89-99 - `notify` writes `["method": .string(method), "params": params]`; `respond(to:result:)` writes `["id": id.json, "result": result]`; `respond(to:errorCode:message:)` writes `["id": id.json, "error": ["code": .int(code), "message": .string(message)]]`
- **Preconditions:** A notification or a response is being sent.
- **Action:** The frame is built.
- **Expected:** A notification carries method and params and NO id. A success response carries id and result and no method and no error. An error response carries id and an error object with exactly code and message and no data member. Each then gains jsonrpc 2.0 from write(). The inbound id's original type is preserved in the response: an integer id is answered with an integer, a string id with a string.
- **Side effects:** One framed line per call.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Same three shapes, with the id type round-tripped.
- **Verify by:** contract fixture (golden frames)

### PR-PROVACP-145 - Inbound ids accept integers, doubles truncated to integers, and strings
- **Source:** DroppyCode/Core/Support/JSONRPC.swift:3-29 - `RPCID` init from JSONValue: `.int(let id)` -> .int; `.double(let id)` -> `.int(Int(id))`; `.string(let id)` -> .string; anything else returns nil
- **Preconditions:** An inbound message carries an id.
- **Action:** The id is parsed.
- **Expected:** An integer id is taken as is. A JSON number that parsed as a double is TRUNCATED toward zero to an integer, so 2.0 and 2.7 both become 2 and would collide. A string id is taken as is. A boolean, null, array or object id fails to parse, and the message is then treated as having no id: with a method it becomes a notification, without one it is dropped.
- **Persistence:** None.
- **Failure cases:** A double-valued id colliding with an integer id of the same whole part.
- **Cancellation:** not cancellable
- **Windows path:** Same three-way parse including the truncation, which matters because JSON numbers in JS are all doubles: an integral number must map to the integer branch and a fractional one must be truncated, not rejected.
- **Verify by:** unit (id-parsing table)

### PR-PROVACP-146 - An inbound message with a method is a request when it has an id and a notification when it does not

- **Preconditions:** A parsed inbound message.
- **Action:** handle() dispatches it.
- **Expected:** A non-object message (an array, a bare string) is dropped. A message with a string method and a parseable id goes to the request handler; with no handler installed it is answered -32601 "Method not found". A message with a method and no id goes to the notification handler. Missing params become JSON null, which is what handleNotification then subscripts.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Same dispatch.
- **Verify by:** unit

### PR-PROVACP-147 - A reply is matched to its pending request, and an unmatched reply is dropped

- **Failure cases:** A duplicate reply for the same id is dropped, because the entry was already removed.
- **Cancellation:** not cancellable
- **Windows path:** Same, including the two default values.
