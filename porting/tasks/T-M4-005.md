### PR-MCP-139 - signIn discovers the authorization server, mints PKCE and state, runs the callback server, then exchanges the code
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:134-160 signIn(serverID:serverName:url:)
- **Preconditions:** An OAuth server that is not signed in.
- **Action:** probeOnce calls signIn.
- **Expected:** In order: discover(url:) against the remote address; verifier = a 32-byte random token, base64url; challenge = the SHA-256 of the verifier, base64url; state = a 24-byte random token, base64url. Then runCallbackServer with the server's display name and the expected state; inside its ready callback, once the loopback port is known, clientRegistration runs and the authorization URL is built - a nil URL throws MCPOAuthError.metadataFailed("The authorization address isn't valid."). Finally exchangeCode runs with the returned code, the redirect URI and the verifier. Every step throws an MCPOAuthError whose errorDescription becomes the card's failure message.
- **Side effects:** one or more metadata HTTP GETs; possibly one dynamic client registration POST; opens a loopback TCP listener and the user's default browser; one token-endpoint POST
- **Persistence:** on success the session is written to protected storage under "MCP <id> oauth"; a new registration is written under "MCP <id> oauth-client"
- **Failure cases:** any of the eleven MCPOAuthError cases, rendered per PR-MCP-160
- **Cancellation:** cancelling the probe cancels the callback listener through the task-cancellation handler, and the pending continuation resumes with MCPOAuthError.cancelled
- **Windows path:** Same order. The browser is opened with the OS default-handler call; do not embed a web view, which would change the user's session and cookie context. Protected storage is Windows Credential Manager (OD-0008 B3), under the same account strings.
- **Verify by:** integration test with a stub authorization server driving the whole flow

### PR-MCP-140 - Discovery reads protected-resource metadata from the 401 challenge, or probes two well-known paths
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:200-248 discover(url:) | DroppyCode/Services/MCP/MCPOAuth.swift:250-283 protectedResourceMetadataURL
- **Preconditions:** An OAuth upstream address.
- **Action:** discover runs.
- **Expected:** An unparseable address throws discoveryFailed("That address doesn't look like a URL."). A GET of the address with Accept: application/json and a 30-second timeout is made; only a 401 response is inspected, and every WWW-Authenticate header on it (matched case-insensitively, whether a single string or a list) is scanned for a resource_metadata parameter and a scope parameter, stopping once both are found. When a resource_metadata URL was found, it is fetched and authorization_servers[0], resource and scopes_supported are read from it. When it was NOT found, two candidates are tried in order: "<origin>/.well-known/oauth-protected-resource<path of the address>" then "<origin>/.well-known/oauth-protected-resource"; the first that parses AND has either an authorization_servers array or a resource string is used and the loop stops. scopes_supported becomes the scope list only when it yields at least one non-empty name. When no scopes were found that way, the scopes from the challenge are used. issuer defaults to the address's origin; it is trimmed of leading and trailing "/" characters and, if empty, throws discoveryFailed("That address doesn't look like a URL."). Only authorization_servers[0] is ever used; later entries are ignored.
- **Side effects:** one GET of the MCP address plus up to three metadata GETs
- **Persistence:** none
- **Failure cases:** a non-401 answer or a network failure simply yields no challenge and falls through to the two candidates; no usable metadata anywhere -> metadataFailed with the last error detail
- **Cancellation:** each request is a cancellation point
- **Windows path:** Same order, same two candidates, same single-issuer rule, and accept a bare unquoted resource_metadata value.
- **Verify by:** contract fixture replaying a challenge-carrying 401 and one with no challenge

### PR-MCP-141 - A WWW-Authenticate parameter is read quoted or bare up to the next comma or space
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:285-309 resourceMetadataURL, challengeParameter and challengeScopes
- **Preconditions:** A challenge header string.
- **Action:** A parameter is extracted.
- **Expected:** Find the first occurrence of "<name>=" anywhere in the header (no token-boundary check, so a parameter name that is a suffix of another would mis-match). Trim the remainder of leading whitespace. When it starts with a double quote, the value is everything up to the next double quote, and an unterminated quote yields nil. Otherwise the value is the leading run of characters that are neither a comma nor a space. An empty value yields nil. challengeScopes splits the scope parameter on single spaces, drops empty names, and yields nil when nothing remains.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** a malformed challenge yields nil and discovery falls back to the well-known candidates
- **Cancellation:** not cancellable
- **Windows path:** Same permissive parse; Stripe sends resource_metadata unquoted and would be lost by a strict RFC 9110 parser.
- **Verify by:** unit with a quoted value, a bare value followed by a comma, and an unterminated quote

### PR-MCP-142 - Authorization-server metadata is sought at up to four candidate URLs, path-first for an issuer with a path
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:311-352 fetchAuthorizationServerMetadata
- **Preconditions:** An issuer string.
- **Action:** The metadata is fetched.
- **Expected:** base = the issuer trimmed of leading and trailing "/". When the issuer parses and has a path that is neither empty nor "/", two candidates come first: "<origin>/.well-known/oauth-authorization-server<path>" then "<origin>/.well-known/openid-configuration<path>". Then always: "<base>/.well-known/oauth-authorization-server" and "<base>/.well-known/openid-configuration". Each is fetched in order; the first that parses and has a non-empty authorization_endpoint AND a non-empty token_endpoint wins and yields AuthServerMetadata(issuer: base, authorizationEndpoint, tokenEndpoint, registrationEndpoint: the registration_endpoint string or nil, resource, resourceScopes). A document missing either endpoint records the detail "It's missing the addresses needed to sign in." and the loop continues. Exhausting the candidates throws metadataFailed(lastError), where lastError is the detail from the LAST failure only.
- **Side effects:** up to four HTTP GETs
- **Persistence:** none
- **Failure cases:** metadataFailed rendered as "The server's sign-in details didn't make sense. <detail>", or without the detail when it is empty
- **Cancellation:** each GET is a cancellation point
- **Windows path:** Same candidate order. Stripe's issuer https://access.stripe.com/mcp needs the path-after-well-known forms first; the rest answer at the path-first forms below them.
- **Verify by:** contract fixture over a path-bearing and a path-free issuer

### PR-MCP-143 - A stored OAuth client is reused only when its issuer matches the discovered one
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:356-364 the reuse branch of clientRegistration
- **Preconditions:** A sign-in is starting.
- **Action:** clientRegistration runs.
- **Expected:** Read protected storage account "MCP <id> oauth-client"; parse it as JSON; require a non-empty client_id AND require its "issuer" field to equal the discovered metadata's issuer exactly. Only then reuse it, carrying client_secret when present. Any mismatch or missing piece falls through to a fresh dynamic registration.
- **Side effects:** one protected-storage read
- **Persistence:** none on the reuse path
- **Failure cases:** an issuer change forces a fresh registration, which may then fail with registrationUnsupported
- **Cancellation:** not cancellable
- **Windows path:** Same exact-string issuer comparison; a looser match would reuse a client registered with a different authorization server. Protected storage is Windows Credential Manager (OD-0008 B3), under the same account strings.
- **Verify by:** unit with a matching and a mismatching stored issuer

### PR-MCP-144 - Dynamic client registration POSTs a fixed body and stores the resulting client
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:365-400 the registration branch of clientRegistration
- **Preconditions:** No reusable stored client.
- **Action:** clientRegistration registers.
- **Expected:** A missing or empty registration_endpoint throws registrationUnsupported -> "This server doesn't let apps sign in on their own.". Otherwise POST JSON with exactly these members: client_name "Marrow"; redirect_uris a one-element array holding the loopback redirect URI; grant_types ["authorization_code", "refresh_token"]; response_types ["code"]; token_endpoint_auth_method "none"; and scope, joined with single spaces, only when the discovered resource scopes are non-empty. A non-2xx status, an unparseable body, or a missing or empty client_id throws registrationFailed with the server's own error_description or error when present, else "The server only signs in apps it has approved (403), so this one can't yet." for status 403 and "The server refused to set things up (<status>)." otherwise. On success the client is stored under "MCP <id> oauth-client" as JSON with sorted keys holding client_id, issuer, and client_secret only when non-empty.
- **Side effects:** one registration POST; one protected-storage write
- **Persistence:** "MCP <id> oauth-client" holding {client_id, issuer, client_secret?}
- **Failure cases:** the three registrationFailed renderings above, each prefixed "Sign-in setup failed. "
- **Cancellation:** the POST is a cancellation point
- **Windows path:** Same body members in the same JSON shape. client_name is "Marrow" (OD-0012 F1). Protected storage is Windows Credential Manager (OD-0008 B3), under the same account strings.
- **Verify by:** contract fixture asserting the exact registration body and the stored client JSON

### PR-MCP-145 - The callback server listens on an OS-assigned loopback port and redirects to /callback there
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:404-459 runCallbackServer
- **Preconditions:** A sign-in is starting.
- **Action:** runCallbackServer runs.
- **Expected:** TCP parameters with requiredLocalEndpoint 127.0.0.1 at any port, and NO interface-type constraint (unlike the proxy's listener, which pins loopback). A construction failure throws network("Couldn't listen for the sign-in reply."), which renders as just that sentence. On ready, the assigned port gives redirectURI = "http://127.0.0.1:<port>/callback"; the ready callback then registers the client, stores the redirect URI and client for the later handler, and opens the authorization URL in the default browser on the main thread. A failure inside that callback finishes the wait with the thrown error. A failed listener state gives network("The connection to the browser broke."); a cancelled state gives MCPOAuthError.cancelled -> "Sign-in was cancelled.". The completion is idempotent under a lock, so the first outcome wins and the listener is cancelled with it.
- **Side effects:** opens a loopback TCP listener on an ephemeral port; opens the default browser
- **Persistence:** the registration may write "MCP <id> oauth-client"
- **Failure cases:** the three network and cancellation messages above
- **Cancellation:** the task-cancellation handler cancels the listener, which resumes the continuation with .cancelled
- **Windows path:** Bind 127.0.0.1 with an OS-assigned port and no interface-type constraint. Windows Firewall must not prompt for a loopback-only listener; verify that on a clean machine. Protected storage is Windows Credential Manager (OD-0008 B3), under the same account strings.
- **Verify by:** integration test driving a real loopback callback

### PR-MCP-146 - A sign-in that is not completed in the browser times out after 300 seconds
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:130 callbackTimeout | DroppyCode/Services/MCP/MCPOAuth.swift:452-454 the scheduled timeout
- **Preconditions:** The callback listener started.
- **Action:** 300 seconds pass.
- **Expected:** A timer scheduled on the callback queue fires unconditionally at +300 seconds and finishes the wait with MCPOAuthError.timedOut -> "Sign-in timed out. Try again and complete it in the browser.". Because the completion is idempotent, a flow that already finished is unaffected and the timer is a no-op. The timer is not cancelled early, so it always fires once.
- **Side effects:** cancels the listener when it is the first outcome
- **Persistence:** none
- **Failure cases:** the timedOut message above becomes the card's failure text
- **Cancellation:** an earlier cancellation wins because finish is first-outcome-wins
- **Windows path:** Same 300-second deadline and the same always-fires timer.
- **Verify by:** integration test with a shortened, injected deadline

### PR-MCP-147 - The callback server reads only the request head, giving up past 1 MiB with no reply
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:461-496 receiveRequest
- **Preconditions:** A browser connected to the callback listener.
- **Action:** Bytes arrive.
- **Expected:** Reading stops immediately, cancelling the connection, when the wait has already finished. Otherwise bytes accumulate until CR LF CR LF; the head is everything up to and including that terminator. When the stream completes, errors, or the buffer passes 1048576 bytes without a terminator, the connection is cancelled with no reply at all and no outcome is recorded.
- **Side effects:** may close the connection silently
- **Persistence:** none
- **Failure cases:** a truncated request leaves the flow waiting until the 300-second timeout
- **Cancellation:** a finished wait short-circuits every further read
- **Windows path:** Same 1 MiB cap and the same silent close.
- **Verify by:** contract fixture sending an oversized head

### PR-MCP-148 - The callback accepts only GET and only the /callback path
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:506-525 the method and path checks
- **Preconditions:** A head was read.
- **Action:** handleRequest parses the request line.
- **Expected:** Only the first line of the head is parsed, split on spaces. When it has fewer than two parts or the method is not exactly "GET", answer 405 with status text "Method Not Allowed" and body "<html><body>Method not allowed.</body></html>", then cancel the connection with no outcome recorded. When the target is neither exactly "/callback" nor prefixed "/callback?", answer 404 with status text "Not Found" and body "<html><body>Not found.</body></html>", then cancel with no outcome. Query items are parsed by prefixing "http://127.0.0.1" to the target.
- **Side effects:** writes a small HTML body and closes the connection
- **Persistence:** none
- **Failure cases:** neither rejection records an outcome, so the flow keeps waiting until the timeout
- **Cancellation:** not cancellable
- **Windows path:** Verbatim bodies and status texts, and the same no-outcome behavior: a favicon request must not abort a sign-in.
- **Verify by:** contract fixture sending POST /callback and GET /favicon.ico
