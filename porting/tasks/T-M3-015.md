## Requirements

### PR-GIT-154 - A path under the git directory is skipped entirely and marks nothing
- **Source:** DroppyCode/Services/Git/WorkingTreeWatch.swift:195-196 - // Git's own writes (objects, refs, the index) do not change the working files. if path.hasPrefix(gitPrefix) { continue } | DroppyCode/Services/Git/WorkingTreeWatch.swift:135 - gitPrefix = gitRoot + "/", with gitRoot = realpath of the git directory | DroppyCode/Services/Git/WorkingTreeWatch.swift:143 - the git directory is a second stream root only when it lies outside the working root
- **Preconditions:** The stream is running; this path was not lost and is not a cookie path.
- **Action:** A path beginning with the git directory prefix is classified.
- **Expected:** The path is skipped with no effect at all: changed stays as it was, everything is untouched, and nothing is added to the directory list. Git's own writes to objects, refs and the index do not change the working files, which is why the app can watch the git directory for its cookies without every git command it runs waking a capture. The prefix is the realpath-resolved git directory with a trailing separator, so the git directory itself, without the separator, does not match this rule and falls through to the root rules.
- **Persistence:** None.
- **Failure cases:** A repository whose git directory lies INSIDE the working root still matches here, so changes under .git never mark the tree changed even though the root rule would otherwise catch them
- **Cancellation:** not cancellable
- **Windows path:** Same rule. Resolve the git directory to its real path once, as the source does with realpath(3), so a junction, a substituted drive or an 8.3 short name cannot make the prefix test miss.
- **Verify by:** unit over a path inside the git directory, the git directory itself, and a working file with a similar prefix

### PR-GIT-155 - A path outside the working root, or the root itself, marks the batch changed and sets everything
- **Source:** DroppyCode/Services/Git/WorkingTreeWatch.swift:197 - changed = true, set before the root test, so every path that reaches this point marks the batch changed whichever branch it then takes | DroppyCode/Services/Git/WorkingTreeWatch.swift:198-203 - // The directory holding what changed, relative to the root, or the entry itself // when it sits at the root; a change to the root, or outside it, means the whole tree. guard path.hasPrefix(rootPrefix), path.utf8.count > rootPrefixBytes else { everything = true; continue } | DroppyCode/Services/Git/WorkingTreeWatch.swift:134 and :137 - rootPrefix = root + "/" with root = realpath of the directory; rootPrefixBytes = rootPrefix.utf8.count, a BYTE count
- **Preconditions:** The stream is running; this path was not lost, is not a cookie path and is not under the git directory.
- **Action:** The path fails the root test.
- **Expected:** changed is set to true FIRST, unconditionally, for every path that gets this far. The root test then requires both that the path begins with the root plus a separator and that its UTF-8 length is strictly greater than that prefix's UTF-8 length. Failing either, everything is set to true and the path is skipped. Two distinct inputs take this branch: a path that is not under the working root at all - which happens when the git directory is a second stream root and something inside it was neither a cookie nor under gitPrefix - and the working root itself, which is exactly the prefix length. The length test is in BYTES against a byte count, while the cookie rule's drop is in CHARACTERS; the two units are not interchangeable and a non-ASCII project path makes them differ.
- **Persistence:** None within this rule; committed under the lock by PR-GIT-157.
- **Failure cases:** Any event that cannot be placed inside the root costs the next capture a full tree walk
- **Cancellation:** not cancellable
- **Windows path:** Same rule and the same byte-length comparison. Resolve the working root to its real path once; on Windows the comparison is also case-insensitive in effect, which a prefix test on the raw strings does not give, so normalise case the same way for both the prefix and the incoming path or the branch fires on every event.
- **Verify by:** unit over the root itself, a path outside the root, and a path one byte longer than the prefix

### PR-GIT-156 - Any other path contributes the directory holding it, relative to the root, or the entry itself when it sits at the root
- **Source:** DroppyCode/Services/Git/WorkingTreeWatch.swift:204-205 - let relative = path[rootPrefix.endIndex...]; directories.append(String(relative.lastIndex(of: "/").map { relative[..<$0] } ?? relative)) | DroppyCode/Services/Git/WorkingTreeWatch.swift:197 - changed was already set to true for this path
- **Preconditions:** The path is under the working root and longer than the root prefix.
- **Action:** The path's contribution is derived.
- **Expected:** The path is cut at the end of the root prefix, giving a root-relative remainder with no leading separator. The contribution is the remainder up to its LAST separator, exclusive; when the remainder holds no separator, meaning the entry sits directly at the root, the contribution is the remainder itself, i.e. the entry's own name and not the empty string for the root directory. The result is appended to the batch's directory list, duplicates and all: no deduplication happens here, it happens in the set under the lock. Nothing is normalised, lowercased or resolved at this point.
- **Persistence:** None within this rule; committed under the lock by PR-GIT-157.
- **Failure cases:** A file at the root contributes its own file name where every other entry contributes a directory name, so the changed set mixes the two kinds; the pathspec pass (PR-GIT-075) is what makes that harmless
- **Cancellation:** not cancellable
- **Windows path:** Same derivation with the platform's separator. The contribution is later handed to git as a pathspec, so it must end up forward-slashed at that boundary, not here.
- **Verify by:** unit over a nested file, a file directly at the root, and two files in one directory

### PR-GIT-157 - The batch is committed under the lock in one pass: the generation rises once, the cookie is raised, the set grows or collapses, and matured waiters are resumed outside the lock
- **Source:** DroppyCode/Services/Git/WorkingTreeWatch.swift:207 - guard changed || cookie > 0 else { return } | DroppyCode/Services/Git/WorkingTreeWatch.swift:208-223 - state.withLock { if changed { state.generation &+= 1 }; state.cookieSeen = max(state.cookieSeen, cookie); if everything { state.changed = nil } else if var set = state.changed { ... state.changed = set }; let seen = state.cookieSeen; guard state.waiters.contains(where: { $0.cookie <= seen }) else { return [] }; let ready = state.waiters.filter { $0.cookie <= seen }.map(\.continuation); state.waiters.removeAll { $0.cookie <= seen }; return ready } | DroppyCode/Services/Git/WorkingTreeWatch.swift:224-225 - // Outside the lock: a resumed caller takes it next. for continuation in ready { continuation.resume(returning: true) }
- **Preconditions:** A batch has been classified into changed, everything, a directory list and a cookie number.
- **Action:** The batch is committed.
- **Expected:** A batch that changed nothing and carried no cookie returns before taking the lock at all. Under the lock, in this order: the generation is incremented ONCE per callback, not once per path, and only when changed is set, using wrapping addition; the seen cookie is raised to the maximum of itself and the batch's; then, when everything is set the changed set is dropped to nil, otherwise, and only when a set already exists, the batch's directories are inserted into it - a nil set stays nil, so a tree already marked whole-tree is never partially re-narrowed. Waiters whose cookie is at or below the raised seen counter are collected, removed from the list and returned; the early return of an empty array when none has matured avoids building the list. The collected continuations are resumed with true OUTSIDE the lock, so a resumed caller takes the lock next rather than re-entering it.
- **Side effects:** Matured waiters are resumed with true
- **Persistence:** The watch's generation, cookieSeen and changed set.
- **Failure cases:** A waiter whose cookie matured in an earlier batch was already removed then, so it is not resumed twice
- **Cancellation:** The timeout path (PR-GIT-077) is the other remover of a waiter, and whichever of the two removes it is the one that resumes it.
- **Windows path:** Same order and the same resume-outside-the-lock rule. Wrapping addition on the generation must be preserved; a trapping add would crash after 2^64 batches where the source wraps.
- **Verify by:** unit asserting one generation bump for a multi-path batch, no bump for a cookie-only batch, and that a waiter is resumed after the lock is released
