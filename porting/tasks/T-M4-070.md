### PR-PROVCLI-229 - Command Code queues a tool row, diverts todo_write, snapshots a file before a write and rescans the gate
- **Source:** DroppyCode/Services/Providers/CommandCodeSession.swift:342-356 - tool_queued with the comment at :371 | DroppyCode/Services/Providers/CommandCodeSession.swift:640-646 - snapshot reads text files up to 1 MB and returns nil otherwise
- **Preconditions:** A tool_queued event with a call id and a tool name.
- **Action:** handleEvent processes it.
- **Expected:** The name and input are recorded. A tool named exactly "todo_write" emits .todos from its input and RETURNS, drawing no row. A tool named exactly "write_file" with a string file_path takes a snapshot of that file FIRST, storing the empty string when the snapshot is nil, so the row's diff can later be the file before against the content written. Then .toolStarted is emitted with the built row. Finally scanApprovals() is called immediately, because the gate's request file may already be on disk by the time the row exists. The snapshot reads a file only when its size is at most 1000000 bytes and it decodes as UTF-8; anything else - binary, huge or missing - reads as nil and is stored as the empty string, so a write shows as a whole-file addition.
- **Side effects:** A file read; provider events; a directory scan
- **Persistence:** none
- **Failure cases:** An unreadable file yields an empty baseline.
- **Cancellation:** not cancellable
- **Windows path:** The 1 MB ceiling and the UTF-8 requirement are product behavior. On Windows a file the CLI has open may still be readable, but a locked file reads as nil and the diff then shows the whole file as added; that is the same outcome the source has for an unreadable file.
- **Verify by:** unit test over a text file, a binary file, a 2 MB file and a missing file
