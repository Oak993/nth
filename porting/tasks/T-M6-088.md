### PR-SETTINGS-001 - Settings opens as a single reused, non-resizable 780 x 580 AppKit window titled "Settings"
- **Source:** DroppyCode/App/Window/WindowManager.swift:21 Size.settings - NSSize(width: 780, height: 580) | DroppyCode/App/Window/WindowManager.swift:80-84 makeSettingsWindow() - makeWindow(title: "Settings", size: Size.settings, resizable: false, windowClass: SecondaryWindow.self) { SettingsView() }; window.center() | DroppyCode/App/Window/WindowManager.swift:32-37 showSettings(page:) - `let window = settingsWindow ?? makeSettingsWindow(); settingsWindow = window`, so one window is built once and reused | DroppyCode/App/Window/WindowManager.swift:92-99 makeWindow - style [.titled, .closable, .miniaturizable, .fullSizeContentView]; resizable is NOT inserted for settings; window.title = title; window.isReleasedWhenClosed = false; window.animationBehavior = .documentWindow; window.tabbingMode = .disallowed; WindowChrome.configure(window)
- **Preconditions:** The application is running. The settings window may or may not already exist.
- **Action:** Anything calls WindowManager.shared.showSettings(page:) - the Settings shortcut, a menu item, or an in-app link.
- **Expected:** The settings window is created the first time and reused on every later call. Its title is the literal "Settings". Its content size is 780 x 580 points. It has a close button and a minimise button and a full-size content view, and it is NOT resizable (the .resizable style mask bit is only inserted when `resizable` is true, and settings passes false). Window tabbing is disallowed. Closing the window does not release it, so its state survives a close and reopen.
- **Side effects:** Creates one NSWindow and one hosted SwiftUI view tree on first open
- **Persistence:** The settings window has no frame autosave name (unlike the main window's "DroppyCodeMainWindow"), so its position is not persisted across launches.
- **Failure cases:** None. The window is created unconditionally.
- **Cancellation:** not cancellable
- **Windows path:** A separate BrowserWindow (or equivalent modal-less child window) of exactly 780 x 580 client area, resizable: false, minimizable: true, with the same title. Windows has no window tabbing, so tabbingMode has no analogue and is dropped. isReleasedWhenClosed maps to hiding rather than destroying the window on close so its in-memory state survives. There is no menu bar (OD-0008 C3): the window opens from the Settings shortcut (Ctrl+, by default, OD-0008 B7), the command palette and the in-app links, never from a menu item. ED-063 (probe P7, porting/probes/p7/RESULT.md): on Avalonia 12.1.2 app-drawn caption controls declared only through Win32Properties.SetNonClientHitTestResult do nothing and right-click opens no system menu, so the window keeps WindowDecorations.Full with ExtendClientAreaToDecorationsHint, declares its leading-edge controls and drag region through SetNonClientHitTestResult, and a WndProc hook performs the controls' actions (WM_NCLBUTTONDOWN on a control swallowed, the SC_* command posted on WM_NCLBUTTONUP) and shows the system menu on WM_CONTEXTMENU and SC_KEYMENU. ED-063 records this for the main window; the settings window's caption controls are configured by the same WindowChrome.configure (WindowManager.swift:101), so the same hook serves them.
- **Verify by:** interaction test: open settings, assert window size and title; close and reopen, assert the same window instance state (selected page) is retained

### PR-SETTINGS-002 - Opening settings centres the window over the main window and clamps it onto that screen
- **Source:** DroppyCode/App/Window/WindowManager.swift:32-37 showSettings(page:) - calls centerOverMainWindow(window) then present(window) | DroppyCode/App/Window/WindowManager.swift:40-55 centerOverMainWindow(_:) - guard main window exists, isVisible and not miniaturized else window.center(); origin.x = (parent.midX - frame.width / 2).rounded(); origin.y = (parent.midY - frame.height / 2).rounded(); then clamped into (main.screen ?? NSScreen.main)?.visibleFrame with min/max on both axes; window.setFrame(frame, display: false) | DroppyCode/App/Window/WindowManager.swift:57-60 present(_:) - NSApp.activate(); window.makeKeyAndOrderFront(nil)
- **Preconditions:** Settings is being shown.
- **Action:** showSettings runs.
- **Expected:** If the main window exists, is visible and is not minimised, the settings window is moved so its centre is on the main window's centre, with both coordinates rounded to whole points, then clamped so its left edge is at least the screen's visible minX and its right edge at most visible maxX, and likewise vertically. If the main window is missing, hidden or minimised, the window is centred on screen instead. The frame is set with display: false. Then the application is activated and the window is made key and ordered front.
- **Side effects:** Activates the application
- **Persistence:** Nothing persisted.
- **Failure cases:** No screen available: the visibleFrame clamp is skipped (the optional chain yields nil) and the centred frame is used unclamped.
- **Cancellation:** not cancellable
- **Windows path:** Compute the centred rectangle against the main window's bounds and clamp into the work area of the display the main window is on (Electron screen.getDisplayMatching), then show and focus.
- **Verify by:** interaction test with a main window at a known position on a known display

### PR-THEME-039 - Changing the theme sets the window's colour scheme and the whole process appearance
- **Source:** DroppyCode/App/Window/WindowManager.swift:151 `.preferredColorScheme(model.settings.theme.spec.scheme)` | DroppyCode/App/Window/WindowManager.swift:152-159 `.onChange(of: model.settings.theme, initial: true) { _, theme in NSApp.appearance = switch theme.spec.scheme { case nil: nil; case .light: NSAppearance(named: .aqua); case .dark: NSAppearance(named: .darkAqua); @unknown default: nil } }`
- **Preconditions:** A hosted window exists.
- **Action:** The theme is chosen, and once at window creation (initial: true).
- **Expected:** The window tree's colour scheme is set to the theme's fixed scheme, or left to the OS when the theme is System. In the same step the process-wide appearance is set to light for a light theme, dark for a dark theme, and cleared (follow the OS) for System, so framework-drawn chrome outside the app's own views (menus, the window's own controls, panels) matches too.
- **Side effects:** Changes the process appearance, which repaints framework-drawn controls in every window including ones the app did not build
- **Persistence:** not persisted here; see PR-THEME-044
- **Failure cases:** An unknown future scheme value clears the process appearance rather than guessing.
- **Cancellation:** not cancellable
- **Windows path:** Platform boundary: set the app's dark-mode state for framework chrome (immersive dark mode on each window and the app's own resource theme) and clear it back to the OS setting for System. Both halves must happen: the in-app scheme alone leaves title bars and native menus out of step. The main window's chrome is built as ED-063 decides (probe P7): WindowDecorations.Full with ExtendClientAreaToDecorationsHint and a 44 px title bar, the leading-edge controls declared through Win32Properties.SetNonClientHitTestResult, and a WndProc hook that performs minimise, maximise, restore and close and shows the system menu. Owner ruling OD-0013: that window chrome is not accepted until the one-frame live-resize edge strip measured by probe P4 is gone; it is not downgraded to a deviation without the owner.
- **Verify by:** interaction test: picking Light while the OS is dark leaves no dark framework chrome anywhere; restart test: the process appearance is applied once at launch, not only on a later change

### PR-THEME-040 - The window root applies the theme accent as the view tint through a single unconditional branch
- **Source:** DroppyCode/App/Window/WindowManager.swift:177 `.modifier(ThemeTint(theme: model.settings.theme))` | DroppyCode/App/Window/WindowManager.swift:183-193 ThemeTint: `content.tint(theme.spec.accent)` with the comment that an `if` here rebuilt the whole window's content when a theme with an accent replaced one without, so Settings jumped back to its top on a theme change
- **Preconditions:** A hosted window exists.
- **Action:** The theme changes.
- **Expected:** The accent is applied as the tint for the whole window's content, so prominent buttons, toggles and progress indicators follow the theme. A nil accent is applied as a nil tint, which keeps the system accent. The modifier has exactly one branch: the view identity of the window content does not change across a theme change, so scroll positions and page state survive it.
- **Persistence:** not persisted
- **Failure cases:** None expressed in source.
- **Cancellation:** not cancellable
- **Windows path:** Apply the accent as one inherited value on the root. The single-branch rule is a real bug fix: any Windows implementation that swaps the subtree when the accent becomes non-nil will reset Settings' scroll position on a theme change.
- **Verify by:** interaction test: scroll Settings to the bottom, change the theme, the scroll position is unchanged

### PR-WIN-003 - The main window is built at most once and cached for the process lifetime
- **Source:** DroppyCode/App/Window/WindowManager.swift:15-16 private var mainWindow / settingsWindow: NSWindow? | DroppyCode/App/Window/WindowManager.swift:26-30 showMain(): `let window = mainWindow ?? makeMainWindow(); mainWindow = window; present(window)` | DroppyCode/App/Window/WindowManager.swift:98 window.isReleasedWhenClosed = false
- **Preconditions:** None.
- **Action:** showMain() is called, from launch, from the Window menu item, from a notification click, or from a dock reopen.
- **Expected:** The first call builds the window; every later call reuses the same instance. Closing the window does not destroy it (isReleasedWhenClosed = false), so a later showMain() shows the same window with its state intact. DEVIATION (OD-0008 C1): in the port, closing the MAIN window quits the app (after the upstream wait while a Hydra merge runs, PR-WIN-073), so the reuse applies within one run: every showMain() during the run, from the showMainWindow chord or a notification click, returns the same instance. Closing the Settings window still hides it for reuse.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** One cached top-level window handle per window. Closing the Settings window hides rather than destroys it, so its object and content survive a close/reopen cycle; closing the main window quits the app (OD-0008 C1).
- **Verify by:** interaction test: showMain() twice returns the same instance; closing Settings and reopening it retains its state; closing the main window ends the process

### PR-WIN-006 - The main window restores its last frame from the autosave name DroppyCodeMainWindow, and centers only when there is none

- **Preconditions:** None.
- **Action:** A window is created.
