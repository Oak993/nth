### PR-MCP-193 - The JavaScript bridge is installed beside the app's data and rewritten only when its text changed
- **Source:** DroppyCode/Services/MCP/MCPBridgeSource.swift:240-251 installBridge
- **Preconditions:** A Pi or Command Code session is starting.
- **Action:** installBridge runs.
- **Expected:** The base is the user's Application Support directory, falling back to <home>/Library/Application Support. The directory is <base>/<app display name>/MCP, created with intermediate directories. The file is droppy-mcp-bridge.mjs. Its bytes are the bridge source encoded as UTF-8; it is written atomically ONLY when the file's current contents differ, so a new build's bridge replaces the old one and an unchanged one is not touched. The file's URL is returned.
- **Side effects:** may create a directory and write one file
- **Persistence:** <app data>/MCP/droppy-mcp-bridge.mjs
- **Failure cases:** a directory or write failure throws to the caller, which is the session launch
- **Cancellation:** not cancellable
- **Windows path:** macOS writes to <Application Support>/<AppName>/MCP while the provider configs live in <Storage.root>/mcp; on a case-insensitive filesystem those collapse, so write droppy-mcp-bridge.mjs into %LOCALAPPDATA%\<AppName>\mcp\ and derive the base from the OS app-data root rather than the capture-aware storage root. Keep the write-only-if-changed check. The path handed to Pi and Command Code must be importable by Node: a bare drive-letter path fails in a dynamic import, so hand them a file:// URL. That is a genuine porting decision, not a parity break, since the macOS POSIX path works as is.
- **Verify by:** integration test asserting the file is written once and not rewritten on an unchanged relaunch

### PR-MCP-195 - The bridge connects each server with a 15-second cap, strictly one after another, and never kills a spawned child
- **Source:** DroppyCode/Services/MCP/MCPBridgeSource.swift:16-17 PROTOCOL_VERSION and CONNECT_TIMEOUT_MS | DroppyCode/Services/MCP/MCPBridgeSource.swift:50-56 withTimeout | DroppyCode/Services/MCP/MCPBridgeSource.swift:218-234 loadMCPTools
- **Preconditions:** A server map was read.
- **Action:** loadMCPTools runs.
- **Expected:** Server keys are iterated in object order with an await inside the loop, so connections are strictly sequential and N hung servers cost N times 15 seconds of host startup. A member is remote when it is an object whose "type" is "http" and whose "url" is a string, and local when it is an object whose "command" is a string; anything else is ignored. Each connection is raced against a 15000 ms timer that rejects with "timed out"; the timer is cleared either way. A failure prints "droppy mcp: skipping <server>: <message>" to standard error and moves on. There is NO kill, unref or signal anywhere in the file, so a server abandoned at the timeout keeps its spawned child alive for the whole lifetime of the Pi or Command Code host. This is upstream behavior and is reproduced.
- **Side effects:** spawns one child process per local server, some of which are never reaped; one console line per skipped server
- **Persistence:** none
- **Failure cases:** a hung server leaks its process and delays startup by 15 seconds
- **Cancellation:** not cancellable
- **Windows path:** Reproduce: the bridge .mjs must not kill children and must stay sequential. On Windows the leak is worse, since an orphaned npx or node child of a host process survives with no process-group kill to catch it. Record it as an upstream defect rather than fixing it inside shipped text.
- **Verify by:** integration test with a hung stand-in server asserting the 15-second skip and the surviving child
- **Upstream defect 14: reproduce it faithfully, do not fix it.**

### PR-MCP-196 - The bridge speaks a deliberately different dialect from the two Swift clients
- **Source:** DroppyCode/Services/MCP/MCPBridgeSource.swift:138 and :203 the clientInfo with no version | DroppyCode/Services/MCP/MCPBridgeSource.swift:154-158 postMessage's headers and lowercase session header | DroppyCode/Services/MCP/MCPBridgeSource.swift:161-172 the SSE acceptance rule | DroppyCode/Services/MCP/MCPBridgeSource.swift:35-48 contentText, describe and schemaOf
- **Preconditions:** The bridge is connecting a server.
- **Action:** It sends and receives messages.
- **Expected:** initialize params are {protocolVersion: "2025-06-18", capabilities: {}, clientInfo: {name: "Droppy Code"}} - NO version field. Remote requests send the entry's headers plus Content-Type: application/json and Accept: application/json, text/event-stream, and NO MCP-Protocol-Version header at all; the session header is the lowercase "mcp-session-id" on both send and read. An SSE frame is accepted when its data parses to an object having "result" OR "error" - not, as in the Swift clients, an "id" - and a data payload of "[DONE]" is skipped. A tool's description falls back to its own name when absent or empty, and its schema falls back to the literal {type: "object"} with no properties key. Result content maps a text item to its text and EVERY other item to the literal "[image]", joined with newlines; an isError result is returned as "Error: " plus that text or, when empty, "Error: tool failed"; a thrown error is returned as "Error: " plus its message rather than rejecting.
- **Side effects:** none beyond the requests themselves
- **Persistence:** none
- **Failure cases:** a tool failure is returned as an "Error: …" string, so the host sees a successful call with error text
- **Cancellation:** not cancellable
- **Windows path:** Copy the bridge text character for character, including the missing header, the version-less clientInfo, the lowercase session header, the result-or-error SSE rule and the "[image]" catch-all. Normalizing the three clients would change what remote servers see from Pi and Command Code.
- **Verify by:** contract fixture capturing the bridge's wire traffic against a stub server

### PR-MCP-197 - The bridge's stdio transport frames JSON lines, matches replies by id, and fails every pending call when the child dies
- **Source:** DroppyCode/Services/MCP/MCPBridgeSource.swift:76-152 connectStdio
- **Preconditions:** A local server member.
- **Action:** connectStdio runs.
- **Expected:** The child is spawned with the host environment plus the entry's env, and stdio ["pipe", "pipe", "ignore"] - stderr is discarded at the pipe level. Ids start at 0 and increment. stdout is accumulated and split on "\n"; each non-empty line is parsed and, when its id is pending, resolves that call. Writes are JSON plus a newline; a write error removes the pending entry and rejects. A child error event, or its exit, fails every pending call with {error: {message: <text>}} and rejects the connection once. The handshake is initialize, then the notifications/initialized notification with an empty params object, then tools/list paged until nextCursor is falsy, with an empty params object on the first page. Tools are then wrapped with a call function bound to tools/call.
- **Side effects:** spawns a child process that is never killed
- **Persistence:** none
- **Failure cases:** "process exited" is the message when the child dies
- **Cancellation:** not cancellable
- **Windows path:** Shipped JavaScript: copy verbatim. Note the spawn call passes a bare command name, which on Windows requires shell resolution for .cmd shims such as npx - that is a real platform boundary in text that must otherwise stay byte-identical, and it must be escalated rather than silently edited.
- **Verify by:** integration test against a scripted stdio stand-in server

### PR-MCP-198 - The bridge's remote transport carries a session id forward and swallows notification failures

- **Side effects:** one HTTP request per message
- **Persistence:** none
- **Failure cases:** "empty response (status <status>)" and "request failed"
- **Cancellation:** not cancellable
- **Windows path:** Shipped JavaScript: copy verbatim.
- **Verify by:** contract fixture against a stub remote server
