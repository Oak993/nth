### PR-PROVCLI-219 - Command Code interrupt terminates the process and relies on the CLI having persisted finished turns
- **Source:** DroppyCode/Services/Providers/CommandCodeSession.swift:229-235 - guard turnActive; interruptRequested = true; the comment at :232-233; process?.terminate() | porting/port_impacts.md entry 24
- **Preconditions:** turnActive is true.
- **Action:** The user stops the turn.
- **Expected:** With no active turn nothing happens. Otherwise interruptRequested is set and the process is TERMINATED - there is no interrupt message, because there is no protocol channel back to the CLI. The comment records that the CLI has already persisted every turn it finished, so the next --resume picks up from there, and that the signal ends the run with exit code 130.
- **Side effects:** Process termination
- **Persistence:** The CLI's own transcript holds every completed turn.
- **Failure cases:** Work in the interrupted turn is lost, which is expected.
- **Cancellation:** This IS the cancellation path.
- **Windows path:** Windows has no SIGTERM with delivery semantics; TerminateProcess is the practical equivalent and behaves like SIGKILL. That is acceptable for parity BECAUSE the source already relies only on the CLI's on-disk persistence of completed turns and nothing is flushed on the signal. The observable difference to accept is the EXIT CODE: the source keys on 130, and Windows reports whatever TerminateProcess was given, so the code that keys on 130 must be relaxed (port_impacts.md entry 24).
- **Verify by:** interaction test asserting an interrupted turn is reported as interrupted on Windows despite a different exit code
