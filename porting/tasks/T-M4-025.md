### PR-PROVACP-065 - The prompt is one text block followed by one image block per attached image
- **Source:** DroppyCode/Services/Providers/ACPSession.swift:176-179 - `var prompt: [JSONValue] = [["type": "text", "text": .string(input.text)]]; for (image, base64) in await Attachment.base64Images(input.images) { prompt.append(["type": "image", "mimeType": .string(image.mimeType), "data": .string(base64)]) }` | DroppyCode/Core/Models/Timeline.swift:100-105 - `base64Images` keeps only attachments where `isImage` and whose file could be read, returning (attachment, data.base64EncodedString()) | DroppyCode/Core/Models/Provider.swift:142 - `var supportsImages: Bool { self != .grok && self != .antigravity }`
- **Preconditions:** A turn with text and zero or more attachments.
- **Action:** send() builds the prompt array.
- **Expected:** Element 0 is always {"type": "text", "text": <the turn's text>}, even when the text is empty. Then, in attachment order, one {"type": "image", "mimeType": <the attachment's mime type>, "data": <base64, unpadded by any data: prefix>} per attachment that is an image AND whose file could be read. Non-image attachments and unreadable files are dropped silently. ACPSession itself does not consult supportsImages; Grok's exclusion is enforced upstream in the composer, so an image reaching ACPSession for Grok would still be sent.
- **Side effects:** Reads each attachment file from disk and holds its base64 in memory.
- **Persistence:** None.
- **Failure cases:** An unreadable attachment is omitted with no notice and no error.
- **Cancellation:** not cancellable
- **Windows path:** Same shape. Read the attachment as a Buffer and base64-encode it; do not prefix a data URL.
- **Verify by:** contract fixture (golden session/prompt frame with two images)

### PR-PROVACP-067 - session/prompt is fired in a detached task so send() returns immediately
- **Source:** DroppyCode/Services/Providers/ACPSession.swift:185-195 - `Task { [weak self] in do { let result = try await connection.request("session/prompt", ["sessionId": .string(sessionID), "prompt": .array(prompt)]); self?.finishPrompt(result["stopReason"]?.string, error: nil) } catch { self?.finishPrompt(nil, error: error) } }`
- **Preconditions:** The turn is armed.
- **Action:** send() launches the prompt.
- **Expected:** Method name is exactly "session/prompt" with exactly the parameters sessionId and prompt. send() returns as soon as the task is created, so the caller is not blocked for the length of the turn. The turn ends only when the request resolves: the reply's stopReason string, or nil plus the thrown error, goes to finishPrompt. The task holds only a weak reference to the session, so a deallocated session drops the completion.
- **Side effects:** One long-lived in-flight request for the duration of the turn.
- **Persistence:** None.
- **Failure cases:** A thrown error (including the connection closing) calls finishPrompt(nil, error:).
- **Cancellation:** The request is not cancelled by interrupt(); interruption is signalled out of band by session/cancel (PR-PROVACP-070) and the request still resolves, normally with stopReason "cancelled".
- **Windows path:** Same: a floating promise whose resolution and rejection both route into finishPrompt. Do not await it in the IPC handler.
- **Verify by:** contract fixture plus interaction test (send resolves before the turn completes)

### PR-PROVACP-070 - Interrupting sends session/cancel as a notification, after the permission answers
- **Source:** DroppyCode/Services/Providers/ACPSession.swift:206 - `connection.notify("session/cancel", ["sessionId": .string(sessionID)])`
- **Preconditions:** interrupt() has answered the pending permissions.
- **Action:** interrupt() finishes.
- **Expected:** A NOTIFICATION (no id, no reply expected) with method exactly "session/cancel" and the single parameter sessionId. The order matters: the cancelled permission answers are written first so the agent is not blocked waiting on them when it processes the cancel. The child process is not signalled or killed; interruption is entirely in-band.
- **Side effects:** One notification frame.
- **Persistence:** None.
- **Failure cases:** An agent that ignores session/cancel leaves the turn running until it finishes on its own; the app still reports .interrupted because cancelRequested is set.
- **Cancellation:** This is the cancellation path.
- **Windows path:** Same. Do not substitute a process signal; per port_impacts #24 the wire interrupt ports directly and Windows has no SIGTERM equivalent to fall back on.
- **Verify by:** contract fixture (frame order: responses then notification)
