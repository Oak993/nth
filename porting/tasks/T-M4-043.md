- **Preconditions:** The registry is loading the Antigravity model catalog through listModels(executable:environment:).
- **Action:** The list is non-empty.
- **Expected:** When NO option carries isDefault, the element at list.startIndex is REPLACED by a copy of itself with isDefault true. The copy carries id, name, detail, efforts and defaultEffort across unchanged, so the rewrite changes exactly one field. Nothing happens when some option already is the default, and nothing happens for an empty list because the throw above already returned.

### PR-PROVCLI-438 - Antigravity passes no MCP argv token; connected-server scoping comes only from the generated settings file
- **Source:** DroppyCode/Services/Providers/AntigravitySession.swift:76-81 - var arguments = ["--input-format", "stream-json", "--output-format", "stream-json", "--print-timeout", "30m", "--add-dir", workingDirectory,] | DroppyCode/Services/Providers/AntigravitySession.swift:82-87 - "// Scoping to the connected servers happens through the generated settings file `ProviderRegistry` hands the CLI in `GEMINI_CLI_SYSTEM_SETTINGS_PATH`: it lists those servers and no others, so the user's own stay untouched. `agy` has no `--allowed-mcp-server-names` flag (that one is Claude's) and its flag parser exits 2 with usage text on an unknown flag, which killed every Antigravity session as soon as one MCP server was connected." | DroppyCode/Services/Providers/AntigravitySession.swift:88-92 - the normalize flags, modeArguments(runtimeMode:interaction:) and the resume check follow the comment directly | DroppyCode/Services/Providers/ProviderRegistry.swift:277 - if provider == .antigravity, let path = MCPProviderConfig.geminiSettingsPath() { environment["GEMINI_CLI_SYSTEM_SETTINGS_PATH"] = path }
- **Preconditions:** An Antigravity session starting, with any number of MCP servers connected, including none.
- **Action:** start() builds the argv.
- **Expected:** The argv holds no MCP-related token whatever the MCP settings hold: no "--allowed-mcp-server-names" and no server id. After the fixed eight tokens (--input-format stream-json --output-format stream-json --print-timeout 30m --add-dir <workingDirectory>) come only the --model/--effort pair from normalize, the mode arguments and the resume arguments. MCPProviderConfig.connectedIDs() is not called. The only MCP scoping is the GEMINI_CLI_SYSTEM_SETTINGS_PATH environment variable that ProviderRegistry sets to MCPProviderConfig.geminiSettingsPath() only when that returns a path, which requires the generated gemini-settings.json to be readable, to parse, and to hold a non-empty "mcpServers" object; an existing file with no servers sets nothing (PR-PROVREG-102). A session therefore starts normally with one or more MCP servers connected.
- **Side effects:** None beyond the launch itself; the settings file is written by the registry, not here
- **Persistence:** none
- **Failure cases:** none: no MCP state can add a token the CLI rejects
- **Cancellation:** not cancellable
- **Windows path:** The settings path travels in the child process environment block, not on the command line, so no argv quoting applies to it.
- **Verify by:** contract fixture: start an Antigravity session with three connected MCP servers and assert the spawned argv contains no "--allowed-mcp-server-names" token and none of the three ids, and that the child environment carries GEMINI_CLI_SYSTEM_SETTINGS_PATH
