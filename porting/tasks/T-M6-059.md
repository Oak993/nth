### PR-RUNTIME-039 - recordSessionID holds the id back until the thread already has one
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:1574-1581 - guard let app else { return }; if app.thread(threadID)?.providerSessionID == nil { unsentSessionID = sessionID } else { app.updateThread(threadID) { $0.providerSessionID = sessionID } } | DroppyCode/App/Runtime/ThreadRuntime.swift:417-422 - the field comment explaining why
- **Preconditions:** A CLI session reported its id, either from start() (:1567) or from .sessionReady (:2082).
- **Action:** recordSessionID is called.
- **Expected:** A thread with no stored id keeps the new id in memory only, as unsentSessionID. A thread that already has one takes the new id at once, because a provider may hand out a new id for a conversation it picked up. The stated reason at :417-422 is that a warmed session replaced before its first message was resumed as "no conversation found" and the chat was told its agent lost a conversation that never existed.
- **Side effects:** Possibly a thread record write.
- **Persistence:** ChatThread.providerSessionID when the thread already had one; otherwise nothing is persisted yet.
- **Cancellation:** not cancellable
- **Windows path:** Two branches exactly as written. Both call sites (start and .sessionReady) must go through this one function.
- **Verify by:** unit - both branches; restart test for the held-back case

### PR-RUNTIME-040 - A started session that is no longer the live one throws CancellationError
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:1488 and :1565 - guard session === candidate, !Task.isCancelled else { throw CancellationError() }
- **Preconditions:** start() returned successfully.
- **Action:** The identity and cancellation guard runs before started is set.
- **Expected:** If the runtime's session is a different object, or the task was cancelled while start() ran, a CancellationError is thrown, started stays false, and the defer tears the candidate down with candidate.stop() (since session !== candidate) or releaseSession (since it is).
- **Side effects:** The candidate is stopped.
- **Persistence:** No session id is recorded.
- **Cancellation:** This is the cancellation behavior of ensureSession's happy path.
- **Windows path:** Reference identity plus a cancellation check. A value-equality test would let a replaced session claim the slot.
- **Verify by:** unit

### PR-RUNTIME-041 - The held-back session id reaches the thread only after a send returns without throwing
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:1335-1339 - if let unsentSessionID { self.unsentSessionID = nil; app.updateThread(threadID) { $0.providerSessionID = unsentSessionID } }, placed after session.send(...) and after the two epoch-guarded flag commits
- **Preconditions:** unsentSessionID is set and session.send(...) has just returned.
- **Action:** startTurn continues past the send.
- **Expected:** The id is cleared from memory and written to the thread record, which is what makes the conversation resumable from then on. A send that throws never reaches this line.
- **Side effects:** Thread record written.
- **Persistence:** ChatThread.providerSessionID.
- **Failure cases:** A send that throws leaves the id held back; a later releaseSession discards it entirely (PR-RUNTIME-042).
- **Cancellation:** A cancelled send throws and skips this.
- **Windows path:** Same placement: after the send, after the delivery-flag commits, before recordCommand.
- **Verify by:** restart test - send successfully, relaunch, assert resume; then fail a send and assert no id was stored

### PR-RUNTIME-043 - observe stamps each session with an epoch and drops events from any older one
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:2030-2037 - sessionEpoch += 1; let epoch = sessionEpoch; provider.onEvent = { [weak self] event in guard let self, self.sessionEpoch == epoch else { return }; self.handle(event) } | DroppyCode/App/Runtime/ThreadRuntime.swift:436-440 - the field comment: a CLI that closes long after it was let go used to end the turn that replaced it and take down the live session
- **Preconditions:** A session object has just been constructed.
- **Action:** observe(_:) is called from inside the session factory.
- **Expected:** The epoch counter is incremented and captured. Every event the session later emits is compared against the current counter and dropped if it no longer matches. The runtime holds the session weakly through the closure's [weak self], so a dropped runtime silences its sessions.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** A monotonically increasing integer captured per handler. This is the only thing that silences a closing session; clearing the handler alone is not enough (PR-RUNTIME-044).
- **Verify by:** unit - emit from a released session and assert no timeline change

### PR-RUNTIME-044 - releaseSession resets four fields before its early return and clears the handler one loop turn later
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:2042-2056 - the epoch bump, sessionSignature = nil, unsentSessionID = nil, antiSlopFallbackSent = false, continuationSent = false all precede guard let old = session else { return }; then session = nil; if stop { old.stop() }; Task { old.onEvent = nil } | DroppyCode/App/Runtime/ThreadRuntime.swift:2039-2041 and :2046-2049 - the comments stating both reasons
- **Preconditions:** Any caller lets a session go.
- **Action:** releaseSession(stop:) runs, with or without a live session.
- **Expected:** The four resets run even when there is no session, so a session that was never made still leaves the next one to deliver the anti-slop policy and the forwarded continuation. When a session exists it is detached from the runtime, stopped only when stop is true, and its handler is cleared asynchronously on the next loop turn because a closing session usually speaks from inside that very handler; the epoch check, not the nil handler, is what actually silences it.
- **Side effects:** Provider process or connection stopped when stop is true.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Keep the ordering and the deferred handler clear. Clearing the handler synchronously inside an event dispatch can mutate the collection being iterated.
- **Verify by:** unit - call with no session and assert both delivery flags reset

### PR-RUNTIME-045 - stopSession releases, ends native heads, forces a save and closes the running turn as interrupted
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:2058-2075 - releaseSession(stop: true); stopNativeHeads(); guard phase != .idle else { return }; saveNow(); let turnID = currentTurnID; currentTurnID = nil; Task { await finishTurn(status: .interrupted, turnID: turnID) }
- **Preconditions:** A caller wants the session gone (revert's Codex and Copilot arms, the Claude arm, or AppModel releasing a deferred session).
- **Action:** stopSession() is called.
- **Expected:** The session is stopped and its events are already being dropped by the epoch, so nothing else will close the turn; the turn is therefore closed by hand as .interrupted. currentTurnID is cleared before finishTurn is scheduled, exactly as a stop during a start does, so a message still on its way never goes. saveNow() runs first because the turn's events may not have been written yet and the five-second timer may not outlive the runtime.
- **Side effects:** Session stopped; head threads finished; thread document written.
- **Persistence:** Full thread document write through saveNow.
- **Failure cases:** An idle runtime returns after the release and the head teardown, with no save and no turn to close.
- **Cancellation:** not cancellable
- **Windows path:** Same order: release, heads, idle check, save, take the id, clear it, finish.
- **Verify by:** integration test - stop a running turn's session and assert one .turnEnd row with status interrupted and a written document

### PR-RUNTIME-046 - warmSession starts a CLI session ahead of the first message under nine conditions
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:1380-1391 - guard phase == .idle, session == nil, warmup == nil, !isReverting, let app, let thread = app.thread(threadID), !thread.isArchived, !thread.provider.isAPIKeyBased, let project = app.project(thread.projectID); directory = thread.worktreePath ?? project.path; warmup = Task { await ensureModel(thread); guard phase == .idle, session == nil else { warmup = nil; return }; if (try? await ensureSession(directory: directory)) != nil { warmup = nil } } | DroppyCode/App/Runtime/ThreadRuntime.swift:1376-1379 - the comment: about half a second for claude
- **Preconditions:** The user has focused or opened a chat that is idle, unarchived, sessionless and not reverting, on a CLI provider.
- **Action:** warmSession() is called.
- **Expected:** A detached warm-up task loads the model default and then starts the session. API-key providers are excluded, so they never warm and the only ensureSession caller for them is inside startTurn. A send in the meantime waits for warmup rather than starting a second process (PR-RUNTIME-064).
- **Side effects:** Provider process started; possibly a model catalog load and a thread record write through ensureModel.
- **Persistence:** Through ensureModel, possibly ChatThread.model and ChatThread.effort.
- **Failure cases:** Any guard failing is a silent no-op.
- **Cancellation:** The warm-up task is never cancelled by this file; its inner re-check of phase and session is what abandons it.
- **Windows path:** Same guards. The half-second saving is larger on Windows, where process creation is more expensive.
- **Verify by:** interaction test
