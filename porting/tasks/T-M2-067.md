### PR-PROVACP-164 - PendingReplies registers a request id before sending, honours cancellation, and can time out to a value or a cancellation error
- **Source:** DroppyCode/Core/Support/PendingReplies.swift:3-6 - `/// Replies waiting on a request id. The id is registered before `send` runs, so a fast` / `/// reply can't arrive before anyone is waiting for it.` / `@MainActor` / `final class PendingReplies<Value: Sendable> {` | DroppyCode/Core/Support/PendingReplies.swift:9-36 register(_:timeout:timeoutValue:send:) - `try Task.checkCancellation()` (:17); `continuations[id] = continuation` then `send()` (:19-20); with a timeout, `Task { try? await Task.sleep(for: timeout); if let timeoutValue { self.resolve(id, timeoutValue) } else { self.fail(id, CancellationError()) } }` (:21-29); `onCancel: { Task { @MainActor [weak self] in self?.continuations.removeValue(forKey: id)?.resume(throwing: CancellationError()) } }` (:31-35) | DroppyCode/Services/Providers/ClaudeSession.swift:306 and DroppyCode/Services/Providers/PiSession.swift:260-270 - the two users
- **Preconditions:** A caller registers a request id, optionally with a timeout and a timeout value, and a send closure.
- **Action:** register runs.
- **Expected:** If the calling task is already cancelled, register throws CancellationError and neither stores the id nor calls send. Otherwise the waiting continuation is stored under the id first and send runs after it, so a reply that comes back at once always finds its waiter. With a timeout, a separate task that does not inherit the caller's cancellation sleeps for that duration and then resolves the id with timeoutValue when one was given, or fails it with CancellationError when none was; if the id was already answered this does nothing. When the calling task is cancelled while waiting, a main-actor task removes the entry and resumes the waiter by throwing CancellationError; a reply that won the race has already resumed it, and then the removal finds nothing.
- **Side effects:** Calls send exactly once when not already cancelled; Starts one timer task per registration that has a timeout
- **Persistence:** none
- **Failure cases:** Already cancelled: CancellationError, send not called; Timeout without timeoutValue: CancellationError; Cancelled while waiting: CancellationError
- **Cancellation:** Cancellation is honoured before the send and while waiting; the timeout task is not cancelled with the caller and runs to the end of its sleep.
- **Windows path:** A main-thread-confined map from string id to a waiter (for example a TaskCompletionSource) with the same order: cancellation check, store, send, optional timer, and removal plus a cancellation fault on cancel. The Swift CancellationError maps to the port's cancellation error (B3_PLAN.md section 3 N1, Core.Support.PendingReplies).
- **Verify by:** unit: pre-cancelled (no send, CancellationError); a reply sent synchronously from inside send is received; a timeout with and without timeoutValue; cancellation while waiting; a reply racing a cancellation

### PR-PROVACP-165 - PendingReplies resolve and fail report whether an id was waiting; resolveAll and failAll empty the map before resuming
- **Source:** DroppyCode/Core/Support/PendingReplies.swift:38-50 - `@discardableResult func resolve(_ id: String, _ value: Value) -> Bool {` / `guard let continuation = continuations.removeValue(forKey: id) else { return false }` / `continuation.resume(returning: value)` / `return true`, and `fail(_:_:)` the same with `resume(throwing: error)` | DroppyCode/Core/Support/PendingReplies.swift:52-62 - `func resolveAll(_ value: Value) {` / `let waiting = Array(continuations.values)` / `continuations.removeAll()` / `for continuation in waiting { continuation.resume(returning: value) }`, and `failAll(_:)` the same with `resume(throwing: error)` | DroppyCode/Services/Providers/ClaudeSession.swift:338, :340, :684 and DroppyCode/Services/Providers/PiSession.swift:288-294, :594 - the callers
- **Preconditions:** Zero or more requests are waiting.
- **Action:** A reply, an error, or a close arrives.
- **Expected:** resolve(id, value) and fail(id, error) remove the waiter for that id and resume it with the value or the error, returning true; when no waiter has that id they do nothing and return false. resolveAll(value) and failAll(error) first take a copy of every waiter, then empty the map, then resume each copied waiter with the value or the error, so a waiter resumed this way can register again without being swept up by the same call. The order in which the waiters are resumed is the dictionary's, which is unspecified.
- **Side effects:** Resumes waiting callers
- **Persistence:** none
- **Failure cases:** An unknown id is ignored (false)
- **Cancellation:** not cancellable
- **Windows path:** The same semantics over the port's waiter map; the resume order across waiters must not be relied on.
- **Verify by:** unit: resolve and fail on a known and an unknown id (true and false); resolveAll and failAll with several waiters, and with a waiter that registers again when resumed
