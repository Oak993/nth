### PR-TERM-099 - The write classification decides whether a tool row snapshots the working tree, and whether Command Code auto-approves a shell call
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:3341-3348 watchCommand - the comment says a command that cannot write needs no snapshots at all; the guard requires mayWriteFiles(call.title), a repository, and a before-tree, then stores the tree task, clears settledTree and bumps treeEpoch | DroppyCode/App/Runtime/ThreadRuntime.swift:3447 - the same guard on the Hydra command path | DroppyCode/Services/Providers/CommandCodeSession.swift:708-711 - in .auto runtime mode, the tools "shell_command", "powershell" and "monitor_command" are auto-approved exactly when !mayWriteFiles(input["command"]?.string ?? "")
- **Preconditions:** An agent issues a shell tool call.
- **Action:** The classifier answers.
- **Expected:** A writer answer makes the runtime take a before-tree snapshot so the command's row can report its file edits, and makes Command Code in auto mode withhold approval so the user is asked. A reader answer skips the snapshot entirely and, in auto mode, approves the call without asking. A missing or non-string command field is treated as the empty string, which reads, so such a call is auto-approved.
- **Side effects:** A writer answer costs several git processes over the checkout.
- **Persistence:** None directly; the resulting diff becomes part of the turn's record.
- **Failure cases:** A misclassified reader means an edit is never reported on that row, and in auto mode means a writing command is approved without asking. This is the reason the lists must be ported verbatim.
- **Cancellation:** not cancellable
- **Windows path:** Same two consumers with the same predicate, including the OD-0008 A8 corrections (PR-TERM-098, PR-TERM-118, PR-TERM-119), so the corrected commands are both snapshotted and asked for in .auto. The three Command Code tool names are protocol constants and are unchanged.
- **Verify by:** integration test over a reading and a writing command in both consumers

### PR-USAGE-082 - A reported usage event invalidates the cached credits and, for API-key providers, the cached plan limits
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:2177-2184 case .usage(let usage): self.usage = usage; saveRevision += 1; if let provider = thread?.provider { app?.providers.invalidateCredits(provider); app?.providers.invalidatePlanLimits(provider) } | DroppyCode/Services/Providers/ProviderRegistry.swift:702-707 invalidateCredits - guard exposesCredits; creditsFetchedAt[provider] = nil | DroppyCode/Services/Providers/ProviderRegistry.swift:709-715 invalidatePlanLimits - guard provider.isAPIKeyBased && exposesLimits; limitsFetchedAt[provider] = nil
- **Preconditions:** A provider session reports context usage for a thread.
- **Action:** The runtime handles the usage event.
- **Expected:** The thread's usage is replaced, the save revision is bumped so the thread document is written, and the provider's cached fetch timestamps are cleared so the next panel open reads fresh numbers rather than pre-turn ones. Credits are invalidated for any provider that exposes them; plan limits are invalidated only for API-key providers that expose limits, which in the pinned source is Z.ai alone. The cached values themselves are not cleared, only their freshness.
- **Side effects:** Schedules a thread document save.
- **Persistence:** The usage value is persisted in the thread document (PR-USAGE-084).
- **Failure cases:** A CLI-based provider's plan limits are NOT invalidated by a turn, so its windows can still be up to 60 seconds stale after a turn.
- **Cancellation:** not cancellable
- **Windows path:** Same event handling and the same two guards.
- **Verify by:** unit test on both invalidation guards plus an interaction test that a turn makes the next popover open re-read
