# T-M0-003: P4

| Field | Value |
| --- | --- |
| Milestone | M0: probes that must pass before production code |
| Risk | **STANDARD** |
| Who can run it | **A HUMAN at an unlocked Windows desktop.** It needs a visible, composited window. A headless worker cannot do it: a locked or disconnected session composites nothing, which was measured on this machine. |

## The probe, verbatim from the stack decision

P4 - Acrylic plus extended client area plus live resize, all three at once. Drag-resize a 1320x860 frameless acrylic window running P1's glass surface and a spring animation. PASS: no margin artefact at any edge (WindowImpl.cs:1183 / issue #8316), and the spring shows no visible stall, snap or discontinuity across WM_ENTERSIZEMOVE and WM_EXITSIZEMOVE, with per-frame times logged. FAIL: record 'animation not held during live resize' as a named deviation and decide the reduced-fidelity resize behaviour BEFORE the chrome is designed.

## Rules

- Read `WORKER_BRIEF.md` first. Model the probe on `porting/probes/p1-glass/`, which passed.
- A probe PROVES or DISPROVES one capability. Report the measured result, whichever it is.
  A FAIL reported honestly is a valuable result. A PASS you did not measure is worthless.
- Build a control case that must fail when the thing under test is absent, as P1 did with
  its tint-only render. Without one, a PASS cannot be trusted.
- Never send a prompt to a real AI CLI; `--version` or `--help` only.
- Set `MARROW_PORT_DATA_DIR` to a throwaway folder before running anything.
