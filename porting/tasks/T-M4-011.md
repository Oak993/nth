### PR-MCP-169 - writeAll deletes all four provider config files when nothing is enabled, and otherwise writes all four
- **Source:** DroppyCode/Services/MCP/MCPProviderConfig.swift:148-159 writeAll | DroppyCode/Services/MCP/MCPProviderConfig.swift:240-243 write
- **Preconditions:** exportAll computed the enabled list.
- **Action:** writeAll runs.

A non-empty list writes all four, in the order claude, codex, copilot, gemini. Each write creates the parent directory first and replaces the file atomically with pretty-printed JSON. Deletion is what makes claudeConfigPath, geminiSettingsPath, copilotConfigJSON, codexOverrides, connectedIDs and acpServers all degrade to nil or empty together, so a session started with nothing connected passes no MCP flags at all. proxy-port and managed.json are never touched by writeAll.

- **Persistence:** the four provider config files
- **Failure cases:** individual write or delete failures are swallowed, which can leave a stale file that a provider then reads
- **Cancellation:** not cancellable
- **Windows path:** Same four names, same delete-on-empty rule, same atomic replace. Never delete proxy-port here.
- **Verify by:** integration test toggling the last server off and asserting all four files are gone

### PR-MCP-170 - acpServers rebuilds a JSON array from claude.json, in sorted id order
- **Source:** DroppyCode/Services/MCP/MCPProviderConfig.swift:77-124 acpServers(allowsHTTP:)
- **Preconditions:** An ACP session is starting.
- **Action:** acpServers is called with the agent's HTTP capability.
- **Expected:** Re-read <data root>/mcp/claude.json; a missing, unparseable or empty mcpServers object yields an empty array. Ids are iterated in sorted order. An entry counts as remote when its "type" is "http" OR it has a "url" string. Remote with allowsHTTP true: {"type": "http", "name": <id>, "url": <url>, "headers": [{"name": <k>, "value": <v>}, ...]} with header keys sorted. Remote with allowsHTTP false: rewritten as a stdio launch {"name": <id>, "command": "npx", "args": ["-y", "mcp-remote", <url>, then per sorted header key "--header" and the single string "<key>: <value>" with a colon and one space], "env": []} - env is an empty ARRAY, not an object, and there is no type key. Local: {"name": <id>, "command": <command or empty string>, "args": <the raw JSON array from the file>, "env": [{"name": <k>, "value": <v>}, ...]} with env keys sorted. This is the only producer of "mcp-remote" in the source, and its output never becomes a resolved server.
- **Side effects:** one file read
- **Persistence:** none; the array is passed as a session parameter
- **Failure cases:** a missing file yields an empty array and the session gets no MCP servers
- **Cancellation:** not cancellable
- **Windows path:** Same shapes, including the empty env array and the "<key>: <value>" header string. It must run AFTER writeAll, because it reads the file.
- **Verify by:** contract fixture over both capability values

### PR-MCP-171 - Codex user servers named in ~/.codex/config.toml are switched off for the session by plain name only
- **Source:** DroppyCode/Services/MCP/MCPProviderConfig.swift:161-197 codexUserServerNames | DroppyCode/Services/MCP/MCPProviderConfig.swift:199-210 codexOverrides
- **Preconditions:** A Codex session is starting.
- **Action:** codexOverrides is built.
- **Expected:** Return nil unless codex.json parses and its mcp_servers object is non-empty. Otherwise take that object and, for every name from codexUserServerNames that is not already a key, add {"enabled": false}. codexUserServerNames parses ~/.codex/config.toml line by line: trim; require the prefix "[mcp_servers."; drop it; require a "]" to exist and the text after it to be empty or start with "#"; take the text before the "]"; when it starts with a single or double quote the name is the content up to the matching same quote, else when it contains a dot the name is the part before the first dot, else the whole segment; trim it; DROP it entirely when it is empty or contains any whitespace, "[", "]", single quote, double quote, comma or dot; collect into a set and return it sorted. The file itself is never modified: enabled=false is a config override for the session only. A nested table path such as imap-email.env would name an entry that exists nowhere in the user's config and make Codex reject its whole configuration, failing every turn at once, which is why only bare names survive.
- **Side effects:** one read of ~/.codex/config.toml
- **Persistence:** none; the user's own config file is never written
- **Failure cases:** an unreadable config.toml yields an empty list and no overrides are added
- **Cancellation:** not cancellable
- **Windows path:** Same line parser and the same six-character rejection set. The home directory is the Windows user profile; the path is %USERPROFILE%\.codex\config.toml.
- **Verify by:** unit over quoted, dotted, commented and malformed table headers
