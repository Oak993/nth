### PR-THEME-044 - The chosen theme is written to the "appTheme" default on every change, and mirrored into the theme manager in the same step
- **Source:** DroppyCode/App/AppSettings.swift:135 `static let appTheme = "appTheme"` | DroppyCode/App/AppSettings.swift:286-291 `var theme: AppTheme { didSet { defaults.set(theme.rawValue, forKey: Key.appTheme); ThemeManager.current = theme } }`
- **Preconditions:** Settings are loaded.
- **Action:** The user picks a theme.
- **Expected:** The theme's raw value string is written to the key "appTheme" at once (no debounce, no save button), and ThemeManager.current is set to the same theme, which rebuilds the spec and posts the change notification (PR-THEME-036). The order is: persist, then broadcast.
- **Side effects:** Writes the "appTheme" default; Triggers the theme-change broadcast and every repaint it causes
- **Persistence:** The theme raw value under the exact key "appTheme", written immediately on change.
- **Failure cases:** None expressed in source: the write has no error branch.
- **Cancellation:** not cancellable
- **Windows path:** Persist the same key name and the same camelCase token values, so a settings file written by either build reads on the other.
- **Verify by:** restart test: pick a theme, restart, the same theme is active; unit: the persisted key name and value

### PR-THEME-045 - At launch the theme is read from "appTheme", falling back to the legacy "appearance" key and then to System
- **Source:** DroppyCode/App/AppSettings.swift:137 `static let appearance = "appearance"` | DroppyCode/App/AppSettings.swift:727-732 comment "The old System/Light/Dark choice maps straight onto the same themes." then `let initialTheme = AppTheme(rawValue: defaults.string(forKey: Key.appTheme) ?? "") ?? AppTheme(rawValue: defaults.string(forKey: Key.appearance) ?? "") ?? .system`, then `theme = initialTheme` and `ThemeManager.current = initialTheme`
- **Preconditions:** The app is starting and settings are being constructed.
- **Action:** The stored theme is read.
- **Expected:** The value of "appTheme" is parsed as a theme id. If it is missing or not one of the 26 ids, the legacy "appearance" key is parsed the same way (its old values "system", "light" and "dark" are still valid theme ids). If that also fails, the theme is System. The resolved theme is assigned to the settings property and mirrored into the theme manager during initialization.
- **Side effects:** Sets ThemeManager.current during settings construction, before any window exists
- **Persistence:** reads "appTheme", then "appearance"; writes nothing at launch
- **Failure cases:** "appTheme" holds an unknown string: falls through to "appearance".; Both keys missing or unknown: System.; Note the legacy key is read but never written, so a migration is one-way; the old key is left in place.
- **Cancellation:** not cancellable
- **Windows path:** Keep both key names and the same two-step fallback, so a profile written by an older build still opens on its chosen appearance. The legacy key must not be deleted on read: upstream leaves it.
- **Verify by:** restart test with only "appearance" set to "dark"; unit: the three fallback branches
