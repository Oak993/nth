### PR-STORE-123 - Image thumbnails are keyed by path, pixel size and the square flag, at a fixed 2x scale
- **Source:** DroppyCode/Core/Support/ThumbnailCache.swift:22-26 - func thumbnail(for path: String, pointSize: CGFloat, fillingSquare: Bool = false) async -> Thumbnail? { guard !Task.isCancelled else { return nil }; let pixels = max(1, Int((pointSize * 2).rounded(.up))); let key = "\(path)#\(pixels)#\(fillingSquare)"; if let cached = thumbnails.value(for: key) { return cached } } | DroppyCode/Core/Support/ThumbnailCache.swift:16 - private var thumbnails = RecentCache<String, Thumbnail>(limit: 120, costLimit: 32 * 1_024 * 1_024)
- **Preconditions:** A message or popover is showing an image attachment.
- **Action:** Requesting a thumbnail.
- **Expected:** The requested pixel size is always point size times two, rounded up, clamped to at least 1: the scale factor is hard-coded, not taken from the display. The cache key is the path, "#", the pixel count, "#", and the boolean rendered by string interpolation as "true" or "false". The cache holds 120 entries or 33554432 bytes of decoded bitmap, whichever binds first. A cancelled caller gets nil before anything else happens.
- **Persistence:** none; in-memory only
- **Failure cases:** A display at 1x or 3x still gets a 2x thumbnail, which is source behaviour.
- **Cancellation:** not cancellable
- **Windows path:** Keep the hard-coded 2x rather than substituting the Windows DPI scale: changing it changes memory use and image sharpness across every attachment row. Same key format, same two limits.
- **Verify by:** unit on the key format plus a capture comparison of an attachment row

### PR-STORE-124 - Concurrent requests for the same thumbnail share one decode, and a caller giving up does not cancel it
- **Source:** DroppyCode/Core/Support/ThumbnailCache.swift:5-8 - doc comment "Downsampled image attachments, decoded off the main actor and kept for reuse... The decodes run outside the actor, so fifteen thumbnails for the downloads popover decode side by side instead of one behind the other, and callers asking for the same thumbnail share one decode." | DroppyCode/Core/Support/ThumbnailCache.swift:27-42 - if let pending = inFlight[key] { task = pending } else { decodes += 1; task = Task.detached(priority: .userInitiated) { Self.decode(...) }; inFlight[key] = task }; comment "A caller giving up waits the decode out rather than cancelling it for the others."; let thumbnail = await task.value; if inFlight[key] == task { inFlight[key] = nil; if let thumbnail { thumbnails.insert(thumbnail, for: key, cost: thumbnail.image.bytesPerRow * thumbnail.image.height) } }; return Task.isCancelled ? nil : thumbnail | DroppyCode/Core/Support/ThumbnailCache.swift:20 - private(set) var decodes = 0, "How many decodes have started, for tests of the sharing."
- **Preconditions:** Several rows ask for the same image at the same size at once.
- **Action:** The requests arrive.
- **Expected:** The first starts a detached user-initiated decode and records it by key; the others await the same task. The started-decode counter increments once. The in-flight entry is cleared and the result cached only when the map still holds that same task, so a superseded decode never evicts a newer one. The cache cost charged is bytesPerRow times height, the real decoded bitmap size. A caller cancelled while waiting gets nil, but the decode still completes and is still cached for the others.
- **Side effects:** One background decode per distinct key; Reads the image file from disk
- **Persistence:** none
- **Failure cases:** A decode that returns nil clears the in-flight entry without caching anything, so the next request retries.
- **Cancellation:** Cancelling a caller returns nil to that caller only; the shared decode is deliberately not cancelled.
- **Windows path:** Same coalescing by key, the same deliberate refusal to cancel a shared decode, and the same cost measure. The decodes counter is a test hook and must remain readable by tests.
- **Verify by:** unit asserting one decode for fifteen simultaneous requests

### PR-STORE-125 - Thumbnail decoding applies the EXIF transform, caches immediately and never upsizes beyond the request
- **Source:** DroppyCode/Core/Support/ThumbnailCache.swift:44-62 - private nonisolated static func decode(_ path:pixels:fillingSquare:) -> Thumbnail? { guard let source = CGImageSourceCreateWithURL(URL(fileURLWithPath: path) as CFURL, nil) else { return nil }; ... options kCGImageSourceCreateThumbnailFromImageAlways: true, kCGImageSourceCreateThumbnailWithTransform: true, kCGImageSourceShouldCacheImmediately: true, kCGImageSourceThumbnailMaxPixelSize: pixels; guard let image = CGImageSourceCreateThumbnailAtIndex(source, 0, options) else { return nil }; return Thumbnail(image: image) }
- **Preconditions:** A decode is running.
- **Action:** Decoding the file at index 0.
- **Expected:** Always build a thumbnail from the full image rather than using an embedded one, apply the EXIF orientation, decode the bitmap immediately rather than lazily at draw time, and bound the longest edge to the requested pixel count. A file that cannot be opened, or an image that cannot be built, yields nil.
- **Side effects:** Reads and decodes the image file
- **Persistence:** none
- **Failure cases:** A deleted attachment file yields nil and the row shows no image.
- **Cancellation:** not cancellable
- **Windows path:** Same four decode behaviours. Immediate decoding is load-bearing: a lazily decoded bitmap would move the decode cost onto the UI thread at draw time, which is exactly what this cache exists to avoid.
- **Verify by:** unit over a rotated JPEG fixture

### PR-STORE-126 - A square-filling thumbnail is enlarged by the aspect ratio and clamped to 2048 pixels

- **Preconditions:** A thumbnail is requested with fillingSquare true.
- **Action:** Decoding.
- **Expected:** The requested pixel size is multiplied by the aspect ratio (long edge over short edge), rounded up, and clamped to a maximum of 2048, so the short edge still fills the square at the requested size. A source with no readable dimensions, or a zero short edge, falls through and uses the unmodified pixel count.
- **Persistence:** none
- **Failure cases:** A very wide panorama is clamped at 2048 and therefore does not fill the square at full sharpness. Reproduce.
- **Cancellation:** not cancellable
- **Windows path:** Same formula, same ceiling and the same literal 2048 clamp.
- **Verify by:** unit over a 4:1 image

- **Preconditions:** A row has already shown this image at this size.
- **Action:** The row scrolls back into view.

- **Cancellation:** not cancellable

- **Verify by:** unit on both key formats
