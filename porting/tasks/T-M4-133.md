### PR-PROVREG-155 - An API-key catalog load installs the seed first, needs a non-empty key, and marks the attempt before the fetch
- **Source:** DroppyCode/Services/Providers/ProviderRegistry.swift:646-672 loadAPICatalog - the seed is chosen by provider and the function returns for any provider without one; when the current list is empty the seed is installed; the loading flag is set and cleared by defer; an empty key returns before any fetch; attemptedCatalogs is inserted BEFORE the fetch, unlike the CLI path; a non-empty result updates the catalog and stores the date
- **Preconditions:** The provider is deepseek, meta or zai.
- **Action:** loadAPICatalog runs.
- **Expected:** Order is: pick the seed, install it if the catalog is empty, set the loading flag, read the key, return early when empty, mark the attempt, fetch, and update only on a non-empty list. Because the attempt is marked before the fetch, a failed API-key catalog fetch is NOT retried this launch, which is the opposite of the CLI path.
- **Side effects:** One network request per fetch.
- **Persistence:** A delivered list is written to both catalog keys.
- **Failure cases:** Empty key: the seed stays and the attempt is NOT marked, because the early return precedes the insert.; Fetch throws or returns empty: nothing is updated but the attempt is already marked, so no retry this launch.
- **Cancellation:** not cancellable
- **Windows path:** Same ordering, including the asymmetry with the CLI path.
- **Verify by:** contract fixture against mock endpoints, asserting the retry asymmetry

### PR-PROVREG-156 - updateCatalog ignores an empty list and a list identical to the current one, then rewrites the whole cache blob
- **Source:** DroppyCode/Services/Providers/ProviderRegistry.swift:796-812 updateCatalog - after the provider-specific merge, the guard requires the list to be non-empty and different from the stored one; the catalog is assigned; then the ENTIRE catalogs dictionary is re-encoded and written to the cache key
- **Preconditions:** A catalog arrived.
- **Action:** updateCatalog is called.
- **Expected:** No write happens for an empty list or an unchanged list. When a write does happen, every provider's catalog is re-encoded together, so there is no per-provider partial write.
- **Side effects:** One settings write of the full blob.
- **Persistence:** Key "providerModelCatalogs", the whole dictionary.
- **Failure cases:** Encoding failure: nothing is written and the in-memory catalog is still updated, so the two disagree until the next successful write.; A crash mid-write loses every provider's cache together.
- **Cancellation:** not cancellable
- **Windows path:** Same whole-blob write, which is upstream behavior and must not be optimised into per-provider writes.
- **Verify by:** unit plus restart test

### PR-PROVREG-164 - A forced limits read arriving while a read is in flight is queued, not dropped, and runs when the in-flight read finishes

- **Preconditions:** A limits read is in flight for the provider.

### PR-PROVREG-167 - A limits read is bounded by a 25 second watchdog that clears the loading flag and drains the forced queue
- **Source:** DroppyCode/Services/Providers/ProviderRegistry.swift:696 and :629 - a watchdog task sleeps 25 seconds, then removes the provider from loadingLimits and calls drainedForcedRead | DroppyCode/Services/Providers/ProviderRegistry.swift:698 and :631 - the read task cancels the watchdog in its defer, removes the loading flag and drains the queue
- **Preconditions:** A limits read has started.
- **Action:** The read takes longer than 25 seconds.
- **Expected:** After exactly 25 seconds the spinner stops and the provider is no longer marked loading, so a later read is allowed even though the first is still running. The read itself is not cancelled and may still deliver a result afterwards.
- **Side effects:** A second concurrent read becomes possible after the watchdog fires.

- **Failure cases:** The watchdog firing and the read completing both call drainedForcedRead; the set removal makes the second a no-op.
- **Cancellation:** The watchdog is cancelled when the read finishes first. The read task itself is never cancelled by the watchdog.
- **Windows path:** Same 25 second bound and the same non-cancelling semantics.
- **Verify by:** interaction test with a hung reader
