## Requirements

### PR-LAUNCH-001 - Launch prologue runs six steps in a fixed, load-bearing order before any window exists
- **Source:** DroppyCode/App/DroppyCodeApp.swift:3-19 @main struct DroppyCodeApp.init() - the whole prologue, in order: DCInstallNotificationGuard(), signal(SIGPIPE, SIG_IGN), WebsiteCaptures.prepare(), LegacyMigration.run(), HangWatchdog.start(), SwitchLatency.start() | DroppyCode/App/DroppyCodeApp.swift:8-9 comment - 'Before anything posts a notification' | DroppyCode/App/DroppyCodeApp.swift:13 comment - 'Before anything reads settings or the library.'
- **Preconditions:** Process has started; no window, no AppModel and no settings read has happened yet. AppDelegate is attached with @NSApplicationDelegateAdaptor (DroppyCodeApp.swift:5) but applicationDidFinishLaunching has not run.
- **Action:** The process enters the app entry point.
- **Expected:** Exactly these six steps run, in this order, synchronously on the main thread, before the scene body is evaluated and before applicationDidFinishLaunching: (1) DCInstallNotificationGuard(), (2) signal(SIGPIPE, SIG_IGN), (3) WebsiteCaptures.prepare(), (4) LegacyMigration.run(), (5) HangWatchdog.start(), (6) SwitchLatency.start(). No other work happens first. The ordering is stated by the source's own comments as load-bearing: the notification guard must precede any posted notification, and the capture prep plus legacy migration must precede any read of settings or the library.
- **Side effects:** Installs a process-wide NSNotificationCenter guard (see PR-LAUNCH-002); Changes the SIGPIPE disposition process-wide (see PR-LAUNCH-003); May create capture scratch directories and wipe a defaults suite (see PR-LAUNCH-008); May copy UserDefaults keys and move an Application Support folder (see PR-LAUNCH-011, PR-LAUNCH-012); Spawns the hang-watchdog background thread (see PR-LAUNCH-014)
- **Persistence:** Only through the steps it calls; the prologue itself persists nothing.
- **Failure cases:** No step reports failure to the caller; every one of the six is a void call with its own internal try?/guard handling. A failure inside any step cannot abort launch.
- **Cancellation:** not cancellable
- **Windows path:** A single startup function called before the main window is created and before the settings/library store is first touched, keeping the same relative order for the steps that are ported. Step 1 (an Objective-C exception net) has no Windows analogue and is not ported (port_impacts.md:384 entry 188); step 2 has no Windows analogue (no SIGPIPE) and is replaced by the pipe-write error handling recorded in platform_adaptations PA-0004.
- **Verify by:** unit test on the startup sequencer asserting call order; restart test asserting no settings or library read occurs before the migration step

### PR-LAUNCH-002 - A process-wide notification guard swallows observer exceptions raised during the two name-based NSNotificationCenter post methods
- **Source:** DroppyCode/App/DroppyCodeApp.swift:10 DCInstallNotificationGuard() - the call site, first statement of init() | DroppyCode/App/Window/DCNotificationGuard.m:43-56 DCInstallNotificationGuard - dispatch_once, swizzles postNotificationName:object:userInfo: and postNotificationName:object: with method_setImplementation, each guarded by a NULL Method check | DroppyCode/App/Window/DCNotificationGuard.m:27-41 DCPostWithUserInfoGuarded / DCPostObjectGuarded - @try around the saved original IMP, @catch calls DCNotificationRaised | DroppyCode/App/Window/DCNotificationGuard.m:5-22 DCNotificationLog/DCNotificationOrigin/DCNotificationRaised - os_log_create("iordv.droppycode", "notification"), first MIN(frames.count, 12) callStackSymbols joined by newline
- **Preconditions:** Process start, before any notification is posted.
- **Action:** An observer raises an NSException while a notification is being posted through one of the two guarded selectors.
- **Expected:** The exception does not escape the post. One os_log_error line is written on subsystem "iordv.droppycode", category "notification", with the verbatim format "An observer raised while %{public}@ was posted, dropped: %{public}@ %{public}@\n%{public}@" carrying the notification name, exception.name, exception.reason (empty string when nil) and the first at most 12 call-stack frames joined by newlines. The post returns normally and the remaining work (window ordering, popover presentation) completes. The raising observer still never sees its notification.
- **Side effects:** Process-wide method swizzle affecting every NSNotificationCenter, including Apple framework posts; os_log error entries
- **Persistence:** Nothing is persisted.
- **Failure cases:** If either selector is absent, class_getInstanceMethod returns NULL and that swizzle is skipped silently; the other is still installed.; postNotification: (the NSNotification-object overload) is NOT guarded; an exception raised through it is not caught.
- **Cancellation:** not cancellable; installation is idempotent via dispatch_once, so repeated calls neither stack guards nor lose the original IMPs
- **Windows path:** PLATFORM BOUNDARY: not ported. port_impacts.md:384 entry 188 - 'DCDisplayCycleGuardedWindow and DCNotificationGuard are macOS-only AppKit exception nets: Do not re-implement.' There is no NSNotificationCenter and no ViewBridge on Windows.
- **Verify by:** no Windows verification; recorded as a macOS-only construct in COMPATIBILITY notes

### PR-LAUNCH-003 - SIGPIPE is ignored process-wide so a write to an exited provider process reports EPIPE instead of killing the app
- **Source:** DroppyCode/App/DroppyCodeApp.swift:11-12 - comment 'Provider processes can exit while we write to them; report EPIPE instead of crashing.' followed by signal(SIGPIPE, SIG_IGN)
- **Preconditions:** Process start, step 2 of the prologue.
- **Action:** The app writes to the stdin of a provider child process that has already exited.
- **Expected:** The write fails with EPIPE and is handled by the caller; the app is not terminated by the signal.
- **Side effects:** Changes the process-wide disposition of SIGPIPE
- **Persistence:** Nothing is persisted.
- **Failure cases:** None reported; signal() returns the previous handler and the result is discarded.
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY: Windows has no SIGPIPE. The equivalent is that a write to a closed pipe returns ERROR_BROKEN_PIPE / ERROR_NO_DATA, which must be surfaced to the same provider-session error path rather than thrown as an unhandled fault (platform_adaptations PA-0004).
- **Verify by:** unit test: write to a closed child stdin and assert the provider session reports the write error rather than the process faulting

### PR-LAUNCH-014 - The hang watchdog starts once and runs a background thread that pings and checks every 0.5 seconds
- **Source:** DroppyCode/App/DroppyCodeApp.swift:16-17 - comment 'A frozen main thread gets its stacks written to ~/Library/Logs/Droppy Code.' then HangWatchdog.start() | DroppyCode/Core/Support/HangWatchdog.swift:42-60 start() - the state.withLock started latch returning false on a second call, then a Thread whose body is 'while true { Thread.sleep(forTimeInterval: 0.5); ping(); check() }', thread.name = "hang-watchdog", thread.qualityOfService = .utility | DroppyCode/Core/Support/HangWatchdog.swift:34-40 - OSAllocatedUnfairLock<State> with lastPong, reportedThisStall, started | DroppyCode/Core/Support/HangWatchdog.swift:15-16 - 'it stays on in every build'

### PR-LAUNCH-072 - The source has no single-instance lock; a second launch is a separate process
- **Source:** DroppyCode/App/DroppyCodeApp.swift:1-26 - the entry point installs no instance lock, mutex or port | DroppyCode/App/AppDelegate.swift:1-87 - no instance arbitration in any lifecycle callback | DroppyCode/Core/Support/CaptureRun.swift:9-19 - the capture invocation relies on launching another copy with arguments, implying multiple instances are possible | porting/dead_code.md:93 entry 42 - records the documented capture invocation, which opens a new instance
- **Preconditions:** A copy of the app is already running.
- **Action:** The app is launched again.
- **Expected:** Nothing in the source prevents a second process. macOS Launch Services normally activates the running copy instead of starting a second one for a double-click, but the app itself contributes no lock, and the documented capture invocation deliberately bypasses that to start a second instance. Two instances would share the same store root with no coordination.
- **Side effects:** Two processes writing the same library.json, with only the atomic-write guarantee between them
- **Persistence:** Unsynchronised access to the same store root.
- **Failure cases:** Concurrent writes: last writer wins per file, atomically; there is no lock, no merge and no warning.
- **Cancellation:** not applicable
- **Windows path:** ENGINEERING DECISION required: Windows has no Launch Services single-activation behavior, so without an explicit lock a double-click WOULD start a second process, which is a behavioral divergence rather than a reproduction. A single-instance mutex that activates the running window is the faithful outcome of the macOS behavior; the source cannot settle it because the arbitration lives outside the app. Record the choice.
- **Verify by:** interaction test: launching twice results in one visible main window

### PR-LAUNCH-073 - Quit is the stock application-termination menu item; the app replaces the settings and save command groups but not termination
- **Source:** DroppyCode/App/DroppyCodeApp.swift:23-24 - the Settings scene carries .commands { AppCommands(model:) } | DroppyCode/App/AppCommands.swift:12-15 - CommandGroup(replacing: .appSettings) with Button("Settings…") | DroppyCode/App/AppCommands.swift:17-19 - CommandGroup(replacing: .saveItem) {} with the comment about the stock Close taking Cmd-W | DroppyCode/App/AppCommands.swift:11-101 - no CommandGroup for .appTermination anywhere in the body
- **Preconditions:** The menu bar is built.
- **Action:** The user opens the application menu.
- **Expected:** The Quit item is the system-provided one, with the system-provided label and shortcut derived from the bundle name; the app neither replaces nor relabels it. Choosing it enters the termination sequence specified by PR-LAUNCH-049 to PR-LAUNCH-051. The app DOES replace the settings group, with "Settings…", and empties the save group.
- **Side effects:** Triggers the termination sequence
- **Persistence:** None.
- **Cancellation:** The quit can be deferred but never refused (PR-LAUNCH-050).
- **Windows path:** PLATFORM BOUNDARY: Windows has no application menu with a system Quit item. The equivalents that must reach the same termination sequence are the window close button, Alt+F4, the taskbar Close command and a session end. The exact label of any Exit menu item the port adds is NOT derivable from this source and must be recorded as a deliberate Windows addition, not invented as parity.
- **Verify by:** interaction test: each Windows close affordance runs the full termination sequence
