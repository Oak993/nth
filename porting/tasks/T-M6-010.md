### PR-LAUNCH-050 - A quit during a Hydra merge is deferred, polled every 250 ms, and capped at 4 minutes
- **Source:** DroppyCode/App/AppDelegate.swift:41-43 - comment 'A quit while the team's work is going out waits for it: the merge is a minute or two of git and one model call, and losing it half-way leaves the work unmerged until the user's next message. Capped, so a stuck merge never holds the quit.' | DroppyCode/App/AppDelegate.swift:46-53 - 'let deadline = Date.now.addingTimeInterval(4 * 60)'; 'while model.isAnyHydraMergeRunning, Date.now < deadline { try? await Task.sleep(for: .milliseconds(250)) }'; 'sender.reply(toApplicationShouldTerminate: true)'; the method returns .terminateLater | porting/platform_adaptations.md:136-148 PA-0006
- **Preconditions:** At least one live runtime is merging Hydra work when the quit arrives.
- **Action:** The user quits.
- **Expected:** The immediate reply is terminateLater, so the process stays alive. A main-actor task polls every 250 milliseconds. It stops as soon as no runtime is merging, or when 240 seconds (4 * 60) have passed since the quit was requested, whichever comes first. In BOTH cases it then replies true and the termination continues into applicationWillTerminate. The app therefore always quits within about 4 minutes; a stuck merge never blocks the quit forever.
- **Side effects:** The app stays alive and its windows stay on screen while waiting; the merge keeps running and may complete
- **Persistence:** Whatever the merge itself persists.
- **Failure cases:** The merge does not finish within 240 seconds: the app quits anyway with the merge incomplete; Task.sleep failing is swallowed by try?, which would spin the loop faster but not change the outcome
- **Cancellation:** The deferral cannot be cancelled and there is no user-visible way to say 'quit now'. The reply is unconditionally true; the quit is never refused.
- **Windows path:** PLATFORM BOUNDARY (platform_adaptations PA-0006): the Windows close and shutdown path must offer the same deferral with the same 250 ms poll and the same 240 second cap, and must then run the same three shutdown steps in the same order. A Windows session end (logoff or shutdown) grants only a limited time before the OS terminates the process, so the 4 minute cap cannot be honoured under session end; that divergence must be recorded rather than hidden.
- **Verify by:** interaction test: quit with a simulated merge that finishes at 10 s, and one that never finishes, asserting exit at about 10 s and at about 240 s

### PR-LAUNCH-051 - Termination runs exactly three steps in this order: save everything, flush the token ledger, terminate the MCP servers
- **Source:** DroppyCode/App/AppDelegate.swift:56-61 applicationWillTerminate - 'model?.saveBeforeQuit()', then 'TokenLedger.shared.flushLiveSpend()', then the comment 'The MCP servers the hub started go with the app.' and 'MCPHub.terminateAll()'
- **Preconditions:** Termination has been approved, immediately or after the merge wait.
- **Action:** applicationWillTerminate runs.
- **Expected:** Exactly three steps, in this order, synchronously on the main thread: (1) model?.saveBeforeQuit(), a no-op if the model is nil; (2) TokenLedger.shared.flushLiveSpend(); (3) MCPHub.terminateAll(). No other work happens, and nothing here is conditional on the capture-run flag.
- **Side effects:** Synchronous disk writes; child process termination
- **Persistence:** library.json, every unsaved thread document, and the live-spend state file.
- **Failure cases:** Each step swallows its own failures; none can abort the sequence.
- **Cancellation:** not cancellable; termination has already been agreed
- **Windows path:** The Windows shutdown handler runs the same three steps in the same order (platform_adaptations PA-0006). Child-process cleanup at exit is an explicit Gate E check.
- **Verify by:** unit test on the shutdown sequencer asserting order; Gate E check that no child process survives

### PR-LAUNCH-058 - Termination terminates every MCP server the hub started, escalating to a process-group kill
- **Source:** DroppyCode/App/AppDelegate.swift:59-60 - comment 'The MCP servers the hub started go with the app.' then MCPHub.terminateAll() | DroppyCode/Services/MCP/MCPHub.swift:30 - nonisolated static func terminateAll() { liveProcesses.terminateAll() } | DroppyCode/Services/MCP/MCPHub.swift:367-375 - 'let running = state.withLock { $0.filter(\.isRunning) }'; 'for process in running { process.terminate() }'; then 'for process in running where process.isRunning { let pid = process.processIdentifier; kill(getpgid(pid) == pid ? -pid : pid, SIGKILL) }'
- **Preconditions:** Termination step 3, the last step.
- **Action:** MCPHub.terminateAll() runs.
- **Expected:** The set of running server processes is snapshotted under the lock. Every one is sent SIGTERM. Then, in a second pass with no wait between them, any that is still running is killed: if the process is its own process-group leader the SIGKILL goes to the whole group as a negative pid, otherwise only to that process. This is what stops a server from leaving a tree of orphans.
- **Side effects:** Terminates and possibly force-kills child process trees
- **Persistence:** None.
- **Failure cases:** A process that ignores SIGTERM is force-killed in the same call; There is no wait between the two passes, so in practice the second pass will usually still see the process running and force-kill it
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY (platform_adaptations PA-0007 and port_impacts.md entry 54): Windows has no SIGTERM with these delivery semantics. The candidate is a Job Object per spawned child with JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE to match the negative-pid group kill, preceded by a cooperative shutdown or console control event. This must be probed, not assumed. Gate E checks that no npx or node child survives the app.
- **Verify by:** Gate E check: after quit, no MCP server child process or grandchild remains

### PR-LAUNCH-059 - Nothing in the quit path cancels the hang watchdog, the Hydra watchdog, the merge sweep, the update checker or the idle-stop tasks
