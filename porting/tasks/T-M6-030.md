### PR-HYDRA-143 - hydraPickerPairs lists pairs whose provider is installed and enabled, in setup order

- **Action:** The pair rows are gathered.
- **Expected:** Every pair whose provider counts as installed AND is enabled, in the order they were set up. A provider no check has looked at yet counts as installed, because the chat a launch opens is built before the providers are probed and must still find the pair it was last worked in.

- **Verify by:** unit over an unprobed provider, a disabled one and a missing one

### PR-HYDRA-145 - enterHydraPair switches the chat's provider, model, effort and fast mode, pins the pair, and writes five settings
- **Source:** DroppyCode/App/AppModel+HydraPairs.swift:29-52 func enterHydraPair(_ pair:for threadID:) - switchesProvider is pair.provider != thread.provider; the thread gains the provider and a cleared providerSessionID when it switches, then the lead's model, effort and fastMode, the pair id and hydraEnabled true; a switching chat stops its old session; then settings.remember(model:effort:for:), settings.defaultProvider, settings.lastHydraPairID, settings.hydraEnabled = true and settings.hydraDefaultEnabled = true
- **Preconditions:** The user tapped a pair row in the composer's model picker.
- **Action:** The chat enters the pair.
- **Expected:** One tap does all of this: the chat moves to the pair's provider when it differs, discarding its provider session id and stopping its old session; its model, effort and fast mode become the pair's lead values as computed by hydraLead; hydraPairID is pinned and hydraEnabled is set true. Then five settings are written: the remembered model and effort for that provider, the default provider, the last pair id, hydraEnabled true and hydraDefaultEnabled true. The session is left to restart itself; the runtime launches the next turn with the pair's head definitions on its own.
- **Side effects:** The old provider session is stopped on a provider switch; Five settings writes
- **Persistence:** ChatThread.provider, .providerSessionID, .model, .effort, .fastMode, .hydraPairID, .hydraEnabled; AppSettings model preference, defaultProvider, lastHydraPairID, hydraEnabled, hydraDefaultEnabled.
- **Failure cases:** The thread is missing: nothing happens
- **Cancellation:** not cancellable
- **Windows path:** Stopping the old session must terminate the CLI process cleanly before the next turn starts one.
- **Verify by:** interaction test entering a same-provider pair and a cross-provider pair

### PR-HYDRA-146 - hydraLead resolves the lead model, effort and fast mode a chat runs on as a pair's lead
- **Source:** DroppyCode/App/AppModel+HydraPairs.swift:55-81 func hydraLead(of pair:for thread:) - the option is the pair's lead model when it names one, else the provider's default when the chat is arriving from another provider, else the chat's current model on that provider; modelID is option?.id ?? pair.orchestratorModel ?? (switchesProvider ? nil : thread.model); the effort is the pair's own when the option offers it or the option is unknown, else the remembered preference's effort when that model offers it, else nil; fastMode is (option?.supportsFast ?? false) && preference.fastMode
- **Preconditions:** A chat is entering or being moved along with a pair.
- **Action:** The lead triple is computed.
- **Expected:** A pair with no lead model runs on any model, so the chat keeps the one it is on; arriving from another provider there is nothing to keep and it takes that provider's default. The pair's lead model id is the chat's even before the provider's catalogue lists it, so the chip shows the id until the list arrives rather than leaving the pair's checkmark on a model the chat is not on. The pair's own effort wins when the resolved model offers it, or when the model is not yet known (option nil, so the `?? true` branch applies); without one the chat picks up what this model was last left on, the way choosing the model by hand does. Fast mode is on only when the model supports it AND the remembered preference has it on.
- **Persistence:** Reads the remembered model preference.
- **Cancellation:** not cancellable
- **Windows path:** Reproduce the `option?.efforts.contains(chosen) ?? true` leniency; a strict check would drop the pair's effort before the catalogue loads.
- **Verify by:** unit over a pair with and without a lead model, before and after the catalogue loads

### PR-HYDRA-147 - updateHydraPair moves the chats leading with it along, and lets them go when the pair's provider changes
- **Source:** DroppyCode/App/AppModel+HydraPairs.swift:88-106 func updateHydraPair(_ id:_ change:) - the change is applied in settings and nothing more happens when the pair is unchanged; for every thread pinned to the pair with Hydra on, a pair whose provider no longer matches the thread's clears the thread's hydraPairID and the thread is skipped; otherwise the lead triple is recomputed and written only when it differs, and the model and effort are remembered for the pair's provider
- **Preconditions:** The user edited a pair in Settings.
- **Action:** The pair is updated.
- **Expected:** A pair is where those chats are, so a new lead model or effort is theirs at once, exactly as entering the pair set them, and the chip says so. A pair whose LEAD PROVIDER changes lets its chats go instead: each has its hydraPairID cleared and stays on its own model with Hydra as it was, because a chat does not change provider under a conversation. Writes happen only when something actually differs.
- **Side effects:** Threads are rewritten; the model preference is remembered
- **Persistence:** ChatThread.hydraPairID, .model, .effort, .fastMode.
- **Failure cases:** The change left the pair identical: nothing happens at all
- **Cancellation:** not cancellable
- **Windows path:** Reproduce the provider-change release; silently moving a chat to another provider mid-conversation would break its session.
- **Verify by:** interaction test changing a pair's lead model and changing its provider
