### PR-STORE-040 - removeSynchronously cancels pending writes for the paths and removes them on the writer queue
- **Source:** DroppyCode/Services/Store/Storage.swift:363-365 - removeSynchronously(_ url: URL) { removeSynchronously([url]) } | DroppyCode/Services/Store/Storage.swift:367-374 - the array form clears pending for every url under one lock, then queue.sync removes each with try? FileManager.default.removeItem(at:)
- **Preconditions:** None.
- **Action:** Thread deletion.
- **Expected:** All pending entries are cleared under a single lock acquisition, then all removals happen inside a single synchronous queue block. A removal that fails is skipped silently and the loop continues.
- **Side effects:** Files removed; Caller blocks once
- **Failure cases:** try? swallows every removal error, including a Windows sharing violation.
- **Cancellation:** not cancellable
- **Windows path:** Same shape. Clear the read-only attribute before each delete and retry transient failures per PA-0015; a permanently failing delete is still swallowed, matching the source. Windows: PA-0015 applies - file replace, delete and rename can fail transiently with a sharing violation, so the operation retries with backoff, clears the read-only attribute before a delete, uses an atomic replace primitive and surfaces a real error after a bounded number of attempts rather than dropping the write.
- **Verify by:** interaction test with a locked file

### PR-STORE-041 - waitForQueuedWrites is an empty synchronous block used as a full-queue barrier
- **Source:** DroppyCode/Services/Store/Storage.swift:376-379 - doc comment "Returns once every write queued so far has landed, so a read that follows sees them." and func waitForQueuedWrites() { queue.sync {} }
- **Preconditions:** None.
- **Action:** A thread read, or the quit path after its synchronous writes.
- **Expected:** The caller blocks until the writer queue reaches this empty block, which by serial ordering means every previously enqueued write has finished. It is a whole-queue barrier, not a per-file wait.
- **Side effects:** Blocks the calling thread
- **Failure cases:** A write enqueued after the barrier begins is not waited for.
- **Cancellation:** not cancellable
- **Windows path:** Post a sentinel work item to the same serial worker and wait on it. It must never be called from the UI thread; in the source both callers are on background tasks.
- **Verify by:** unit

### PR-STORE-044 - The warm queue stops growing at the pending limit
- **Source:** DroppyCode/Services/Store/Storage.swift:287 - guard state.queue.count < pendingLimit else { break }
- **Preconditions:** The queue already holds 24 requests.
- **Action:** Warming more ids.
- **Expected:** The loop breaks, so the remaining ids of that call are dropped silently and are not remembered for later. Note this is a break, not a continue: once the limit is reached nothing further in the same call is enqueued even if a later id would otherwise be cheap.
- **Persistence:** none
- **Failure cases:** The dropped ids are simply not prefetched; opening one of those threads falls back to the synchronous detached history load.
- **Cancellation:** not cancellable
- **Windows path:** Same break semantics. A port that used continue would enqueue a different set.
- **Verify by:** unit warming 40 ids and asserting exactly 24 land

### PR-STORE-046 - A single background worker drains the prefetch queue and clears itself when empty
- **Source:** DroppyCode/Services/Store/Storage.swift:292-307 - guard state.worker == nil, !state.queue.isEmpty else { return state.worker }; let task = Task.detached(priority: .utility) { while let request = next() { ... } }; state.worker = task | DroppyCode/Services/Store/Storage.swift:310-322 - next() returns nil and sets state.worker = nil when the queue is empty
- **Preconditions:** One or more requests queued.
- **Action:** warm() is called.
- **Expected:** At most one detached utility-priority worker exists. It pops requests one at a time under the lock, calls the loader outside the lock, then stores the result under the lock. When the queue empties, next() clears state.worker and returns nil, so the next warm() starts a fresh worker. Decoding is therefore strictly serial, never parallel.
- **Side effects:** One background task while the queue is non-empty; Each decode performs a full writer-queue barrier through Storage.readDocument
- **Persistence:** none
- **Failure cases:** A loader returning nil leaves nothing in the cache but still clears the pending token.
- **Cancellation:** See the cancellation requirement below.
- **Windows path:** One background worker, serial decode, same self-clearing lifecycle. Do not parallelise: each decode takes the writer barrier, and concurrent decodes would multiply the blocking.
- **Verify by:** interaction test asserting exactly one worker under repeated warms

### PR-STORE-047 - Each prefetch request carries a token so a superseded decode is discarded
- **Source:** DroppyCode/Services/Store/Storage.swift:248-251 - private struct Request { let id: UUID; let token = UUID() } | DroppyCode/Services/Store/Storage.swift:290 - state.pending[id] = request.token | DroppyCode/Services/Store/Storage.swift:296-302 - guard state.pending[request.id] == request.token else { return }; state.pending[request.id] = nil; if let result, !Task.isCancelled { state.ready.insert(...) }
- **Preconditions:** A decode is in flight for an id.
- **Action:** take(id) or forget(id) is called for that id while the decode runs.
- **Expected:** The pending token is cleared, so when the decode finishes its token no longer matches and the result is thrown away rather than inserted into the ready cache. A stale document therefore cannot surface after the thread was taken, deleted or opened. The result is also discarded when the worker task itself has been cancelled.
- **Side effects:** The decode work is still done and then wasted
- **Persistence:** none
- **Cancellation:** A cancelled worker still finishes the in-flight load and discards its result at the Task.isCancelled check.
- **Windows path:** Same token compare-and-swap. Without it a deleted thread could be re-inserted into the cache by a decode already under way.
- **Verify by:** unit: start a decode, forget the id, assert the cache stays empty

### PR-STORE-048 - Cancelling the prefetch worker flushes the whole queue and every pending token
- **Source:** DroppyCode/Services/Store/Storage.swift:310-322 - private func next() -> Request? { state.withLock { state in if Task.isCancelled { state.queue.removeAll(keepingCapacity: true); state.pending.removeAll(keepingCapacity: true) } ... } }
- **Preconditions:** The worker task has been cancelled and requests remain.
- **Action:** The worker asks for its next request.
- **Expected:** The whole queue and the whole pending map are cleared while keeping their capacity, the guard then sees an empty queue, state.worker is set to nil and nil is returned so the worker exits. Already-cached documents in the ready cache are untouched.
- **Persistence:** none
- **Failure cases:** Every queued id is silently dropped; a later open of one of them falls back to the synchronous load path.
- **Cancellation:** This is the cancellation behaviour.
- **Windows path:** Same flush, same preserved ready cache, same worker exit.
- **Verify by:** unit
