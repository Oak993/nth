### PR-MCP-187 - A hub HTTP client initializes once per client and never clears that flag except on stop
- **Source:** DroppyCode/Services/MCP/MCPHub.swift:310-341 httpRPC | DroppyCode/Services/MCP/MCPHub.swift:173-178 stop
- **Preconditions:** An http spec.
- **Action:** httpRPC runs.

When not yet initialized: POST initialize with a 60-second timeout; an empty body throws server("The server sent something unexpected: empty reply."); an error reply throws through checkReply; a non-object result throws server("The server sent something unexpected: missing result."); the session id is adopted when present; initialized is set; then the notifications/initialized notification is posted with a 30-second timeout and its errors are swallowed EXCEPT CancellationError. - **Cancellation:** each POST is a cancellation point
- **Windows path:** Reproduce: do not clear initialized anywhere but stop, and add no restart to the HTTP path.
- **Verify by:** integration test dropping the remote session and asserting the client does not re-initialize
- **Upstream defect 20: reproduce it faithfully, do not fix it.**

### PR-MCP-191 - Every server process started this run is terminated when the app quits
- **Source:** DroppyCode/Services/MCP/MCPHub.swift:21-30 liveProcesses, track and terminateAll | DroppyCode/Services/MCP/MCPHub.swift:355-376 MCPLiveProcesses - :357 private final class MCPLiveProcesses: Sendable { | :358 private let state = Mutex<[StdioProcess]>([]) | :362 processes.removeAll { !$0.isRunning } | :363 processes.append(process) | :368 let running = state.withLock { $0.filter(\.isRunning) } | :369 for process in running { process.terminate() } | :370 // The app is quitting, so the delayed SIGKILL in terminate() never fires. | :373 kill(getpgid(pid) == pid ? -pid : pid, SIGKILL)
- **Preconditions:** The app is quitting.
- **Action:** terminateAll runs from the application-will-terminate path.
- **Expected:** The live-process list drops already-exited entries whenever a new one is added. terminateAll takes the running processes under the lock, terminates each (StdioProcess.terminate, which also queues a stdin close and schedules a kill 3 seconds later that never runs at quit), then kills any that is still running - the whole process group when the child leads one, otherwise the single pid. It is synchronous and does nothing asynchronous, because nothing asynchronous would get to run at quit. Without it a child process outlives its parent and an npx server would keep running until the machine restarts.
- **Side effects:** terminates and kills every in-app MCP child process
- **Persistence:** none
- **Failure cases:** a process that ignores both is left running, which the source accepts
- **Cancellation:** not cancellable
- **Windows path:** Wire this to the app-quit path and kill the whole process tree, not just the immediate child: npx spawns node as a grandchild and a per-pid kill leaks it. This is the platform boundary - Windows has no process groups, so a job object or a tree kill is the equivalent.
- **Verify by:** integration test quitting the app with two servers running and asserting no orphan remains
