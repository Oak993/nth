### PR-MCP-191 - Every server process started this run is terminated when the app quits
- **Source:** DroppyCode/Services/MCP/MCPHub.swift:21-30 liveProcesses, track and terminateAll | DroppyCode/Services/MCP/MCPHub.swift:535-557 MCPLiveProcesses - :537 private final class MCPLiveProcesses: Sendable { | :538 private let state = Mutex<[Process]>([]) | :542 processes.removeAll { !$0.isRunning } | :543 processes.append(process) | :548 let running = state.withLock { $0.filter(\.isRunning) } | :550 process.terminate() | :554 kill(getpgid(pid) == pid ? -pid : pid, SIGKILL)
- **Preconditions:** The app is quitting.
- **Action:** terminateAll runs from the application-will-terminate path.
- **Expected:** The live-process list drops already-exited entries whenever a new one is added. terminateAll takes the running processes under the lock, terminates each, then kills any that is still running - the whole process group when the child leads one, otherwise the single pid. It is synchronous and does nothing asynchronous, because nothing asynchronous would get to run at quit. Without it a child process outlives its parent and an npx server would keep running until the machine restarts.
- **Side effects:** terminates and kills every in-app MCP child process
- **Persistence:** none
- **Failure cases:** a process that ignores both is left running, which the source accepts
- **Cancellation:** not cancellable
- **Windows path:** Wire this to the app-quit path and kill the whole process tree, not just the immediate child: npx spawns node as a grandchild and a per-pid kill leaks it. This is the platform boundary - Windows has no process groups, so a job object or a tree kill is the equivalent.
- **Verify by:** integration test quitting the app with two servers running and asserting no orphan remains

- **Action:** notifications/initialized is posted.

- **Side effects:** one HTTP POST that nobody reads the reply of
- **Persistence:** none
- **Failure cases:** a server that rejects the notification is treated as initialized anyway; upstream behaviour, reproduced
- **Cancellation:** A CancellationError from this post is the one error that propagates.
- **Windows path:** 30 seconds, and keep the swallow-except-cancellation shape exactly: a blanket catch that also swallowed cancellation would leave a stopping client running.
- **Verify by:** unit asserting the value, that a server error is swallowed, and that a cancellation propagates
