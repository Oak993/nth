### PR-MCP-095 - Secret values are addressed by the account string "MCP <server id> <field key>" in one container named by the app
- **Source:** DroppyCode/Services/MCP/MCPKeychain.swift:6-8 account(server:field:) | DroppyCode/Services/MCP/MCPKeychain.swift:13-19 the query with kSecAttrService = AppInfo.name
- **Preconditions:** none
- **Action:** Any secret is read, written or deleted.
- **Expected:** The item is a generic password whose service is the app display name and whose account is the literal "MCP " + serverID + " " + fieldKey - one space after MCP and one between the two parts, with no escaping, so a server id or field key containing a space produces an ambiguous account string. Two field names are reserved by the OAuth layer and are not entry fields: "oauth" and "oauth-client".
- **Side effects:** none
- **Persistence:** the account string is the persisted key; the same container also holds the four API-provider key accounts
- **Failure cases:** none
- **Cancellation:** not cancellable
- **Windows path:** Windows Credential Manager (OD-0008 B3) keeps the same flat account namespace for the whole app, with the account format "MCP <server> <field>" verbatim and the app display name standing for the Keychain service, so the partitioning matches. kSecAttrAccessibleWhenUnlocked has no Credential Manager counterpart; that is recorded, not invented around.
- **Verify by:** integration test asserting the exact account strings written

### PR-MCP-096 - Reading a secret trims it and treats a whitespace-only value as absent

- **Preconditions:** none
- **Action:** A secret is read.
- **Expected:** Under a capture run the function returns nil before touching the store at all. Otherwise it fetches exactly one matching item and returns its data decoded as UTF-8, trimmed of whitespace and newlines - but returns nil when the lookup fails, when the data is not valid UTF-8, or when the trimmed value is empty. So a stored value of spaces reads back as nil and the field falls through to its default.
- **Side effects:** one credential-store read

- **Failure cases:** a locked or unavailable store returns nil, which surfaces as a missing key rather than an error
- **Cancellation:** not cancellable
- **Windows path:** Same trimming and same nil-on-empty. The capture-run short circuit is capture-mode behavior, not user-reachable runtime behavior, and is recorded in dead_code entry 44; it is not a shipped requirement. Protected storage is Windows Credential Manager (OD-0008 B3), under the same account strings.
- **Verify by:** unit with a whitespace-only stored value

### PR-MCP-098 - Writing a secret updates in place first and only creates the item when none exists
- **Source:** DroppyCode/Services/MCP/MCPKeychain.swift:36-49 the update-then-add path of set
- **Preconditions:** none
- **Action:** set is called with a non-empty value.
- **Expected:** The value is trimmed and encoded as UTF-8. SecItemUpdate is attempted against (class generic password, service = app name, account = the account string) with only the data attribute; success returns true. Any status other than errSecItemNotFound returns false. On errSecItemNotFound, SecItemAdd is called with the same query plus the data and kSecAttrAccessibleWhenUnlocked, and its success is the return value. Because the update path carries no accessibility attribute, an item created by an earlier build keeps its original accessibility forever - accessibility never migrates. This is upstream behavior.
- **Side effects:** one credential-store write
- **Persistence:** the trimmed value under the account string
- **Failure cases:** a store failure returns false, which only saveCustomValues acts on
- **Cancellation:** not cancellable
- **Windows path:** Reproduce the update-then-add shape and the trimming against Windows Credential Manager (OD-0008 B3). Credential Manager has no accessibility attribute, so defect 21 has no Windows analogue and the attribute has no counterpart; record that rather than inventing one.
- **Verify by:** unit over the three status outcomes
- **Upstream defect 21: reproduce it faithfully, do not fix it.**

### PR-MCP-099 - deleteAll removes only the fields the passed entry declares
- **Source:** DroppyCode/Services/MCP/MCPKeychain.swift:25-31 deleteAll(server entry:)
- **Preconditions:** A disconnect is running.
- **Action:** deleteAll(server: entry) is called.
- **Expected:** For each field of the entry, in field order, delete (entry.id, field.key). The function takes the ENTRY, not an id, precisely so a custom server - which is not in the catalog - has its variables deleted rather than silently nothing. The two OAuth field names are not entry fields and are deleted separately by MCPOAuth.signOut. Upstream discards each deletion's result; on disconnect Marrow checks it and reports a failed deletion other than a missing item (OD-0008 A12, PR-MCP-228).
- **Side effects:** one deletion per declared field
- **Persistence:** those items are removed
- **Failure cases:** a field the entry no longer declares is left orphaned in the store; a store that refuses a deletion: upstream reports nothing; Marrow reports it (OD-0008 A12)
- **Cancellation:** not cancellable
- **Windows path:** Same signature: pass the entry, never look the id up in the catalog. The items live in Windows Credential Manager (OD-0008 B3); each deletion is checked (OD-0008 A12).
- **Verify by:** unit with a custom server asserting its variables are actually deleted; a store refusing a deletion produces a reported failure

- **Preconditions:** A catalog entry or custom-server entry with zero or more declared fields.
- **Action:** Its stored secrets are destroyed.
- **Expected:** One delete per field the ENTRY object declares, iterated in the entry's own field order. The account string is the literal "MCP ", the server id, a single space, and the field's key - three parts joined by single spaces, with no separator characters of any other kind. The service is AppInfo.name, one service for the whole app. Upstream discards the delete result, so a missing item, a locked store and a refusal are indistinguishable and none is reported. Marrow checks it (OD-0008 A12): a failed deletion is reported to the user instead of a silent success. Two details are ENGINEERING DECISIONS, not ruling text (see the deviation): an item that did not exist is not a failure, and the rest of disconnect still runs (PR-MCP-061). Crucially the fields come from the ENTRY, not from a catalog lookup by id: a custom server is not in the catalog, so looking it up there would iterate an empty field list and silently delete nothing. An entry with no declared fields deletes nothing and is not an error. A field the entry NO LONGER declares keeps an orphaned item forever, because nothing enumerates the store.
- **Side effects:** One stored secret destroyed per declared field, unrecoverably; a failed deletion is reported to the user
- **Persistence:** The secrets leave Windows Credential Manager (OD-0008 B3) permanently; they must be re-obtained from the provider.
- **Failure cases:** A locked or unavailable store: upstream deletes nothing and disconnect still reports success; Marrow reports the failed deletion; An entry whose declared fields changed since the values were written leaves orphans
- **Cancellation:** not cancellable once started
- **Windows path:** Use Windows Credential Manager (OD-0008 B3) and destroy exactly the items the entry declares under the same three-part account string. - **Verify by:** integration test asserting one delete per declared field with the exact account string, a no-op for an entry with no fields, that a custom server's fields are taken from the entry rather than the catalog, and that a store refusing a deletion produces a reported failure instead of success
