### PR-MCP-111 - A probed child is asked to stop and is killed a second later, by process group when it leads one
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:226-235 terminate | DroppyCode/Services/MCP/MCPHub.swift:285-294 the identical terminate in MCPClient
- **Preconditions:** A child process exists.
- **Action:** The probe finishes, fails or is cancelled, or a hub client stops.
- **Expected:** If the process is not running, do nothing. Otherwise send the terminate signal, then one second later, if it is still running, kill it: the whole process group when getpgid(pid) == pid (the child leads its own group), otherwise the single pid. The one-second delay runs on a background utility queue and is not awaited.
- **Side effects:** terminates and possibly kills a child process tree
- **Persistence:** none
- **Failure cases:** a child that ignores the terminate is killed after one second
- **Cancellation:** this IS part of the cancellation cleanup
- **Windows path:** Windows has no process groups or signals. The equivalent is a graceful close followed one second later by a forced kill of the whole process tree, which matters because npx spawns node as a grandchild; a bare per-pid kill would leak it. Name this as the platform boundary.
- **Verify by:** integration test asserting no orphaned node process survives a cancelled probe

### PR-MCP-112 - Probe stdout is split on newlines and stderr is capped at 64000 bytes, keeping the last 16000
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:383-425 StdioConversation
- **Preconditions:** A probe is reading from the child.
- **Action:** Bytes arrive on stdout or stderr.
- **Expected:** stdout bytes accumulate in a buffer; every time a 0x0A byte is found, the bytes before it become one pending line and the buffer is advanced past the newline, so a partial line is held until it completes. stderr accumulates and, whenever it exceeds 64000 bytes, is replaced by its last 16000 bytes. The exit status is recorded once by the termination handler. All four operations are serialized under one lock. takeLines drains and clears the pending list.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** a server that writes a very long line with no newline is never parsed and the probe times out
- **Cancellation:** the handlers are detached by the probe's deferred cleanup
- **Windows path:** Same framing on 0x0A only: a server emitting CRLF leaves the carriage return at the end of the line, and the JSON parser tolerates it. Same two byte caps.
- **Verify by:** unit feeding split writes and an oversized stderr

### PR-MCP-113 - A remote probe POSTs initialize, initialized and up to ten tools/list pages, carrying the session id forward
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:239-300 probeRemote
- **Preconditions:** A resolved server with a url.
- **Action:** probeRemote runs.
- **Expected:** An unparseable url throws malformed("invalid URL"). Each post carries the session id held so far and adopts any new one from the response, keeping the old when the response has none. Sequence: initialize (id 1) -> require a non-nil, object body and no error, require result to be an object or throw malformed("missing result"), read serverInfo.name and serverInfo.version; then the notifications/initialized notification, whose errors are swallowed EXCEPT CancellationError which is rethrown; then at most 10 tools/list pages with the same cursor rule as the stdio probe. An empty reply body throws malformed("empty reply"); a non-object body throws malformed("invalid reply").
- **Side effects:** one HTTPS or loopback POST per message
- **Persistence:** serverVersion and tools are persisted by the store on success
- **Failure cases:** see PR-MCP-114 and PR-MCP-115 for the status-code branches
- **Cancellation:** each POST is a cancellation point
- **Windows path:** Same sequence and the same swallow-except-cancellation on the notification.
- **Verify by:** contract fixture against a stub streamable-HTTP server

### PR-MCP-116 - A probe POST sets four headers, times out at 30 seconds, and reports a non-2xx with the first 2000 characters of the body
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:302-333 postJSON
- **Preconditions:** A remote probe message is ready.
- **Action:** postJSON runs.
- **Expected:** POST with timeoutInterval 30. The resolved server's headers are applied first, then Content-Type: application/json, Accept: application/json, text/event-stream and MCP-Protocol-Version: 2025-06-18 are set - so a resolved header named any of those three is overwritten. Mcp-Session-Id is set only when a session id is held. A non-HTTPURLResponse throws malformed("invalid reply"). The Mcp-Session-Id response header is returned. A status outside 200..<300 throws MCPProbeError.http(status:body:) where body is the response decoded as UTF-8, truncated to its first 2000 characters and then trimmed. On success: when the response Content-Type contains "text/event-stream", the body is the first usable SSE message; when the data is empty the body is nil; otherwise the data is parsed as JSON.
- **Side effects:** one HTTP request
- **Persistence:** none
- **Failure cases:** non-2xx -> .http, rendered as "That key was refused. Press Try again and paste a new one." for 401 and 403, "Nothing answered at that address. Check the address and try again." for 404, and "The server answered <status>." otherwise
- **Cancellation:** the request is a cancellation point
- **Windows path:** Same 30-second flat timeout for the probe's remote leg. Do not unify it with the hub's 30/60/120 or the proxy's 3600.
- **Verify by:** contract fixture asserting the four headers and the 2000-character truncation

### PR-MCP-117 - An SSE response yields the first data line that parses as an object carrying an id
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:335-347 firstSSEMessage | DroppyCode/Services/MCP/MCPHub.swift:480-492 the hub's identical copy
- **Preconditions:** A response whose Content-Type contains text/event-stream.
- **Action:** The body is scanned.
- **Expected:** Split the whole body on newlines. For each line, trim whitespace; skip unless it starts with "data:"; take the remainder after those five characters and trim it; parse it as JSON; accept it only when it is an object AND has an "id" key. Return the first such value, or nil when none matches. A notification frame, which has no id, is therefore never returned.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** nil bubbles up as malformed("empty reply") in the probe or "The server sent something unexpected: empty reply." in the hub
- **Cancellation:** not cancellable
- **Windows path:** Same. Note the installed JavaScript bridge accepts a frame with "result" or "error" instead of "id" (PR-MCP-196): the three clients differ deliberately.
- **Verify by:** unit with a notification frame before the reply frame
