### PR-MCP-111 - A probed or hub stdio child is stopped by closing its stdin, a terminate signal, and a kill of the pid alone 3 seconds later
- **Source:** DroppyCode/Services/MCP/MCPWire.swift:152-154 MCPStdioConnection.stop - :153 process.terminate() | DroppyCode/Core/Support/StdioProcess.swift:120-129 terminate - :122 writeQueue.async { try? handle.close() } | :123 guard process.isRunning else { return } | :124 process.terminate() | :126 DispatchQueue.global().asyncAfter(deadline: .now() + 3) { | :127 if process.isRunning { kill(process.processIdentifier, SIGKILL) } | DroppyCode/Services/MCP/MCPProbe.swift:95 defer { connection.stop() } | DroppyCode/Services/MCP/MCPHub.swift:173-178 stop - :174 stdio?.stop()
- **Preconditions:** A stdio connection exists.
- **Action:** The probe finishes, fails or is cancelled, or a hub client stops.
- **Expected:** The stdin write handle is closed on the process's serial write queue, whether or not the child is still running. If the child is not running, nothing else happens. Otherwise the terminate signal (SIGTERM) is sent to the child, and 3 seconds later, on a background queue and not awaited, the child is killed with SIGKILL if it is still running. Both signals go to the child's pid alone, never to its process group, so a grandchild such as the node process npx starts is signalled by neither. The probe and every hub client stop their children this same way.
- **Side effects:** closes the child's stdin; terminates and possibly kills the child process
- **Persistence:** none
- **Failure cases:** a child that ignores the terminate signal is killed 3 seconds later; a grandchild the child started is not signalled and can outlive it
- **Cancellation:** this IS part of the cancellation cleanup
- **Windows path:** Stop through the port's StdioProcess termination ladder (ED-126): close stdin, then the graceful stop to the child, then TerminateProcess on that pid alone at +3 s with no job object. The B2 windows_path asked for a whole-tree kill after one second because npx starts node as a grandchild; upstream B3 signals the pid alone after 3 seconds. UNRESOLVED (B3_PLAN.md 6.1 O3): whether the port keeps a tree kill for MCP children needs an owner ruling.
- **Verify by:** integration test with a stand-in server that ignores the graceful stop, asserting that its stdin reaches EOF first and that the kill lands 3 seconds later

### PR-MCP-117 - An event-stream response yields the first data line whose object id equals the request id, read as it arrives, and a notification's event stream is not read
- **Source:** DroppyCode/Services/MCP/MCPWire.swift:85-102 the event-stream branch of post - :86 guard contentType.contains("text/event-stream") else { | :92 guard let id else { return MCPHTTPReply(sessionID: session, body: nil) } | :93 for try await line in bytes.lines { | :94 let trimmed = line.trimmingCharacters(in: .whitespaces) | :95 guard trimmed.hasPrefix("data:") else { continue } | :96 let text = trimmed.dropFirst(5).trimmingCharacters(in: .whitespaces) | :98 value.object != nil, value["id"]?.int == id | :100 return MCPHTTPReply(sessionID: session, body: value) | :102 return MCPHTTPReply(sessionID: session, body: nil) | DroppyCode/Core/Support/JSONValue.swift:83-90 int - an integer, a finite double truncated, or a string Int() parses | DroppyCode/Services/MCP/MCPProbe.swift:152 and DroppyCode/Services/MCP/MCPHub.swift:345, the two callers
- **Preconditions:** A 2xx response whose Content-Type contains text/event-stream.
- **Action:** The body is read.
- **Expected:** When the POST carried no JSON-RPC id (the notifications/initialized notification), the body is nil at once and the stream is never read. Otherwise the stream is read line by line as it arrives. For each line, trim whitespace; skip it unless it starts with "data:"; take the remainder after those five characters and trim it; parse it as JSON; accept it only when it is an object whose "id", read as an integer (an integer, a finite double truncated toward zero, or a string Int() parses), EQUALS the request's id. The first such value is returned immediately, without waiting for the stream to end, so a server that holds the stream open does not hang the caller. A frame for another id, a notification frame without an id and anything unparseable are skipped. When the stream ends without a match the body is nil.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** nil bubbles up as malformed("empty reply") in the probe or "The server sent something unexpected: empty reply." in the hub; the notification's nil body is ignored by both callers; an error while the stream is read is thrown as it is
- **Cancellation:** reading the stream is a cancellation point
- **Windows path:** Read the event stream incrementally and return at the first matching frame; do not buffer the whole body. On the notification path do not read the stream, and release the unread response so it does not hold its connection open. Note the installed JavaScript bridge accepts a frame with "result" or "error" instead of an id (PR-MCP-196): the clients differ deliberately.
- **Verify by:** unit with a notification frame and a frame for another id before the reply frame, a stream held open after the reply, and a notification POST answered as an event stream

### PR-MCP-232 - A stdio reply that arrives before its request waits, or for an id nobody is waiting on, is kept by id for a later wait
- **Source:** DroppyCode/Services/MCP/MCPWire.swift:125-131 the connection state - :127 var pending: [RPCID: CheckedContinuation<JSONValue, Error>] = [:] | :128 var buffered: [RPCID: JSONValue] = [:] | DroppyCode/Services/MCP/MCPWire.swift:219-228 handle - :220 guard let object = message.object, | :221 let rawID = object["id"], let id = RPCID(rawID) else { return } | :223 if let continuation = state.pending.removeValue(forKey: id) { return continuation } | :224 state.buffered[id] = message | DroppyCode/Services/MCP/MCPWire.swift:198-217 awaitReply - :203 if let value = state.buffered.removeValue(forKey: id) { return .success(value) } | :204 if state.closed { return .failure(MCPWireError.exited(state.exitStatus)) } | :205 state.pending[id] = continuation | DroppyCode/Services/MCP/MCPWire.swift:164-168 the counter only ever increases, so an id is never reused on a connection
- **Preconditions:** A stdio connection (the probe's, or a hub client's) is running.
- **Action:** A message arrives on the child's stdout.
- **Expected:** A message that is not a JSON object, has no "id", or whose id is neither a number nor a string (for example null) is ignored. Otherwise, when a request is waiting for that id it is handed the message at once and stops waiting. When none is, the message is kept under its id, replacing any message kept earlier for the same id, and the next wait for that id takes it at once without suspending, so a reply that arrives before its request has started waiting is not lost. - **Failure cases:** a server that answers ids nobody asked for grows the kept set for the life of the connection
- **Cancellation:** not cancellable; a waiting request that is cancelled gives up its slot (PR-MCP-235)
- **Windows path:** Keep a pending map and a kept-reply map keyed by the exact id (PR-MCP-233) under one lock, check the kept map before registering a wait, and never drop an unclaimed reply.
- **Verify by:** unit with a scripted server that answers before the request is awaited, answers an id nobody asked for, and answers a request after it timed out

### PR-MCP-234 - A stdio request fails with the child's exit status: at once when the child is not running, and for waiting requests once the child's output has ended

- **Preconditions:** A stdio connection whose child may have exited.
- **Action:** A request is made, or the child exits while requests wait.
- **Expected:** A request made when the child is no longer running sends nothing and fails with exited(<status>) once the child's exit status is known. Otherwise waiting requests keep waiting until the connection's message stream ends, which happens when the child's stdout closes, or 1 second after the child exits when something else (such as a grandchild) still holds stdout open. Messages the child wrote before that are delivered first. The connection then waits for the exit status, marks itself closed and fails every waiting request with exited(<status>); a wait that begins after that fails the same way at once, unless a reply for its id is already kept (PR-MCP-232). - **Persistence:** none

- **Cancellation:** not cancellable
- **Windows path:** Report the exit only after the output stream has ended (EOF, or 1 second after exit), always with the exit code, and fail every waiting request with it.
- **Verify by:** integration test with a stand-in server that exits mid-request, one that exits while a child process keeps its stdout open, and a request made after the exit

### PR-MCP-235 - Each stdio request races its reply against a timer of its timeout, and a request that ends without a reply gives up its id
- **Source:** DroppyCode/Services/MCP/MCPWire.swift:162-187 request - :170 return try await withThrowingTaskGroup(of: JSONValue.self) { group in | :171 group.addTask { try await self.awaitReply(key) } | :173 try await Task.sleep(for: .seconds(timeout)) | :174 throw MCPWireError.timedOut | :176 self.process.send(MCPWire.request(id: id, method: method, params: params)) | :179 group.cancelAll() | :182 group.cancelAll() | :183 self.abandon(key) | DroppyCode/Services/MCP/MCPWire.swift:198-217 awaitReply - :214 } onCancel: { | :215 self.abandon(id) | DroppyCode/Services/MCP/MCPWire.swift:230-233 abandon - :232 continuation?.resume(throwing: CancellationError())
- **Preconditions:** A stdio request was made on a running child.
- **Action:** The request waits.
- **Expected:** The request takes the connection's next id, starts a wait for that id and a timer of `timeout` seconds side by side, and only then queues the request line for the child's stdin. Whichever finishes first decides: a reply is returned and the timer is cancelled; the timer ending throws timedOut; an exit report throws exited(<status>) (PR-MCP-234). On any failure the other task is cancelled and the id is abandoned: its wait slot is removed and resumed with CancellationError, so nothing is left waiting. A cancelled caller cancels both tasks, the wait gives up its slot the same way, and CancellationError reaches the caller. A reply that comes after its request gave up is kept, not delivered (PR-MCP-232). The timer is per request: each hub call gets its own full timeout, and the probe hands in the time left before its deadline (PR-MCP-109).
- **Side effects:** queues one JSON line for the child's stdin on the process's write queue
- **Persistence:** none
- **Failure cases:** "The server didn't answer in time." in both callers when the timer wins
- **Cancellation:** cancelling the caller abandons the id and throws CancellationError
- **Windows path:** Race the reply against a per-request timer; on timeout, error or cancellation remove the pending entry so that a late reply is only kept, and let CancellationError reach the caller.
- **Verify by:** unit with a scripted server that never answers, one that answers after the timeout (kept, not delivered), and a caller cancelled mid-wait
