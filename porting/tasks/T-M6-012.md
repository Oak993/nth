### PR-WIN-070 - On a first launch the welcome tour opens 700 milliseconds after the main window
- **Source:** DroppyCode/App/AppDelegate.swift:18-20 `if !windows.model.settings.hasSeenTour { Task { @MainActor in try? await Task.sleep(for: .milliseconds(700)); Tour.present(model: windows.model) } }` | porting/port_impacts.md entry 191 (C1): 'first-run gate on persisted hasSeenTour (default false) with a 700 ms delay after the main window shows; both finish and close write the flag'
- **Preconditions:** The persisted hasSeenTour flag is false, which is its default.
- **Action:** Launch finishes.
- **Expected:** The main window appears first; exactly 700 milliseconds later the welcome tour is presented. On every later launch, with the flag set, nothing happens. The delay is unconditional: it is not shortened when the window is already drawn.
- **Persistence:** Reads the persisted hasSeenTour flag; the tour itself writes it on both finish and close.
- **Cancellation:** The sleep is not cancelled anywhere in this file; quitting during it ends the process.
- **Windows path:** A 700 ms one-shot timer on the UI thread after the window is shown, gated on the same persisted flag with the same default.
- **Verify by:** interaction test on a fresh profile, timing the gap

### PR-WIN-071 - A relaunch after an installed update arms the celebration and opens Settings on About
- **Source:** DroppyCode/App/AppDelegate.swift:23-27 the comment 'The relaunch after an install: the update story finishes on About, where it began.' and `if AppUpdater.shared.consumeRelaunchMarker() { UpdateInstallProgress.shared.armCelebration(); windows.showSettings(page: .about) }`

- **Expected:** The marker is consumed, so this happens once and not on the next launch; the celebration is armed; the Settings window opens directly on the About page, centered over the main window, and takes focus.

- **Verify by:** interaction test with a planted marker; restart test asserting it happens only once

### PR-WIN-072 - Clicking the app in the dock with no visible windows brings the main window back
- **Source:** DroppyCode/App/AppDelegate.swift:30-33 `func applicationShouldHandleReopen(_ sender: NSApplication, hasVisibleWindows flag: Bool) -> Bool { if !flag { WindowManager.shared.showMain() }; return true }`
- **Preconditions:** The app is running with every window closed.
- **Action:** The user activates the app from the dock.
- **Expected:** The main window is shown again, reusing the same cached instance with its content intact. With a window already visible, nothing extra happens. DEVIATION (OD-0008 C1): in the port closing the main window quits the app, so a running app with every window closed does not arise and this reopen path is not reached from a closed window. ENGINEERING DECISION ED-002 (porting/engineering_decisions.md, not an owner ruling): a second launch attempt runs this same path in the running instance, bringing its existing main window forward instead of starting a second copy.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** A single-instance lock (ED-002): a second launch attempt restores and foregrounds the running instance's existing main window rather than creating one. Under OD-0008 C1 there is no windowless running state to reopen from.
- **Verify by:** interaction test: with the app running, launch it a second time and assert the same main window with its state comes forward and no second process remains (ED-002)

### PR-WIN-073 - Quitting while a helper-team merge is running waits for it, capped at four minutes
- **Source:** DroppyCode/App/AppDelegate.swift:35-48 the comment 'A quit while the team's work is going out waits for it: the merge is a minute or two of git and one model call, and losing it half-way leaves the work unmerged until the user's next message. Capped, so a stuck merge never holds the quit.' and `guard let model, model.isAnyHydraMergeRunning else { return .terminateNow }`, then a task polling every 250 ms until the merge ends or `Date.now.addingTimeInterval(4 * 60)` passes, then `sender.reply(toApplicationShouldTerminate: true)`; the function returns .terminateLater
- **Preconditions:** A helper-team merge is in flight.
- **Action:** The user quits: upstream by the stock Quit command; in the port by the main window's close button or Alt+F4 (OD-0008 C1, C2).
- **Expected:** The quit is deferred. The merge state is polled every 250 milliseconds. The quit proceeds as soon as no merge is running, or after four minutes, whichever comes first. With no merge running the quit is immediate. In the port this wait applies to closing the main window and to Alt+F4, which are the only ways to quit (OD-0008 C1, C2).
- **Side effects:** Delays process exit by up to four minutes
- **Persistence:** nothing persisted
- **Failure cases:** A merge that never finishes: the quit proceeds anyway at the four-minute deadline, and the merge is lost
- **Cancellation:** The quit cannot be cancelled once deferred; the source has no path back to .terminateCancel.
- **Windows path:** Intercept the close/shutdown request, poll the same state at the same interval, and allow the exit at the same deadline. Note that Windows gives an app about five seconds to respond to a session end before it may be killed, so the four-minute wait survives an ordinary quit but not a system shutdown; record that divergence rather than shortening the cap.
- **Verify by:** interaction test with a stubbed merge that never finishes, timing the deadline

### PR-WIN-074 - On termination the model is saved, live spend is flushed and every MCP server the hub started is stopped
- **Source:** DroppyCode/App/AppDelegate.swift:50-55 applicationWillTerminate: `model?.saveBeforeQuit(); TokenLedger.shared.flushLiveSpend()` and, with the comment 'The MCP servers the hub started go with the app.', `MCPHub.terminateAll()`
- **Preconditions:** The process is about to exit.
- **Action:** Termination begins.
- **Expected:** In this order: the model is saved, the token ledger's live spend is flushed, and every MCP server process the hub started is terminated. A nil model skips only the save.
- **Side effects:** Writes the library and the token ledger; Terminates child processes
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Same order. Child MCP processes must be terminated as a group so their own children do not survive; on Windows a job object holding the hub's children makes this reliable (platform_adaptations.md PA-0007).
- **Verify by:** interaction test: quit with an MCP server running and assert no orphaned process remains

### PR-WIN-075 - A notification for the thread the user is already reading is not shown
- **Source:** DroppyCode/App/AppDelegate.swift:57-69 userNotificationCenter(_:willPresent:): the thread id is read from `notification.request.content.userInfo["threadID"] as? String`, and `let isOpenChat = await MainActor.run { NSApp.isActive && self.model?.selectedThreadID == notifiedID }`; `if isOpenChat { return [] }`; otherwise `return [.banner, .sound]`
- **Preconditions:** A notification arrives while the app is running.
- **Action:** The system asks how to present it.
- **Expected:** If the app is active AND the notification's threadID equals the selected thread, nothing is presented: no banner and no sound. In every other case, including an inactive app or a different thread or a missing or unparseable threadID, a banner is shown and the sound is played.
- **Side effects:** Plays the notification sound when presented
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** The equivalent suppression check on the toast path: the app is foreground and the toast's threadID matches the selected thread. The userInfo key is the literal string "threadID".
- **Verify by:** interaction test with the thread open and with a different thread selected

### PR-WIN-076 - Clicking a thread notification opens the main window and selects that thread; an update notification opens Settings on About instead
- **Source:** DroppyCode/App/AppDelegate.swift:71-86 userNotificationCenter(_:didReceive:): `let identifier = userInfo["threadID"] as? String; let isUpdate = userInfo["update"] != nil`; then on the main actor `if !isUpdate { WindowManager.shared.showMain() }`; `if let identifier, let threadID = UUID(uuidString: identifier) { self.model?.selectedThreadID = threadID }`; `NSApp.activate()`; `if isUpdate { WindowManager.shared.showSettings(page: .about) }`
- **Preconditions:** A notification was posted by the app.
- **Action:** The user clicks it.
- **Expected:** For an ordinary notification the main window is shown, the named thread is selected if the id parses, and the app is activated. For an update notification, identified by the mere presence of the userInfo key "update" whatever its value, the main window is NOT shown; the app is activated and the Settings window opens on the About page. A threadID that is present but not a valid UUID is ignored without error.
- **Side effects:** Shows a window and takes foreground
- **Persistence:** nothing persisted
- **Failure cases:** An unparseable threadID leaves the selection unchanged and still shows the window
- **Cancellation:** not cancellable
- **Windows path:** Toast activation carries the same two keys, "threadID" and "update", with the same presence-not-value test for "update" and the same ordering: show or skip the main window, set the selection, activate, then open Settings for an update.
- **Verify by:** interaction test for both notification kinds
