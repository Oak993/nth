### PR-LAUNCH-015 - Each ping resets the last-pong time and clears the reported-this-stall flag on the main thread
- **Source:** DroppyCode/Core/Support/HangWatchdog.swift:62-69 ping() - DispatchQueue.main.async { state.withLock { state.lastPong = Date(); state.reportedThisStall = false } }
- **Preconditions:** Watchdog thread running.
- **Action:** The watchdog enqueues a ping and the main thread drains it.
- **Expected:** lastPong becomes the time the main thread ran the block and reportedThisStall becomes false, so the next stall is eligible for its own report. A main thread that never drains the block never updates lastPong, which is exactly the condition the check detects.
- **Side effects:** One main-queue block every 0.5 s
- **Persistence:** Nothing is persisted.
- **Failure cases:** A wedged main thread simply never runs the block; that is the detection mechanism, not a failure.
- **Cancellation:** not cancellable
- **Windows path:** Post to the UI thread's message queue and timestamp when it runs.
- **Verify by:** unit test: block the UI thread and assert lastPong stops advancing

- **Side effects:** One os_log error line; one report file (see PR-LAUNCH-018)
- **Persistence:** A report file under the logs folder.
- **Failure cases:** None; the guard is total.
- **Cancellation:** not cancellable

- **Source:** DroppyCode/Core/Support/HangWatchdog.swift:28 - private static let sampleSeconds = 2 | DroppyCode/Core/Support/HangWatchdog.swift:83-84 - 'Runs on the watchdog's own thread, never the main one, so a stuck main thread cannot stop the report.' | DroppyCode/Core/Support/HangWatchdog.swift:95-100 - process.executableURL = URL(fileURLWithPath: "/usr/bin/sample"); process.arguments = [String(ProcessInfo.processInfo.processIdentifier), String(sampleSeconds), "-mayDie"]; one Pipe used for both standardOutput and standardError | DroppyCode/Core/Support/HangWatchdog.swift:102-112 - try process.run(); readDataToEndOfFile(); waitUntilExit(); body = String(decoding: data, as: UTF8.self); the non-zero-status prefix and the catch body
- **Preconditions:** A stall was just detected.
- **Action:** writeReport(stalledFor:) runs.
- **Expected:** The external process /usr/bin/sample is launched with the exact three-element argument vector [<this process's pid>, "2", "-mayDie"], its combined stdout and stderr are read to end, and the process is waited on. The whole operation happens on the watchdog thread so a wedged main thread cannot block it.
- **Side effects:** Launches an external process; reads its output
- **Persistence:** Feeds the report body.
- **Failure cases:** process.terminationStatus != 0: the body is prefixed with the verbatim string "sample exited with status <n>\n\n" and the rest of the captured output is kept; try process.run() throws: the body becomes the verbatim string "sample could not run: <error.localizedDescription>\n" and no output is read

The two failure bodies name a macOS tool, so their Windows wording is a deliberate, recorded choice.

### PR-LAUNCH-019 - Hang reports are trimmed to the 10 newest, by ascending file name

- **Preconditions:** A report has just been written into the folder.
- **Action:** trimReports runs.
- **Expected:** Only files whose name starts with "hang-" and ends with ".txt" are considered. They are sorted by name ascending, which given the ISO8601 stamp is chronological, and the oldest are deleted until exactly 10 remain. Files that do not match the pattern are never touched.
- **Side effects:** Deletes report files
- **Persistence:** At most 10 report files survive.
- **Failure cases:** contentsOfDirectory failing returns early and nothing is trimmed; Each removeItem is try? and a failure is silent
- **Cancellation:** not cancellable
- **Windows path:** Same 10-file cap, same prefix and suffix filter, same ascending-name ordering.
- **Verify by:** unit test seeding 13 report files and asserting the 3 oldest are removed and non-matching files survive

### PR-LAUNCH-021 - The hang watchdog is never stopped, including at quit
- **Source:** DroppyCode/Core/Support/HangWatchdog.swift:50-56 - the thread body is 'while true' with no cancellation check and no exit | DroppyCode/Core/Support/HangWatchdog.swift:17-131 - the enum declares no stop(), pause() or teardown | DroppyCode/App/AppDelegate.swift:50-55 applicationWillTerminate - saveBeforeQuit, flushLiveSpend and MCPHub.terminateAll only; the watchdog is not touched
- **Preconditions:** App is quitting.
- **Action:** The termination sequence runs.
- **Expected:** The watchdog thread keeps pinging and checking until the process itself exits. A stall during the quit sequence can therefore still produce a report.
- **Side effects:** A report can be written during the quit sequence
- **Persistence:** Possibly one more report file.
- **Cancellation:** not cancellable

- **Verify by:** restart test: the process exits cleanly with the watchdog thread still running

### PR-LAUNCH-080 - Background work started at launch is exactly four long-lived loops, one activation observer and per-thread idle timers
