## Requirements

### PR-WIN-042 - Dragging the sidebar's edge outward from a hidden sidebar starts from zero with no animation
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:322-338 beginDrag: cancels the slide task, clears isSliding and slideDelta, sets isDragging = true; if already visible it just records anchorWidth = width and returns; otherwise anchorWidth = 0 and, inside a Transaction with disablesAnimations = true, `width = 0; isVisible = true`
- **Preconditions:** The sidebar is hidden and the leading-edge strip is active (PR-WIN-054).
- **Action:** The user presses the strip at the window's leading edge.
- **Expected:** Any running slide is cancelled, the sidebar becomes visible at width zero with animations suppressed for that state change, and the drag anchors at zero so the width tracks the pointer from the very first pixel. There is no jump.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Suppress the visibility transition for this one state change; a transition here makes the sidebar jump to its resting width before the drag takes over.
- **Verify by:** interaction test: from hidden, press and drag the leading edge and assert the width starts at 0

### PR-WIN-043 - While the edge is held, the sidebar width follows the pointer clamped to 0...440, below its own minimum
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:340-342 `func drag(by translation: CGFloat) { width = min(Self.maximumWidth, max(0, anchorWidth + translation)) }` | porting/upstream_defects.md entry 64: 'drag(by:) clamps the live width to 0...440, below the 210 minimum; only endDrag() decides between collapsing (width < 110) and flooring at 210. A width between 0 and 110 during the drag is a real transient state the chat pane lays out against.'
- **Preconditions:** A sidebar edge drag is in progress.
- **Action:** The pointer moves.
- **Expected:** width becomes anchorWidth plus the translation, clamped to at least 0 and at most 440. It is NOT floored at the 210 minimum during the drag, so the sidebar can be dragged down to any width including zero, and the chat pane genuinely lays out against those intermediate widths. The floor is applied only on release.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Reproduce the transient sub-minimum widths exactly. Flooring during the drag would change how the sidebar and the chat pane behave mid-gesture, which is visible.
- **Verify by:** unit: drag to 50 and assert width == 50; interaction test that the chat pane lays out against it
- **Upstream defect 64: reproduce it faithfully, do not fix it.**

### PR-WIN-044 - Releasing the edge below 110 collapses the sidebar and restores its resting width
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:344-356 endDrag: `if width < Self.collapseThreshold { beginSlide(delta: width); withAnimation(Chrome.panelSlide) { isVisible = false }; width = restingWidth }` | DroppyCode/UI/Chrome/WindowChrome.swift:242 collapseThreshold = 110
- **Preconditions:** A drag is in progress with the live width below 110.
- **Action:** The user releases the pointer.
- **Expected:** A slide begins carrying the current width as its delta, the sidebar becomes hidden on the panel-slide animation, and the width snaps back to the resting width so a later toggle reopens at the size the user last settled on rather than at the collapse width.
- **Persistence:** persist() runs afterwards, writing both keys (PR-WIN-047).
- **Cancellation:** not cancellable
- **Windows path:** Same threshold, same order: begin the slide bookkeeping, animate to hidden, then reset the width.
- **Verify by:** interaction test: drag to 60, release, assert hidden and that a later toggle reopens at the previous resting width

### PR-WIN-045 - Releasing the edge at 110 or above settles the width at no less than 210 and makes it the new resting width
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:349-353 `let settled = max(Self.minimumWidth, width); restingWidth = settled; withAnimation(Chrome.panelSlide) { width = settled }`
- **Preconditions:** A drag is in progress with the live width at 110 or above.
- **Action:** The user releases the pointer.
- **Expected:** The width settles at the larger of 210 and the dragged width, springs there on the panel-slide animation, and becomes the new resting width. A release between 110 and 210 therefore springs outward to 210 rather than collapsing.
- **Persistence:** persist() writes "sidebarWidth" as the resting width (PR-WIN-047).
- **Cancellation:** not cancellable
- **Windows path:** Same arithmetic and the same visible spring back out to 210 from the 110...210 band.
- **Verify by:** unit: release at 150 yields 210; interaction test for the spring

### PR-WIN-046 - Toggling the sidebar opens it at its resting width and records the pane's width change for the slide
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:358-364 toggle: `let opening = !isVisible; if opening { width = restingWidth }; beginSlide(delta: opening ? -restingWidth : width); withAnimation(Chrome.panelSlide) { isVisible.toggle() }; persist()` | DroppyCode/UI/Chrome/WindowChrome.swift:263-271 doc comments for isSliding and slideDelta: 'negative while the sidebar opens, positive while it closes. Zero outside a slide.'
- **Preconditions:** The sidebar is visible or hidden.
- **Action:** The Toggle sidebar menu item, its chord, or the toolbar list button fires.
- **Expected:** Opening first sets the width to the resting width, then starts a slide whose delta is minus the resting width; closing starts a slide whose delta is plus the current width. The visibility flips on the panel-slide animation. The chat pane reads isSliding and slideDelta to treat the whole slide as one pane reshape with a single layout width rather than as a spring.
- **Persistence:** persist() writes both keys on every toggle (PR-WIN-047).
- **Cancellation:** not cancellable
- **Windows path:** Signed delta with the same sign convention, consumed by the chat pane as one reshape.
- **Verify by:** unit: the sign of slideDelta in both directions; interaction test that the timeline does not spring during the slide

### PR-WIN-047 - Every sidebar toggle and every drag release rewrites both sidebar keys, including the one that did not change
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:366-370 `private func persist() { let defaults = CaptureRun.defaults ?? .standard; defaults.set(Double(restingWidth), forKey: Key.width); defaults.set(startsOpen, forKey: Key.startsOpen) }` | DroppyCode/UI/Chrome/WindowChrome.swift:255-257 the startsOpen didSet also calls persist() | DroppyCode/UI/Chrome/WindowChrome.swift:354 and :363 persist() from endDrag and toggle | porting/upstream_defects.md entry 63: 'persist() writes sidebarStartsOpen on every sidebar toggle and every drag release although neither changes it, materialising the default false on disk after the first interaction.'
- **Preconditions:** The app has been launched and the user interacts with the sidebar.
- **Action:** The user toggles the sidebar, releases an edge drag, or changes the Appearance setting.
- **Expected:** Both "sidebarWidth" (as a Double, taken from the resting width, never the live width) and "sidebarStartsOpen" are written. The second write is redundant for a toggle or a drag, and its effect is that the default false is materialised on disk the first time the user touches the sidebar.
- **Persistence:** Writes "sidebarWidth" (Double, restingWidth) and "sidebarStartsOpen" (Bool, startsOpen), both on every persist().
- **Cancellation:** not cancellable
- **Windows path:** Reproduce the redundant write. A port that writes only the changed key leaves the settings file in a different state than upstream after the first interaction, which is observable.
- **Verify by:** restart test plus a settings-file assertion that both keys exist after one toggle
- **Upstream defect 63: reproduce it faithfully, do not fix it.**

### PR-WIN-048 - A slide is considered visually settled after 420 milliseconds, or 220 with Reduce Motion
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:279-280 `private static var slideRun: Int { NSWorkspace.shared.accessibilityDisplayShouldReduceMotion ? 220 : 420 }` with the comment 'The spring of Chrome.panelSlide is visually settled by then.' | DroppyCode/UI/Chrome/WindowChrome.swift:310-320 beginSlide: sets slideDelta and isSliding, cancels any previous task, then a task that sleeps slideRun milliseconds and, if not cancelled, clears isSliding and sets slideDelta back to 0
- **Preconditions:** A slide has begun from a toggle or a collapsing drag release.
- **Action:** Time passes, or a new slide or drag begins.
- **Expected:** After 420 ms (220 ms with Reduce Motion) the sliding flag clears and the delta returns to zero. A new slide cancels the pending clear and starts its own; beginDrag also cancels it and clears both immediately, so a drag that interrupts a slide leaves no stale delta.
- **Persistence:** nothing persisted
- **Cancellation:** The pending clear is cancelled by a later beginSlide or by beginDrag; a cancelled task performs no writes.
- **Windows path:** A cancellable timer per slide with the same two durations, reading the animations-enabled system flag live.
- **Verify by:** unit: start a slide, start a second before the first expires, assert only one clear fires
