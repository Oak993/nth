### PR-MCP-059 - connect commits drafts, secrets to protected storage and the rest to the connection
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:103-112 connect's draft-commit loop | DroppyCode/Services/MCP/MCPKeychain.swift:30-50 set
- **Preconditions:** Drafts exist for the entry.
- **Action:** connect(entry) runs.
- **Expected:** For each field of the entry in field order, if the draft map has a value for that key: when field.kind is .secret, write it to protected storage under account "MCP <entry id> <field key>"; otherwise assign connection.values[field.key] = the text verbatim, including an empty string. Fields with no draft entry are untouched. The credential write's return value is ignored here, so a storage failure on connect is silent - unlike saveCustomValues, which checks it.
- **Side effects:** one protected-storage write per drafted secret field
- **Persistence:** secrets under "MCP <id> <field>"; non-secret drafted values into mcp.json on the save that follows
- **Failure cases:** a protected-storage write that fails is not reported; the probe then runs without the secret and fails with the server's own error
- **Cancellation:** not cancellable
- **Windows path:** Same order and the same ignored return value. Do not add error reporting here - saveCustomValues is the only path that surfaces a storage failure.
- **Verify by:** unit plus an integration test with a failing credential store

### PR-MCP-060 - connect stores the connection, clears the draft, saves, sets connecting and probes
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:113-117 the tail of connect
- **Preconditions:** none
- **Action:** connect(entry) finishes its commit phase.
- **Expected:** In this exact order: connections[entry.id] = connection; drafts[entry.id] = nil; save() writes mcp.json; states[entry.id] = .connecting; startProbe(entry). exportAll is NOT called here, so a newly connecting server does not reach any provider config until its probe succeeds.
- **Side effects:** writes <data root>/mcp.json atomically
- **Persistence:** mcp.json now carries the connection row with connectedAt still nil
- **Failure cases:** a failed write is swallowed (try?) and the in-memory state still shows connecting
- **Cancellation:** the probe started here is the cancellable part
- **Windows path:** Same order. The absence of an exportAll here is load-bearing: it keeps a half-configured server out of the providers.
- **Verify by:** unit asserting no provider config is rewritten on connect, only on probe success

### PR-MCP-064 - A successful probe writes the tools and version only when a connection row still exists, but always marks the state connected

### PR-MCP-065 - An OAuth probe that is refused once signs out, unregisters and probes a second time
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:322-333 the two catch clauses inside startProbe | DroppyCode/Services/MCP/MCPStore.swift:303-314 probeOnce
- **Preconditions:** The resolved server has a non-nil oauthUpstream.
- **Action:** The first probe throws MCPProbeError.unauthorizedOAuth, or MCPProbeError.http with status 401 or 403.
- **Expected:** Both catch clauses do the same three things: try Task.checkCancellation(); MCPOAuth.signOut(serverID:); MCPProxy.shared.unregister(serverID:); then call probeOnce again. probeOnce, finding the server no longer signed in, runs the full browser sign-in, re-registers the proxy route and probes through it. There is exactly one retry: a second failure propagates to the outer catch. Both clauses are guarded on resolved.oauthUpstream != nil, so a plain HTTP server that answers 401 is not retried.
- **Side effects:** deletes the OAuth session and client from protected storage; removes then re-adds the proxy route; opens the user's browser for a fresh sign-in
- **Persistence:** a new OAuth session is stored on success
- **Failure cases:** the second probe's error becomes the card's .failed message; a cancellation between the two attempts aborts silently
- **Cancellation:** checkCancellation runs before the sign-out, so a cancelled probe does not destroy a working session
- **Windows path:** Same two clauses, same single retry, same cancellation check placement.
- **Verify by:** contract fixture: a stub MCP server answering 401 once then succeeding

### PR-MCP-066 - probeOnce signs in, registers the proxy route, then probes through the route
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:303-314 probeOnce
- **Preconditions:** A resolved server.
- **Action:** The probe task runs one attempt.
- **Expected:** If resolved.oauthUpstream is non-nil: when MCPOAuth.isSignedIn(serverID:) is false, run MCPOAuth.signIn(serverID:serverName:url:) with the entry's name and the upstream address, which opens the browser and waits; then always call MCPProxy.shared.register(serverID:upstream:headers: [:], usesOAuth: true). Finally call MCPProbe.probe(resolved) - which, because resolve pointed url at the proxy, goes through the local route exactly as every provider will. For a non-OAuth server the whole block is skipped and the probe runs directly.
- **Side effects:** may open the default browser and start a loopback callback listener; adds a route to the proxy table
- **Persistence:** the OAuth session lands in protected storage during signIn
- **Failure cases:** signIn throws an MCPOAuthError, whose errorDescription becomes the card's failure message
- **Cancellation:** cancelling the probe task cancels the callback listener through its task-cancellation handler
- **Windows path:** Same order: sign in, register, probe through the loopback route. Probing the upstream directly would skip the proxy and hide proxy faults.
- **Verify by:** integration test asserting the probe request arrives at the local proxy, not the upstream
