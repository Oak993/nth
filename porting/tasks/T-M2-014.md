### PR-STORE-142 - A recipe effort is applied only when the resolved model actually offers it
- **Source:** DroppyCode/Core/Models/HydraCookbook.swift:44-48 - doc comment "The effort asked for when the model offers it; nil otherwise, which keeps the default." then static func effort(_ wanted: String?, for option: ModelOption?) -> String? { guard let wanted, let option, option.efforts.contains(wanted) else { return nil }; return wanted }
- **Preconditions:** A recipe has been matched to a concrete model.
- **Action:** Building the pair from the recipe.
- **Expected:** The wanted effort is returned only when it is non-nil, a model option was resolved, and that option’s efforts list contains the wanted value exactly. Otherwise nil is returned, which leaves the model on its own default effort. The comparison is an exact string containment check against the catalog’s effort names, with no case folding and no aliasing, so "high", "medium" and "max" must appear verbatim in the catalog.
- **Persistence:** The resulting effort is stored on the created HydraPair.
- **Failure cases:** A model whose catalog spells the level differently gets nil and keeps its default.
- **Cancellation:** not cancellable
- **Windows path:** Same exact-match rule with no normalisation.
- **Verify by:** unit over a model with and without the wanted effort

### PR-STORE-143 - A pair counts as already added when its two providers and two models match, ignoring effort
- **Source:** DroppyCode/Core/Models/HydraCookbook.swift:50-53 - doc comment "Whether a pair like this one is already set up: the same providers and models." then static func isAdded(_ pair: HydraPair, in pairs: [HydraPair]) -> Bool { pairs.contains { $0.provider == pair.provider && $0.headsProvider == pair.headsProvider && $0.orchestratorModel == pair.orchestratorModel && $0.workerModel == pair.workerModel } }
- **Preconditions:** Some pairs are already configured.
- **Action:** The ready-made list decides whether to mark a recipe as added.
- **Expected:** Exactly four fields are compared: provider, headsProvider, orchestratorModel and workerModel. Efforts, the head cap, the pair name and the head profiles are deliberately NOT compared, so the two same-model recipes that differ only in effort (for example "Opus 5 max, Opus 5 medium" against another Opus-on-Opus pair) read as already added once either is configured.
- **Failure cases:** This is the reason two efforts of one model cannot both be offered as distinct additions; it is source behaviour and is reproduced.
- **Cancellation:** not cancellable
- **Windows path:** Compare exactly these four fields and no more.
- **Verify by:** unit with two pairs differing only in effort
