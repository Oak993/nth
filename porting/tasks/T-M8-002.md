### PR-UPDATE-041 - install() runs at most one install at a time and never in a development build
- **Source:** DroppyCode/App/AppUpdater.swift:261-283 install(_ update:) - guard installTask == nil, !AppInfo.isDevelopment else { return }; installTask = Task { defer { installTask = nil }; progress.begin(); ... }
- **Preconditions:** The user pressed the install button with a waiting release.
- **Action:** install() is called.
- **Expected:** A second call while an install is in flight does nothing at all: no second begin(), no second download. In a development build the call is a complete no-op, so the button appears to do nothing. The task clears installTask on every exit path.
- **Persistence:** None at this step.
- **Failure cases:** Silent no-op in both guarded cases, with no message shown.
- **Cancellation:** not cancellable; nothing cancels installTask.
- **Windows path:** Same single-flight guard in the main process. The install is genuinely not cancellable once started; do not add a cancel affordance the source does not have.
- **Verify by:** interaction test

### PR-UPDATE-042 - The install sequence is download, verify, stage, hand off, with one progress report between each step
- **Source:** DroppyCode/App/AppUpdater.swift:263-282 progress.begin(); let image = try await download(update.downloadURL); progress.beginVerification(); let staged = try await stage(image:expectedVersion:); progress.beginStaging(); try handOff(staged:version:); catch { progress.fail(); alert }
- **Preconditions:** install() passed its guards.
- **Action:** The install task runs.
- **Expected:** Exactly this order: begin, download (with byte reports), beginVerification, stage (mount, copy, signature, version, Gatekeeper), beginStaging, handOff. Note that beginVerification is reported BEFORE stage() runs and beginStaging AFTER it returns, so the naming and the actual work are offset by one step; reproduce the reporting points as written. Any throw goes to fail() plus the alert.
- **Side effects:** See the individual steps.
- **Persistence:** The relaunch marker, written inside handOff.
- **Failure cases:** Any thrown error: progress.fail() then a modal alert (PR-UPDATE-055).
- **Cancellation:** not cancellable
- **Windows path:** Same five reporting points in the same order, even though the Windows work between them differs. UNK-0009 is resolved by OD-0008 C6: until the owner has a Windows release feed no release qualifies, so this path is not reached and its live verification waits on that feed.
- **Verify by:** interaction test

### PR-UPDATE-047 - The downloaded image is mounted read-only into a private 0700 staging directory and the app inside is copied out
- **Source:** DroppyCode/App/AppUpdater.swift:299-330 stage - staging = temporaryDirectory/DroppyCodeUpdate-<uuid>/; createDirectory(withIntermediateDirectories: true, attributes: [.posixPermissions: 0o700]); mount = staging/image; Shell.run(/usr/bin/hdiutil, ["attach", "-nobrowse", "-readonly", "-noautoopen", "-mountpoint", mount.path, image.path], timeout: 120); staged = staging/<Bundle.main.bundleURL.lastPathComponent>; contents.first(where: { $0.pathExtension == "app" }); Shell.run(/usr/bin/ditto, [source.path, staged.path], timeout: 300); Shell.run(/usr/bin/hdiutil, ["detach", mount.path, "-force"], timeout: 60); removeItem(at: image)
- **Preconditions:** The artifact downloaded successfully.
- **Action:** stage() runs.
- **Expected:** A per-install staging directory with owner-only permissions; the image attached with exactly those five hdiutil arguments and a 120 s timeout; the first entry in the mount root whose path extension is "app" copied by ditto (300 s) to a path whose last component equals the RUNNING bundle's file name, so the installed bundle keeps its filename; then the image detached with -force (60 s) and the downloaded file deleted. The detach and the delete run on BOTH the success and the error path.
- **Side effects:** Four child processes.; A staging directory tree.; Deletion of the downloaded artifact.
