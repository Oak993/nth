### PR-SETTINGS-085 - Every setting persists itself on write, with no explicit save and no debounce
- **Source:** DroppyCode/App/AppSettings.swift:110-112 - @MainActor @Observable final class AppSettings | DroppyCode/App/AppSettings.swift:189-191, :201-203, :253-255 and every other stored property - each declares `didSet { defaults.set(..., forKey: Key....) }`, for example :253-255 `var appZoom: Int { didSet { defaults.set(appZoom, forKey: Key.appZoom) } }` | DroppyCode/App/AppSettings.swift:184 - @ObservationIgnored private let defaults = WebsiteCaptures.defaults ?? .standard
- **Preconditions:** An AppSettings instance exists.
- **Action:** Any settings property is assigned, from a control, from code, or from the model picker.
- **Expected:** The write is persisted inside the property's own observer, synchronously, on the main actor. There is no Save button, no apply step, no debounce and no batching anywhere in the settings window. A slider dragged across its range therefore writes on every step, and a text editor bound to a setting writes on every keystroke.
- **Side effects:** A defaults write per assignment
- **Persistence:** UserDefaults, immediately.
- **Failure cases:** A defaults write that fails is not reported anywhere; UserDefaults.set has no error path.
- **Cancellation:** There is no cancel: a change is committed the moment it is made, and closing the window does not revert anything.
- **Windows path:** Persist on change, but coalesce the disk write behind a short timer so a slider drag does not fsync per frame. The in-memory value must still update synchronously so the UI is identical; only the flush is coalesced. Record the coalescing as a deliberate platform decision.
- **Verify by:** restart test: change a value, kill the process without a clean quit, restart and assert the value survived

### PR-SETTINGS-089 - The Keychain is read once, lazily and off the main thread, and the fill must not write back
- **Source:** DroppyCode/App/AppSettings.swift:364-366 comment - "Read once, on the first ask, and cached: a Keychain query on every render made Settings lag, and two of them before the window exists made launch wait on securityd." | DroppyCode/App/AppSettings.swift:402-403 - @ObservationIgnored private var didReadKeychain / isReadingKeychain | DroppyCode/App/AppSettings.swift:433-441 readKeys(fallbacks:) - one Keychain round trip per key, four in all, nonisolated and static | DroppyCode/App/AppSettings.swift:450-453 readKeychainIfNeeded - guards on didReadKeychain and fills synchronously
- **Preconditions:** The app has launched. No key has been asked for yet.
- **Action:** Either the window comes up and the background load runs, or something asks for a key first.
- **Expected:** The four keys start empty. The Keychain is queried exactly once per launch, four round trips in one pass, and cached. The background load runs the query off the main actor so neither the first frame nor the first ask waits on the credential daemon; an ask that arrives first reads synchronously for itself, and whichever happens first wins because both are guarded on the same flag. While the four values are being filled in, a re-entry flag suppresses every observer, so the fill writes nothing to the Keychain and nothing to the plaintext fallback. Each observer also skips when the new value equals the old one, so a no-op assignment never writes.
- **Side effects:** Four credential-store reads; Possible deletion of plaintext fallback keys after the fill
- **Persistence:** Reads the Keychain and the four fallback keys; may delete the fallback keys.
- **Failure cases:** A Keychain read that returns empty is treated as 'not in the Keychain', so the plaintext fallback is used as the value and is left in place.
- **Cancellation:** The background load is a detached task with no cancellation path; a synchronous ask that lands first simply makes it a no-op.
- **Windows path:** One lazy, cached, asynchronous read of the four secrets from Windows Credential Manager (OD-0008 B3), with the same re-entry guard so hydrating the fields does not re-write the store. Windows has no securityd launch stall, but the single cached read is kept so the observable behaviour and the number of store reads match. A plaintext settings value is only ever deleted, never used as a place to write (OD-0008 A6, PR-SETTINGS-088).
- **Verify by:** unit test: hydrate the four fields from a stubbed Credential Manager and assert zero writes back; assert exactly four reads per launch
