### PR-STORE-062 - Attachment copies and transcodes run off the main actor and append in source order
- **Source:** DroppyCode/Services/Store/Storage.swift:150-162 - @MainActor @discardableResult static func attach(...) -> Task<Void, Never>? { ... return Task.detached(priority: .userInitiated) { let imported = batch.compactMap(importSource); let kept = await MainActor.run { let room = max(0, attachmentLimit - attachments.wrappedValue.count); attachments.wrappedValue.append(contentsOf: imported.prefix(room)); return room }; ... } }
- **Preconditions:** At least one free slot.
- **Action:** Dropping several files at once.
- **Expected:** A detached user-initiated task imports every source in order, dropping any that fail (compactMap). Back on the main actor the free room is recounted, because more attachments may have arrived meanwhile, and only that many of the imported results are appended, in the original order. The task handle is returned and the result is discardable.
- **Side effects:** Files copied into <root>/attachments/; Image transcodes on the detached task
- **Persistence:** One file per accepted attachment under <root>/attachments/
- **Failure cases:** A source that fails to import is silently omitted; nothing is reported.
- **Cancellation:** The returned task is cancellable by the caller, but the import loop performs no cancellation check, so cancelling has no effect until after every source has already been copied.
- **Windows path:** Same detached import, same recount on the UI thread, same order. The absence of a cancellation check inside the loop is source behaviour and is reproduced.
- **Verify by:** interaction test dropping a large video and asserting the composer stays responsive

### PR-STORE-063 - Copies that arrive past the limit are deleted again
- **Source:** DroppyCode/Services/Store/Storage.swift:161 - for orphan in imported.dropFirst(kept) { try? FileManager.default.removeItem(at: orphan.url) }
- **Preconditions:** More attachments were added by another route while this batch was being copied.
- **Action:** The batch lands.
- **Expected:** Every imported attachment past the recounted room has its copied file removed immediately, so it never becomes an orphan waiting for the daily sweep. The deletion failure is swallowed by try?.
- **Side effects:** Files removed from <root>/attachments/
- **Failure cases:** A failed removal leaves a file that the orphan sweep will collect a day later.
- **Cancellation:** not cancellable
- **Windows path:** Same immediate cleanup. PA-0015: the file was just written by this process, so a transient sharing violation is plausible; retry before giving up, then fall through to the same silent swallow. Windows: PA-0015 applies - file replace, delete and rename can fail transiently with a sharing violation, so the operation retries with backoff, clears the read-only attribute before a delete, uses an atomic replace primitive and surfaces a real error after a bounded number of attempts rather than dropping the write.
- **Verify by:** interaction test racing two drops

### PR-STORE-066 - The MIME type of a stored attachment comes from a fixed ten-branch extension table
- **Source:** DroppyCode/Services/Store/Storage.swift:218-232 - enum MimeType { static func of(_ fileExtension: String) -> String { switch fileExtension.lowercased() { case "png": "image/png"; case "jpg", "jpeg": "image/jpeg"; case "gif": "image/gif"; case "webp": "image/webp"; case "heic": "image/heic"; case "pdf": "application/pdf"; case "json": "application/json"; case "md", "markdown": "text/markdown"; default: "text/plain" } } }
- **Preconditions:** None.
- **Action:** Any attachment import.
- **Expected:** The extension is lowercased and mapped exactly: "png" -> "image/png"; "jpg" and "jpeg" -> "image/jpeg"; "gif" -> "image/gif"; "webp" -> "image/webp"; "heic" -> "image/heic"; "pdf" -> "application/pdf"; "json" -> "application/json"; "md" and "markdown" -> "text/markdown"; everything else, including no extension at all, -> "text/plain". There is no system type lookup and no content sniffing.
- **Persistence:** The resulting string is stored in the Attachment record inside the thread document.
- **Failure cases:** A .heif source never reaches this table with "heif" because importSource transcodes it to jpg first; an unrecognised binary is labelled "text/plain", and Attachment.isImage (mimeType.hasPrefix("image/")) is therefore false for it.
- **Cancellation:** not cancellable
- **Windows path:** The same literal table, in this order, with the same default. Do not substitute a registry or system MIME lookup: Windows would return different strings, which providers see.
- **Verify by:** unit covering all ten branches plus the default

- **Failure cases:** Missing pixel dimensions, a failed thumbnail creation, a failed destination creation or a failed finalize all return nil.
- **Cancellation:** not cancellable

- **Verify by:** contract fixture comparing dimensions and orientation of the produced file
