### PR-WIN-232 - A drag handle re-reads the real pointer position when it attaches to a window, so a handle that appears already under the pointer shows its grip at once
- **Source:** DroppyCode/UI/Chrome/DragHandle.swift:127-138 viewDidMoveToWindow: `if window == nil, isDragging { isDragging = false; if dragCursor != nil { NSCursor.pop() } }`; then, `if grip != nil { refreshHover(); updateGrip(animated: false) }` | DroppyCode/UI/Chrome/DragHandle.swift:142-151 refreshHover - reads `window.mouseLocationOutsideOfEventStream`, converted into the view, and sets isHovering from bounds.contains(point) | DroppyCode/App/Views/Terminal/TerminalPanel.swift:121-130 - the terminal drawer's strip attaches when the drawer first appears or when it is shown again; if the pointer already sits over the top 8-point strip at that moment, the grip must be shown
- **Preconditions:** A DragHandleView (or a view that owns one) is added to, or moved between, windows.
- **Action:** The handle attaches to a window.
- **Expected:** When the handle has a grip configured, attaching to a window immediately re-reads the pointer's actual current position and, if it falls inside the handle's bounds, shows the grip at its shown length and 0.6 opacity with animations disabled (a snap, not a transition). This is not gated by refreshesHoverOnLayout: it always runs on attach, for every DragHandle (Sidebar's strip and Terminal's alike). If the handle was mid-drag when it left its previous window, that drag state is cleared first (PR-WIN-233) before the hover re-read runs.
- **Persistence:** None.
- **Failure cases:** No window (window is nil): the drag-state clear still runs, but refreshHover and updateGrip are skipped since there is no window's mouse location to read
- **Cancellation:** not cancellable
- **Windows path:** On attach (control loaded into a visual tree, or moved between windows), hit-test the pointer's current position against the handle's bounds and set the grip's shown state accordingly, unanimated. This matters most for a drawer or panel that can appear already under a resting pointer.
- **Verify by:** interaction test: rest the pointer over where a hidden drawer's strip will appear, show the drawer, assert the grip is shown at once with no animation

### PR-WIN-233 - A drag handle taken out of its window mid-drag clears its drag state and pops a pushed drag cursor, but does NOT call onEnd
- **Source:** DroppyCode/UI/Chrome/DragHandle.swift:127-133 viewDidMoveToWindow: `if window == nil, isDragging { isDragging = false; if dragCursor != nil { NSCursor.pop() } }` - no call to onEnd or onChange | DroppyCode/App/Views/Chat/SubagentPanel.swift:724-731 (B2) - the only place this state was previously covered, in the panel's own PanelDragHandleView, before N8 shares it
- **Preconditions:** A drag handle is mid-drag (isDragging true) when its view is removed from its window - for example the drawer or panel it belongs to is dismissed or toggled closed while the mouse button is still held.
- **Action:** The handle's view leaves its window.
- **Expected:** isDragging is cleared to false and, if a dragCursor was pushed for this drag, it is popped. Critically, onEnd is NOT called and onChange is not called with a final delta: whatever the caller does in onEnd (Terminal commits terminalHeight and clears isTerminalResizing; the sidebar strip commits its width) does not run. A caller that only commits state in onEnd can therefore be left in a stuck intermediate state after this happens.
- **Side effects:** A pushed cursor is popped; The caller's onEnd/onChange side effects (a settings commit, a flag reset) do NOT run
- **Persistence:** Whatever onEnd would have written is NOT written.
- **Failure cases:** A caller relying on onEnd for cleanup (clearing a busy flag, committing a value) must handle this path separately, since it will not fire here
- **Cancellation:** not applicable; this IS the cancellation-like path
- **Windows path:** When a drag handle's control is detached from its visual tree or moved to a different window mid-drag, clear the drag state and release any captured pointer/pushed cursor, but do not invoke the completion callback. Record this as a pre-existing port gap where the current implementation calls end() on capture loss instead (6.2): TerminalPanel's capture-lost path must be corrected to match this record, not the other way around.
- **Verify by:** interaction test: start a drag, then remove the handle's window (or dismiss the panel) while still holding the mouse button; assert onEnd was never called and isDragging is false afterward

### PR-WIN-234 - DragHandleView's component contract: axis travel signs, grip and glow defaults, the 0.18 s/4 pt metrics, slop gating, and cursor-identity invalidation
- **Source:** DroppyCode/UI/Chrome/DragHandle.swift:257-266 travel(to:) - `.horizontal`: `CGSize(width: point.x - pressOrigin.x, height: 0)`; `.vertical`: `CGSize(width: 0, height: point.y - pressOrigin.y)`; `.free`: `CGSize(width: point.x - pressOrigin.x, height: pressOrigin.y - point.y)` (y inverted, running down like a panel offset, unlike the other two axes which run up) | DroppyCode/UI/Chrome/DragHandle.swift:18-30 Grip defaults: alpha 0.6, hoverGlow 0.05, dragGlow 0.10, glowInset nil, refreshesHoverOnLayout false | DroppyCode/UI/Chrome/DragHandle.swift:58-61 Metrics: glowRadius 4, duration 0.18 | DroppyCode/UI/Chrome/DragHandle.swift:198-220 slop gating in mouseDown/mouseDragged: with slop 0, isDragging becomes true and onBegin fires on mouseDown itself; with slop > 0, mouseDown leaves isDragging false, and mouseDragged waits until `abs(travel.width) >= slop || abs(travel.height) >= slop` before setting isDragging true and firing onBegin
- **Preconditions:** None; a component-level contract every DragHandle instance follows regardless of its caller.
- **Action:** Any DragHandle is configured, dragged, or re-rendered.
- **Expected:** Travel is reported in the axis's own terms: horizontal reports x only, vertical reports y only (positive means up, i.e. AppKit's native sense), and free reports both with y inverted to run down, matching a panel's own offset convention. Grip defaults (usable without setting every field) are alpha 0.6, hoverGlow 0.05, dragGlow 0.10, no glow (glowInset nil) and no layout-driven hover re-read (refreshesHoverOnLayout false); Sidebar overrides glowInset and refreshesHoverOnLayout, Terminal overrides neither. Every grip's animation, when animated, runs 0.18 s ease-out; a glow's corner radius is always 4. A handle with slop 0 (Sidebar, Terminal) starts dragging on press; a handle with slop > 0 (none exist yet, but the mechanism supports it) waits for that much combined travel first. Setting `cursor` to the same NSCursor instance is a no-op (identity check); an actual change invalidates the window's cursor rects so the new cursor takes effect without waiting for the next mouse move. Reconfiguring a handle with the same or a compatibly-present grip never interrupts a hover or drag animation already in flight.
- **Persistence:** None.
- **Cancellation:** not applicable; this is a static contract
- **Windows path:** Port this as the shared DragHandleView/DragHandle component's own contract, independent of any one caller: the axis travel signs (free's y-inversion is easy to get backwards, and SubagentPanel.cs:908-913 already has this exact sign bug pre-existing at B2, per 6.2), the grip/glow defaults, the 0.18 s/4 pt metrics, slop as a configurable threshold even though no current caller sets it above 0, cursor-identity-based invalidation (not value equality), and animation continuity across re-renders.
- **Verify by:** unit: travel signs for each axis, including a regression test for the free-axis y-inversion; the default field values; slop 0 versus slop > 0 gating; setting the same cursor instance twice does not re-invalidate; reconfiguring mid-animation does not reset it
