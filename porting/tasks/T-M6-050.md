### PR-LAUNCH-009 - Legacy migration is skipped entirely in a development build
- **Source:** DroppyCode/App/LegacyMigration.swift:10 - 'guard !AppInfo.isDevelopment else { return }' as the first statement of run() | DroppyCode/Core/Support/Text.swift:5 AppInfo.isDevelopment - Bundle.main.bundleIdentifier == "iordv.droppycode.dev"
- **Preconditions:** Prologue step 4; the running bundle identifier is "iordv.droppycode.dev".
- **Action:** LegacyMigration.run() is called.
- **Expected:** run() returns immediately. No defaults are copied, no folder is moved, and the marker key is NOT written, so a later release build on the same machine still performs the migration.
- **Persistence:** Nothing is persisted in a development build.
- **Cancellation:** not cancellable
- **Windows path:** Keep a build-identity check with the same semantics: a development build never migrates and never consumes the marker. The identity token is a Windows build identifier, not a bundle id.
- **Verify by:** unit test with the development identity set

### PR-LAUNCH-010 - Legacy migration runs at most once, guarded by the boolean default "migratedFromEarlierName"
- **Source:** DroppyCode/App/LegacyMigration.swift:5 - private static let marker = "migratedFromEarlierName" | DroppyCode/App/LegacyMigration.swift:11-12 - 'let defaults = UserDefaults.standard' then 'guard !defaults.bool(forKey: marker) else { return }' | DroppyCode/App/LegacyMigration.swift:25 - defaults.set(true, forKey: marker)
- **Preconditions:** Release build; the marker key is absent or false.
- **Action:** LegacyMigration.run() is called.
- **Expected:** The migration body runs, and at the end the key "migratedFromEarlierName" is set to true in the standard defaults. On every later launch the guard short-circuits and the migration never runs again.
- **Side effects:** One boolean write to the standard defaults
- **Persistence:** UserDefaults.standard key "migratedFromEarlierName", Bool, absent by default (read as false).
- **Failure cases:** None; the write is unconditional once the body is reached.
- **Cancellation:** not cancellable
- **Windows path:** Same key name, same type, same default, in the Windows settings store.
- **Verify by:** restart test: second launch performs no migration work

### PR-LAUNCH-011 - Legacy migration copies every key of the former bundle's defaults domain, and an existing value always wins
- **Source:** DroppyCode/App/LegacyMigration.swift:6 - private static let formerBundleIdentifier = "iordv.cody" | DroppyCode/App/LegacyMigration.swift:13-17 - 'if let former = defaults.persistentDomain(forName: formerBundleIdentifier) { for (key, value) in former where defaults.object(forKey: key) == nil { defaults.set(value, forKey: key) } }'
- **Preconditions:** Release build, marker false, a persistent defaults domain exists for "iordv.cody".
- **Action:** The migration body runs.
- **Expected:** Every key in the former domain whose current value is nil is written into the standard defaults under the same key with the same value. A key that already has any current value is left untouched. Keys are copied in unspecified dictionary order; the outcome does not depend on order because each decision is per key.
- **Side effects:** Reads another bundle identifier's persistent defaults domain; writes zero or more keys into the standard defaults
- **Persistence:** Arbitrary keys, copied verbatim under their own names.
- **Failure cases:** No former domain: the whole 'if let' is skipped and the folder move is still attempted.
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY: Windows has no per-bundle-identifier defaults domain. The port must define the former settings location for the earlier Windows name and reproduce the existing-value-wins rule. If the Windows build has no predecessor under the former name, the copy has no source and only the marker write applies.
- **Verify by:** unit test with a seeded former store, asserting existing values win

### PR-LAUNCH-012 - Legacy migration renames the Application Support folder "Cody" to "Droppy Code" only when the destination does not exist
- **Source:** DroppyCode/App/LegacyMigration.swift:7 - private static let formerSupportFolder = "Cody" | DroppyCode/App/LegacyMigration.swift:18-24 - support = FileManager.default.urls(for: .applicationSupportDirectory, in: .userDomainMask)[0]; formerLibrary = support/"Cody"; library = support/"Droppy Code"; 'if fileManager.fileExists(atPath: formerLibrary.path), !fileManager.fileExists(atPath: library.path) { try? fileManager.moveItem(at: formerLibrary, to: library) }'
- **Preconditions:** Release build, marker false.
- **Action:** The migration body reaches the folder step.
- **Expected:** If ~/Library/Application Support/Cody exists and ~/Library/Application Support/Droppy Code does not, the former is moved (a single rename) to the latter, carrying the library, thread histories and attachments. If either condition fails, nothing is moved and an existing new-name library is never clobbered. The destination name is the literal "Droppy Code" with a space, created with isDirectory: true.
- **Side effects:** One filesystem move of a whole directory tree
- **Persistence:** The library, thread documents and attachments change location.
- **Failure cases:** The move is wrapped in try? - a failure (permissions, cross-volume, partial state) is silently ignored, the marker is still set to true at :25, and the migration is never retried.
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY: %APPDATA% or %LOCALAPPDATA% in place of ~/Library/Application Support (port_impacts.md entry 113 requires the two-root split to be chosen deliberately). The same existence preconditions and the same silent-failure-then-mark-done behavior must be reproduced.
- **Verify by:** integration test over the four existence combinations, plus a failing-move case asserting the marker is still set

### PR-LAUNCH-013 - UPSTREAM DEFECT: the migration's destination folder is the hardcoded literal "Droppy Code", not AppInfo.name
- **Source:** DroppyCode/App/LegacyMigration.swift:21 - support.appendingPathComponent("Droppy Code", isDirectory: true), a string literal | DroppyCode/Services/Store/Storage.swift:22 - base.appendingPathComponent(AppInfo.name, isDirectory: true), the folder the app actually reads | DroppyCode/Core/Support/Text.swift:4 AppInfo.name - CFBundleDisplayName with fallback "Droppy Code" | porting/upstream_defects.md:105 entry 46
- **Preconditions:** Release build, marker false, the old folder present.
- **Action:** The migration moves the folder while the app's display name is not "Droppy Code".
- **Expected:** The migration writes to a folder named by the literal while Storage reads from a folder named by the display name. With the display name unchanged the two agree and the defect is invisible; with a changed display name the migrated library lands in a folder the store never reads and the user appears to have lost everything. This is upstream behavior and is recorded as such.
- **Side effects:** A folder the store does not read
- **Persistence:** The moved library tree.
- **Failure cases:** Silent: nothing reports the mismatch.
- **Cancellation:** not cancellable
- **Windows path:** SIGNIFICANT for this port, because the product identity is renamed by owner-approved deviation. The literal and the store's name-derived path must be reconciled as a deliberate, recorded decision rather than copied blindly; copying the literal would migrate into a folder the Windows store never reads, which is data loss rather than an ordinary quirk. Escalate under the standing contract if reproducing it would strand a user's library.
- **Verify by:** integration test asserting the migrated folder is the folder the store subsequently reads
- **Upstream defect 46: reproduce it faithfully, do not fix it.**

### PR-STORE-103 - Settings and the store folder are carried over once from the app’s former name
- **Source:** DroppyCode/App/LegacyMigration.swift:1-26 - doc comment "Carries settings, the library and thread histories over from the app’s earlier name, once."; private static let marker = "migratedFromEarlierName"; formerBundleIdentifier = "iordv.cody"; formerSupportFolder = "Cody"; run() { guard !AppInfo.isDevelopment else { return }; guard !defaults.bool(forKey: marker) else { return }; if let former = defaults.persistentDomain(forName: formerBundleIdentifier) { for (key, value) in former where defaults.object(forKey: key) == nil { defaults.set(value, forKey: key) } }; ... defaults.set(true, forKey: marker) }
- **Preconditions:** A release build that has not run the migration before.
- **Action:** App launch.
- **Expected:** A development build skips the migration entirely. Otherwise, if the preference key "migratedFromEarlierName" is not already true, every preference from the domain "iordv.cody" is copied across, but only for keys the current domain does not already hold, so the current app’s own settings always win. The marker is then set to true so it never runs again.
- **Side effects:** Writes preference keys; May move a directory
- **Persistence:** Preference key "migratedFromEarlierName" (Bool). The copied keys keep their original names.
- **Failure cases:** The marker is set at the end unconditionally, even when the folder move failed, so a failed migration is never retried.
- **Cancellation:** not cancellable
- **Windows path:** The macOS persistent-domain merge has no Windows equivalent, since a Windows build has never shipped under the former name and there is no "iordv.cody" preference domain on the machine. Record this as a no-op on Windows rather than inventing a Windows source to read. The folder-move half is likewise a no-op unless the port defines its own earlier-name folder, which it must not do without a ruling.
- **Verify by:** unit on the guard order; the migration itself is unreachable on a first Windows install
