### PR-RUNTIME-060 - generateTitle writes a 48-character single line and then asks the text engine for a better one

- **Preconditions:** A turn is starting in a directory.
- **Action:** The detached capture task is started.
- **Expected:** The working directory is the thread's worktree path when it has one, otherwise the project path. The ref is refs/droppy-code/checkpoints/ followed by the thread UUID lowercased, a slash, the turn index, a hyphen and the literal phase "start". A non-repository directory yields false and no checkpoint. The capture runs concurrently with the session start and both are awaited before the prompt is sent, so nothing the agent does can slip past the snapshot.

### PR-RUNTIME-064 - A turn awaits any warm-up, starts the session, records the base checkpoint and then awaits the session
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:1242-1252 - if let warmup { await warmup.value }; let start = Task { _ = try await self.ensureSession(directory: directory) }; if await checkpoint.value { updateTurn(turn.id) { $0.baseCheckpoint = checkpointRef } }; try await start.value | DroppyCode/App/Runtime/ThreadRuntime.swift:1243-1246 - the comment on why the session is picked up from the runtime rather than returned as a value
- **Preconditions:** The checkpoint task has been started.
- **Action:** The do block runs.
- **Expected:** Exactly this order: wait out any warm-up so a session started while the message was typed is the one used; start ensureSession as its own task; await the checkpoint and write baseCheckpoint onto the turn when it succeeded; then await the session start, which rethrows into the catch. The session is read back from the runtime's own field afterwards because a session is not Sendable.
- **Side effects:** Possibly a provider process start; a turn record write.
- **Persistence:** TurnRecord.baseCheckpoint.
- **Failure cases:** ensureSession throwing lands in the catch (PR-RUNTIME-077).
- **Cancellation:** Cancelling the enclosing task cancels the awaits; the detached checkpoint task keeps running.
- **Windows path:** Keep the concurrency: sequencing the checkpoint before the session start adds seconds to every first message on a large repository.
- **Verify by:** interaction test asserting both tasks overlap
