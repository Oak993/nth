### PR-CHAT-129 - Every finished reply's markdown is parsed off the main thread when a thread opens and when a turn ends
- **Source:** DroppyCode/App/Views/Chat/ThreadTimeline.swift:272-280 warmMarkdown - collects every non-streaming assistant message's text and awaits MarkdownView.warm; does nothing when there are none | DroppyCode/App/Views/Chat/ThreadTimeline.swift:586 called at the end of the thread-open task | DroppyCode/App/Views/Chat/ThreadTimeline.swift:616 called again when a turn stops running
- **Preconditions:** A thread is opened or a turn ends.
- **Action:** The warm pass runs.
- **Expected:** Rows scrolling into view for the first time never parse markdown on the frame. Texts already cached are skipped by the cache itself. Streaming messages are excluded, because their text is still changing.
- **Side effects:** Background parsing work proportional to the thread's size
- **Persistence:** None; a process-lifetime parse cache.
- **Cancellation:** The warm pass is part of the thread task and is cancelled on a thread switch.
- **Windows path:** Windows must parse off the UI thread and hand back an immutable block list; parsing on the layout pass is what this exists to avoid.
- **Verify by:** interaction test measuring first-scroll frame times on a long thread

### PR-CHAT-130 - Sending a message brings the reader back to the end, but an unattended turn does not
- **Source:** DroppyCode/App/Views/Chat/ThreadTimeline.swift:603-640 onChange(of: runtime.isRunning) - on start, the phase is reset to idle, wasAtEnd is read, unattended is derived by comparing the runtime's autoStartedTurnToken with the last one this view saw, and the timeline pins and scrolls to the end when the reader was at the end or the turn was not unattended; already at the end it snaps unanimated, otherwise it glides with .easeOut(duration: 0.25); a viewport refresh is always armed | DroppyCode/App/Views/Chat/ThreadTimeline.swift:82-84 seenAutoStartedTurnToken is nil until the first turn this view sees start, so a view that appears mid-conversation reads its next turn as a send
- **Preconditions:** A turn starts.
- **Action:** Either the user sent a message, or the turn started by itself.
- **Expected:** A send, and any turn for a reader already at the end, brings the reader down: unanimated if they were already there, otherwise a quarter-second ease-out glide. A turn nothing was sent for, for a reader who had scrolled up, is a row arriving like any other and the jump button tells them about it. Whatever phase the last scroll was left in is cleared first, so the turn's own scroll is not read as its continuation.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** The token comparison is the only way to tell a send from an unattended start; a port without it will yank readers down on every auto-continue.
- **Verify by:** interaction test for both cases

### PR-CHAT-131 - When a turn ends the timeline puts a reader at the end back on the end and re-checks its layout
- **Source:** DroppyCode/App/Views/Chat/ThreadTimeline.swift:605-617 the not-running branch - a pinned reader is scrolled to the bottom on the next main-queue turn, unanimated; a viewport refresh and a blank watch are armed; the markdown warm pass runs
- **Preconditions:** A turn finishes.
- **Action:** The turn's steps fold into its answer.
- **Expected:** The fold happens in the block the turn has had all along. A reader at the end is put back on the end once that has laid out, and the lazy stack is told where the viewport is either way, because a fold can move the viewport off the rows the stack built.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Defer the scroll one turn; it is issued from a change handler that runs during an update.
- **Verify by:** interaction test ending a long turn while at the end

- **Verify by:** interaction test for each of the guards
