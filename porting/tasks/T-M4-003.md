### PR-MCP-177 - The in-app hub lists tools per server, caching successes and blacklisting servers whose listing failed
- **Source:** DroppyCode/Services/MCP/MCPHub.swift:50-76 tools()
- **Preconditions:** An in-app model-API provider is assembling its tool list.
- **Action:** MCPHub.tools() is awaited.
- **Expected:** Specs are read from claude.json on first use and cached until reload. Server ids are iterated in sorted order. A server with a cached tool list contributes it without any network or process work. A server in the failed set is skipped entirely. Otherwise a client is created or reused, listTools is awaited, and on success the list is cached and appended. On failure the line "MCPHub: <id>: <message>" is printed, the id is added to the failed set and the client is stopped. The whole result is sorted by server id, then by tool name.
- **Side effects:** may launch one child process or open one HTTP session per server; one unconditional console line per failure
- **Persistence:** none
- **Failure cases:** a failing server is silently absent from the model's tool list
- **Cancellation:** awaiting tools() is a cancellation point; a cancelled listTools is treated as a failure and blacklists the server
- **Windows path:** Same ordering and caching. The sort is observable because it fixes the order tools are presented to the model.
- **Verify by:** integration test with one good and one failing stand-in server
- **Upstream defect 25: reproduce it faithfully, do not fix it.**

### PR-MCP-178 - A tool call name is mcp__ plus the server id, two underscores, and the tool name
- **Source:** DroppyCode/Services/MCP/MCPHub.swift:37 callName | DroppyCode/Services/MCP/MCPHub.swift:108-116 parse(callName:)
- **Preconditions:** none
- **Action:** A tool is exposed to a model, or a model's call is routed.
- **Expected:** callName = "mcp__" + server + "__" + name. parse requires the "mcp__" prefix, then finds the FIRST occurrence of "__" in the remainder: the text before it is the server and the text after it is the tool, and both must be non-empty or the parse fails. So a server id containing a double underscore would split at the wrong place; no catalog id or makeID-minted id contains one, but a tool name containing "__" is safe because only the first separator is used.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** an unparseable name throws MCPHubError.unknownTool(name) -> "Unknown tool: <name>."
- **Cancellation:** not cancellable
- **Windows path:** Same grammar; it is the contract between the model, the transcript renderer and the hub.
- **Verify by:** unit with a tool name containing a double underscore

### PR-MCP-179 - A tool call is rejected only when its server is unknown or its name is absent from a cached list

- **Persistence:** none

- **Cancellation:** cancellation propagates as CancellationError, not as a server error
- **Windows path:** Reproduce the asymmetry exactly: do not add a failed-set check to call(). A listing failure hides the server from the tool list yet a direct call still relaunches it.
- **Verify by:** integration test calling a tool on a server whose listing failed
- **Upstream defect 19: reproduce it faithfully, do not fix it.**

### PR-MCP-181 - The hub reads its server specs from claude.json, preferring a command over a url

- **Preconditions:** none
- **Action:** The hub loads specs.
- **Expected:** Read <data root>/mcp/claude.json; a missing, unparseable file or a missing mcpServers object yields an empty map, so the hub exposes no tools. - **Side effects:** one file read
- **Persistence:** none

- **Cancellation:** not cancellable

### PR-MCP-184 - A hub stdio client restarts at most once and is then permanently dead

- **Side effects:** may launch a child process
- **Persistence:** none

- **Cancellation:** not cancellable

### PR-MCP-185 - A hub stdio client launches with the login environment, registers for quit-time termination, and handshakes with a 60-second initialize
- **Source:** DroppyCode/Services/MCP/MCPHub.swift:324-390 startStdio | DroppyCode/Services/MCP/MCPHub.swift:20-29 liveProcesses, track and terminateAll
- **Preconditions:** A stdio spec that must be started.
- **Action:** startStdio runs.
- **Expected:** An unresolvable command throws server("<command> isn't installed."). The environment is the login environment with the spec's env layered on; the working directory is the user's home. stdout is line-buffered by a conversation object; stderr is DRAINED AND DISCARDED (its handler reads and throws the bytes away, unlike the probe, which keeps them for error messages). A launch failure detaches both handlers, terminates the process and throws server(<the system error's description>). On success the process is recorded with MCPHub.track so the app can end it at quit. Then: initialize with the next id and a 60-second timeout; a reply whose result is not an object throws server("The server sent something unexpected: missing result."); then the notifications/initialized notification; then initialized is set. Any failure in that block runs stop() and rethrows, wrapping non-MCPHubError, non-CancellationError errors as server(<description>).
- **Side effects:** launches a child process and records it in the live-process list
- **Persistence:** none
- **Failure cases:** the two literal messages above, each ending with a full stop
- **Cancellation:** a cancellation during the handshake stops the client and rethrows CancellationError
- **Windows path:** Same layering, cwd and stderr discarding. The live-process list must be wired to the app-quit path so no npx or node child survives the app; on Windows an orphan survives until Task Manager.
- **Verify by:** integration test asserting no child survives app quit

### PR-MCP-186 - The hub's stdio reader demultiplexes replies by id so two calls in flight do not steal each other's answers
- **Source:** DroppyCode/Services/MCP/MCPHub.swift:392-417 waitStdio | DroppyCode/Services/MCP/MCPHub.swift:168-171 the replies map
- **Preconditions:** A request was written.
- **Action:** waitStdio waits.
- **Expected:** Repeatedly: drain the conversation's complete lines and file every parseable object carrying an integer id into a replies map; if the awaited id is present, remove it, run checkReply and return it; if the process reported an exit code, throw server("The server quit (exit <code>)."); if the process is no longer running, throw server("The server quit."); if the deadline has passed, clear the awaited id's slot and throw server("The server didn't answer in time."); otherwise sleep 10 milliseconds and repeat. Unlike the probe, replies for other ids are KEPT, which is what lets two concurrent calls on one server each get their own.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** the three literal messages above, each ending with a full stop
- **Cancellation:** the sleep is the cancellation point
- **Windows path:** Same 10 ms interval (the probe uses 5 ms) and the same reply retention. Do not unify the two readers.
- **Verify by:** integration test issuing two concurrent calls to one stand-in server
