### PR-MCP-131 - The proxy forwards exactly five client headers, adds the route's headers and a fresh bearer token, and holds the upstream request for an hour
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:309-343 sendUpstream
- **Preconditions:** A route was found.
- **Action:** The request is relayed.
- **Expected:** An unparseable upstream URL throws a bad-URL error, caught by the caller as 502 {"error":"upstream request failed"}. The upstream request uses the client's method verbatim (any method is relayed) and timeoutInterval 3600, so a streaming session survives an hour. Exactly five client headers are copied, in this order, lowercase name to canonical name: content-type to Content-Type, accept to Accept, mcp-session-id to Mcp-Session-Id, mcp-protocol-version to MCP-Protocol-Version, last-event-id to Last-Event-ID. Nothing else is forwarded: no cookies, no user agent, no client Authorization. The route's own headers are applied next. When the route uses OAuth, an access token is fetched and set as "Bearer <token>"; a failure there answers 401 with {"error":"<the error's localized description>"} and returns. A non-empty body is attached.
- **Side effects:** one upstream HTTPS request; may trigger an OAuth token refresh
- **Persistence:** a refresh rewrites the stored OAuth session
- **Failure cases:** token failure -> 401 with the OAuth error text, for example {"error":"You're signed out. Sign in again to continue."}; any thrown error -> 502 {"error":"upstream request failed"} and a printed line "MCPProxy: request to '<id>' failed: <message>"
- **Cancellation:** not cancellable once relayed
- **Windows path:** Forward exactly those five headers and no more. The hour-long timeout is what keeps SSE sessions alive.
- **Verify by:** contract fixture asserting the exact header set reaching a stub upstream

### PR-MCP-132 - An upstream 401 on an OAuth route is retried once with a re-fetched token, which is usually the same token
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:344-355 the 401 replay | DroppyCode/Services/MCP/MCPOAuth.swift:172-176 the expiry window
- **Preconditions:** An OAuth route relayed a request.
- **Action:** The upstream answers 401.
- **Expected:** Ask MCPOAuth.accessToken for the server again with try?; on success set the Authorization header to the new bearer value and re-send the identical request once, then use that response. There is no second retry. Because accessToken only refreshes when a stored expires_at is within 90 seconds, a session stored without expires_in has no expiry and the second call returns the very same token, making the replay a byte-identical retry that gets the same 401. There is no forced-refresh path anywhere. This is upstream behavior and is reproduced.
- **Side effects:** one extra upstream request; possibly one token refresh
- **Persistence:** a successful refresh rewrites the stored session
- **Failure cases:** a missing HTTP response after the replay throws and becomes 502 {"error":"upstream request failed"}
- **Cancellation:** not cancellable
- **Windows path:** Reproduce including the useless replay. Add no force-refresh parameter and synthesize no expires_at when the provider omits expires_in.
- **Verify by:** contract fixture with a stub answering 401 twice and asserting exactly two upstream requests
- **Upstream defect 18: reproduce it faithfully, do not fix it.**

### PR-MCP-134 - An event-stream response is relayed as chunked transfer with one chunk per byte
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:372-387 the SSE branch of writeBack
- **Preconditions:** The upstream Content-Type lowercased contains "text/event-stream".
- **Action:** The body is relayed.
- **Expected:** Transfer-Encoding: chunked and Connection: close are appended to the copied headers and the status head is sent. Then, for every byte of the upstream stream, the three-part frame "1\r\n" + that one byte + "\r\n" is sent as its own awaited write - six bytes on the wire and one async round trip per payload byte. A stream error ends the loop silently. The terminating chunk "0\r\n\r\n" is sent, then the connection is cancelled and forgotten. This is severely inefficient but correctness-preserving, and it is upstream behavior: reproduce it rather than batching, because timing-sensitive downstream behavior may depend on the flush per byte.
- **Side effects:** one socket write per payload byte
- **Persistence:** none
- **Failure cases:** an upstream stream error truncates the relay without an error frame; the terminating chunk is still sent
- **Cancellation:** cancelling the connection ends the relay
- **Windows path:** Reproduce the per-byte framing. Record it as a known upstream defect rather than silently fixing it.
- **Verify by:** contract fixture counting the chunks emitted for a known payload
- **Upstream defect 10: reproduce it faithfully, do not fix it.**

### PR-MCP-135 - A non-streaming response is buffered whole, one byte at a time, then sent with a Content-Length
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:388-400 the non-SSE branch of writeBack
- **Preconditions:** The upstream Content-Type does not contain text/event-stream.
- **Action:** The body is relayed.
- **Expected:** Every byte of the upstream stream is appended to an in-memory buffer, so nothing is sent until the upstream response is complete and a large tool result costs an O(n) per-byte loop. Content-Length with the buffer's byte count and Connection: close are appended, the status head and the buffer are sent as one write, and the connection is cancelled and forgotten. Unlike the SSE branch, a stream error here is NOT caught and propagates to the caller, which answers 502 {"error":"upstream request failed"} - on a connection whose response may already be partly written.
- **Side effects:** holds the whole response in memory
- **Persistence:** none
- **Failure cases:** a mid-stream upstream error escapes and triggers the caller's 502 path
- **Cancellation:** not cancellable
- **Windows path:** Reproduce the buffering and the asymmetric error handling between the two branches.
- **Verify by:** contract fixture with a large body and one with a mid-stream failure
- **Upstream defect 11: reproduce it faithfully, do not fix it.**

### PR-MCP-136 - A proxy-generated response is a JSON error with three headers and closes the connection
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:411-422 respond | DroppyCode/Services/MCP/MCPProxy.swift:424-431 statusHead | DroppyCode/Services/MCP/MCPProxy.swift:452-459 jsonError
- **Preconditions:** The proxy is refusing or failing a request.
- **Action:** respond is called.
- **Expected:** The head is "HTTP/1.1 <status> <reason phrase>\r\n" followed by, in this order, "Content-Type: application/json", "Content-Length: <byte count>", "Connection: close", each ended with CRLF, then a blank CRLF. The body follows. When the write completes the connection is cancelled and forgotten. jsonError escapes backslash to double backslash and double quote to backslash-quote, replaces each newline and each carriage return with a single space, and wraps the result as {"error":"<escaped>"} with no spaces around the colon.
- **Side effects:** closes the connection
- **Persistence:** none
- **Failure cases:** this is the failure rendering
- **Cancellation:** not cancellable
- **Windows path:** Byte-identical head and body construction; providers parse these bodies.
- **Verify by:** unit on the escaping plus a contract fixture on the bytes

### PR-MCP-138 - The proxy tracks open connections and is never shut down during the app's life
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:173-181 accept and forget - :174 state.withLock { $0.connections[ObjectIdentifier(connection)] = connection } | :175 connection.start(queue: queue) | :180 state.withLock { _ = $0.connections.removeValue(forKey: ObjectIdentifier(connection)) } | DroppyCode/Services/MCP/MCPProxy.swift:137-150 stop, which has zero call sites - :138 let (listener, open) = state.withLock { state -> (NWListener?, [NWConnection]) in | :143 state.running = false | :146 listener?.cancel() | :148 connection.cancel()
- **Preconditions:** none
- **Action:** A connection is accepted or finished.
- **Expected:** Every accepted connection is stored by identity in a lock-guarded map, started on the proxy's own queue, and removed from the map when it is cancelled or its stream ends. stop() would cancel the listener and every open connection and clear running, but it has no call sites anywhere in the source: the proxy is started once from the store's initializer and runs until the process exits.
- **Side effects:** the connection map grows and shrinks with traffic
- **Persistence:** none
- **Failure cases:** a connection cancelled without going through forget would leak an entry; every cancel path in the file calls forget
- **Cancellation:** individual connections are cancelled; the listener never is
- **Windows path:** The teardown entry point may be a no-op or omitted entirely, but never shut the proxy down where the source does not - an OAuth server would become unreachable mid-session.
- **Verify by:** integration test asserting the listener is still accepting after every MCP flow
