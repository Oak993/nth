### PR-MCP-121 - The proxy route for a server is exactly http://127.0.0.1:<port>/mcp/<server id>
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:37-39 url(for:)

- **Windows path:** Byte-identical string; providers read it from the config files.
- **Verify by:** unit

### PR-MCP-127 - The proxy reads a request head until the blank line and refuses one over 65536 bytes

- **Windows path:** Same limit and the same silent close on a truncated head.

### PR-MCP-129 - The proxy refuses chunked request bodies and bodies over 32 MiB, and truncates a short body silently
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:52 bodyLimit | DroppyCode/Services/MCP/MCPProxy.swift:232-252 handleExchange | DroppyCode/Services/MCP/MCPProxy.swift:254-276 readBody
- **Preconditions:** A head was parsed.
- **Action:** The body is read.
- **Expected:** A transfer-encoding header whose value lowercased contains "chunked" answers 411 with {"error":"chunked request bodies are not supported"}. contentLength = max(0, the integer parse of content-length, or 0 when absent or unparseable) - a negative value therefore becomes 0. A contentLength over 33554432 answers 413 with {"error":"request body too large"}. When the bytes already buffered reach contentLength, exactly that many are taken and the request is routed. This silent truncation is upstream behavior and is reproduced.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** the three refusals above with those exact JSON bodies; a short body is relayed truncated with no refusal
- **Cancellation:** the connection ending is what triggers the truncated relay
- **Windows path:** Reproduce all four behaviors, including the max(0, ...) parse and the silent truncation. Do not add a 400 for short bodies.
- **Verify by:** contract fixture for each refusal plus one that closes the socket mid-body
- **Upstream defect 12: reproduce it faithfully, do not fix it.**
