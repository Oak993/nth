## Requirements

### PR-TERM-107 - StdioProcess owns one child with three pipes and exposes its parsed messages as a stream that finishes when stdout closes
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:4-9 - the doc comment: a child process that exchanges JSON messages over stdio, one per line or behind a Content-Length header; reading, parsing and writing happen on private queues; parsed messages are delivered through messages, which finishes once stdout closes or the process exits | DroppyCode/Core/Support/StdioProcess.swift:13-45 - messages is an AsyncStream<JSONValue>; the parser, the stderr tail, the exit status and the exit waiters live in one Mutex<State> (:23-30); the init sets executableURL, arguments, currentDirectoryURL, environment and all three standard handles; framing defaults to .lines
- **Preconditions:** A provider or MCP server is to be launched.
- **Action:** A StdioProcess is constructed.
- **Expected:** The child is configured with the given executable, arguments, working directory and environment, and with all three streams piped. Framing is line-delimited unless contentLength is requested. Nothing is launched until start().
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Same configuration. Platform boundary: the working directory and environment block are Windows-shaped, and the child must be launched without a console window.
- **Verify by:** contract fixture

### PR-TERM-108 - start() installs both read handlers and the termination handler before launching, and tears them down and finishes the stream if the launch throws
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:54-87 start() - the stdout handler consumes data or, on empty data, clears itself and calls finishOutput; the stderr handler appends or, on empty data or a dead self, clears itself; the termination handler calls didExit; then try process.run(), and on a throw both handlers are cleared, the continuation is finished and the error is rethrown
- **Preconditions:** A StdioProcess has been constructed.
- **Action:** start() is called and the executable cannot be launched.
- **Expected:** Both readability handlers and the termination handler are installed first. If run() throws, both handlers are removed, the message stream is finished so every consumer's loop ends cleanly, and the error propagates to the caller. A successful launch leaves the handlers in place.
- **Side effects:** A child process is launched on the success path.
- **Persistence:** None.
- **Failure cases:** Launch failure yields a finished, empty message stream plus a thrown error; consumers must not hang.
- **Cancellation:** not cancellable
- **Windows path:** Same ordering and the same cleanup on a failed launch.
- **Verify by:** contract fixture with a missing executable

### PR-TERM-109 - send() serializes a message on a private serial queue and frames it as a line or behind a Content-Length header
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:89-103 send(_:) - on the writeQueue, the message's data is taken; for .lines the payload is the body plus a single 0x0A; for .contentLength it is "Content-Length: \(body.count)\r\n\r\n" as UTF-8 followed by the body; the write uses try? and its error is ignored | DroppyCode/Core/Support/StdioProcess.swift:21 - the queue is labelled "droppycode.stdio.write"
- **Preconditions:** The child is running.
- **Action:** A message is sent.
- **Expected:** Writes are serialized on one queue, so messages cannot interleave. Line framing appends exactly one LF and no CR. Content-Length framing emits the header name with that exact capitalization, a colon, a space, the byte count of the body, CR LF CR LF, then the body, with no other headers. Write errors are swallowed.
- **Side effects:** Bytes are written to the child.
- **Persistence:** None.
- **Failure cases:** The child has exited: the write fails silently and the message is lost with no error surfaced.
- **Cancellation:** not cancellable
- **Windows path:** Same framing bytes exactly, and the same single serial write queue. The header must not gain a Content-Type line.
- **Verify by:** unit test comparing the emitted bytes for both framings

### PR-TERM-110 - write() sends raw bytes unframed and closeInput() closes the child's stdin, both on the same write queue
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:105-111 write(_:) - the comment says this writes raw bytes to the process's stdin, a prompt piped to a one-shot CLI; the write is on the writeQueue with try? | DroppyCode/Core/Support/StdioProcess.swift:113-117 closeInput() - the comment says it closes stdin for a process that reads its input to the end before it starts; the close is on the writeQueue with try?
- **Preconditions:** The child is running.
- **Action:** A caller pipes a prompt and then closes stdin.
- **Expected:** The raw bytes are written with no framing added. Because both operations use the same serial queue, a close issued after a write always happens after that write completes. Both swallow their errors.
- **Side effects:** Bytes written; the child sees end of input after the close.
- **Persistence:** None.
- **Failure cases:** Writing after the close fails silently.
- **Cancellation:** not cancellable
- **Windows path:** Same ordering guarantee through one serial writer.
- **Verify by:** contract fixture piping a prompt to a one-shot child

### PR-TERM-111 - StdioProcess.terminate closes stdin first, then terminates, then kills after three seconds
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:119-128 terminate() - the stdin handle is closed on the writeQueue; the method returns early unless the process is running; otherwise process.terminate() and, three seconds later on a global queue, kill(process.processIdentifier, SIGKILL) when it is still running
- **Preconditions:** A child is to be stopped.
- **Action:** terminate() is called.
- **Expected:** stdin is always closed, even when the process has already exited, which is what lets a child that is waiting on input finish on its own. Then SIGTERM, then SIGKILL three seconds later if needed. Note the kill targets the single pid, NOT the process group, which differs from Shell.terminate (PR-TERM-085) and from its one-second gap. Both asymmetries are in the source and are kept.
- **Side effects:** Signals are delivered to the child only; grandchildren are not targeted.
- **Persistence:** None.
- **Failure cases:** A grandchild that inherited stdout keeps it open past the child's exit; PR-TERM-114 handles that separately.
- **Cancellation:** not cancellable
- **Windows path:** Same order and the same three-second gap, and the same single-process (not tree) scope, so the two ladders stay distinguishable. Platform boundary: graceful stop and forced termination in place of the two signals.
- **Verify by:** contract fixture with a child that ignores the graceful stop

### PR-TERM-112 - waitForExit returns the stored status at once when the child has already exited, and otherwise queues a waiter that is resumed exactly once
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:130-139 waitForExit() - inside state.withLock, an existing exitStatus is returned; otherwise the continuation is appended to exitWaiters and nil returned; a returned status is resumed outside the lock | DroppyCode/Core/Support/StdioProcess.swift:167-174 didExit - inside state.withLock it stores the status, takes and clears the waiter list, then resumes every waiter outside the lock
- **Preconditions:** A caller wants the child's exit status.
- **Action:** waitForExit is awaited before or after the exit.
- **Expected:** Either branch yields the same Int32. Waiters are resumed once each, outside the lock, and the list is cleared so a second exit callback would wake nobody.
- **Persistence:** None.
- **Cancellation:** The continuation is not cancellable; it is a non-throwing continuation.
- **Windows path:** Same two-branch shape.
- **Verify by:** unit test awaiting before and after exit

### PR-TERM-113 - Each delivered frame has trailing carriage returns and spaces stripped, and empty or unparseable frames are dropped silently
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:141-151 consume and deliver - frames come from the framer inside state.withLock; deliver removes trailing bytes while they are 0x0D or 0x20, then requires a non-empty line and a successful JSONValue.parse before yielding to the stream
- **Preconditions:** The child is emitting output.
- **Action:** A frame arrives.
- **Expected:** Trailing CR and space bytes are stripped in a loop, so CRLF line endings and trailing padding both work. A frame that is empty after stripping is dropped. A frame that is not valid JSON is dropped with no diagnostic: a CLI that prints a banner line to stdout simply has that line ignored. Leading whitespace is NOT stripped.
- **Persistence:** None.
- **Failure cases:** Malformed JSON is invisible to the caller; only the stderr tail (PR-TERM-115) can explain a silent provider.
- **Cancellation:** not cancellable
- **Windows path:** Same stripping set and the same silent drops. The CR stripping is what makes CRLF-emitting Windows children work without a separate normalization step.
- **Verify by:** unit test over CRLF, padded, empty and non-JSON frames

### PR-TERM-114 - The message stream is finished when stdout closes, and again one second after the child exits, because a grandchild can hold stdout open
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:153-156 finishOutput - flushes the framer's remainder (taken inside state.withLock) through deliver, then finishes the continuation | DroppyCode/Core/Support/StdioProcess.swift:176-181 - the comment: a grandchild can inherit stdout and keep it open after the provider exits; one second after the exit, the stdout readabilityHandler is cleared and finishOutput is called | DroppyCode/Core/Support/StdioProcess.swift:62-64 - an empty read also clears the handler and calls finishOutput
- **Preconditions:** The child has exited or closed stdout.
- **Action:** Either path runs.
- **Expected:** Any partial frame left in the framer is delivered first (and dropped if it does not parse), then the stream finishes, which is what ends the consumer's read loop. Because AsyncStream.Continuation.finish is idempotent, calling it from both paths is safe. The one-second delay bounds how long a consumer waits on a stream held open by a grandchild.
- **Persistence:** None.
- **Failure cases:** A grandchild holding stdout past the delay has its later output discarded, because the handler was cleared.
- **Cancellation:** not cancellable
- **Windows path:** Same two termination paths and the same one-second bound. Platform boundary: handle inheritance on Windows must be restricted so a grandchild does not hold the pipe, or the same bound applied.
- **Verify by:** contract fixture with a child that leaves a grandchild holding stdout

### PR-TERM-115 - Standard error is buffered to a bounded tail and exposed as the last 4000 bytes decoded as UTF-8
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:49-52 errorTail - the comment says it is the last few kilobytes written to stderr, used when a provider fails; it returns String(decoding: $0.errorBuffer.suffix(4_000), as: UTF8.self) inside state.withLock | DroppyCode/Core/Support/StdioProcess.swift:158-165 appendError - appends inside state.withLock and, once the buffer exceeds 64,000 bytes, replaces it with its last 16,000 bytes
- **Preconditions:** The child is writing to stderr.
- **Action:** A caller reads errorTail after a failure.
- **Expected:** The buffer grows to at most 64,000 bytes before being cut to its last 16,000. errorTail returns the last 4,000 bytes of whatever is held, decoded lossily as UTF-8, which can begin mid-character and mid-line. Nothing from stderr is ever parsed or surfaced except through this accessor.
- **Persistence:** None.
- **Failure cases:** A truncated multi-byte character at the start becomes a replacement character; the source does not guard against it.
- **Cancellation:** not cancellable
- **Windows path:** Same three numbers (4,000, 64,000, 16,000) and the same lossy decode. Do not normalize CRLF in the stderr tail.
- **Verify by:** unit test over the trimming thresholds
