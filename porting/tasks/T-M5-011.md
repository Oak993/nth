### PR-SIDEBAR-104 - The same RowAction runs at three different times depending on where it was invoked
- **Source:** DroppyCode/UI/Chrome/Popovers.swift:258-265 PopoverItem - a row with a confirmation runs `action()` synchronously BEFORE the popover closes, then shows the confirmation and closes after a hold | DroppyCode/UI/Chrome/Popovers.swift:269-273 - a plain popover row closes first and runs `Task { @MainActor in action() }` one turn later, so an action that presents a sheet or alert is not swallowed | DroppyCode/UI/Chrome/Popovers.swift:365-378 RowActionMenuButtons - a context-menu row runs `item.action()` synchronously inside the AppKit menu callback | E:/Droppy/port/porting/upstream_defects.md:137 entry 62
- **Preconditions:** A RowAction is invoked.
- **Action:** The user chooses the item.
- **Expected:** From an ellipsis popover the action runs one main-actor turn after the popover closes. From a context menu it runs synchronously inside the menu callback. (No sidebar RowAction sets `confirms`, so the third timing does not arise here, but the shared component supports it.) The sidebar depends on this difference: the popover path calls the row's own settle and reopen directly while the menu path posts a finish request. This is an upstream inconsistency recorded as a defect and is reproduced, not unified.
- **Persistence:** None.
- **Failure cases:** An action that presents a popover would be swallowed if run before the presenting popover closed, which is why the deferral exists.
- **Cancellation:** not cancellable
- **Windows path:** Reproduce both timings separately. Collapsing them to one would change whether a follow-on popover can present.
- **Verify by:** unit test on the dispatcher asserting the two timings differ.
- **Upstream defect 62: reproduce it faithfully, do not fix it.**
