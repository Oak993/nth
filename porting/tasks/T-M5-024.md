### PR-WIN-022 - Window chrome configuration is idempotent per window
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:104-110 `private static let configuredWindows = NSHashTable<NSWindow>.weakObjects()` and `if configuredWindows.contains(window) { return }; configuredWindows.add(window)` with the comment 'Idempotent: viewDidMoveToWindow fires on every reorder, so the setup pays once.' | DroppyCode/App/Window/WindowManager.swift:101 WindowChrome.configure(window) at creation | DroppyCode/UI/Chrome/WindowChrome.swift:51 WindowChrome.configure(window) again from the probe view's viewDidMoveToWindow
- **Preconditions:** A window may or may not already be configured.
- **Action:** configure(window) is called, which happens once at creation and again from the probe view on every view reorder.
- **Expected:** The eleven window properties are set exactly once per window. Later calls return immediately. The registry holds windows weakly, so a closed and released window drops out on its own and never keeps the window alive.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** A weak-keyed set of already-configured windows, or an equivalent per-window flag. It must not retain the window.
- **Verify by:** unit: call configure twice and assert the second call performs no work

### PR-WIN-023 - The window draws its own chrome: transparent title bar, hidden title, no separator
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:111-114 `window.styleMask.insert(.fullSizeContentView); window.titlebarAppearsTransparent = true; window.titleVisibility = .hidden` and the comment 'A focused window draws a separator under the title bar that cuts through the rounded corner.' above `window.titlebarSeparatorStyle = .none`
- **Preconditions:** A window has been created.
- **Action:** configure(window) runs.
- **Expected:** The content view extends under the title bar, the title bar itself draws nothing, the window title string is not drawn, and no separator line is drawn under the title bar in any focus state. The separator is suppressed specifically because a focused window's separator cut through the window's rounded corner.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Extend the client area over the caption (WM_NCCALCSIZE returning a zero top inset, or DwmExtendFrameIntoClientArea with the app painting the caption). Draw no caption text and no caption separator in any activation state. ED-063 (porting/probes/p7/RESULT.md run 4): on Avalonia 12.1.2 the main window does this with WindowDecorations.Full, ExtendClientAreaToDecorationsHint and a 44 px title bar. OD-0013: the chrome is not accepted while live resize shows the edge strip probe P4 measured.
- **Verify by:** capture comparison in both focus states

### PR-WIN-024 - The window is non-opaque with a clear background and keeps its system shadow
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:115-120 `window.isOpaque = false; window.backgroundColor = .clear; window.hasShadow = true; window.isMovableByWindowBackground = false; window.invalidateShadow()`
- **Preconditions:** A window has been created.
- **Action:** configure(window) runs.
- **Expected:** The window is not opaque and its own background is fully clear, so what is seen is entirely the WindowBackdrop the content draws (PR-WIN-058). The system shadow is kept and is invalidated once so it is recomputed against the new, transparent shape. Dragging the window's background does not move the window; only the explicit drag regions do (PR-WIN-193 and PR-WIN-194).
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** A layered or composition-backed window with per-pixel alpha, the DWM shadow retained, and no system-provided background brush. Critically, the system must not move the window on a background press; only the app's own drag regions move it. ED-063 keeps WindowDecorations.Full for the main window, so the DWM shadow and the DWM minimise, maximise and restore animations stay (BorderOnly and None lose them). OD-0014: the window stays clear by default, as upstream: until the user sets a wallpaper the glass sits over the desktop, as Acrylic plus the app-drawn scrim (OD-0005, probe P3). OD-0013: during live resize the growing edges must not show the window's own backdrop without the app layer.
- **Verify by:** capture comparison of the rounded corner against a contrasting desktop; interaction test that a press on a non-drag region does not move the window

### PR-WIN-025 - The key view loop is recalculated by the frameworks on demand, not rebuilt during layout
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:121-131 the eleven-line comment ending 'Full Keyboard Access is what makes Tab move between controls at all, and the loop is still rebuilt for it, just on demand.' and `window.autorecalculatesKeyViewLoop = true`
- **Preconditions:** A window has been created.
- **Action:** configure(window) runs.
- **Expected:** The focus order is marked dirty when the tree changes and rebuilt only when Tab navigation asks for it. It is never rebuilt synchronously during layout. The source records that the other setting froze the main thread until a force quit, because the focus-order walk never ended inside the composer's follow-up queue tab.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Tab order must be computed lazily, when a Tab key is actually processed, never eagerly on every tree or visibility change. This is a hang-prevention contract, not an aesthetic one.
- **Verify by:** unit: focus order is not computed during a layout pass; stress test with the composer's queue tab open

### PR-WIN-026 - The title bar reaches down 44 points, to the bottom of the chrome row
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:139-150 the doc comment and `static var titlebarHeight: CGFloat { Chrome.sheetInset + Chrome.chromeTopPadding + Chrome.capsuleHeight }` | DroppyCode/UI/Chrome/Chrome.swift:11 sheetInset = 0; :32 chromeTopPadding = 12; :33-38 capsuleContentHeight = 28, capsuleVerticalPadding = 2, `capsuleHeight { capsuleContentHeight + capsuleVerticalPadding * 2 }` = 32 | porting/extracts/chrome-design-tokens.md section 3 resolved table: capsuleHeight = 32
- **Preconditions:** A window has been configured.
- **Action:** The title bar's reach is computed.
- **Expected:** titlebarHeight resolves to exactly 0 + 12 + 32 = 44 points. The window's clickable title bar region reaches that far down, so the traffic lights are inside it in either placement and take their clicks and hovers. The visible consequence is that the gaps in the chrome row drag the window as a title bar's do, while the controls on that row never do.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** The caption hit region is 44 logical pixels tall from the top of the client area, scaled by DPI. Return HTCAPTION from WM_NCHITTEST inside that band except where a control's no-drag region covers it (PR-WIN-194). ED-063: the main window's title bar is 44 px (the source geometry) under WindowDecorations.Full with ExtendClientAreaToDecorationsHint, and the leading-edge controls are declared through Win32Properties.SetNonClientHitTestResult.
- **Verify by:** unit assertion that the computed value is 44; interaction test that a press in a chrome-row gap moves the window and a press on a chrome control does not

### PR-WIN-027 - The title bar container is stretched downward only, never shrunk, and its top edge never moves
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:152-155 titlebarContainer(of:) = `window.standardWindowButton(.closeButton)?.superview?.superview` | DroppyCode/UI/Chrome/WindowChrome.swift:161-172 fitTitlebar: `guard fitted.height < titlebarHeight else { return }`; flipped branch sets height; unflipped branch sets `fitted.origin.y = fitted.maxY - titlebarHeight` then the height; `container.frame = fitted` | DroppyCode/UI/Chrome/WindowChrome.swift:158-160 comment 'Never lays out synchronously: the fit lands on the frame and AppKit's own pass lays it out, so a notification fired mid-tiling costs one frame assignment.'
- **Preconditions:** The window has a title bar container.
- **Action:** fitTitlebar(of:) is called, from a placement, from the container's frame change, or from the end of a live resize.
- **Expected:** If the container is already at least 44 points tall, nothing happens. Otherwise its height becomes exactly 44 with its top edge kept where it is, which in an unflipped coordinate system means moving the origin down to maxY minus 44. The assignment never triggers a synchronous layout or draw.
- **Persistence:** nothing persisted
- **Failure cases:** The window has no title bar container or the container has no superview: the function returns having done nothing
- **Cancellation:** not cancellable
- **Windows path:** The caption hit region is computed, not a real child view, so on Windows this is the WM_NCHITTEST band of PR-WIN-026 rather than a view resize. The grow-only rule and the fixed top edge survive as the rule that the band is never smaller than 44 and always starts at the client top.
- **Verify by:** unit: the grow-only guard and the unflipped origin arithmetic

### PR-WIN-028 - A title bar the system re-tiles smaller is refitted once, after the current layout pass
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:58-66 the probe sets `container.postsFrameChangedNotifications = true` and observes NSView.frameDidChangeNotification on the container, with the comment 'AppKit tiles the title bar back to its own height when the window resizes, and with that the buttons level with the chrome are out of its reach again.' | DroppyCode/UI/Chrome/WindowChrome.swift:77-87 titlebarFrameDidChange: `guard let container = notification.object as? NSView, container.frame.height < WindowChrome.titlebarHeight, !titlebarFitPending else { return }`, then a main-actor Task that clears the flag and calls fitTitlebar | DroppyCode/UI/Chrome/WindowChrome.swift:73-76 comment that the fit waits so the container is never resized halfway through a pass laying out its subviews
- **Preconditions:** The probe view is in a window and is observing the title bar container.
- **Action:** The system re-tiles the title bar container back to its own height, which happens on every window resize.
- **Expected:** At most one refit is queued. A container that is already tall enough queues nothing, and a second notification while a fit is pending queues nothing. The queued fit runs after the current layout pass, then clears the pending flag. This is cheap enough to run on every frame of a live resize.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Windows does not re-tile a caption view, so the notification has no direct analogue; the coalescing contract maps to recomputing the caption band at most once per layout pass when the DPI or frame changes. Record the divergence rather than inventing a notification.
- **Verify by:** unit: coalescing under a burst of frame changes

### PR-WIN-029 - When a live resize ends, the window buttons are placed unanimated and the title bar is refitted

- **Preconditions:** The window is being resized.
- **Action:** The resize drag ends.
- **Expected:** One final placement of the three window buttons with no animation, followed by a refit of the title bar. During the drag itself the buttons follow unanimated (PR-WIN-037), so this settles them exactly.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** On WM_EXITSIZEMOVE, recompute the button placement with animation suppressed and recompute the caption band. OD-0013 governs the live resize that ends here: the edge strip probe P4 measured must be gone before the window chrome is accepted.
- **Verify by:** interaction test: resize while the sidebar is hidden, assert the buttons land exactly on the chrome row's center line

### PR-WIN-031 - The three window buttons are 14 points across, on a 23-point pitch, in close, minimize, zoom order

- **Preconditions:** The window is configured.
- **Action:** placeTrafficLights runs.
- **Expected:** Three buttons, each exactly 14 by 14 points, laid out left to right as close, then minimize, then zoom, at x = leading + 0, leading + 23 and leading + 46. The three together span 60 points.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
