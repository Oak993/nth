### PR-MCP-127 - The proxy reads a request head until the blank line and refuses one over 65536 bytes

- **Action:** Bytes arrive.

- **Cancellation:** the connection is cancelled on stream end
- **Windows path:** Same limit and the same silent close on a truncated head.
- **Verify by:** contract fixture sending an oversized head

### PR-MCP-128 - The proxy parses only the request line and folds header names to lowercase, decoding the head as Latin-1
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:212-228 parseHead
- **Preconditions:** A head was read.
- **Action:** parseHead runs.
- **Expected:** Decode the head bytes as ISO Latin-1, which never fails on arbitrary bytes. Split on CRLF. The first line must split into exactly three space-separated parts with the first two non-empty, giving method and path; anything else returns nil and the exchange answers 400 with {"error":"bad request"}. Every later line with a colon contributes a header: the name is the text before the first colon, trimmed and lowercased; the value is the text after it, trimmed. An empty name is skipped. - **Side effects:** none
- **Persistence:** none
- **Failure cases:** 400 with that exact body
- **Cancellation:** not cancellable
- **Windows path:** Same Latin-1 decode (not UTF-8, which would reject some byte sequences), same lowercasing, same last-wins on duplicates.

### PR-MCP-129 - The proxy refuses chunked request bodies and bodies over 32 MiB, and truncates a short body silently
- **Source:** DroppyCode/Services/MCP/MCPProxy.swift:50 bodyLimit | DroppyCode/Services/MCP/MCPProxy.swift:230-250 handleExchange | DroppyCode/Services/MCP/MCPProxy.swift:252-274 readBody
- **Preconditions:** A head was parsed.
- **Action:** The body is read.
- **Expected:** A transfer-encoding header whose value lowercased contains "chunked" answers 411 with {"error":"chunked request bodies are not supported"}. contentLength = max(0, the integer parse of content-length, or 0 when absent or unparseable) - a negative value therefore becomes 0. A contentLength over 33554432 answers 413 with {"error":"request body too large"}. When the bytes already buffered reach contentLength, exactly that many are taken and the request is routed. Otherwise more are read; if the stream completes or errors early, whatever was received is routed AS THE BODY with no error at all, so a client that dies mid-upload has its truncated payload relayed upstream. This silent truncation is upstream behavior and is reproduced.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** the three refusals above with those exact JSON bodies; a short body is relayed truncated with no refusal
- **Cancellation:** the connection ending is what triggers the truncated relay
- **Windows path:** Reproduce all four behaviors, including the max(0, ...) parse and the silent truncation. Do not add a 400 for short bodies.
- **Verify by:** contract fixture for each refusal plus one that closes the socket mid-body
- **Upstream defect 12: reproduce it faithfully, do not fix it.**
