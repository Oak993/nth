### PR-PROVREG-121 - Grok auth is read from the file .grok/auth.json in the home directory with no process launch
- **Source:** DroppyCode/Services/Providers/ProviderRegistry.swift:790-801 auth case .grok - the URL is the home directory with ".grok/auth.json" appended; the file is read and deserialized as a top-level object
- **Preconditions:** Grok is installed.
- **Action:** The auth probe runs.
- **Expected:** No process is spawned for Grok auth. The file is read directly. An unreadable file or a root that is not a JSON object gives unknown.
- **Side effects:** READS A THIRD-PARTY CREDENTIAL FILE. This is the Grok CLI's own token store, not an app-owned secret; the app only reads it and never writes it.
- **Persistence:** None.
- **Failure cases:** File missing or unparseable: unknown.; Root object empty: signedOut.
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY AND POLICY DECISION. The home directory and the path separator change. Beyond that, whether the Windows build may read the Grok CLI's credential file at all is a policy question the source does not answer: the source does read it, and the port's own safety rules forbid reading agent credential files. Decide explicitly; do not transliterate. Treated identically to PR-PROVREG-177, PR-PROVCLI-313 and PR-PROVCLI-255.
- **Verify by:** contract fixture with a synthetic auth.json

### PR-PROVREG-122 - The Grok account is the first non-empty email across the nested entries, then the first non-empty first_name, then nil
- **Source:** DroppyCode/Services/Providers/ProviderRegistry.swift:793-801 auth case .grok - an empty root object gives signedOut; entries are the root values that are themselves dictionaries; the first non-empty "email" wins, else the first non-empty "first_name", else signedIn(nil)
- **Preconditions:** The auth file parsed to a non-empty object.
- **Action:** The account label is derived.
- **Expected:** A non-empty root always means signed in, even with no readable account fields. Field precedence is exactly email, then first_name. The iteration order over the root values is unspecified in source, so with two accounts the chosen one is not deterministic.
- **Persistence:** None.
- **Failure cases:** No account fields: signedIn(nil).
- **Cancellation:** not cancellable
- **Windows path:** Same precedence. The non-determinism with multiple accounts is upstream behavior and should be recorded, not repaired by sorting.
- **Verify by:** unit over synthetic auth files
