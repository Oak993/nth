### PR-SIDEBAR-136 - No glide flies when Reduce Motion is on or the source frame is degenerate, and a relaunch replaces any glide already in the air for that thread
- **Source:** DroppyCode/App/Views/Sidebar/RowGlide.swift:63-82 launch - `guard from.width > 1, from.height > 1, !NSWorkspace.shared.accessibilityDisplayShouldReduceMotion else { return }`; `glides.removeAll { $0.threadID == threadID }`; then the new glide is appended and `setHiding(threadID, true)`
- **Preconditions:** A glide is requested.
- **Action:** launch runs.
- **Expected:** With Reduce Motion on, or with a source frame no wider or taller than 1 pt, nothing is launched and the row is never hidden, so the thread simply moves with the list's own animation. Otherwise any existing glide for that thread is discarded and the new one replaces it, and the thread's row is hidden.
- **Persistence:** None.
- **Failure cases:** Reduce Motion: no ghost at all.
- **Cancellation:** A relaunch cancels the previous glide for the same thread without running its finish, so its hiding flag is inherited by the new one.
- **Windows path:** Reduce Motion maps to the Windows client-area-animation system setting. Platform boundary: accessibility settings.
- **Verify by:** interaction test with the system reduced-motion setting on and off.

### PR-SIDEBAR-141 - A glide hands the row back 0.12 s before its spring settles and removes itself 0.12 s later
- **Source:** DroppyCode/App/Views/Sidebar/RowGlide.swift:230-236 RowGlideView.task - `let duration = RowGlideAnimator.spring.settlingDuration`; `try? await Task.sleep(for: .seconds(max(duration - 0.12, 0)))`; `RowGlideAnimator.shared.arrive(glide.id)`; `try? await Task.sleep(for: .seconds(0.12))`; `RowGlideAnimator.shared.finish(glide.id)` | DroppyCode/App/Views/Sidebar/RowGlide.swift:113-125 arrive and finish
- **Preconditions:** A glide has started.
- **Action:** Time passes.
- **Expected:** At the spring's settling duration less 0.12 s (clamped at zero), the real row is shown again under the ghost's last frames, so the handover never shows a gap. 0.12 s after that the ghost is removed from the layer. The two sleeps are driven by the flight's own task, which is cancelled when the ghost view is torn down.
- **Side effects:** One task per glide.
- **Persistence:** None.
- **Failure cases:** View torn down mid-flight: the task is cancelled, the sleeps throw, and neither arrive nor finish runs, leaving the glide in the array and its row hidden. This is the source behavior.
- **Cancellation:** Task cancellation aborts both sleeps.
- **Windows path:** The spring's settling duration must be computed the same way for the timing to line up. Platform boundary: spring solver. The 0.12 s handover is literal.
- **Verify by:** unit test on the timing with a controlled clock.
