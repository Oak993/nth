### PR-COMPOSER-163 - Releasing over a pair target bundles the rows; otherwise the row settles back on a spring
- **Source:** DroppyCode/App/Views/Composer/FollowUpQueueTab.swift:284-296 dragEnded - with a pair target, bundleFollowUp runs inside .spring(response: 0.36, dampingFraction: 0.78) with a levelChange haptic and the target is cleared; then, if a row was held, drag is reset inside .spring(response: 0.32, dampingFraction: 0.8) so the offset animates from wherever the pointer let go back to the row's slot (no cursor call: the grip's `.pointerStyle(isDragged ? .grabActive : .grabIdle)` reverts on its own once isDragged becomes false) | DroppyCode/App/Runtime/ThreadRuntime.swift:834-847 bundleFollowUp - both prompts take the target's bundle id, or a fresh one; the dragged prompt moves to sit right after the bundle's last prompt | DroppyCode/App/Views/Composer/FollowUpQueueTab.swift:165-178 a local left-mouse-up monitor ends a drag the gesture never reports
- **Preconditions:** A drag is in progress.
- **Action:** The user releases the mouse.
- **Expected:** With a pair target lit, the two prompts join one bundle and the dragged prompt moves after the bundle's last member, on a spring of response 0.36 and damping 0.78, with a level-change haptic. Either way the held row settles back into its slot on a spring of response 0.32 and damping 0.8; the grip's pointer style falls back to grab-idle because isDragged becomes false, with no explicit cursor call needed. A gesture cancelled from under the pointer is caught by the mouse-up monitor.
- **Side effects:** Haptic feedback; The queue is saved
- **Persistence:** bundleID and order saved.
- **Failure cases:** Dropping a row onto itself is rejected by bundleFollowUp's id != target guard.
- **Cancellation:** The monitor is removed when the drag ends and on disappearance.
- **Windows path:** Same springs, same insertion point. The mouse-up monitor becomes an app-scoped message filter or a capture release. No cursor pop to reproduce; the pointer-style binding (PR-COMPOSER-159) handles the revert.

### PR-COMPOSER-173 - The pencil toggles an editor popover whose edit lives on the thread
- **Source:** DroppyCode/App/Views/Composer/FollowUpQueueTab.swift:440-449 the pencil sets runtime.followUpEdit to a PromptEdit of this prompt, or to nil when it was already open; the button reports its window rect to the editor popover and syncs it | DroppyCode/App/Views/Composer/FollowUpQueueTab.swift:336-340 isEditing is runtime.followUpEdit?.id == prompt.id | DroppyCode/App/Runtime/ThreadRuntime.swift:213-216 followUpEdit lives on the thread so leaving mid-edit and coming back finds the editor open where it was left | DroppyCode/App/Views/Composer/FollowUpQueueTab.swift:489-492 leaving closes the popover and the preview but leaves the edit
- **Preconditions:** A follow-up is queued.
- **Action:** The user clicks the pencil, then clicks it again.

- **Failure cases:** The row's prompt leaves the queue: the edit is cleared and the popover closes.
- **Cancellation:** not cancellable
- **Windows path:** Same ownership: the edit belongs to the thread runtime, the popover to the row.
- **Verify by:** interaction test switching threads mid-edit
