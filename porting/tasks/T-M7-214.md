### PR-TERM-029 - The terminal's colours are re-applied on every host update but the session skips redundant applications

- **Cancellation:** not cancellable

### PR-TERM-031 - Escape inside the terminal closes the drawer only when the shell itself owns the terminal foreground, and is swallowed when it does
- **Source:** DroppyCode/App/Views/Terminal/TerminalPanel.swift:320-322 - the doc comment: Escape in the terminal with the shell at its prompt closes the panel the way Command-J closes it; a program in the foreground (vim, claude, less) gets its Escape as ever | DroppyCode/App/Views/Terminal/TerminalPanel.swift:339-346 - NSEvent.addLocalMonitorForEvents(matching: .keyDown) with guards: a live view, event.keyCode == 53, event.modifierFlags.intersection(KeyChord.allowedModifiers).isEmpty, event.window?.firstResponder === view, and TerminalSession.foregroundJobIsTheShell(view.process.shellPid); then onEscapeAtPrompt() and return nil | DroppyCode/Core/Models/Shortcuts.swift:6 - KeyChord.allowedModifiers is [.control, .option, .shift, .command] | DroppyCode/App/Views/Terminal/TerminalPanel.swift:59 - the closure passed in is { runtime.isTerminalVisible = false }
- **Preconditions:** The terminal view is the window's first responder.
- **Action:** The user presses Escape with no Control, Option, Shift or Command held.
- **Expected:** All five conditions must hold: the view is alive, the key is Escape (macOS keyCode 53), no allowed modifier is held, the terminal view is the window's first responder, and the shell owns the terminal foreground. Then the drawer closes and the event is consumed (the monitor returns nil), so Escape never reaches the shell. If any condition fails the event is returned unchanged and behaves normally, so Escape inside vim, less or an agent CLI still reaches that program.
- **Side effects:** The panel hides; sessions keep running.
- **Persistence:** None.
- **Failure cases:** foregroundJobIsTheShell cannot answer (non-positive pid or failed sysctl): it returns false, so Escape is passed through to the terminal and the drawer stays open.
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY, unresolved. ConPTY exposes no foreground process group and no tpgid, so the fifth condition has no translation. An explicit engineering decision is required (for example: track whether a non-shell child is running under the pty, or require a modifier or a different key). Bare-Escape-at-prompt is an approximation and must be labelled as one, never presented as parity.
- **Verify by:** interaction test with the shell at its prompt and again with a foreground program running
- **Depends on UNK-0005**, which is unresolved. Implement only the part the source settles; flag the rest.

### PR-TERM-032 - The Escape monitor is process-wide, installed once per hosted session and removed when the host's coordinator dies
- **Source:** DroppyCode/App/Views/Terminal/TerminalPanel.swift:324-332 Coordinator - holds keyMonitor: Any? and removes it with NSEvent.removeMonitor in deinit | DroppyCode/App/Views/Terminal/TerminalPanel.swift:334-347 makeNSView - installs the monitor once when the representable's view is made | DroppyCode/App/Views/Terminal/TerminalPanel.swift:60 - the host is keyed .id(selected.id), so a tab change makes a new representable and a new coordinator
- **Preconditions:** A session is hosted.
- **Action:** The user switches tabs or closes the drawer.
- **Expected:** Exactly one monitor exists per hosted session. Switching tabs creates the new host's monitor and releases the old coordinator, whose deinit removes the old monitor. The monitor captures the terminal view weakly, so it does not keep it alive; when the view is gone the guard fails and the event passes through.
- **Side effects:** A process-wide keyDown monitor is installed and removed.
- **Persistence:** None.
- **Failure cases:** If the coordinator outlived the view the monitor would still run, but the weak view guard makes it inert.
- **Cancellation:** not cancellable
- **Windows path:** A document-level keydown listener scoped to the session, attached and detached with the terminal component. Avoid leaking one listener per tab switch.
- **Verify by:** unit test counting installed listeners across repeated tab switches

### PR-TERM-033 - While the window is live-resizing, the hosted terminal's autoresizing is parked and its frame is synced at most once every 50 milliseconds
- **Source:** DroppyCode/App/Views/Terminal/TerminalPanel.swift:378-381 - the doc comment: SwiftTerm re-wraps its buffer on every frame-size change, so a live resize that moved the frame every frame reflowed per frame; while the drag lasts the view's autoresizing is parked and its frame lands at most every beat | DroppyCode/App/Views/Terminal/TerminalPanel.swift:402-406 - on NSWindow.willStartLiveResizeNotification, hostedView.autoresizingMask = [] | DroppyCode/App/Views/Terminal/TerminalPanel.swift:414-426 resizeSubviews - requires a hosted view and window.inLiveResize, returns if a pendingSync already exists, otherwise schedules a DispatchWorkItem 50 ms out on the main queue that clears pendingSync and calls syncFrame
- **Preconditions:** A terminal is hosted and the user starts a live window resize.
- **Action:** The window is dragged by its edge.
- **Expected:** On the resize starting, the terminal view's autoresizing mask is cleared so it stops following the container per frame. Each layout pass schedules one 50 ms coalescing beat if none is pending; the beat clears itself and syncs the frame once, so the terminal re-wraps at most 20 times a second instead of once per frame. A beat already in flight is not restarted by further layout passes.
- **Side effects:** One main-queue work item per beat.
- **Persistence:** None.
- **Failure cases:** No hosted view or the window is not live-resizing: nothing is scheduled and the ordinary autoresizing path applies.
- **Cancellation:** The pending beat is cancelled by finishResize and by the container's deinit.
- **Windows path:** Throttle the terminal fit/reflow to one call per 50 ms while a window resize is in progress, and stop the element from following the container in the meantime. Platform boundary: Windows has no willStartLiveResize notification; use the window's resize-modal messages or an equivalent in the host layer.
- **Verify by:** unit test on the coalescer plus a timing assertion during a scripted resize
