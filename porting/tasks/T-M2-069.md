### PR-GIT-004 - A timed-out git process is terminated then killed and reported as a failed result, never as a thrown timeout
- **Source:** DroppyCode/Core/Support/Shell.swift:81-85 - the deadline Task sleeps for timeout seconds then calls terminate(process) | DroppyCode/Core/Support/Shell.swift:110-118 - terminate() sends SIGTERM, then one second later kill(getpgid(pid) == pid ? -pid : pid, SIGKILL) | DroppyCode/Core/Support/Shell.swift:105 - await collector.finished(within: 3) after the process ends | DroppyCode/Core/Support/Shell.swift:107 - returns ShellResult(status:stdout:stderr:); the timeout is never thrown
- **Preconditions:** A git invocation exceeds its budget.
- **Action:** The watchdog fires.
- **Expected:** The process is asked to terminate, then force-killed one second later, preferring the process group when the process is its own group leader. Output collection is then given a further 3 s. The call returns a ShellResult with a non-zero status, and Git.check turns that into a thrown ShellError carrying failureMessage.
- **Side effects:** Child process tree termination
- **Persistence:** None.
- **Failure cases:** A child that ignores termination is force-killed after 1 s
- **Cancellation:** not cancellable
- **Windows path:** Platform boundary: there is no SIGTERM. Use a Job Object per spawn so the kill reaches the whole tree, with the same 1 s gap between the graceful request and the hard kill, and the same 3 s output-drain ceiling.
- **Verify by:** interaction test: a git shim that sleeps past its budget, asserting a failed result rather than a thrown timeout

### PR-TERM-081 - Shell.run launches a process off the main actor with three pipes, a working directory and an environment, and returns status plus both streams
- **Source:** DroppyCode/Core/Support/Shell.swift:36-56 - the @concurrent run(_:_:in:environment:input:timeout:outputLimit:) signature and its setup: executableURL, arguments, currentDirectoryURL only when a directory is given, environment defaulting to LoginEnvironment.current, stdout and stderr Pipes, a stdin Pipe only when input is non-nil, and standardInput set to FileHandle.nullDevice when there is no input | DroppyCode/Core/Support/Shell.swift:4-12 struct ShellResult - status: Int32, stdout: Data, stderr: Data, with succeeded == (status == 0), output and errorOutput decoding UTF-8, and trimmedOutput = output.trimmed | DroppyCode/Core/Support/Text.swift:132 - var trimmed: String { trimmingCharacters(in: .whitespacesAndNewlines) }, so trimmedOutput still trims whitespace and newlines
- **Preconditions:** An executable URL is known.
- **Action:** A caller awaits Shell.run.
- **Expected:** The process runs off the main actor. With no directory argument the child inherits the app's own working directory rather than being given one. With no environment argument it gets LoginEnvironment.current. With no input, stdin is the null device, so a child that reads stdin sees EOF immediately rather than blocking. The result carries the raw exit status and both streams as Data; text accessors decode UTF-8 lossily via String(decoding:as:).
- **Side effects:** A child process is launched.
- **Persistence:** None.
- **Failure cases:** process.run() throws (missing or non-executable file): the error is rethrown to the caller through the continuation and no result is produced.
- **Cancellation:** See PR-TERM-085 and PR-TERM-086.
- **Windows path:** CreateProcess-equivalent with three pipes and NUL as stdin when there is no input. Platform boundary: Windows has no direct equivalent of inheriting the parent's cwd selectively, and the child must be given an explicit environment block.
- **Verify by:** contract fixture over a known child

### PR-TERM-083 - Output is collected through readability handlers into tail-bounded buffers, trimmed only once a buffer holds twice the limit
- **Source:** DroppyCode/Core/Support/Shell.swift:57-60 - an OutputCollector is made with the limit and installed as the readabilityHandler of both read handles | DroppyCode/Core/Support/Shell.swift:265-288 OutputCollector.reader and append - empty data clears the handler and closes the stream; otherwise the chunk is appended inside state.withLock (a Mutex<State>, :251-258), and when a limit exists and the buffer exceeds limit * 2 the buffer becomes its last `limit` bytes | DroppyCode/Core/Support/Shell.swift:282-284 - the comment: keeps the tail within the limit, trimming by whole chunks once the buffer holds twice the limit, so a stream that never ends costs O(limit) memory and amortized O(1) per byte | DroppyCode/Core/Support/Shell.swift:32-35 - the comment: with an outputLimit only that many bytes of each stream's tail are kept; a command a model runs can print without end for the whole timeout, and the app's own commands keep it all
- **Preconditions:** A command is producing output.
- **Action:** Data arrives on either stream.
- **Expected:** With outputLimit nil (the default) everything is kept. With a limit, each stream's buffer may grow up to twice the limit before being cut back to its last `limit` bytes, so the returned Data can legitimately be larger than the limit at the moment the process ends. The head of a long stream is discarded, not the tail.
- **Persistence:** None.
- **Failure cases:** A single chunk larger than twice the limit still trims correctly, to the last `limit` bytes of the combined buffer.
- **Cancellation:** not cancellable
- **Windows path:** Same two-times-limit hysteresis; do not trim on every append, and do not trim to exactly the limit at the end.
- **Verify by:** unit test feeding chunks past the threshold and asserting the retained byte range

### PR-TERM-084 - A command that outlives its timeout is terminated; the default timeout is 120 seconds
- **Source:** DroppyCode/Core/Support/Shell.swift:42 - timeout: TimeInterval = 120 is the default parameter | DroppyCode/Core/Support/Shell.swift:81-85 - after a successful run() a deadline Task sleeps for the timeout and, unless it is cancelled, calls terminate(process) | DroppyCode/Core/Support/Shell.swift:63-68 and :103 - the deadline is cancelled in the defer and again after the status arrives
- **Preconditions:** A command is running.
- **Action:** The timeout elapses.
- **Expected:** The process is terminated (PR-TERM-085) and the call returns with whatever exit status the termination produced, which is non-zero, so ShellResult.succeeded is false. The deadline task is cancelled as soon as the process exits normally, and again on the way out, so a finished command never gets killed late.
- **Side effects:** The child receives SIGTERM and possibly SIGKILL.
- **Persistence:** None.
- **Failure cases:** The caller sees a failed result rather than a thrown timeout error; the distinction between a timeout and an ordinary failure is not reported.
- **Cancellation:** The deadline itself is cancelled on normal completion.
- **Windows path:** Same default of 120 seconds and the same silent degradation to a failed result. Platform boundary: the termination mechanism (PR-TERM-085).
- **Verify by:** contract fixture with a sleeping child and a short timeout

### PR-TERM-085 - Termination is a two-step ladder: terminate now, then kill the process group one second later if it is still running
- **Source:** DroppyCode/Core/Support/Shell.swift:110-118 terminate(_:) - returns unless the process is running; calls process.terminate(); then on a global .utility queue one second later, if it is still running, calls kill with -pid when getpgid(pid) == pid and with pid otherwise, sending SIGKILL | porting/critiques/triage_summary.json:92 - notes that neither call site uses setsid, so whether the group dies depends on the child
- **Preconditions:** A process is running and must stop.
- **Action:** terminate is called by the timeout or by cancellation.
- **Expected:** SIGTERM first. Exactly one second later, if the process is still alive, SIGKILL is sent to the whole process group when the process is its own group leader, and to the single process otherwise. The one-second gap and the group-leader test are both load-bearing: a child that is not a group leader has only itself killed, so its own children survive.
- **Side effects:** Signals are delivered; grandchildren may or may not die depending on the group test.
- **Persistence:** None.
- **Failure cases:** A child that is not a group leader can leave grandchildren running. This is upstream behaviour and is not repaired.
- **Cancellation:** not cancellable
- **Windows path:** PLATFORM BOUNDARY. Windows has no signals and no process groups in this sense. The closest faithful shape is a graceful stop request followed one second later by a forced termination, with the tree-versus-single distinction resolved by a Job Object. Whether the port kills the tree or only the process must be an explicit engineering decision that records the difference from the source, not a silent choice.
- **Verify by:** contract fixture with a child that spawns a grandchild

### PR-TERM-086 - A cancelled Shell.run throws before launching, or terminates the child and throws if it has already started
- **Source:** DroppyCode/Core/Support/Shell.swift:62 - let cancelled = Mutex(false) | DroppyCode/Core/Support/Shell.swift:69-71 - withTaskCancellationHandler first calls try Task.checkCancellation() | DroppyCode/Core/Support/Shell.swift:77-80 - inside cancelled.withLock, if the flag is already set a CancellationError is thrown instead of running the process | DroppyCode/Core/Support/Shell.swift:97-102 - onCancel sets the flag and calls terminate(process), both under the same lock
- **Preconditions:** The calling task may be cancelled at any point.
- **Action:** The task is cancelled.
- **Expected:** Cancellation before launch: CancellationError is thrown and nothing is spawned. Cancellation racing the launch: the lock makes the two paths exclusive, so either the flag is seen and nothing launches, or the process launches and is then terminated. Cancellation after launch: the child is terminated through the same ladder and the call throws CancellationError at one of the two later checkpoints rather than returning a partial result.
- **Side effects:** The child is terminated.
- **Persistence:** None.
- **Failure cases:** Output already collected before cancellation is discarded, because the checkpoints throw rather than return.
- **Cancellation:** This requirement is the cancellation behaviour.
- **Windows path:** Same three checkpoints and the same mutual exclusion between the cancel handler and the launch.
- **Verify by:** unit test cancelling at each of the three points

### PR-TERM-087 - After the process exits, output collection is awaited with a three-second grace and then forced closed
- **Source:** DroppyCode/Core/Support/Shell.swift:105 - let output = await collector.finished(within: 3) | DroppyCode/Core/Support/Shell.swift:290-314 finished(within:) - returns immediately when both streams are already closed; otherwise starts a deadline task that, after the timeout, force-closes both streams; waits on a continuation registered inside state.withLock; cancels the deadline in a defer; the cancellation handler also force-closes both streams | DroppyCode/Core/Support/Shell.swift:316-324 close(_:) - only the transition that completes the second stream takes the waiters inside state.withLock and wakes them after it, exactly once
- **Preconditions:** A child has exited but its pipes may still hold data or be held open by a grandchild.
- **Action:** Shell.run waits for the collector.
- **Expected:** If both streams already reported end of file, the buffers are returned at once. Otherwise the call waits up to 3 seconds; after that both streams are treated as closed and whatever was collected is returned. Waiters are resumed exactly once, when the second of the two streams closes.
- **Persistence:** None.
- **Failure cases:** A grandchild holding the pipe open costs exactly three seconds and yields a possibly truncated stdout, with exit status 0. porting/upstream_defects.md:324 records this as the one real short-answer-with-exit-0 path.
- **Cancellation:** Cancelling the surrounding task force-closes both streams immediately.
- **Windows path:** Same 3-second grace and the same once-only wake.
- **Verify by:** contract fixture where the child leaves a grandchild holding stdout

### PR-TERM-088 - Supplied stdin data is written on a background queue and the handle is closed afterwards, with both errors swallowed
- **Source:** DroppyCode/Core/Support/Shell.swift:90-95 - when input and stdin both exist, a DispatchQueue.global(qos: .userInitiated) block does try? write(contentsOf: input) then try? close()
- **Preconditions:** Shell.run was called with input data.
- **Action:** The process has started.
- **Expected:** The data is written to the child's stdin from a background queue, so a child that does not read promptly cannot block the caller, and the handle is then closed so the child sees end of input. Both the write and the close ignore their errors, so a child that exits before reading produces no visible failure from this path (the broken-pipe write simply fails silently).
- **Side effects:** Bytes are written to the child.
- **Persistence:** None.
- **Failure cases:** Write fails (child already gone): silently ignored; the command's own exit status is what the caller sees.
- **Cancellation:** The write is not cancelled explicitly; the handle closing ends it.
- **Windows path:** Same background write and close, with the same error suppression.
- **Verify by:** contract fixture piping a large input to a child that exits early
