### PR-WIN-052 - The grip and glow animate over 0.18 seconds ease-out, or snap when the change is not a hover change
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:497-516 updateGrip(animated:): `CATransaction.begin(); if animated { CATransaction.setAnimationDuration(Grip.duration); CATransaction.setAnimationTimingFunction(CAMediaTimingFunction(name: .easeOut)) } else { CATransaction.setDisableActions(true) }` ... `CATransaction.commit()` | DroppyCode/UI/Chrome/WindowChrome.swift:468-476 layout(): `let hovered = isHovering; refreshHover(); updateGrip(animated: hovered != isHovering)` | DroppyCode/UI/Chrome/WindowChrome.swift:478-482 viewDidMoveToWindow uses animated: false; :407-414 the isActive didSet uses animated: false; :534-551 mouseDown and mouseUp use animated: true
- **Preconditions:** The strip is in a window.
- **Action:** Any of: a layout pass, entering a window, the active flag flipping, a mouse enter or exit, a press, or a release.
- **Expected:** The grip and glow animate over exactly 0.18 seconds on an ease-out curve when the change came from a hover change, a press or a release, and snap with animations disabled when it came from a layout pass that did not change the hover state, from entering a window, or from the active flag flipping. This duration has no Reduce Motion branch.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Same duration, same curve, same six trigger sites with the same animated/unanimated split.
- **Verify by:** unit: the animated flag per trigger site

### PR-WIN-053 - Pressing the resize strip never moves the window, even though the strip runs through the title bar
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:518-522 `override func acceptsFirstMouse(for event: NSEvent?) -> Bool { true }` and, with the comment 'The strip's top runs through the title bar, where AppKit moves the window for any view that lets it; a press on the grip resizes the sidebar and nothing else.', `override var mouseDownCanMoveWindow: Bool { false }` | DroppyCode/App/Views/RootView.swift:30 and :62 `.padding(.top, Chrome.trafficLightTop + Chrome.trafficLightDiameter)` - the strip starts 30 points down but still overlaps the 44-point title bar band
- **Preconditions:** The window may be inactive.
- **Action:** The user presses the strip, including as the click that activates the window.
- **Expected:** The press begins a sidebar resize. It never moves the window, even in the 30-to-44 point band where the strip overlaps the title bar. A first click on an inactive window both activates the window and starts the resize; it is not swallowed by the activation.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** The strip's hit region must return a client hit rather than HTCAPTION inside the caption band, and must act on the activating click rather than swallowing it (the opposite of the default, which eats the activating click).
- **Verify by:** interaction test: from an inactive window, one click-drag on the strip resizes the sidebar

### PR-WIN-054 - The strip is fully inert when inactive: no cursor, no hover, no hit
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:407-414 the isActive didSet: invalidates cursor rects, refreshes hover, updates the grip unanimated | DroppyCode/UI/Chrome/WindowChrome.swift:488-495 refreshHover: `guard isActive, let window, !isHiddenOrHasHiddenAncestor else { isHovering = false; return }` | DroppyCode/UI/Chrome/WindowChrome.swift:526 resetCursorRects guards on isActive; :530-532 `override func hitTest(_ point: NSPoint) -> NSView? { isActive ? super.hitTest(point) : nil }` | DroppyCode/App/Views/RootView.swift:24 trailing strip isActive: `!onlyFloats && sidebar.isVisible`; :58 leading strip isActive: `!onlyFloats && !sidebar.isVisible`
- **Preconditions:** Exactly one of the two strips is active at a time, and neither is active when the sidebar only floats.
- **Action:** The pointer moves over or presses an inactive strip.
- **Expected:** Nothing happens: no cursor change, no hover state, and the press reaches whatever is behind the strip. The trailing strip (on the sidebar's own edge) is active only while the sidebar is visible; the leading strip (on the window's leading edge, which pulls the sidebar back out) is active only while it is hidden; with the sidebar set to float only, neither is active.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Two mutually exclusive hit regions with the same three-way activation rule; an inactive region is excluded from hit testing entirely rather than merely ignoring events.
- **Verify by:** interaction test across all three sidebar modes

### PR-WIN-055 - Sidebar drag deltas are measured from the press point, and the release sends one final delta before ending
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:534-539 mouseDown: `pressOriginX = event.locationInWindow.x; isDragging = true; updateGrip(animated: true); onBegin?()` | DroppyCode/UI/Chrome/WindowChrome.swift:541-543 mouseDragged: `onChange?(event.locationInWindow.x - pressOriginX)` | DroppyCode/UI/Chrome/WindowChrome.swift:545-552 mouseUp: `onChange?(event.locationInWindow.x - pressOriginX)` first, then isDragging = false, then onEnd?(), then refreshHover() and updateGrip(animated: true), with the comment 'No exit arrives while the button is held; the release decides from the cursor.'
- **Preconditions:** The strip is active.
- **Action:** The user presses, drags and releases.
- **Expected:** The press records the x coordinate in window space and begins the drag. Every move reports the signed difference from that origin. The release reports the final difference BEFORE ending the drag, so the settle decision in endDrag sees the true release position, then ends the drag, then re-reads the real cursor position and animates the grip accordingly.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Same order on button-up: report the final delta, then end. Ending first loses the last few pixels of the gesture. Capture the mouse for the duration so moves outside the strip still report.
- **Verify by:** unit: the ordering of the final onChange and onEnd; interaction test with a fast release

### PR-WIN-056 - The strip re-reads the real cursor position rather than trusting enter and exit events
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:486-495 refreshHover: `let point = convert(window.mouseLocationOutsideOfEventStream, from: nil); isHovering = bounds.contains(point)` with the comment 'Reads the cursor's actual place, so isHovering never outlives the cursor being over the strip; the entered/exited pair only keeps it true while the mouse itself moves.' | DroppyCode/UI/Chrome/WindowChrome.swift:468-476 layout() comment 'The strip moves with the sidebar's edge: a toggle, or a release that springs the width back, carries it out from under a resting cursor, and AppKit only reports enter and exit for the mouse moving. Each new frame asks where the cursor is now.' | DroppyCode/UI/Chrome/WindowChrome.swift:554-560 updateTrackingAreas: `NSTrackingArea(rect: .zero, options: [.mouseEnteredAndExited, .activeAlways, .inVisibleRect], owner: self, userInfo: nil)`, replacing any previous area
- **Preconditions:** The strip is active and in a window.
- **Action:** The sidebar is toggled, or a release springs the width back, so the strip moves out from under a stationary cursor.
- **Expected:** On each layout pass, on entering a window and on mouse-up, the hover state is recomputed from the cursor's actual position rather than left as the last enter/exit event said. The tracking region always follows the visible bounds and is always active, whether or not the app is frontmost.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Poll the cursor position on layout rather than relying on WM_MOUSELEAVE, which does not fire when the element moves out from under a stationary pointer. Track hover while the app is in the background too.
- **Verify by:** interaction test: rest the pointer on the strip, toggle the sidebar with the keyboard, assert the grip retracts

### PR-WIN-057 - The strip's grip and glow follow the light and dark appearance
- **Source:** DroppyCode/UI/Chrome/WindowChrome.swift:455-461 applyColors: `effectiveAppearance.performAsCurrentDrawingAppearance { let color = NSColor.labelColor.cgColor; gripLayer.backgroundColor = color; glowLayer.backgroundColor = color }` | DroppyCode/UI/Chrome/WindowChrome.swift:463-466 viewDidChangeEffectiveAppearance calls applyColors again | DroppyCode/UI/Chrome/WindowChrome.swift:450-452 the glow layer is added first and the grip second, so the grip draws on top
- **Preconditions:** The strip exists.
- **Action:** The appearance changes, from a theme change or from the system.
- **Expected:** Both layers are repainted in the label color resolved for the new appearance. The layers hold resolved colors rather than dynamic ones, which is why the explicit re-resolve on appearance change is required. The glow is beneath the grip.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Layer-backed fills must be re-resolved on a theme or system light/dark change; a cached brush that is not invalidated reproduces the bug this override prevents.
- **Verify by:** interaction test: switch theme with the pointer hovering the strip
