### PR-MCP-100 - MCPProbe.probe dispatches on command then url and rejects a server with neither
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:52-61 probe(_:)
- **Preconditions:** A resolved server.
- **Action:** The store probes it.
- **Expected:** If command is non-nil, run the stdio probe (even when url is also set). Otherwise, if url is non-nil, run the remote probe. Otherwise throw MCPProbeError.malformed("missing command or URL"), which renders as "The server sent something unexpected: missing command or URL".
- **Side effects:** none before dispatch
- **Persistence:** none
- **Failure cases:** neither set -> the malformed message above
- **Cancellation:** the whole probe runs inside a cancellable task
- **Windows path:** Same precedence: command wins over url.
- **Verify by:** unit

### PR-MCP-101 - Every MCP client sends protocol version 2025-06-18 and identifies itself as Marrow 1.0
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:66-72 initializeParams | DroppyCode/Services/MCP/MCPHub.swift:258-264 MCPClient.initializeParams
- **Preconditions:** none
- **Action:** An initialize request is built by the probe or the in-app hub.
- **Expected:** params = {"protocolVersion": "2025-06-18", "capabilities": {}, "clientInfo": {"name": "Marrow", "version": "1.0"}} exactly, with capabilities an empty object. The same version string is also sent as the MCP-Protocol-Version HTTP header on every remote POST from these two clients.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** a server that rejects the version answers an error, which surfaces through checkReply
- **Cancellation:** not cancellable
- **Windows path:** Same three params verbatim. The clientInfo name is "Marrow" (OD-0012 F1); the version "1.0" is a literal unrelated to the app version and stays "1.0". The installed JavaScript bridge deliberately sends no version and no protocol header (PR-MCP-196) - do not normalize the three clients.
- **Verify by:** contract fixture capturing the initialize payload from all three clients

### PR-MCP-106 - A stdio probe gives the server 90 seconds, or 240 when its arguments contain mcp-remote
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:88-89 isOAuth and the deadline
- **Preconditions:** A resolved stdio server.
- **Action:** probeStdio computes its deadline.
- **Expected:** isOAuth = server.args.contains("mcp-remote") as an exact element match. deadline = now + 240 seconds when true, now + 90 seconds otherwise. No built-in catalog server can reach the 240-second branch: mcp-remote is produced only by acpServers(allowsHTTP: false), whose output never becomes an MCPResolvedServer. Only a user-authored custom stdio server whose arguments literally contain "mcp-remote" reaches it.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** passing the deadline throws .timedOut -> "The server didn't answer in time."
- **Cancellation:** the deadline check runs inside the polling loop alongside the cancellation check
- **Windows path:** Implement the branch exactly, but design no 240-second wait into the built-in server experience; the real OAuth retry comes from the HTTP path.
- **Verify by:** unit on the two deadlines

### PR-MCP-107 - A probed stdio server inherits the login environment with its own variables layered on, and runs in the home directory
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:119-132 environment, process setup and the three pipes
- **Preconditions:** A resolved stdio server.
- **Action:** probeStdio launches the child.
- **Expected:** environment = LoginEnvironment.current, then each pair of server.env assigned over it (server values win). executableURL = the resolved executable, arguments = server.args verbatim (the command itself is NOT repeated as argv[0] in this list), currentDirectoryURL = the current user's home directory. stdin, stdout and stderr are all pipes.
- **Side effects:** launches a child process
- **Persistence:** none
- **Failure cases:** a launch failure detaches both readability handlers, terminates the process and rethrows the system error, whose localizedDescription becomes the card's failure message
- **Cancellation:** the deferred cleanup runs on every exit path, including cancellation: handlers detached, process terminated, stdin closed
- **Windows path:** Same layering and the same working directory (the Windows user profile). Arguments must be passed as a vector, never as a joined command line, or arguments containing spaces or quotes would be re-split.
- **Verify by:** integration test with a scripted stand-in server asserting the child's environment and cwd

### PR-MCP-108 - The stdio probe performs initialize, notifications/initialized, then up to ten tools/list pages
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:193-216 the handshake and pagination loop
- **Preconditions:** The child is running.
- **Action:** probeStdio runs its conversation.
- **Expected:** Send request id 1 initialize with the standard params; await the reply with id 1; require result to be an object or throw malformed("missing result"); read serverInfo.name and serverInfo.version from it. Send the notifications/initialized notification. Then loop at most 10 times: build params as an empty object, adding "cursor" only when a cursor is held; send tools/list with the next id; await that id's reply; append its result's tool summaries; stop when result.nextCursor is absent or empty, otherwise carry the cursor into the next page. Return MCPProbeResult(serverName, serverVersion, tools). A server that keeps returning a cursor is cut off after the tenth page with the tools gathered so far.
- **Side effects:** writes each JSON message followed by a single 0x0A byte to the child's stdin
- **Persistence:** serverVersion and the tool list are persisted by the store on success; serverName is read and then discarded, never persisted or displayed
- **Failure cases:** a non-object result -> "The server sent something unexpected: missing result"; an error reply -> the checkReply message
- **Cancellation:** the surrounding task is cancellable; the cancellation is observed by the store, not inside the loop
- **Windows path:** Same sequence, same newline framing, same 10-page cap.
- **Verify by:** contract fixture with a scripted server returning three pages and one returning eleven

### PR-MCP-109 - The stdio reply loop polls every 5 milliseconds and gives up on exit or deadline
- **Source:** DroppyCode/Services/MCP/MCPProbe.swift:175-191 nextReply
- **Preconditions:** A request was sent.
- **Action:** The probe waits for the matching reply.
- **Expected:** Repeatedly: take every complete line buffered from stdout; parse each as JSON and skip anything that is not an object or whose "id" is not the awaited integer; on a match run checkReply and return it. If the child has exited, throw exitError(code:isOAuth:stderr:). If the deadline has passed, throw exitError(code: nil, ...). Otherwise sleep 5 milliseconds and repeat. Replies for other ids are discarded, not queued - unlike the in-app hub, which keeps them.
- **Side effects:** none
- **Persistence:** none
- **Failure cases:** exit -> "The server quit (exit <code>). <last non-empty stderr line>" or "The server quit (exit <code>)."; deadline -> "The server didn't answer in time."
- **Cancellation:** the sleep is the cancellation point; a cancelled task throws CancellationError out of it
- **Windows path:** Same 5 ms interval and the same discard-other-ids behavior. The interval is observable as probe latency.
- **Verify by:** unit plus a scripted-server timing test
