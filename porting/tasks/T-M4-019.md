### PR-MCP-081 - saveCustoms writes custom-mcp.json pretty-printed with sorted keys and no date strategy
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:265-270 saveCustoms()
- **Preconditions:** A custom server was added, edited or removed.
- **Action:** saveCustoms() runs.
- **Expected:** JSONEncoder with outputFormatting = [.prettyPrinted, .sortedKeys] only - no date strategy, because MCPCustomServer carries no dates. The payload is the customs array in list order, not sorted. Written atomically to <data root>/custom-mcp.json. Encoding or write failures are swallowed.
- **Side effects:** one atomic file write
- **Persistence:** <data root>/custom-mcp.json
- **Failure cases:** silent on failure
- **Cancellation:** not cancellable
- **Windows path:** Same. Customs are written in list order while connections are written sorted by id: the two files differ deliberately. After a failed load of custom-mcp.json, saveCustoms does not write the file at all (OD-0008 A2, PR-MCP-089).
- **Verify by:** contract fixture comparing the emitted bytes

### PR-MCP-082 - exportAll rebuilds the proxy routes, writes the provider configs, runs the legacy cleanup and reloads the hub, in that order
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:273-284 exportAll()
- **Preconditions:** Any of: store init, disconnect, setEnabled, a successful probe, saveCustom on a connected server.
- **Action:** exportAll() runs.
- **Expected:** servers = enabledServers (computed once). Then, in order: MCPProxy.shared.replaceAll with one route per server that has a non-nil oauthUpstream, each (serverID: server.id, upstream: remote, headers: [:], usesOAuth: true) - every non-OAuth server is filtered out, so the route table holds only OAuth servers and every route carries empty headers and usesOAuth true; MCPProviderConfig.writeAll(servers); MCPExternalSync.sync(servers); and a detached task calling MCPHub.shared.reload(). replaceAll REPLACES the whole table, so a route registered by a probe for a server that is not yet connected is dropped here.
- **Side effects:** rewrites the proxy route table wholesale; writes or deletes claude.json, codex.json, copilot.json and gemini-settings.json; upstream only, not ported (ED-061, PR-MCP-176): possibly rewrites ~/.cursor/mcp.json, ~/.config/opencode/opencode.json and ~/.gemini/settings.json once, then deletes mcp/managed.json; stops every in-app MCP client process and clears the hub's caches
- **Persistence:** the four provider config files
- **Failure cases:** file write failures are swallowed individually
- **Cancellation:** not cancellable
- **Windows path:** Same steps in the same order, except MCPExternalSync.sync, which never executes and is not ported (ED-061, porting/dead_code.md entry 11, PR-MCP-176). The hub reload is asynchronous and must not block the caller.
- **Verify by:** integration test asserting the three ported effects (the proxy route table, the provider configs, the hub reload) and their order, and that mcp/managed.json is never read, written or deleted (MCPExternalSync is not ported, ED-061, PR-MCP-176)

### PR-MCP-083 - MCPStore.init loads, starts the proxy and exports before anything can resolve a route
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:22-28 init()
- **Preconditions:** App start.
- **Action:** The store is constructed.
- **Expected:** Exactly three statements in order: load(); MCPProxy.shared.start(); exportAll(). The proxy is up before the probe, the hub or any launch can resolve a route to it. Because exportAll runs synchronously right after start(), the configs are written before the listener can report a bind failure - which is why a port repick leaves those configs pointing at the dead port (PR-MCP-124).
- **Side effects:** opens the loopback listener; writes the four provider config files (or deletes them when nothing is enabled); may create <data root>/mcp/ and write mcp/proxy-port
- **Persistence:** proxy-port and the provider configs
- **Failure cases:** a listener that cannot bind logs and, once, repicks
- **Cancellation:** not cancellable
- **Windows path:** Same order and the same synchronous export. Do not await the listener's ready state before exporting: that would change which port the configs carry.
- **Verify by:** integration test on start-up ordering
