### PR-STORE-032 - A bulk delete drains the writer queue once and cancels queued saves for the deleted files
- **Source:** DroppyCode/Services/Store/Storage.swift:76-78 - doc comment: "Deletes several threads’ files in one hop to the writer, so a bulk delete waits for the queued saves once rather than once per thread. A save of a thread may still be on its way to the writer; the removal takes its place, so the thread never comes back." | DroppyCode/Services/Store/Storage.swift:82 - DiskWriter.shared.removeSynchronously(ids.map(threadURL)) | DroppyCode/Services/Store/Storage.swift:362-369 - removeSynchronously clears pending[url] for every url, then queue.sync removes each file with try? FileManager.default.removeItem(at:) | DroppyCode/App/AppModel.swift:990 - Storage.deleteDocuments(removed.map(\.id)) on an archive clear
- **Preconditions:** Zero or more of the threads have a save waiting on the writer queue.
- **Action:** Deleting several threads at once.
- **Expected:** Every pending snapshot for those URLs is dropped from the writer’s pending map first, so a queued save can no longer resurrect a deleted thread, then one synchronous hop onto the writer queue removes all the files. The caller blocks for exactly one drain regardless of how many threads are deleted.
- **Side effects:** Files removed from <root>/threads/; The calling thread blocks once on the writer queue
- **Persistence:** The thread files are gone; library.json is updated separately by the caller through scheduleSave.
- **Failure cases:** Each removeItem is called with try?, so a file that cannot be deleted is left behind silently and the loop continues with the next one.
- **Cancellation:** not cancellable
- **Windows path:** Same single-hop bulk delete and the same cancellation of pending writes. PA-0015 bites hardest here: a Windows delete of a file whose handle a reader still holds fails with a sharing violation, so the delete retries with backoff and clears the read-only attribute first. Because the source swallows the failure, a port that surfaces a dialog here would be a deviation; surface it in a log and keep going. Windows: PA-0015 applies - file replace, delete and rename can fail transiently with a sharing violation, so the operation retries with backoff, clears the read-only attribute before a delete, uses an atomic replace primitive and surfaces a real error after a bounded number of attempts rather than dropping the write.
- **Verify by:** interaction test holding a read handle open across the delete

### PR-STORE-035 - The disk writer is a single serial background queue at utility quality of service
- **Source:** DroppyCode/Services/Store/Storage.swift:326-328 - final class DiskWriter: Sendable { static let shared = DiskWriter(); private let queue = DispatchQueue(label: "droppycode.storage.write", qos: .utility) }
- **Preconditions:** None.
- **Action:** Any storage write.
- **Expected:** Every write, synchronous write, removal and barrier in this area goes through one serial queue labelled exactly "droppycode.storage.write" at utility priority. Writes therefore never overlap and always land in enqueue order.

### PR-STORE-036 - Queued writes coalesce per file to the newest snapshot
- **Source:** DroppyCode/Services/Store/Storage.swift:329-332 - doc comment: "The newest snapshot waiting per file. A save queued behind a slow write is replaced by the next one for the same file, so a backlog never encodes and writes documents that are already stale when their turn comes." | DroppyCode/Services/Store/Storage.swift:340-351 - encodeAndWrite stores the value in pending[url], notes whether one was already there, and only schedules a queue hop when there was not; the hop removes the value from pending and writes whatever is there at that moment
- **Preconditions:** A write for this URL may already be waiting.
- **Action:** DiskWriter.shared.encodeAndWrite(value, to: url) called repeatedly for the same URL.
- **Expected:** The pending map holds at most one snapshot per URL. The first call schedules one asynchronous hop; later calls only replace the snapshot. When the hop runs it takes whatever snapshot is current and writes that, so N rapid saves of one thread produce one encode and one write, of the newest state. Encoding happens on the writer queue, not at the call site.
- **Side effects:** One background encode and write per coalesced burst
- **Persistence:** The target file.
- **Failure cases:** The hop guards on removeValue returning a value; if a synchronous write or a removal took the entry first, the hop does nothing.
- **Cancellation:** A pending snapshot is cancelled by removeSynchronously or by writeSynchronously for the same URL.
- **Windows path:** Same pending map keyed by target path, same at-most-one-hop rule, same encode-on-the-worker. A port that encodes at the call site moves the cost back onto the main thread.
- **Verify by:** interaction test counting encodes under a burst

### PR-STORE-037 - A write that cannot be encoded is silently skipped
- **Source:** DroppyCode/Services/Store/Storage.swift:381-382 - private static func write(_ value: any Encodable, to url: URL) { guard let data = try? JSONEncoder.storage.encode(value) else { return } ... }
- **Preconditions:** A value that fails to encode (for example a non-finite Double reached through a JSON field).
- **Action:** The writer reaches that snapshot.
- **Expected:** Nothing is written and nothing is logged. The existing file on disk is left as it was, and the in-memory state silently diverges from disk until a later encodable snapshot succeeds.
- **Persistence:** The previous file contents survive.
- **Failure cases:** No message, no retry, no notification. This is an ordinary quirk under AM-0001: the previous good file survives, so nothing already on disk is destroyed.
- **Cancellation:** not cancellable
- **Windows path:** Reproduce, but log the failure in the port’s diagnostic log. Logging is additive and changes no observable product behaviour.
- **Verify by:** unit with an unencodable fixture

- **Side effects:** A system log line on failure

- **Failure cases:** Disk full, permission denied, or a sharing violation: the log line above and nothing else. The user is not told their work did not save.
- **Cancellation:** not cancellable

PA-0015: the replace can fail transiently while another process holds the target open, so retry with backoff and only then log. The log message text is a system-log string, not user-visible UI; its product name is "Marrow" (OD-0012 F1): "Marrow could not save <file name>: <error description>". Windows: PA-0015 applies - file replace, delete and rename can fail transiently with a sharing violation, so the operation retries with backoff, clears the read-only attribute before a delete, uses an atomic replace primitive and surfaces a real error after a bounded number of attempts rather than dropping the write.
- **Verify by:** interaction test that holds the target open during a write, plus an inspection of partially written files under a killed process

### PR-STORE-041 - waitForQueuedWrites is an empty synchronous block used as a full-queue barrier
- **Source:** DroppyCode/Services/Store/Storage.swift:371-374 - doc comment "Returns once every write queued so far has landed, so a read that follows sees them." and func waitForQueuedWrites() { queue.sync {} }
- **Preconditions:** None.
- **Action:** A thread read, or the quit path after its synchronous writes.
- **Expected:** The caller blocks until the writer queue reaches this empty block, which by serial ordering means every previously enqueued write has finished. It is a whole-queue barrier, not a per-file wait.
- **Side effects:** Blocks the calling thread
- **Failure cases:** A write enqueued after the barrier begins is not waited for.
- **Cancellation:** not cancellable
- **Windows path:** Post a sentinel work item to the same serial worker and wait on it. It must never be called from the UI thread; in the source both callers are on background tasks.
- **Verify by:** unit
