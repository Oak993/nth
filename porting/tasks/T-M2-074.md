## Requirements

### PR-PROVACP-154 - Outbound frames are newline-terminated in line framing and header-prefixed in Content-Length framing
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:89-103 - `let body = message.data(); switch framing { case .lines: payload = body + Data([0x0A]); case .contentLength: payload = Data("Content-Length: \(body.count)\r\n\r\n".utf8) + body }; try? handle.write(contentsOf: payload)`; JSONValue.swift:59-63 - `data()` serializes with `.fragmentsAllowed` and `.withoutEscapingSlashes`, falling back to the four bytes of `null`
- **Preconditions:** A frame is being written.
- **Action:** send() runs on the write queue.
- **Expected:** In line framing the JSON body is followed by a single 0x0A, never CRLF. The body is compact JSON with NO pretty printing, NO sorted keys and, importantly, forward slashes NOT escaped, so a URL inside a prompt goes out as https://example.com rather than https:\/\/example.com. A serialization failure writes the literal `null`. Write failures are swallowed.
- **Side effects:** Bytes written to the child's stdin.
- **Persistence:** None.
- **Failure cases:** A write to a closed pipe is swallowed by `try?`; the failure surfaces only when the connection closes.
- **Cancellation:** not cancellable
- **Windows path:** Same: terminate with 0x0A only, and do not let the platform translate it to CRLF - write raw bytes to the stdin stream, not through a text-mode writer. Do not escape forward slashes.
- **Verify by:** contract fixture (byte-level assertion on a frame containing a URL)

### PR-PROVACP-155 - Each framed message has trailing carriage returns and spaces removed, and is dropped when empty or unparseable
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:146-151 - `while let last = line.last, last == 0x0D || last == 0x20 { line.removeLast() }; guard !line.isEmpty, let message = JSONValue.parse(line) else { return }; continuation.yield(message)`
- **Preconditions:** The framer produced a message.
- **Action:** deliver() runs.
- **Expected:** Trailing bytes are stripped one at a time while they are the carriage return 0x0D or the space 0x20 - so a CRLF-terminated line and a space-padded line both parse. Tabs are not stripped. An empty result is dropped. A body that does not parse as JSON is dropped SILENTLY: a CLI that prints a banner or a progress line to stdout is ignored rather than breaking the session. Parsing uses fragmentsAllowed, so a bare JSON scalar is accepted and then discarded by handle()'s object check.
- **Side effects:** A parsed message is yielded to the connection's reader.
- **Persistence:** None.
- **Failure cases:** Non-JSON stdout noise disappears with no log and no notice.
- **Cancellation:** not cancellable
- **Windows path:** Same two-byte strip. This is what makes a CRLF-writing Windows CLI work despite the LF-only framer.
- **Verify by:** unit (CRLF line, padded line, banner line)

### PR-PROVACP-156 - The stderr tail keeps at most the last four kilobytes for display and trims its buffer at sixty-four kilobytes
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:50-52 - `var errorTail: String { state.withLock { String(decoding: $0.errorBuffer.suffix(4_000), as: UTF8.self) } }` | DroppyCode/Core/Support/StdioProcess.swift:158-165 - `state.withLock { state in state.errorBuffer.append(data); if state.errorBuffer.count > 64_000 { state.errorBuffer = Data(state.errorBuffer.suffix(16_000)) } }`
- **Preconditions:** The child writes to stderr.
- **Action:** Bytes are appended and later read.
- **Expected:** The buffer grows until it exceeds 64,000 bytes, at which point it is cut to its last 16,000 bytes. errorTail decodes the last 4,000 bytes as UTF-8, so a multi-byte character straddling that boundary is replaced rather than dropping the read. These three literals are the contract: 64,000, 16,000 and 4,000.
- **Side effects:** At most 64,000 bytes of stderr held per process.
- **Persistence:** None; stderr is never written to disk by this area.
- **Cancellation:** not cancellable
- **Windows path:** Same three limits, measured in bytes not characters.
- **Verify by:** unit (feed 100 KB, assert the trim points)

### PR-PROVACP-157 - Terminating closes stdin first, then asks the process to stop, then kills it three seconds later
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:119-128 - `let handle = stdin.fileHandleForWriting; writeQueue.async { try? handle.close() }; guard process.isRunning else { return }; process.terminate(); let process = process; DispatchQueue.global().asyncAfter(deadline: .now() + 3) { if process.isRunning { kill(process.processIdentifier, SIGKILL) } }`
- **Preconditions:** stop() was called, or the connection was closed.
- **Action:** terminate() runs.
- **Expected:** Stdin is closed on the write queue, so it is ordered after any frames already queued. A process that is not running returns at that point, with no signal. Otherwise SIGTERM is sent and, exactly 3 seconds later and only if the process is still running, SIGKILL is sent to THAT PROCESS ONLY - the pid, not the process group, so grandchildren are not killed.
- **Side effects:** The child is terminated. Any grandchildren it spawned, such as an mcp-remote npx process, are left running.
- **Persistence:** None.
- **Failure cases:** A child that ignores SIGTERM runs for a further 3 seconds.
- **Cancellation:** This is the teardown path.
- **Windows path:** Named platform boundary. Windows has no SIGTERM with delivery semantics: per port_impacts #24, TerminateProcess is the practical equivalent and behaves like SIGKILL, so the graceful window collapses. The specification for Windows is: close stdin first, then request termination, then after the same 3 seconds force-kill if still running - preserving the ordering and the 3-second timing even though the first step is already forceful. Do NOT introduce a Job Object group kill here: the source kills the pid only, and killing the group would change observable behavior for mcp-remote grandchildren. PA-0007's Job Object candidate applies to Shell.swift, which is a different code path.
- **Verify by:** interaction test on Windows (assert stdin closes first, the child dies, and a grandchild survives, matching macOS)

### PR-PROVACP-158 - Stdout closing finishes the message stream, after flushing any buffered remainder
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:55-67,153-156 - the stdout readability handler sets `handle.readabilityHandler = nil` and calls `self.finishOutput()` when `data.isEmpty`; `finishOutput` is `if let remainder = state.withLock({ $0.framer.finish() }) { deliver(remainder) }; continuation.finish()`
- **Preconditions:** The child closed stdout or exited.
- **Action:** finishOutput runs.
- **Expected:** Any trailing unterminated line is delivered as a message first (line framing only), then the AsyncStream finishes, which ends the connection's reader loop and triggers didClose. So a final reply written without a newline is still processed before the connection is declared closed.
- **Side effects:** Ends the message stream; leads to JSONRPCConnection.didClose.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Same ordering: flush the remainder, then end the stream.
- **Verify by:** contract fixture (final frame with no trailing newline)

### PR-PROVACP-159 - Process exit waits one second before forcing the output stream closed, because a grandchild can hold stdout open
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:167-182 - `didExit` sets `state.exitStatus = status` and takes and clears `state.exitWaiters` inside `state.withLock`, resumes every waiter with the status, then `DispatchQueue.global().asyncAfter(deadline: .now() + 1) { [weak self] in handle.readabilityHandler = nil; self?.finishOutput() }`; comment at :176: a grandchild can inherit stdout and keep it open after the provider exits
- **Preconditions:** The child process exited.
- **Action:** The termination handler runs.
- **Expected:** Exit waiters are resumed immediately with the exit status. One second later the stdout readability handler is removed and finishOutput is forced, so a grandchild holding the pipe open cannot keep the session alive indefinitely. The delay is the literal 1 second, and it means a crashed agent's exit is reported to the chat about a second after the process died. finishOutput is idempotent in effect because continuation.finish() on an already-finished stream is a no-op.
- **Side effects:** Delays the .exited event by about one second after a crash.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Same 1-second forced close. It matters more on Windows, where an mcp-remote npx grandchild inheriting the handle is common and there is no process-group cleanup (see PR-PROVACP-157).
- **Verify by:** interaction test (agent exits while a grandchild holds stdout; assert the exited event within about a second)

### PR-PROVACP-160 - Reading, writing and parsing happen off the main thread, and events are delivered on the main actor
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:10,21 - `final class StdioProcess: @unchecked Sendable` with a private write queue `DispatchQueue(label: "droppycode.stdio.write")` | DroppyCode/Core/Support/StdioProcess.swift:2,23-30 - `import Synchronization`; `private struct State { var framer: StdioFramer; var errorBuffer = Data(); var exitStatus: Int32?; var exitWaiters: [CheckedContinuation<Int32, Never>] = [] }` held in `private let state: Mutex<State>`, which guards the framer, the error buffer, the exit status and the exit waiters | DroppyCode/Core/Support/StdioProcess.swift:4-9 - doc comment: reading, parsing and writing happen on private queues; parsed messages are delivered through `messages`, which finishes once stdout closes or the process exits | DroppyCode/Core/Support/JSONRPC.swift:40 - `@MainActor final class JSONRPCConnection`
- **Preconditions:** A session is streaming.
- **Action:** Bytes arrive and frames are written.
- **Expected:** Byte reading, framing and JSON parsing run off the main thread; writes are serialized on one queue per process so frames cannot interleave; all protocol state and all event emission happen on the main actor. The observable requirement is ordering: frames are written in call order, and messages are delivered to ACPSession in arrival order.
- **Persistence:** None.
- **Failure cases:** Parsing a very large tool output on the main thread would stall the UI; the source explicitly avoids it.
- **Cancellation:** not cancellable
- **Windows path:** In Electron this maps to the main process doing the stdio work and the renderer never touching the pipe. Preserve write ordering with a single serial queue per child; Node streams give this, but a naive `await` per write must not reorder frames.
- **Verify by:** interaction test (interleaved writes arrive in order) plus a performance guard on a 10 MB tool output

### PR-PROVACP-161 - StdioProcess exposes raw stdin writing, stdin closing and exit waiting, which the ACP path never uses
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:105-117 - `write(_ data: Data)` and `closeInput()`, both on the write queue | DroppyCode/Core/Support/StdioProcess.swift:130-139 - `waitForExit()`: `let exited = state.withLock { state -> Int32? in if let exitStatus = state.exitStatus { return exitStatus }; state.exitWaiters.append(continuation); return nil }; if let exited { continuation.resume(returning: exited) }` | DroppyCode/Core/Support/StdioProcess.swift:47 - `var isRunning: Bool { process.isRunning }` | DroppyCode/Services/Providers/CommandCodeSession.swift:194-195,204 - the only callers of write(_:), closeInput() and waitForExit()
- **Preconditions:** A StdioProcess exists.
- **Action:** Another provider session uses these members.
- **Expected:** These members exist and behave as described, but ACPSession calls none of them: the ACP path uses only start, send, terminate and messages, plus errorTail through the connection. They are specified here because they are part of this area's primary files and are proven live elsewhere - write(_:) and closeInput() by CommandCodeSession, waitForExit() by CommandCodeSession and PiSession - so they are NOT dead code and must be ported.
- **Persistence:** None.
- **Failure cases:** waitForExit for a process that never exits parks forever; there is no timeout.
- **Cancellation:** not cancellable
- **Windows path:** Same surface. StdioProcess.isRunning is a real process check, unlike ACPSession.isRunning (PR-PROVACP-075).
- **Verify by:** unit

### PR-PROVACP-162 - A spawn failure tears down the handlers and finishes the message stream before rethrowing
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:79-86 - `do { try process.run() } catch { stdout.fileHandleForReading.readabilityHandler = nil; stderr.fileHandleForReading.readabilityHandler = nil; continuation.finish(); throw error }`
- **Preconditions:** The executable is missing, not executable, or the working directory does not exist.
- **Action:** start() attempts to run the process.
- **Expected:** Both readability handlers are cleared, the message stream is finished so no reader is left parked, and the original OS error is rethrown. It propagates through JSONRPCConnection.start() and out of ACPSession.start(), so the thread reports the spawn error rather than hanging. Because the stream was finished before the connection's reader task started, didClose may not run: the failure reaches the caller as a thrown error, not as an .exited event.
- **Persistence:** None.
- **Failure cases:** This is the failure path.
- **Cancellation:** not cancellable
- **Windows path:** Same teardown. On Windows the common causes differ: ENOENT for a bare name that only exists as a .cmd shim, and EACCES for a directory. The error text shown to the user is the platform's, which is an accepted observable difference.
- **Verify by:** unit (spawn a nonexistent executable, assert the throw and that no reader is left parked)

### PR-PROVACP-163 - The stderr reader stops permanently on the first empty read
- **Source:** DroppyCode/Core/Support/StdioProcess.swift:68-75 - `guard let self, !data.isEmpty else { handle.readabilityHandler = nil; return }; self.appendError(data)`
- **Preconditions:** The child's stderr reaches end of file, or the process object was deallocated.
- **Action:** The stderr readability handler fires with no data.
- **Expected:** The handler removes itself and no further stderr is collected. Unlike the stdout handler this does not finish the message stream, so stderr closing alone does not end the session. The tail collected up to that point remains available for the failure message.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** Same.
- **Verify by:** unit
