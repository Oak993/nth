### PR-PROVCLI-267 - Pi's session id is a filesystem path and a resume is refused when that file is gone
- **Source:** DroppyCode/Services/Providers/PiSession.swift:8-10 - the header: the session file pi reports in get_state is the resume id | DroppyCode/Services/Providers/PiSession.swift:72 - sessionID = configuration.resumeID.flatMap { $0.isEmpty ? nil : $0 } | DroppyCode/Services/Providers/PiSession.swift:83-85 - if let sessionID, !FileManager.default.fileExists(atPath: sessionID) { throw ProviderError.failed("Pi no longer has this conversation; starting a new one.") }
- **Preconditions:** A resume id.
- **Action:** start() is called.
- **Expected:** An EMPTY resume id is normalized to nil in init. A non-empty one is treated as a FILE PATH and checked with a plain existence test - not a directory scan, in contrast to Command Code. When the file does not exist, start() throws ProviderError.failed with the verbatim message "Pi no longer has this conversation; starting a new one."
- **Side effects:** One filesystem existence check
- **Persistence:** The path is the thread's persisted resume id.
- **Failure cases:** The exact message above; the thread then starts fresh.
- **Cancellation:** not cancellable
- **Windows path:** The stored resume id is an ABSOLUTE PATH produced by the CLI, so it embeds a Windows path in the app's own database. It must round-trip unchanged, including its drive letter and separators, and a thread carried between machines will simply fail this check, which is the intended behavior.
- **Verify by:** interaction test with an existing and a missing session file

### PR-PROVCLI-275 - Pi's handshake is get_state then get_commands, with no initialize and no version negotiation
- **Source:** DroppyCode/Services/Providers/PiSession.swift:136-157 - the handshake sequence | porting/extracts/provider-argv-and-handshakes.md section 6.3
- **Preconditions:** The process started and the reader attached.
- **Action:** start() performs the handshake.
- **Expected:** There is NO initialize. First a request {"type":"get_state"} is sent. Its payload is read from the reply's "data" when present, else from the reply itself. A non-empty "sessionFile" string becomes the session id; failing that, a non-empty "sessionId" string does. The context window is taken from data.model.contextWindow. .sessionReady is emitted with the session id or the EMPTY STRING. Then a request {"type":"get_commands"} is sent, its payload read the same way, and each entry of "commands" with a string "name" becomes a SlashCommand with that name and its "description" or the empty string; a non-empty list is emitted as .commands. Finally started becomes true and stopped false, and start() returns the session id or the empty string.
- **Side effects:** Two stdin lines; up to two provider events
- **Persistence:** The session id is the thread's persisted resume id.
- **Failure cases:** Neither request can fail: both resolve with JSON null after 30 seconds (PR-PROVCLI-276).
- **Cancellation:** not cancellable
- **Windows path:** None beyond the framing.
- **Verify by:** contract fixture comparing both request lines and a unit test over both reply shapes

### PR-PROVCLI-276 - Pi requests are numbered droppy-<n> from 1 and resolve with JSON null after thirty seconds instead of throwing
- **Source:** DroppyCode/Services/Providers/PiSession.swift:258-270 - request(_:) with its doc comment | DroppyCode/Services/Providers/PiSession.swift:288-294 - the response case resolving pendingResponses by id | porting/extracts/provider-argv-and-handshakes.md section 6.9
- **Preconditions:** A live process.
- **Action:** Any request is made.
- **Expected:** With no process the call returns JSON null at once. Otherwise requestCounter is incremented BEFORE use, so the first id is exactly "droppy-1"; the literal prefix is "droppy-", NOT "marrow-" as Claude uses (PR-PROVCLI-019, OD-0012 F1). The id is added to the request object and the line written. The continuation resolves when a line arrives whose type is "response" and whose id matches. A detached Task sleeps exactly 30 seconds and, if the continuation is still pending, resolves it with JSON NULL. The timeout NEVER THROWS. The consequence, recorded as an upstream oddity: a hung get_state leaves start() returning an EMPTY session id rather than reporting an error, and the thread then believes it has a session it cannot resume.
- **Side effects:** One stdin line per request
- **Persistence:** none
- **Failure cases:** A hung CLI silently produces an empty session id and an empty command list.
- **Cancellation:** The 30 second timer is the only bound.
- **Windows path:** None. The id prefix is a contract with the app's own reader. It is "droppy-", which is neither "Droppy Code" nor "droppy-code", the two spellings OD-0012 F1 renames, so it is kept.
- **Verify by:** interaction test with a stand-in that never answers get_state, asserting start() returns an empty id after 30 seconds
- **Upstream defect provider-argv-and-handshakes.md section 10 item 8 (Pi's 30 second timeout resolves null silently, so start() can return an empty session id): reproduce it faithfully, do not fix it.**
