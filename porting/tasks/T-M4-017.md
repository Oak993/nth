### PR-MCP-069 - Any other probe error becomes a failed state carrying the error's own message
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:350-353 the general catch
- **Preconditions:** The probe threw something that is not CancellationError and not needsSetup.
- **Action:** The catch runs.
- **Expected:** If the task was cancelled, return. Otherwise states[entry.id] = .failed(message: error.localizedDescription). For an MCPProbeError or MCPOAuthError that is the errorDescription text specified in PR-MCP-120 and PR-MCP-160; for a system error it is the platform's own description. Nothing is saved and nothing is exported, so a server that had been connected stays in the provider configs with its last good definition while the card shows the failure.
- **Side effects:** the card and the custom row render the message in the danger colour, clipped to 3 lines
- **Persistence:** none
- **Failure cases:** this is the failure path
- **Cancellation:** a cancelled task returns first
- **Windows path:** Same. The message is whatever the error type produced; do not wrap or re-word it.
- **Verify by:** unit over every MCPProbeError case plus an interaction test on the card text

### PR-MCP-070 - saveCustom trims the name, mints the id once, and validates against every taken id
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:156-166 saveCustom(_:replacing:)
- **Preconditions:** The custom editor's Add server or Save is pressed.
- **Action:** saveCustom(server, replacing: oldID) runs.
- **Expected:** The old server is looked up by oldID among customs. taken = every catalog id plus every custom id, minus the old server's own id when editing. The name is trimmed of whitespace and newlines. The id is old?.id when editing and MCPCustomServer.makeID(trimmed name) when adding - a rename NEVER changes the id, so the connection row and the stored secrets stay where they are. MCPCustomError.validate is then run against taken; on failure the error is returned and NOTHING is written: no customs change, no file write, no probe cancellation.
- **Side effects:** none on the failure path
- **Persistence:** none on the failure path
- **Failure cases:** empty name -> "The server needs a name."; id already taken -> "A server named “<name>” already exists." using U+201C and U+201D around the name; stdio with a blank command -> "A stdio server needs a command."; http with a bad URL -> "The URL must start with https:// (or http:// for a local server)."; bad variable key -> "“<key>” is not a valid variable name: letters, digits, `_`, `-` and `.`, starting with a letter or `_`."; duplicate variable key -> "“<key>” is listed twice."
- **Cancellation:** not cancellable
- **Windows path:** Same. The id-minted-once rule is what keeps a rename from orphaning DPAPI-stored secrets.
- **Verify by:** unit over each validation failure plus a rename test asserting the id and the stored secret are unchanged

### PR-MCP-071 - saveCustom cancels the server's probe, clears its draft, and inserts or replaces it in creation order
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:167-175 the commit half of saveCustom
- **Preconditions:** Validation passed.
- **Action:** saveCustom continues.
- **Expected:** probes[server.id] is cancelled and cleared; drafts[server.id] = nil; if a custom with that id exists it is replaced in place (keeping its position in the list), otherwise the new server is appended to the end; saveCustoms() writes <data root>/custom-mcp.json. The list order is creation order and is what the Custom section renders.
- **Side effects:** cancels an in-flight probe and its child process; writes custom-mcp.json atomically, pretty-printed with sorted keys
- **Persistence:** the full customs array in custom-mcp.json
- **Failure cases:** a failed write is swallowed and the in-memory list is still updated
- **Cancellation:** not cancellable
- **Windows path:** Same. Replace in place; do not remove-and-append, which would reorder the section.
- **Verify by:** unit on ordering plus a restart test

### PR-MCP-072 - Saving an edit to a connected custom server drops its connection until the next probe succeeds
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:176-189 the connection-reset tail of saveCustom
- **Preconditions:** The edited custom server has a connection row.
- **Action:** saveCustom commits.
- **Expected:** connection.connectedAt = nil, serverVersion = nil, tools = [], the row is stored, states[server.id] = .notConnected, save() and exportAll() run. Because enabledServers requires connectedAt != nil, the server leaves all four provider config files immediately; it returns only when the editor's follow-up refresh probe succeeds. The connection's values are NOT cleared here - saveCustomValues handles them.
- **Side effects:** writes mcp.json; rewrites or deletes the four provider config files; replaces the proxy route table and reloads the hub
- **Persistence:** connectedAt, serverVersion and tools cleared in mcp.json
- **Failure cases:** none
- **Cancellation:** not cancellable
- **Windows path:** Same. The window where the server is absent from the providers is intentional: the old command or address must not be handed out after an edit.
- **Verify by:** integration test asserting the config files lose the server on save and regain it on a successful re-probe

### PR-MCP-074 - storedValue reads a variable's saved value from the right store for the editor to prefill
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:203-206 storedValue(server:field:secret:)
- **Preconditions:** The custom editor opens on an existing server.
- **Action:** The editor prefills each variable row.
- **Expected:** When secret is true, return the protected-storage value for (id, field), else nil. When secret is false, return connections[id]?.values[field], else nil. There is no cross-store fallback: a variable whose lock state was changed since it was saved reads nil from the new store and the editor leaves the row blank until saveCustomValues migrates it.
- **Side effects:** one protected-storage read per locked variable
- **Persistence:** none
- **Failure cases:** a locked or unavailable credential store yields nil and the row renders empty
- **Cancellation:** not cancellable
- **Windows path:** Same strict branch.
- **Verify by:** unit

### PR-MCP-075 - saveCustomValues writes every secret first and abandons the whole save if any write fails
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:215-218 the secret loop of saveCustomValues
- **Preconditions:** The custom editor's Save has passed saveCustom.
- **Action:** saveCustomValues(values, for: id, replacingFieldsOf: oldEntry) runs.
- **Expected:** First pass, over the items marked isSecret in the order given: MCPKeychain.set(value, server: id, field: key); the first call that returns false makes the function return false immediately, leaving the connection untouched and earlier secrets already written. The editor then shows "The Keychain could not save a value. Keep this editor open and try again." and does not dismiss.
- **Side effects:** one protected-storage write per secret variable, up to the failure point
- **Persistence:** partial: secrets written before the failure stay written
- **Failure cases:** protected storage unavailable -> returns false, the editor keeps the popover open with the message above
- **Cancellation:** not cancellable
- **Windows path:** Same, including the partial-write behavior on failure. The message names the Keychain and is a candidate for a Windows wording deviation, which would have to be recorded rather than assumed.
- **Verify by:** integration test with a failing credential store asserting the popover stays open

### PR-MCP-076 - saveCustomValues deletes the stored secrets of variables the edit no longer declares
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:219-225 the kept set, the oldEntry loop and the values filter
- **Preconditions:** An edit removed one or more variable rows.
- **Action:** saveCustomValues runs.
- **Expected:** kept = the set of keys in the submitted values. For every field of oldEntry (the server as it was before the edit) whose key is NOT in kept, MCPKeychain.delete(server: id, field: key). connection.values is then filtered down to the keys in kept, so a removed plain variable loses its mcp.json value too. oldEntry is nil when adding a new server, in which case the deletion loop does nothing.
- **Side effects:** one protected-storage deletion per removed variable
- **Persistence:** removed keys leave both stores
- **Failure cases:** none; deleting a non-existent item is a no-op
- **Cancellation:** not cancellable
- **Windows path:** Same, and oldEntry must be the pre-edit entry, not the post-edit one.
- **Verify by:** unit removing a locked and an unlocked variable and asserting both stores

### PR-MCP-077 - A variable that changed lock state moves stores and leaves no stale copy behind
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:226-234 the per-item branch of saveCustomValues
- **Preconditions:** A variable's lock button was toggled in the editor.
- **Action:** saveCustomValues runs its second pass.
- **Expected:** For every submitted item: when isSecret, connection.values[key] = nil (removing any plaintext copy) while the value has already gone to protected storage in the first pass; when not isSecret, connection.values[key] = the value, or nil when the value is empty, and MCPKeychain.delete(server: id, field: key) removes any protected copy. So a lock-on move deletes the plaintext and a lock-off move deletes the protected item, and exactly one store holds the value afterwards. An empty value clears the field in both directions.
- **Side effects:** one protected-storage deletion per unlocked variable
- **Persistence:** the value ends up in exactly one store: protected storage for locked variables, mcp.json values for unlocked ones
- **Failure cases:** none
- **Cancellation:** not cancellable
- **Windows path:** Same two-pass shape: all secrets first, then the per-item reconciliation.
- **Verify by:** unit toggling a variable both ways and asserting the other store is empty

### PR-MCP-079 - load reads custom-mcp.json first, then mcp.json, and restores connected states from connectedAt
- **Source:** DroppyCode/Services/MCP/MCPStore.swift:245-260 load()
- **Preconditions:** App start.
- **Action:** MCPStore is constructed.
- **Expected:** Read <data root>/custom-mcp.json and decode [MCPCustomServer]; on any read or decode failure, customs stays empty and load continues. Read <data root>/mcp.json; on a read failure, return (connections stays empty). Decode with dateDecodingStrategy = .iso8601; on a decode failure, return. For each decoded connection: connections[catalogID] = connection and, when connectedAt is not nil, states[catalogID] = .connected(toolCount: connection.tools.count). No probe is run at launch: a server shows as connected from its persisted record until the user refreshes it.
- **Side effects:** two file reads
- **Persistence:** read only
- **Failure cases:** a malformed custom-mcp.json silently loses EVERY custom server; that swallow-and-overwrite behavior is carried by PR-MCP-089 and quarantined under BLK-0002, so only the ordering and the mcp.json half of this requirement are implementable today; a malformed mcp.json silently loses every connection and the page shows nothing connected; this half is NOT quarantined
- **Cancellation:** not cancellable
- **Windows path:** Same order and the same ISO-8601 date strategy on mcp.json only. The customs-decode failure handling is quarantined by BLK-0002 (see PR-MCP-089) and must not be implemented either way; the mcp.json read path proceeds normally.
- **Verify by:** restart test plus unit tests feeding corrupt files
