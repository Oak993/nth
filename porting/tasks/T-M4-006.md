### PR-MCP-149 - The callback checks provider error, then code, then state, and every outcome page is served with HTTP 200
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:530-562 the branch order of handleRequest
- **Preconditions:** A GET of /callback with query items.
- **Action:** The outcome is decided.
- **Expected:** In this exact order. 1) A non-empty "error" query item: the message is "error_description" when it is present and non-empty, else "The sign-in was refused (<error>)."; render the FAILURE page with status 200 and, after it is sent, finish with callbackFailed(message). 2) A missing or empty "code": failure page with "The browser didn't send back a code.", status 200, then callbackFailed with that same sentence. 3) A "state" that does not equal the expected state: failure page with "Sign-in didn't finish. Try again.", status 200, then MCPOAuthError.stateMismatch. 4) Otherwise the SUCCESS page, status 200; only AFTER the page is written is the stored redirect URI and client read, and a missing client or empty redirect URI finishes with callbackFailed("Sign-in didn't finish."), else the flow succeeds with the code, the redirect URI and the client. The page is always sent before the outcome is recorded, so the user sees a result even when the app then fails.
- **Side effects:** writes an HTML page and closes the connection; records the sign-in outcome
- **Persistence:** success leads to a token exchange which writes the session
- **Failure cases:** the four messages above; the state check is the CSRF defence and its message is deliberately vague
- **Cancellation:** not cancellable once a page is being written
- **Windows path:** Same order, same status 200 for every outcome, same send-page-then-resume ordering.
- **Verify by:** contract fixture over all four branches asserting the status and body each time

### PR-MCP-155 - accessToken returns the stored token, refreshing only inside a 90-second window before a known expiry
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:164-183 accessToken
- **Preconditions:** A request needs a bearer token.
- **Action:** accessToken(serverID:) runs.
- **Expected:** Read "MCP <id> oauth"; a missing item, unparseable JSON, a missing access_token or an empty one throws signedOut. needsRefresh is false when there is no expires_at at all, and otherwise true when the current Unix time is at or past expires_at minus 90. When no refresh is needed the stored token is returned as is. When one is needed but there is no non-empty refresh_token, throw signedOut. Otherwise the refresh runs behind the single-flight gate. A session with no expires_at is therefore treated as never expiring, which is what makes the proxy's 401 replay a byte-identical retry.
- **Side effects:** one protected-storage read, and possibly a refresh POST and write
- **Persistence:** a refresh replaces the stored session
- **Failure cases:** signedOut -> "You're signed out. Sign in again to continue.", which the proxy returns as a 401 JSON body
- **Cancellation:** the refresh is a cancellation point
- **Windows path:** Same 90-second window and the same no-expiry-means-never-expires behavior. Do not synthesize an expiry. Protected storage is Windows Credential Manager (OD-0008 B3), under the same account strings.
- **Verify by:** unit over the four branches with a controlled clock
- **Upstream defect 18: reproduce it faithfully, do not fix it.**

### PR-MCP-156 - Concurrent refreshes for one server share a single in-flight token request
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:62-74 OAuthRefreshGate | DroppyCode/Services/MCP/MCPOAuth.swift:129 the shared gate
- **Preconditions:** Two requests for the same server need a refresh at once.
- **Action:** Both call the gate.
- **Expected:** The gate is keyed by server id. The first caller starts a detached refresh task and records it; a second caller arriving while it is recorded awaits the same task's value. The entry is cleared when the first caller returns, whether it succeeded or threw. Different server ids never share a flight. A caller that arrives after the entry is cleared starts a new refresh.
- **Side effects:** one refresh POST instead of two
- **Persistence:** one session write instead of two
- **Failure cases:** a failure is delivered to every waiter
- **Cancellation:** the detached task is not cancelled when a waiter is cancelled
- **Windows path:** Same per-server single-flight. Without it, two providers hitting one server simultaneously would race and one would invalidate the other's refresh token with providers that rotate them. Protected storage is Windows Credential Manager (OD-0008 B3), under the same account strings.
- **Verify by:** unit driving two concurrent callers and asserting one POST

### PR-MCP-158 - signOut deletes both the session and the registered client
- **Source:** DroppyCode/Services/MCP/MCPOAuth.swift:189-192 signOut
- **Preconditions:** none
- **Action:** An address change, a failed retry, a 401 retry, or a disconnect signs the server out.
- **Expected:** Delete protected-storage accounts "MCP <id> oauth" and "MCP <id> oauth-client". Nothing is revoked at the provider: there is no revocation request anywhere in the source, so the token remains valid remotely until it expires. Upstream reports no error and deleting absent items is a no-op. When signOut runs inside disconnect (PR-MCP-061), Marrow reports a failed deletion of either item other than a missing item (OD-0008 A12); on the other three callers (an address change, a failed retry, a 401 retry) nothing is reported, as upstream, because the ruling covers only disconnect.
- **Side effects:** two protected-storage deletions
- **Persistence:** both items are removed
- **Failure cases:** a store that refuses a deletion: upstream reports nothing; inside disconnect Marrow reports it (OD-0008 A12, PR-MCP-061); on the other callers nothing is reported, as upstream
- **Cancellation:** not cancellable
- **Windows path:** Same two deletions and the same absence of a revocation call - adding one would send a request the source never sends. Both items live in Windows Credential Manager (OD-0008 B3). Inside disconnect each deletion is checked and a failure other than a missing item is reported (OD-0008 A12).
- **Verify by:** integration test asserting both accounts are gone; inside disconnect, a store refusing either deletion produces a reported failure and a missing item does not; on the other callers nothing is reported
