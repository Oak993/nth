### PR-WIN-178 - The palette's rows are recomputed only when the query or the library changes, never on selection or hover
- **Source:** DroppyCode/App/Views/Palette/CommandPalette.swift:10-12 the comment 'The rows for the query as the library stands: built when either changes, not on every arrow key or selection change.' and `@State private var items: [Item] = []` | DroppyCode/App/Views/Palette/CommandPalette.swift:15-21 `private struct ResultsKey: Equatable { var query: String; var threads: [ChatThread]; var projects: [Project]; var selectedThreadID: UUID?; var finishActionTitle: String }` | DroppyCode/App/Views/Palette/CommandPalette.swift:102-107 `.onChange(of: ResultsKey(query: query, threads: model.threads, projects: model.projects, selectedThreadID: model.selectedThreadID, finishActionTitle: model.finishActionTitle), initial: true) { _, _ in items = results }`
- **Preconditions:** The palette is open.
- **Action:** The user presses an arrow key or moves the pointer over a row.
- **Expected:** The cached row list is NOT rebuilt. It is rebuilt only when one of exactly five inputs changes: the query, the thread list, the project list, the selected thread, or the finish action title. It is also built once when the palette appears, because the observation runs with initial: true.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Cache the rows against the same five-field key with the same equality, and build once on open. Recomputing per keystroke of navigation is a visible cost on a large library.
- **Verify by:** unit: arrow keys do not recompute; the five inputs each do
