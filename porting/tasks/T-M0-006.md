## The probe, verbatim from the stack decision

P7 - Chrome and windowing, four things in one window. ExtendClientAreaToDecorationsHint plus ExtendClientAreaTitleBarHeightHint plus WindowDecorations; app-drawn caption buttons on the LEADING edge at the derived traffic-light constants (titlebarHeight 44, 14 px buttons on a 23 px pitch, leading 18/14, top 16/21); Win32Properties.SetNonClientHitTestResult declaring those controls Caption / Close / MinButton / MaxButton; and, in the same run, a second window carrying WS_EX_NOACTIVATE (via Win32Properties.AddWindowStylesCallback) with a WM_MOUSEACTIVATE / MA_NOACTIVATE hook (AddWndProcHookCallback) containing a password field. PASS: drag, double-click-to-maximise and the system context menu all work from the app-drawn region; the app-drawn buttons minimise, maximise and close; AND the user can type into the non-activating panel's field. The probe MUST also record, for each WindowDecorations value, whether the Snap Layouts hover flyout appears over the leading-edge maximise button and whether DWM minimize/maximize/restore animations survive - this is AvaloniaUI/Avalonia#21212 and the answer fixes the chrome deviation list before any of it is designed.

## Rules

- Read `WORKER_BRIEF.md` first. Model the probe on `porting/probes/p1-glass/`, which passed.
- A probe PROVES or DISPROVES one capability. Report the measured result, whichever it is.
  A FAIL reported honestly is a valuable result. A PASS you did not measure is worthless.
- Build a control case that must fail when the thing under test is absent, as P1 did with
  its tint-only render. Without one, a PASS cannot be trusted.
- Never send a prompt to a real AI CLI; `--version` or `--help` only.
- Set `MARROW_PORT_DATA_DIR` to a throwaway folder before running anything.
