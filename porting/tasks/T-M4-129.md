### PR-PROVREG-102 - Antigravity receives GEMINI_CLI_SYSTEM_SETTINGS_PATH when a settings path is available
- **Source:** DroppyCode/Services/Providers/ProviderRegistry.swift:276-277 environment(for:) - for antigravity, when MCPProviderConfig.geminiSettingsPath() returns a path, GEMINI_CLI_SYSTEM_SETTINGS_PATH is set to it
- **Preconditions:** The provider is Antigravity.
- **Action:** A session or probe asks for the provider environment.

- **Cancellation:** not cancellable

- **Verify by:** unit on the produced environment map

### PR-PROVREG-106 - refreshAll probes at most four providers at a time, refilling the group as each finishes
- **Source:** DroppyCode/Services/Providers/ProviderRegistry.swift:335-338 probeWidth - the literal 4, with a comment that every check spawns the provider CLI and a dozen node processes at once is a visible stall | DroppyCode/Services/Providers/ProviderRegistry.swift:340-356 refreshAll - seeds the task group with the first four providers in allCases order, then starts the next provider each time one completes
- **Preconditions:** None.
- **Action:** Launch bootstrap or the refresh button calls refreshAll.
- **Expected:** At most 4 provider checks run concurrently. Providers are started in allCases order; completion order is not ordered. The function returns when all 14 have completed. OpenCode Zen and OpenCode Go are checked separately, so the opencode CLI is probed twice.
- **Side effects:** Up to two CLI process launches per non API-key provider; network calls for API-key providers.
- **Persistence:** None directly.
- **Failure cases:** A provider check that throws is swallowed inside refresh, so the group still drains.
- **Cancellation:** The whole group is cancelled with its parent task; individual checks have their own timeouts.
- **Windows path:** Same concurrency limit of 4. Windows process creation is heavier than fork-exec, so the limit matters more, not less.
- **Verify by:** interaction test with instrumented launches asserting the peak concurrency is 4

### PR-PROVREG-107 - refresh marks the provider as checking before doing anything, and the flag is cleared only by the status that replaces it
- **Source:** DroppyCode/Services/Providers/ProviderRegistry.swift:358-361 refresh - the existing status is copied, isChecking set true and stored back | DroppyCode/Services/Providers/ProviderRegistry.swift:368, :377 - both exits assign a freshly constructed ProviderStatus whose isChecking defaults to false
- **Preconditions:** None.
- **Action:** refresh(provider) is called.
- **Expected:** The status card immediately shows "Checking..." (with a horizontal ellipsis) and the Sign in row is suppressed. When the probe completes, a brand new status replaces it with isChecking false. There is no separate clearing step, so an abandoned refresh would leave isChecking true forever.
- **Side effects:** A UI update.
- **Persistence:** None.
- **Failure cases:** If the probe path returned without assigning a status, the checking flag would stick; both current exits do assign.
- **Cancellation:** If the enclosing task is cancelled after the flag is set but before the assignment, the provider stays in the checking state for the rest of the run.
- **Windows path:** Same two-phase update and the same absence of a finally-clear.
- **Verify by:** interaction test observing the status transitions
