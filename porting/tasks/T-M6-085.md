### PR-WIN-011 - The Settings window is re-centered over the main window on every show, clamped to that window's screen
- **Source:** DroppyCode/App/Window/WindowManager.swift:34-37 showSettings: window is fetched or made, then centerOverMainWindow(window), then present(window) | DroppyCode/App/Window/WindowManager.swift:41-55 centerOverMainWindow: `guard let main = mainWindow, main.isVisible, !main.isMiniaturized else { window.center(); return }`; `frame.origin.x = (parent.midX - frame.width / 2).rounded()`; same for y; then `if let visible = (main.screen ?? NSScreen.main)?.visibleFrame { frame.origin.x = min(max(frame.origin.x, visible.minX), visible.maxX - frame.width); frame.origin.y = min(max(frame.origin.y, visible.minY), visible.maxY - frame.height) }`; `window.setFrame(frame, display: false)`
- **Preconditions:** The Settings window exists or is about to be created.
- **Action:** showSettings(page:) is called.
- **Expected:** If the main window exists, is visible and is not minimized, the Settings window's origin is set to the main window's center minus half the settings size, each coordinate rounded to a whole point, then clamped into the working area of the main window's screen (falling back to the primary screen) so that neither the left/top edge falls below the working area minimum nor the right/bottom edge past its maximum. The frame is applied without an immediate display pass. If the main window is missing, hidden or minimized, the Settings window is centered on the screen instead.
- **Persistence:** nothing persisted
- **Failure cases:** Working area narrower or shorter than the settings window: the clamp's max term goes below its min term and the max wins, so the window is pinned to the working area's right/bottom edge. Reproduce this ordering.
- **Cancellation:** not cancellable
- **Windows path:** MonitorFromWindow on the main window, then GetMonitorInfo's rcWork as the clamp rectangle. macOS visibleFrame excludes the menu bar and the Dock; the Windows analogue excludes the taskbar and any app bars. Round each coordinate to a whole logical pixel before clamping, exactly as `.rounded()` does.
- **Verify by:** interaction test across a two-monitor layout, plus a unit test of the clamp arithmetic including the degenerate narrow-monitor case

### PR-WIN-012 - showSettings(page:) sets the requested settings page before the window is created or shown
- **Source:** DroppyCode/App/Window/WindowManager.swift:32-33 `func showSettings(page: SettingsPage? = nil) { if let page { SettingsNavigation.shared.requestedPage = page } ... }`
- **Preconditions:** None.
- **Action:** showSettings(page:) is called with a non-nil page, for example from the relaunch-after-update path or from a provider row's 'Add key' button.
- **Expected:** SettingsNavigation.shared.requestedPage is set before the window is built, so a window created by this very call opens already on the requested page rather than switching pages after it appears. Calling showSettings() with no page leaves the requested page untouched, so the window keeps whichever page it last showed.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** A shared navigation object written before the settings window is constructed, so the first layout already targets the requested page. Do not set it after the window is shown.
- **Verify by:** interaction test: from a cold state, showSettings(page: .about) opens directly on About with no visible page switch

### PR-WIN-013 - Presenting a window activates the application first, then orders that window to the front and makes it key
- **Source:** DroppyCode/App/Window/WindowManager.swift:57-60 `private func present(_ window: NSWindow) { NSApp.activate(); window.makeKeyAndOrderFront(nil) }`
- **Preconditions:** A window instance exists.
- **Action:** showMain() or showSettings() reaches present().
- **Expected:** The application is activated, then the window is brought to the front and takes key status. The order matters: activation first, so the window arrives in an already-foreground app.
- **Side effects:** The application takes foreground; other applications lose it
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Platform boundary: Windows restricts foreground changes (SetForegroundWindow succeeds only for a process that owns the foreground or was granted it). Reproduce activate-then-front; when the system refuses foreground, the window is still brought to the top of the app's own z-order and the taskbar button flashes, which is the closest honest equivalent.
- **Verify by:** interaction test from a background state; record the foreground-restriction divergence

### PR-WIN-014 - A window's content is a plain container view holding one frame-driven hosting view sized to the window
- **Source:** DroppyCode/App/Window/WindowManager.swift:103-108 `let liveResize = WindowLiveResize(window: window); let hosting = FrameHostingView(rootView: AnyView(HostedRoot(model: model, liveResize: liveResize, content: content()))); hosting.frame = frame; let container = NSView(frame: frame); container.addSubview(hosting); window.contentView = container` | DroppyCode/App/Window/WindowManager.swift:194-201 FrameHostingView.init: sizingOptions = []; safeAreaRegions = []; translatesAutoresizingMaskIntoConstraints = true; autoresizingMask = [.width, .height]
- **Preconditions:** A window has been created and configured.
- **Action:** The content view is installed.
- **Expected:** The window's content view is a plain container at the window's frame, and inside it a single hosting view at the same frame that resizes with both axes. The hosting view takes its size from the frame it is given rather than from its content: it declares no sizing options and no safe-area regions, so the content never drives the window's size and never insets itself for a safe area.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** One container child filling the client area, one content host inside it anchored to all four edges. The content must never propose a size upward; the window size is authoritative.
- **Verify by:** unit: the host fills the client area at every size; interaction test: a tall content tree never grows the window

### PR-WIN-015 - The hosting view always claims it can become first responder
- **Source:** DroppyCode/App/Window/WindowManager.swift:207-211 `override var acceptsFirstResponder: Bool { true }` with the comment that every window here holds focusable text and that AppKit asks on every display cycle while content scrolls under the title bar to work out the window's drag region
- **Preconditions:** None.
- **Action:** The frameworks ask whether the hosting view can take focus, which happens on every display cycle while content scrolls under the transparent title bar.
- **Expected:** The answer is an unconditional yes. The default answer would walk the whole view tree looking for a navigable item, once per display cycle.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** The content host reports itself focusable unconditionally rather than deriving the answer from a tree walk. This is a performance contract, not a cosmetic one: reproduce the constant-time answer.
- **Verify by:** unit: the host's focusable answer is constant and does not walk its children

### PR-WIN-016 - A hidden chat column never answers a keyboard chord
- **Source:** DroppyCode/App/Window/WindowManager.swift:213-218 `override func performKeyEquivalent(with event: NSEvent) -> Bool { !isHidden && super.performKeyEquivalent(with: event) }` with the comment that a Return meant for the shown column's card must not land on one behind it | DroppyCode/App/Views/RootView.swift:224-243 ThreadColumns.Coordinator.show: the previous column is set isHidden = true and kept in the pane
- **Preconditions:** Two or more thread columns are built in the detail pane, one shown and the rest hidden.
- **Action:** The user presses a chord that a button in a hidden column also carries, for example Return over an approval card.
- **Expected:** Only the shown column's control answers. A hidden hosting view returns false without consulting its subtree, so the chord is never delivered to a control behind the visible one.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Accelerator dispatch must skip hidden content hosts entirely rather than relying on per-control visibility checks, because the hidden column's controls are otherwise live and would claim the chord.
- **Verify by:** interaction test: switch threads, press Return, assert only the shown column's card acts

### PR-WIN-017 - Live resize of one window sets a flag scoped to that window alone
- **Source:** DroppyCode/App/Window/WindowManager.swift:118-140 WindowLiveResize: `private(set) var isActive = false`; init(window:) registers willStartLiveResizeNotification and didEndLiveResizeNotification with `object: window`, setting isActive true then false on the main queue | DroppyCode/App/Window/WindowManager.swift:131-132 comment 'The window keeps this alive for as long as it exists, so the observations are never taken down: a window is not made twice.'
- **Preconditions:** A window exists.
- **Action:** The user begins and ends dragging a window edge or corner.
- **Expected:** isActive becomes true when the drag begins and false when it ends, for that window only. A resize of a different window leaves this window's flag alone. The observers are deliberately never removed.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** WM_ENTERSIZEMOVE / WM_EXITSIZEMOVE on the window itself, per window. Note that these also fire for a window MOVE on Windows while the macOS notifications fire only for a resize: filter on an actual size change so a move does not suppress the settle animations this flag governs.
- **Verify by:** interaction test: resize one window and assert the other window's flag stays false; move-only test asserts the flag stays false

### PR-WIN-018 - A sidebar-edge or terminal-divider drag counts as a reshape exactly as a window resize does
- **Source:** DroppyCode/App/Window/WindowManager.swift:121-127 `var isPaneResizing = false` with the comment that the pane changes width or height every frame the way a live resize does, and `var isReshaping: Bool { isActive || isPaneResizing }`
- **Preconditions:** A window exists.
- **Action:** The chat view sets isPaneResizing while the sidebar's edge or the terminal's divider is dragged.
- **Expected:** isReshaping is true whenever either the window is in a live resize or a pane is being dragged. Views read isReshaping to hold their settle animations and heavier layout work until the drag ends; a spring restarted every frame is what made panels lag behind the window.
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** One shared reshape flag with the same two inputs, readable from the content tree. isPaneResizing is written by the chat view, not by the window.
- **Verify by:** interaction test: drag the sidebar edge and assert timeline springs are suppressed for the duration
