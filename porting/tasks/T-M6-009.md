### PR-LAUNCH-071 - There is no first-run onboarding beyond the welcome tour, and no account or sign-in step at launch
- **Source:** DroppyCode/App/AppDelegate.swift:16-27 - the complete launch sequence: showMain, openThreadOnLaunch, the conditional tour, bootstrap, update checks, the conditional About page | DroppyCode/App/AppModel.swift:120-146 init() - constructs the stores and loads the library; no onboarding state | DroppyCode/App/AppModel.swift:239-278 bootstrap() - no sign-in, no account and no registration step
- **Preconditions:** A genuinely first launch on a clean machine.
- **Action:** The app launches.
- **Expected:** The main window opens with an empty or freshly created chat, and 700 ms later the welcome tour appears. Nothing asks the user to sign in, create an account, accept terms or choose a data directory. Provider sign-in state is discovered by the provider probes during bootstrap, not asked for.
- **Persistence:** Only hasSeenTour once the tour is dismissed.
- **Cancellation:** not applicable
- **Windows path:** Reproduce. No Windows-only first-run wizard, EULA step or data-folder chooser may be added.
- **Verify by:** capture comparison on a clean data directory

### PR-LAUNCH-074 - Closing the main window does not quit the app
- **Source:** DroppyCode/App/AppDelegate.swift:1-87 - the delegate implements no applicationShouldTerminateAfterLastWindowClosed, so the AppKit default of false applies | DroppyCode/App/AppDelegate.swift:30-33 applicationShouldHandleReopen - exists precisely to bring the main window back when no window is visible, which is only reachable if closing the window left the app running
- **Preconditions:** The main window is the only visible window.
- **Action:** The user closes it.
- **Expected:** The app keeps running with no visible window. Its menu bar stays, and reopening from the Dock shows the main window again (PR-LAUNCH-048). No termination sequence runs and nothing is saved at this point beyond the ordinary debounced saves.
- **Persistence:** None.
- **Cancellation:** not applicable
- **Windows path:** ENGINEERING DECISION required: a Windows app with no window and no tray presence is unreachable, so 'keep running with no window' cannot be ported literally without adding a notification-area icon, which the source does not have. Either the close button exits, a divergence that must be recorded, or a tray affordance is added, an addition that must be recorded. The source settles the macOS behavior but not the Windows one.
- **Verify by:** interaction test on the chosen behavior, with the decision recorded in COMPATIBILITY

### PR-LAUNCH-075 - A quit that arrives before the delegate has its model is never deferred and saves nothing

- **Preconditions:** A quit arrives between process start and the model assignment.
- **Action:** The termination path runs.
- **Expected:** The reply is terminateNow. In applicationWillTerminate the save step is skipped entirely because the model is nil, while flushLiveSpend() and MCPHub.terminateAll() still run. Nothing is lost because nothing was loaded or changed yet.
- **Side effects:** The token ledger flush and MCP termination still run against their empty state
- **Persistence:** No library write.
- **Cancellation:** not applicable
- **Windows path:** Direct port: the shutdown sequence must tolerate a null model and still run the other two steps.
- **Verify by:** unit test on the shutdown sequencer with a null model

### PR-UPDATE-024 - Tapping the update notification opens Settings on About and does not bring the main window forward

- **Action:** The notification response is handled.
- **Expected:** Because userInfo carries "update", showMain() is skipped, the app is activated, and the Settings window opens with the requested page set to About. There is no threadID in an update notification, so no thread selection happens.

- **Verify by:** interaction test

### PR-UPDATE-025 - An update banner arriving while the app is frontmost is still shown, with sound

- **Cancellation:** not cancellable

- **Verify by:** interaction test

### PR-WIN-068 - Launch shows the main window, opens the launch thread, and starts the background work in a fixed order
- **Source:** DroppyCode/App/AppDelegate.swift:8-27 applicationDidFinishLaunching: the notification-centre delegate is set, the model is taken from WindowManager.shared, then windows.showMain(); windows.model.openThreadOnLaunch(); the tour gate; `Task { await windows.model.bootstrap() }`; UpdateChecker.shared.startBackgroundChecks(); the relaunch-marker branch
- **Preconditions:** Process launch, not a capture run.
- **Action:** Launch finishes.
- **Expected:** In this order: the user-notification delegate is installed, the main window is shown, the launch thread is opened, the first-run tour gate is evaluated, the model bootstrap starts asynchronously, background update checks start, and finally the relaunch-after-install branch runs. The window is shown before the bootstrap, so the first frame does not wait on it.
- **Side effects:** Shows the main window and takes foreground; Starts background update checks (network)
- **Persistence:** nothing persisted
- **Cancellation:** not cancellable
- **Windows path:** Same order. The user-notification delegate maps to the Windows toast activation callback, which must be registered before the window is shown so an activation that launched the process is not lost.
- **Verify by:** interaction test: cold launch shows a window before any network call completes

- **Verify by:** unit: with no flag the early return is not taken
