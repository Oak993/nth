### PR-STORE-028 - A thread is saved at most once per revision, and never while its history is still loading
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:3484-3500 - saveNow cancels and clears saveTask, then guard persistenceEnabled, !isLoadingHistory; then guard saveRevision != lastSavedRevision; then lastSavedRevision = saveRevision and DiskWriter.shared.encodeAndWrite(snapshotForPersistence(), to: Storage.threadURL(threadID)) | DroppyCode/App/Runtime/ThreadRuntime.swift:3491 - comment "A save before the history is installed would write an empty thread over the file."
- **Preconditions:** A thread runtime exists.
- **Action:** The periodic save timer fires, or a mutation calls saveNow.
- **Expected:** The timer handle is cleared first so a later scheduleSave is not blocked by a finished task. A save while the history is still being loaded is skipped entirely, so an empty in-memory thread can never overwrite a populated file. A save whose revision equals the last saved revision is skipped, so an idle turn writes nothing. Otherwise the snapshot is encoded and written to <root>/threads/<UUID>.json.
- **Side effects:** Background write of one thread file
- **Persistence:** <root>/threads/<UUID>.json
- **Failure cases:** persistenceEnabled false (quit in progress) skips the save.
- **Cancellation:** The periodic timer is cancelled by saveNow itself and by cancelPersistence; an in-flight encode is not cancellable.
- **Windows path:** Same three guards in the same order. The isLoadingHistory guard is the one that prevents data loss and must not be reordered. Windows: PA-0015 applies - file replace, delete and rename can fail transiently with a sharing violation, so the operation retries with backoff, clears the read-only attribute before a delete, uses an atomic replace primitive and surfaces a real error after a bounded number of attempts rather than dropping the write.
- **Verify by:** interaction test: open a thread, save during the load window, assert the file is untouched
