### PR-RUNTIME-202 - settleBatches hands a delegation batch over only when every head is back and nothing of that batch is still waiting to go out
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:2696-2702 settleBatches - for (batchID, batch) in hydraBatches where batch.pending.isEmpty && !hydraWaiting.contains(where: { $0.batchID == batchID }) { hydraBatches[batchID] = nil; hydraPendingReports += batch.reports.sorted { $0.headIndex < $1.headIndex } } | DroppyCode/App/Runtime/ThreadRuntime.swift:354-357 private struct HydraBatch { var pending: Set<UUID>; var reports: [HydraReport] = [] } | DroppyCode/App/Runtime/ThreadRuntime.swift:285 hydraBatches: [UUID: HydraBatch]; :287 hydraWaiting: [(delegation: HydraDelegation, batchID: UUID, queuedAt: Date)]
- **Preconditions:** One or more delegation batches exist for this lead.
- **Action:** settleBatches runs (called from hydraHeadFinished, dropDelegationBlock and both tails of spawnDelegatedHeads).
- **Expected:** Every batch in hydraBatches is tested against TWO conditions that must both hold: its pending set of head ids is empty, AND no entry of hydraWaiting still carries that batchID. A batch that passes is removed from hydraBatches (set to nil) and its reports are appended to hydraPendingReports sorted ascending by headIndex. A batch failing either test is left untouched, so a batch whose heads are all back but whose remaining tasks are still queued behind the pair cap does NOT report yet. The loop covers the whole dictionary, so several batches can settle in one call; only the order WITHIN one batch is defined.
- **Side effects:** hydraPendingReports grows; hydraBatches shrinks.
- **Persistence:** None; both are in-memory ObservationIgnored state.
- **Failure cases:** A batch whose batchID still appears in hydraWaiting is skipped even with an empty pending set.
- **Cancellation:** not cancellable
- **Windows path:** Swift iterates a copy of the dictionary pairs here, so the body may clear entries safely. A Windows implementation must snapshot the entries before clearing them or it will mutate under its own iterator.
- **Verify by:** unit - a batch with a waiting tail does not settle; the same batch settles once the tail goes out

### PR-RUNTIME-204 - startHydraReportTurn clears the flush flag first and deliberately leaves the reports in place
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:2725-2732 startHydraReportTurn - hydraFlushScheduled = false before the guard, with the comment "Cleared first and the reports left where they are: a turn that cannot run now must be able to be asked for again, by the next head to finish or by the end of whatever the lead is doing instead" | DroppyCode/App/Runtime/ThreadRuntime.swift:2707-2715 flushHydraReports - guard phase == .idle, !hydraFlushScheduled, !flushableHydraReports().isEmpty; hydraFlushScheduled = true
- **Preconditions:** flushHydraReports scheduled this turn and set hydraFlushScheduled true.
- **Action:** The scheduled task runs startHydraReportTurn.
- **Expected:** hydraFlushScheduled is set to false as the FIRST statement, before any guard. No early-return path removes anything from hydraPendingReports. - **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** The ordering is the requirement, not an implementation detail.
- **Verify by:** unit - a run that bails on a busy lead leaves both the flag clear and the reports queued

### PR-RUNTIME-207 - DelegationOutcome is a three-case enum and each case means a different thing to finishTurn
- **Source:** DroppyCode/App/Runtime/ThreadRuntime.swift:2747-2755 private enum DelegationOutcome { case none; case headsOut; case turnStarted } with the doc comments "No block, or nothing came of it", "Heads went out; the lead is free until they report", "The lead is being told something instead, in a turn of its own already on its way" | DroppyCode/App/Runtime/ThreadRuntime.swift:2407-2428 - the finishTurn chain switches on it: delegation != .none makes continues true, and delegation == .headsOut additionally drains the follow-up queue
- **Preconditions:** spawnDelegatedHeads has run.
- **Action:** It returns one of the three cases.
- **Expected:** Exactly three cases exist, named none, headsOut and turnStarted. .none means no block, or a block that came to nothing, and finishTurn falls through to its next branch. .headsOut means heads actually went out and the lead is free until they report, so finishTurn sets continues true AND drains the follow-up queue. .turnStarted means a turn of its own is already on its way to tell the lead something (refuseBlock), so finishTurn sets continues true but does NOT drain the queue, because the refusal turn owns the lead. Collapsing headsOut and turnStarted into one truthy value would let a queued follow-up cut into the refusal turn.
- **Persistence:** None.
- **Cancellation:** not cancellable
- **Windows path:** A three-member union, not a boolean.
- **Verify by:** unit - exhaustiveness over three cases, plus one finishTurn case per case
