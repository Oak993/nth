### PR-SIDEBAR-103 - Context-menu actions capture only value snapshots and hold the model weakly; rename, delete, settle and reopen are posted rather than run

- **Preconditions:** A context menu is opened on a row.
- **Action:** User chooses Rename, Delete, Settle or Reopen.
- **Expected:** The menu's closure writes a value into a box the list owns (rename, delete) or into the model (finish request) and returns. The list observes the box, clears it, and then acts, so the pop, the glide and the popover all happen exactly as if the check or the ellipsis item had been used. No menu closure holds a strong reference to the row's state storage, its frames or its settle handlers, and every one holds the model weakly and bails when it is gone. - **Persistence:** None.
- **Failure cases:** Model already released: the guard returns and nothing happens.
- **Cancellation:** not cancellable
- **Windows path:** The Windows menu implementation must copy the same discipline: no menu item callback may retain a row's live state. Even where the Windows object graph differs, the posted-request indirection is reproduced because the popover and glide behavior depend on the list, not the menu, running the action.
- **Verify by:** unit test that a dismissed menu retains no row state, plus interaction tests that each posted action produces the same visible result as its ellipsis counterpart.
